# 逐阶段开发与独立评审

当前会话是调度者和最终代码评审者，独立开发会话是实现者。按已确认的设计和开发计划一次交付一个 Phase；只有当前会话明确评审通过并通知开发会话后，后者才能进入下一 Phase。持续协作到全部已授权工作完成；外部环境或授权阻塞时明确记录，不把部分完成说成全部完成。

## 启动

1. 先读项目 `AGENTS.md`、对应设计和计划，以及 [dev-workflow skill](../dev-workflow/SKILL.md) 和 [代码评审准则](../../../docs/reviews/code-review-principles-draft.md)。沿用现有 Phase；若计划缺少可验收的阶段边界，先补清每阶段的目标、依赖与完成证据，不为流程另造无意义阶段。
2. 用户本次明确要求独立开发会话，或明确调用本 skill 执行具体开发任务时，才用可用的 `create_thread` 创建项目任务；自动匹配到相近话题不构成开新会话授权。开发任务的首条消息写明**只执行当前 Phase**、交接目标、共享工作区边界、三智能体要求和“收到评审者放行前不进入下一 Phase”。用户已要求当前会话与开发会话双向沟通时，后续评审意见直接用线程消息传递，不让用户转述。工具不可用时说明缺口，不假装已创建或已送达。
3. 创建后保存线程标识；用 `wait_threads` / `read_thread` 或当前可用工具跟踪状态。发送消息后确认对方收到并继续处理，不能把工具返回“已发送”当成完成整个协作。工作区共享时，评审者默认只读开发代码，开发者统一修复；不要并发改同一文件。

## 每个 Phase 的开发交接

开发会话仍遵循项目现有三智能体开发流程：开发者实现并定向自测，独立测试者验证意图与相关回归，独立 CodeReview 者审查当前 diff。用户在本模式明确要求三角色，因此非平凡代码 Phase 均需这三个独立角色，即使项目常规风险级别只规定更低的最低验证人数；纯文档等低风险步骤按项目风险规范处理，不为凑角色新增形式化测试。开发会话不得以内部 CodeReview 代替当前会话的最终评审。

开发会话完成当前 Phase 后，主动向当前会话交接：改动文件与 diff 范围、设计目标如何落地、测试命令及真实结果、内部测试和 CodeReview 发现及修复、未验证场景、计划文档进度。不要让用户在两会话之间传话；不要自行开始下一 Phase。

## 当前会话的放行判断

独立审查当前 Phase 的最终 diff 与验证证据，不能只转述开发会话内部的 CodeReview。以 [代码评审准则](../../../docs/reviews/code-review-principles-draft.md)沿真实调用链核对需求正确性、架构简洁性、兼容性、权限边界和测试有效性；指出冗余代码、无意义重复测试、过度开发或无依据的防御与门禁。阻断意见必须给出可发生的触发条件、代码位置、影响及最小修正方向；不以想象中不可达的场景或个人风格阻断。

- **通过**：明确告知开发会话“Phase N 评审通过，可以开始 Phase N+1”，并给出下一阶段边界；让开发会话同步计划状态，当前会话核验。仅在全部阶段及要求的验收实际完成后宣告整个任务完成。
- **需修复**：把问题直接发给开发会话，保持在当前 Phase。开发者修复并重跑受影响验证后主动回传；评审者复核，直到通过。对同一代码状态复用有效测试结果，不机械重复全套测试。
- **受阻**：先完成不依赖阻塞条件的工作，明确缺少的环境、数据或授权及影响，计划保持“进行中/部分完成”。不因等待部署或真实环境验收而虚报通过。

持续给用户简短进度，最终交代每个 Phase 的结论、验证证据和剩余风险。文档进度与索引按项目 `AGENTS.md` 更新；提交、推送和任何环境部署都只在用户对应明确授权后执行，逐阶段评审通过本身不授予这些权限。
