# 服务器部署及巡检要求

> 本文档定义所有项目服务器（生产 / 测试）的统一部署与巡检要求，分两部分：第一部分为部署要求（新机初始化验收、存量服务器整改），第二部分为每周巡检要求。
>
> 落地现状（2026-09-20）：生产 129.211.65.243 与测试 124.222.3.254 已按部署要求完成整改。

# 第一部分：服务器部署要求

## 1. nginx 访问日志必须记录域名

所有 server（含默认 server）的访问日志必须能区分请求落在哪个域名，禁止只依赖 referer 间接判断。

**要求**：
- `log_format` 必须包含 `$host` 字段（在默认 combined 格式基础上追加 `host=$host` 即可），http 级与各 server 级 `access_log` 显式引用该命名格式
- 多个域名混用同一个 access.log 时，`$host` 是唯一区分手段；也可按 server 拆分独立日志文件，但两种方式至少做一种

注意：server 级重新定义 `access_log` 时若未显式指定格式，会退回默认 combined（无 `$host`），必须在每个 server 级 `access_log` 后也写上格式名。

## 2. 宿主机日志必须有轮转

nginx / 应用等写入宿主机 `/var/log` 的日志必须配置轮转，防止单文件无限增长撑爆磁盘。

**要求**：
- nginx 日志：`/etc/logrotate.d/nginx` 存在且为 `daily` + `compress`；保留份数按磁盘预算定（生产建议 ≥ 14，测试可 52）
- 自定义应用日志：每类日志在 `/etc/logrotate.d/` 有对应条目，不允许「只写不轮转」
- 轮转后必须通知服务重开文件句柄（nginx 用 `kill -USR1` 或 `invoke-rc.d nginx rotate`），否则日志继续写进已改名的旧文件

**应用文件日志兜底**：应用自身按日期切分的日志（如 `app_YYYYMMDD.log`）不受 logrotate 管理时，必须配套保留期清理机制（logrotate 规则的 `maxage` 或应用内清理），不允许历史文件永久累积。

**保留期（过期删除）**：在轮转的基础上，过期日志必须删除，保留期默认 **180 天**：
- logrotate 条目统一加 `maxage 180`，并按保留期校准 `rotate N`（daily 轮转时 `rotate N` 不超过 180）
- 应用自身按日期切分、不受 logrotate 管理的日志，必须有定时清理脚本或应用内过期清理，保证 180 天前的日志文件被删除
- 保留期不允许「无限」；个别日志因合规要求需保留超过 180 天的，在该项目的部署文档中显式记录并说明原因

## 3. 容器日志必须有轮转

Docker json-file 日志（`docker logs` 的底层文件）默认**无大小限制**，会无限增长。所有容器必须带轮转参数。

**要求**：
- `/etc/docker/daemon.json` 统一设置默认值兜底所有新建容器：`log-driver` 用 `json-file`，`log-opts` 设 `max-size`（建议 10m，日志多的服务单独调大）+ `max-file`（建议 3）
- 重建存量容器时显式带上 `--log-opt max-size=... --log-opt max-file=...`（或 compose 服务段加 `logging:` 配置）
- **`daemon.json` 只对新建容器生效，且需重启 docker daemon 后才加载**；存量容器必须逐个检查 `docker inspect` 的 `LogConfig.Config` 是否为空
- `max-file: 1` 表示截断式轮转、不留历史，除非接受该行为否则用 ≥ 3
- 容器 json-file 轮转是**滚动覆盖**（总占用被 `max-size × max-file` 封顶，旧内容自动淘汰），没有日期概念，无需按天过期删除；但两个参数必须都已设置，否则滚动失效、日志无限累积
- 修改 `daemon.json` 或容器 log 配置需要重建容器（compose 项目改 `logging:` 段后 `up -d <service>`；裸 run 容器 rm 后带参重建），注意保留原有端口 / 挂载 / 网络 / 重启策略

## 4. 补充基本要求

| 项 | 要求 |
|----|------|
| 时区 | 宿主机与容器统一 `Asia/Shanghai`（`TZ` 环境变量），日志时间可直接对照业务问题 |
| 日志脱敏 | 日志中禁止明文输出密码、API Key、token 等敏感信息 |
| 磁盘水位 | 日志目录所在分区使用率告警阈值 80%；日志总量（含轮转副本）应有明确磁盘预算 |
| 配置备份 | 改 nginx / daemon.json / compose 等配置前先留 `.bak_时间戳` 备份 |
| SSH 安全 | 禁用 root 密码登录、改非默认端口（或配 fail2ban），见 [fail2ban.md](fail2ban.md) |
| 时间同步 | 宿主机 chrony/ntp 保持同步，日志时间戳才可信 |

## 5. 统一排查清单（新机验收 / 存量整改）

对新服务器 / 存量服务器验收或整改复核时，按顺序执行以下命令核对：

```bash
# 1. nginx 访问日志是否记录域名（看 log_format 是否含 $host，日志行尾是否有 host=xxx）
grep -rn 'log_format' /etc/nginx/nginx.conf /etc/nginx/conf.d/ 2>/dev/null
sudo tail -2 /var/log/nginx/access.log

# 2. 宿主机日志轮转与保留期（nginx 与自定义应用日志）
cat /etc/logrotate.d/nginx
grep -rn 'rotate\|maxage' /etc/logrotate.d/   # 校验 maxage 180 或等效保留期
ls /var/log/nginx/ | head          # 应能看到 .1 / .gz 轮转序列
ls /etc/logrotate.d/

# 3. 容器日志轮转（daemon.json 兜底 + 逐容器实际配置）
cat /etc/docker/daemon.json
for c in $(sudo docker ps --format '{{.Names}}'); do
  echo "--- $c"
  sudo docker inspect $c --format '{{.HostConfig.LogConfig.Type}} {{.HostConfig.LogConfig.Config}}'
done

# 4. 容器日志文件实际大小（无轮转的容器单文件会持续增长）
sudo docker ps -q | xargs -I{} sudo sh -c \
  'docker inspect {} --format "{{.Name}} {{.LogPath}}"' | while read n p; do
  sudo ls -lh "$p" 2>/dev/null | awk -v n=$n '{print n, $5}'
done

# 5. 时区 / 磁盘水位
timedatectl | grep 'Time zone'
df -h /var/log /var/lib/docker
```

**判定标准**：
- 排查 1 无 `host=$host`，或日志行无 `host=` 字段 -> 不合格
- 排查 2 无 logrotate 条目、或目录里只有单个无 `.1`/`.gz` 后缀的大文件 -> 不合格；轮转存在但无 `maxage`（或等效过期清理机制），历史文件无限保留 -> 不合格
- 排查 3 任一容器 `Config` 输出为 `map[]` -> 不合格

# 第二部分：每周巡检要求

每周对本项目服务器及其他项目服务器执行一次巡检，覆盖以下三个维度。发现问题当天闭环：能当场处理的当场处理；不能的记录原因与跟进计划，明确责任人和期限。

## 1. 资源使用是否正常

| 检查项 | 命令 | 判定标准 |
|--------|------|---------|
| 磁盘水位 | `df -h` | 任一分区使用率超过 80% 需定位大文件并处理 |
| 内存 / swap | `free -h` | 内存持续 > 90% 或 swap 被大量占用需排查 |
| CPU 负载 | `uptime`、`top` | load 持续超过 CPU 核数需排查异常进程 |
| 容器状态 | `docker ps -a` | 无意外退出 / 反复重启（Restarting）的容器 |
| 磁盘 IO 与大文件 | `du -sh /var/log /var/lib/docker /var/www/*` | 日志 / 数据目录异常膨胀需定位来源 |

## 2. 有无严重报错日志

| 检查项 | 位置 | 判定标准 |
|--------|------|---------|
| nginx 错误 | `/var/log/nginx/error.log`（含轮转的近 7 天） | 无 unattended 升级、upstream 连接失败等未处理错误堆积 |
| 应用错误日志 | 各应用 `log/` 下 error 日志（如本项目 `log/agent/error_*.log`） | 近 7 天无高频重复的 ERROR / 堆栈；新增错误需定位 |
| 系统级错误 | `journalctl -p err --since "7 days ago"`、`dmesg` | 无 OOM kill、硬件 / 文件系统报错 |
| 数据库 | postgres 容器日志 | 无连接数打满、死锁、磁盘满报错 |

## 3. 有无黑客攻击迹象

| 检查项 | 命令 / 位置 | 判定标准 |
|--------|------------|---------|
| 暴力破解与封禁 | `sudo fail2ban-client status`（逐 jail 查 status） | SSHD 等 jail 正常运行，关注封禁量突增 |
| 异常登录 | `last -a \| head -30`、`sudo lastb \| head -30` | 无非常用地区 / 非常用 IP 的成功登录 |
| 账号与密钥篡改 | `~/.ssh/authorized_keys` 内容、`/etc/passwd` 新增账号、`crontab -l` | 无不明公钥、不明账号、不明定时任务 |
| 异常端口与进程 | `sudo ss -tlnp`、`top` | 无不明监听端口、无可疑高耗进程（挖矿特征） |
| Web 攻击痕迹 | nginx access.log 过滤 `.php`、`/wp-admin`、`/etc/passwd`、`/.env` 等路径 | 仅有扫描 404 属常态；出现 200 命中需立即排查对应文件 |

## 4. 基础软件补丁与版本更新

检查操作系统及 nginx、docker 等基础软件有无重要安全补丁和版本更新。

| 检查项 | 命令 / 位置 | 判定标准 |
|--------|------------|---------|
| OS 安全更新 | `sudo apt update && apt list --upgradable`（关注 security 源条目） | 有 security 类补丁未安装 -> 评估后尽快安排更新窗口 |
| 内核与重启提示 | `/var/run/reboot-required` 是否存在 | 存在则列入下次维护窗口重启计划 |
| nginx 版本 | `nginx -v` | 对比官方最新 stable / 安全公告，无未修复的高危 CVE |
| docker 版本 | `sudo docker version` | 同上；daemon 与 containerd 版本一致 |
| 其他基础组件 | fail2ban、postgres、redis 等按需 `--version` | 有关键安全修复的新版本列入更新计划 |

**更新原则**：
- 安全补丁优先于功能更新；普通功能更新不追新，按维护窗口统一处理
- 生产环境更新前先在测试机验证；涉及 docker daemon 重启、内核升级需重启的操作，选低峰窗口并按第一部分「配置备份」要求先备份
- 巡检只做检查与计划，不在巡检过程中直接升级生产

## 5. 巡检记录

- 每次巡检留档：日期、服务器、各维度结论（正常 / 异常 + 处理方式），格式不限；本项目巡检记录统一存放在 [服务器巡检记录/](服务器巡检记录/) 目录，文件名 `YYYY-MM-DD-主题.md`
- 连续两周出现的同一异常必须升级处理，不允许「记录了但没人管」
- 日志轮转专项（第一部分第 1-3 节要求）无需每周全查，纳入每月一次的统一排查即可（命令见第一部分第 5 节清单）
