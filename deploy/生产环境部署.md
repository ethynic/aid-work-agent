## 1. 迁移摘要（2026-09-11 完成）

旧生产 `124.222.3.254`（内网 172.17.80.10，切换后退化为测试环境）→ 新服务器 `129.211.65.243`。两台分属不同腾讯云账号，内网不互通，**全部走公网迁移**（5Mbps 带宽，大文件用 nohup 后台链式脚本）。不做跨账号 VPC 对等连接；Redis 不用旧账号云 Redis，在新服务器自建容器。

### 1.3 踩坑记录（后续迁移/重建必读）

| 坑 | 根因 | 处理 |
|------|------|------|
| TimescaleDB 跨版本 restore 失败（hypertables 全丢） | 新拉镜像 2.30.0 vs 旧机 2.27.2，catalog 不兼容 | 拉取 2.27.2-pg16 并本地 tag 为 `latest-pg16`，重初始化卷后再 restore；日志库需按 `timescaledb_pre_restore()` → pg_restore → `timescaledb_post_restore()` 流程 |
| 部分表迁移后行数为 0 | 新机 `init-postgres.sql` 过旧（缺列），dump 的 CREATE TABLE 失败连带 COPY 跳过 | 补齐 SQL 后 DROP 表重导 / `ALTER TABLE ADD COLUMN` ×6 + `pg_restore --data-only` |
| `docker cp` 静默失败 | 新机 Docker 29 的已知问题 | 改用 `docker exec -i sh -c "cat > file"` stdin 流式写入 |
| Docker Hub 拉不动 | 公网受限 | `/etc/docker/daemon.json` 配腾讯云内网镜像 `mirror.ccs.tencentyun.com` |
| rsync `-e "ssh -i ..."` 报 `Failed to exec` | rsync 3.4.1 不接受带空格的 -e | 改 `/root/.ssh/config` Host 别名（`oldprod`） |
| nginx 启动报 `limit_conn_zone already bound` | 多份 conf 重复定义全局 zone | 仅保留一份定义，agent1 conf 中的 zone 行删除 |
| Worker 启动 `PermissionError: log/agent` | log 目录被 rsync 排除，docker 以 root 重建 | 宿主机 `chown`/`chmod`（log、storage 等可写目录对齐旧机权限） |
| 改 `.env` 端口后 api 崩溃循环（连 5433 被拒） | **`docker compose restart` 不重新读取 env_file**，容器创建时注入的旧变量仍在 | 必须 `docker compose up -d --force-recreate`；grep 确认 configs/src 无残留 5433 |
| 切换后旧会话引用的 `file_id` 解析报「文件不存在」（如 tr_56de3d10c0a842b4，2026-09-15） | 旧机 Redis 是**腾讯云 Redis 服务**（VPC 内网 IP `172.17.0.7`，不在本机、无本地容器），迁移只在新机自建了空 Redis，`uploaded_file:{file_id}` 元数据未迁；且 excel 等工具的 resolve 磁盘兜底只扫 `conversation/` 场景目录，不扫 `templates/` 等 | 从云 Redis（经旧机 `oldprod` 通道）导出 21 个 TTL=-1 永久元数据键重导入新机（RESP + `redis-cli --pipe`，纯增量 HSET，云 Redis 未改动，测试环境仍直连使用）。注意：redis-cli 的 `--raw` 必须放在子命令**前面**（`redis-cli --raw hgetall k`），放尾部会被当作 HGETALL 参数报 wrong number of arguments |

**数据分歧说明**：新机 9-11~9-14 验证期间产生 8 条测试 `chat_records`（1 个用户，最新 9-14 13:39），本次全量覆盖已丢弃；对应 84 个孤儿附件文件留在新机磁盘（无害）。

**旧生产库已禁用（2026-09-15）**：为防误操作，旧机两库已改名并彻底禁连（连超级用户也无法连接）：

- `aid_work_agent` → `aid_work_agent_rollback_20260915`（`datallowconn=false` + `CONNECTION LIMIT 0`）
- `aid_work_logs` → `aid_work_logs_rollback_20260915`（同上）

> 注意：`aid_user` 在旧库容器中是**超级用户**，`REVOKE CONNECT` / `CONNECTION LIMIT` 对其无效，必须用 `ALLOW_CONNECTIONS false` 才能彻底禁连。

**本次顺利的原因**：空库重建（DROP + CREATE）+ 与旧机相同版本的 timescale 2.27.2 镜像，避开了 9-11 的跨版本 restore 与残留 schema 冲突两类坑；`docker cp` 静默失败坑继续用 stdin `cat | docker exec -i pg_restore` 绕过。

## 3. 回滚步骤与收尾清单（迁移窗口期，至 2026-09-18）

- 旧环境保留 ≥3 天回滚窗口（至 2026-09-18），期间旧机 `aid-agent-api`/`aid-agent-background` 保持 stopped（勿启动，会分叉写入）；**旧生产库已改名禁连**（见 §1.4）。若需回滚，恢复步骤：

  ```sql
  -- 在 aid-postgres 容器内执行
  ALTER DATABASE aid_work_agent_rollback_20260915 WITH ALLOW_CONNECTIONS true CONNECTION LIMIT -1;
  ALTER DATABASE aid_work_logs_rollback_20260915 WITH ALLOW_CONNECTIONS true CONNECTION LIMIT -1;
  ALTER DATABASE aid_work_agent_rollback_20260915 RENAME TO aid_work_agent;
  ALTER DATABASE aid_work_logs_rollback_20260915 RENAME TO aid_work_logs;
  GRANT CONNECT ON DATABASE aid_work_agent TO PUBLIC;
  GRANT CONNECT ON DATABASE aid_work_logs TO PUBLIC;
  ```
  然后启动旧机 `aid-agent-api` / `aid-agent-background`，并把 DNS 切回旧机 IP。窗口结束并确认稳定后，清理：迁移临时 SSH 公钥从旧机 `authorized_keys` 移除（**注意**：`backup-243-to-254` 那条是每日备份专用密钥，勿删）、旧机 `/backups` 历史归档（7-9月）择机处理
