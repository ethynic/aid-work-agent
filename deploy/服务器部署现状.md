每台开发机的密钥可能不同：首次使用时把分配给你的私钥放到该路径并

```bash

sftp -i deploy/ssh_key ubuntu@124.222.3.254 <<'EOF'
cd /var/www/agent2/log
ls
get aid-work-agent.log
quit
EOF
```

> sftp 只能列目录/传文件；执行命令必须用 `ssh`。

**外部回调端点登记**：

| 端点 | 用途 | 备注 |
|------|------|------|
| `/t/{tenant}/(wecom|dingtalk|feishu|wecom_kf|wecom_personal_rpa)/callback/{config_id}` | IM 渠道消息回调 | 每配置独立凭证 |
| `/api/wechat-mp/callback/{config_id}` | 微信公众号服务器配置回调（公众号内容入知识库 WP4，产品版 2026-09-14） | 走 `/api/*` 反代，无需单独 nginx 配置；每配置独立 token（服务端生成）；GET=URL 验证回显 echostr，POST=事件受理（明文+安全模式 AES）；诊断期环境变量 `WECHAT_MP_CALLBACK_TOKEN` 逻辑已移除 |

## 4. Nginx 反向代理（宿主机）

### 4.1 生产服务器（129.211.65.243）

配置位于 `/etc/nginx/conf.d/`，证书在 `/etc/nginx/conf.d/SSL/`（商业泛域名 `*.aidingyi.cn`，从旧服务器迁移）：

| 域名 | 配置文件 | 后端端口 |
|------|---------|---------|
| `agent.aidingyi.cn`（生产主域名） | `agent.aidingyi.cn.conf`（仓库源文件 [deploy/agent.aidingyi.cn.conf](agent.aidingyi.cn.conf)） | `localhost:8000` |

> `agent1.aidingyi.cn` 为迁移验证期临时域名，2026-09-15 已删除其 nginx 配置（备份于新机 `/tmp/agent1.aidingyi.cn.conf.bak_20260915`）；DNS A 记录需在腾讯云控制台另行删除，删除前该域名请求会落到 nginx 默认 server（即生产站点）。

关键配置要点（同旧机生产 conf）：

- **限流**：单 IP 并发连接与请求频率双限制；`limit_conn_zone` 全局 zone 只允许一份定义（多份 conf 重复定义会报 `already bound` 启动失败）。
- **下载接口单独限速**：对话附件/知识库文档等大文件下载点单连接 `limit_rate 128k`、前 1MB 全速、单 IP 并发 2（新增下载点须同步三份 conf 的正则，见 `.claude/rules/backend_dev.md`）。
- **知识库上传限速**：`/api/knowledge/upload` 单文件 `256KB/s`，保证 5Mbps 总带宽不被独占。
- **SSE 流式输出**：`/api/` 路径 `proxy_buffering off` + `proxy_cache off`，长连接超时 600s。
- **静态资源缓存**：JS/CSS/图片 30 天 `immutable`，HTML 不缓存。
- **HTTP → HTTPS**：80 端口 `return 301 https://$host$request_uri`。

## 5. Docker 容器

### 5.1 生产服务器（129.211.65.243）

**compose**：`/var/www/agent/docker-compose.prod.yml`，包含 3 个服务（api / background / redis），Postgres 为独立 compose（见 §6）。

| 容器 | 镜像 | 说明 |
|------|------|------|
| `aid-agent-api` | `aid-agent-api:latest`（镜像 ID 02aa9ecae95a，9-11 从旧机 `docker save/load` 迁移） | API 服务，Gunicorn UvicornWorker，`WORKERS=6`，内存上限 8G |
| `aid-agent-background` | 同镜像 | 定时调度/后台任务，内存上限 4G |
| `aid-redis` | `redis:7.4-alpine`（AOF） | 自建缓存，仅容器网络可达，内存上限 1G |
| `aid-postgres` | `timescale/timescaledb:latest-pg16`（2.27.2） | 独立 postgres compose，对外端口 10864 |

关键 `.env` 配置（真实值见服务器）：

```
DATABASE_URL=postgresql://aid_user:***@172.17.0.9:10864/aid_work_agent
LOGS_DATABASE_URL=postgresql://aid_user:***@172.17.0.9:10864/aid_work_logs
REDIS_HOST=aid-redis
REDIS_KEY_PREFIX=aid-agent
WORKERS=6
LLM_PROVIDER=deepseek/qwen/zhipu   # a/b/c 链式 failover
```

**Volume 挂载**（与旧机生产一致）：

- `/var/www/agent:/app` — 整个项目目录挂载，代码更新后重启容器即可生效
- `/var/www/agent/log:/app/log`、`/var/www/agent/configs:/app/configs`、`/var/www/agent/skills:/app/skills`
- `/var/www/qb3_upload/agent_uploads:/app/uploads`、`/var/www/qb3_upload/agent_storage:/app/storage`（上传/存储，租户附件 475M / 2220 文件）
- `tmpfs /tmp mode=1777 size=200m` — 修复 Debian trixie-slim 上游 `/tmp` 权限问题（Playwright 启动 Chromium 需要）

**健康检查**：api / background / redis 容器均配置 healthcheck（`curl -f http://localhost:8000/health`，interval 30s / retries 3 / start_period 60s）。

> ⚠️ 修改 `.env` 后必须 `docker compose -f docker-compose.prod.yml up -d --force-recreate` 才能生效（`docker compose restart` 不会重新读取 env_file）。
> ⚠️ 新机 Gunicorn 以 `gosu appuser`（uid 1000）运行：`log/`、`storage/` 等可写目录须宿主机预创建并对齐属主（uid 1000），否则 worker 启动报 `PermissionError`。

### 9.1 工作区瘦身：sparse-checkout 排除非运行目录（2026-09-02）

两台服务器的仓库均配置了 git sparse-checkout（新机 git 版本较新，旧机 2.17.1 用老式三件套），`git pull` / `git reset --hard` 时以下目录不再落到工作区：

```
.agents/ .claude/ .codebuddy/ .pytest_cache/ .zcode/ docs/ ext/ openspec/ plans/ test_uploads/ tests/
```

> ⚠️ `deploy/` **必须保留**在检出列表中：容器 ENTRYPOINT 是 `gunicorn -c deploy/gunicorn.conf.py`（经 `.:/app` 挂载读取）、镜像构建 COPY `deploy/fix_tmp.sh`、更新脚本与备份 cron 都依赖它。

> ⚠️ **`plans/` 是运行时可写目录，排除后必须预创建**（2026-09-03 agent3 启动事故教训）：
>
> `plans/` 不仅是文档目录，还是 `PlanManager` 的运行时持久化目录。sparse-checkout 排除后若目录内无未跟踪运行时文件残留，**整个目录会消失**。容器以 uid 1000 运行、项目目录属主不一致时 `mkdir` 报 `PermissionError` → gunicorn worker 无法 boot，容器 crash 循环。
>
> **修复与预防**（属主对齐运行身份 uid 1000 gid 999）：
>
> ```bash
> sudo mkdir -p /var/www/agent3/plans
> sudo chown 1000:999 /var/www/agent3/plans
> ```

配置方式（新 clone 的服务器需重新执行）：

```bash
cd /var/www/agent   # agent2 / agent3 同理
git config core.sparseCheckout true
printf '/*\n!/.agents/\n!/.claude/\n!/.codebuddy/\n!/.pytest_cache/\n!/.zcode/\n!/docs/\n!/ext/\n!/openspec/\n!/plans/\n!/test_uploads/\n!/tests/\n' > .git/info/sparse-checkout
git read-tree -mu HEAD
```

回滚：`git config --unset core.sparseCheckout && rm .git/info/sparse-checkout && git read-tree -mu HEAD`。

常用命令：

### 11.3 按 trace_id 读取日志

用户提供 `trace_id` 时，应到**对应环境的日志库**读取：`obs_traces` 存请求主记录，`obs_spans` 存各步骤明细。

```bash
# 生产：查 trace 主记录（新机容器内 psql）
sudo docker exec -it aid-postgres psql -U aid_user -d aid_work_logs \
  -c "SELECT trace_id, session_id, tenant_id, user_id, status, duration_ms, total_tokens, error_message FROM obs_traces WHERE trace_id = '<trace_id>';"

  -c "SELECT span_type, name, model, prompt_tokens, completion_tokens, status, error_message FROM obs_spans WHERE trace_id = '<trace_id>' ORDER BY start_time;"
```

- 测试环境同理（旧机），把库名换成 `aid_work_logs2`
- 平台级 ERROR 错误日志（含完整堆栈）在**主库**的 `log_error` 表（`WRITE_LOG_ERROR=true` 时写入），不在日志库
- 日志库表结构见 [init-postgres-logs.sql](init-postgres-logs.sql)

## 12. 故障排查

> **文件/存储排查总则**：排查租户文件、附件落盘、存储迁移等问题时，统一
> `sudo docker exec aid-agent-api sh -c '...'` 进**本项目容器**读（例如
> `sudo docker exec aid-agent-api sh -c 'ls -la storage/tenants/'`）。
> **容器内 appuser 身份能正常访问文件是必要且充分的判据**——应用本身即以该身份
> 读写 storage；**宿主机 ubuntu 身份能否访问文件是不必要、也不充分的**，不作为
> 判据（storage 走 docker volume 挂载，宿主机路径与容器内路径不一致，
> 一律以容器内路径为准）。

### 12.1 容器无法启动

```bash
sudo docker logs aid-agent-api --tail 100
# 常见原因：
# - .env 未配置或字段缺失（改 .env 后未 force-recreate 也属此类）
# - 端口冲突
# - 可写目录属主不对：新机 gosu appuser(uid 1000)，log/storage/plans 需预创建并 chown 1000:999
# - 依赖问题：docker compose -f docker-compose.prod.yml build --no-cache
```

### 12.2 Nginx 502

```bash
sudo docker ps | grep aid-agent-api       # 容器是否运行
curl http://localhost:8000/health         # 后端连通性
sudo tail -f /var/log/nginx/error.log
```

### 12.3 Gunicorn Worker 启动失败

```bash
sudo docker logs aid-agent-api 2>&1 | head -100
# 常见原因：
# - LLM API Key 未配置导致 lifespan 初始化失败
# - /dev/shm 不可用（注释 gunicorn.conf.py 中的 worker_tmp_dir）
# - log/plans 等运行时目录缺失或属主错误（见 §9.1 plans/ 事故）
```

### 12.4 API 请求超时

```bash
sudo docker stats aid-agent-api          # 资源使用
# .env 临时调大：WORKER_TIMEOUT=300
# nginx conf 临时调大：proxy_read_timeout 300s
```

### 12.5 文件上传失败

```bash
ls -la /var/www/qb3_upload/agent_storage/
df -h   # 检查磁盘空间
```

### 12.6 Playwright / Chromium 启动失败

```
报错：Permission denied: '/tmp/...'
```

根因：Debian trixie-slim 上游变更导致 `/tmp` 默认 mode=755。处理链：
1. docker-compose 已挂载 `tmpfs /tmp mode=1777`（首选）
2. `fix_tmp.sh`（容器 entrypoint 兜底）
3. 运行时手动修复：`sudo docker exec -u root aid-agent-api chmod 1777 /tmp`

### 12.7 数据库连接耗尽

```bash
# 查看当前连接数
sudo docker exec -it aid-postgres psql -U aid_user -d postgres \
  -c "SELECT datname, count(*) FROM pg_stat_activity GROUP BY datname;"

# 强制断开某库所有连接（谨慎）
sudo docker exec -it aid-postgres psql -U aid_user -d postgres \
  -c "SELECT pg_terminate_backend(pid) FROM pg_stat_activity WHERE datname='aid_work_agent' AND pid <> pg_backend_pid();"
```

### 12.8 迁移相关踩坑速查

以下坑在 2026-09 迁移中踩过，重建/再迁移时必读（详见 [生产环境部署.md](生产环境部署.md) §2.3）：

| 坑 | 处理 |
|------|------|
| TimescaleDB 跨版本 restore 失败（hypertables 全丢） | 用与源库相同版本镜像（2.27.2-pg16），目标库先 DROP + CREATE 空库再全量 pg_restore |
| `docker cp` 静默失败（Docker 29） | 改用 `cat file \| docker exec -i <容器> sh -c "cat > file"` stdin 流式写入 |
| 改 `.env` 后容器仍用旧值 | `docker compose restart` 不重读 env_file，必须 `up -d --force-recreate` |
| Docker Hub 拉不动 | `/etc/docker/daemon.json` 配腾讯云内网镜像 `mirror.ccs.tencentyun.com`（新机已配） |
| rsync `-e "ssh -i ..."` 报错 | 用 `/root/.ssh/config` Host 别名（新机 root 已配 `oldprod` → 124.222.3.254） |
| nginx `limit_conn_zone already bound` | 多份 conf 重复定义全局 zone，仅保留一份 |
| Worker `PermissionError: log/agent` | 可写目录被 rsync/git 排除后缺失，宿主机预创建并 chown 1000:999 |

更完整的排查清单见 [DEPLOYMENT.md](DEPLOYMENT.md) §故障排查 与 [README.md](README.md) §故障排查。
