## 2. 整体架构

```
互联网用户
    ↓ HTTPS (443)
Nginx (宿主机)
    ├── 静态文件 frontend/dist        → 直接返回
    ├── /api/*                        → 反代到本机 Docker 容器
    ├── /uploads/*                    → 宿主机文件系统
    └── /t/{tenant}/(wecom|dingtalk|feishu|wecom_kf)/callback → 反代到本机 Docker 容器

Docker 容器（同一台宿主机，三套环境）
    ├── aid-agent-api   (生产) → Gunicorn(3 workers) → 8000
    ├── aid-agent-api2  (测试) → Gunicorn(3 workers) → 8001
    └── aid-agent-api3  (在线开发) → Gunicorn(3 workers) → 8004

PostgreSQL 容器（单实例双库）
    └── aid-postgres → 5433 → aid_work_agent(生产) + aid_work_agent2(测试、在线开发)

Redis（腾讯云托管）
    └── 172.17.0.7:6379 → 通过 REDIS_KEY_PREFIX 隔离生产/测试/在线开发
```

| `agent3.aidingyi.cn`（在线开发） | [deploy/agent3.aidingyi.cn.conf](agent3.aidingyi.cn.conf) | `localhost:8004` |

复制到 `/etc/nginx/conf.d/` 后生效：


### 3.2 关键配置要点

- **SSL 证书**：`/etc/nginx/conf.d/SSL/aidingyi.cn_nginx/`（泛域名 `*.aidingyi.cn`），TLS 1.2/1.3。
- **限流**：单 IP 并发连接与请求频率双限制（生产用 `perip_conn` / `perip_req`，测试用 `perip_conn_agent2` / `perip_req_agent2`，避免 zone 名冲突）。
- **知识库上传限速**：`/api/knowledge/upload` 单文件 `256KB/s`、单 IP 并发 1、突发 3，保证 5Mbps 总带宽不被独占。
- **SSE 流式输出**：`/api/` 路径 `proxy_buffering off` + `proxy_cache off`，长连接超时 600s。
- **静态资源缓存**：JS/CSS/图片 30 天 `immutable`，HTML 不缓存。
- **HTTP → HTTPS**：80 端口 `return 301 https://$host$request_uri`。

### 4.3 容器内进程模型

生产环境使用 **Gunicorn + UvicornWorker** 多进程模型，参数统一在 [deploy/gunicorn.conf.py](gunicorn.conf.py) 管理，可通过 `.env` 覆盖：

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `WORKERS` | 3 |  |
| `WORKER_TIMEOUT` | 120s | LLM 调用耗时较长，不宜过小 |
| `SERVER_PORT` | 8000 | 容器内监听端口 |

### 4.4 Volume 挂载说明

容器通过 volume 挂载实现代码热更新与数据持久化（3个 compose 文件结构一致，仅路径前缀不同）：

- `.:/app` — 整个项目目录挂载，代码更新后重启容器即可生效
- `./log:/app/log` — 应用日志
- `./configs:/app/configs` — 配置文件
- `./skills:/app/skills` — 技能目录
- `/var/www/qb3_upload/agent_*:/app/uploads|storage` — 上传/存储
- `tmpfs /tmp mode=1777 size=200m` — 修复 Debian trixie-slim 上游 `/tmp` 权限问题（Playwright 启动 Chromium 需要）

## 5. PostgreSQL 数据库

### 5.1 部署方案

采用**单实例 + 双数据库**方案：一个 PostgreSQL 容器同时服务生产和测试环境，通过数据库名 + 用户名隔离，节省服务器资源。

| 环境 | 数据库名 | 用户名 | 用途 |
|------|---------|--------|------|
| 生产 | `aid_work_agent` | `aid_user` | 正式业务数据 |
| 测试 | `aid_work_agent2` | `aid_user2` | 开发测试数据 |
| 生产日志 | `aid_work_logs` | `aid_user` | 平台日志（含 TimescaleDB） |
| 测试日志 | `aid_work_logs2` | `aid_user2` | 开发测试日志 |

### 5.2 容器与镜像

- **容器名**：`aid-postgres`
- **镜像**：`timescale/timescaledb:latest-pg16`（含 pgvector + TimescaleDB 扩展）
- **compose 文件**：[deploy/docker-compose.postgres.yml](docker-compose.postgres.yml)
- **启动命令**（在宿主机 `deploy/` 目录执行）：

```bash
cd /var/www/agent2/deploy   # 或 /var/www/agent/deploy，共用同一份数据卷
docker compose -f docker-compose.postgres.yml up -d
```

> ⚠️ 2026-06-15 曾因 `timescale/timescaledb-ha:pg16` 镜像 `/tmp` 权限 bug 切换到 `latest-pg16`，详见 [docker-compose.postgres.yml](docker-compose.postgres.yml) 顶部注释。升级流程见 [update_postgres.sh](update_postgres.sh)。

### 5.3 关键参数

| 参数 | 值 | 说明 |
|------|-----|------|
| 宿主机端口 | 5433 → 5432 | 避免与系统 PG 冲突 |
| `max_connections` | 80 | 50 用户场景余量 |
| `shared_buffers` | 512MB | 8G 内存约 1/16 |
| `effective_cache_size` | 4096MB | 告知 PG 可用 OS 缓存 |
| `statement_timeout` | 30s | 防慢查询拖垮生产 |
| `idle_in_transaction_session_timeout` | 60s | 防长事务 |
| `random_page_cost` | 1.1 | SSD 优化 |
| `shm_size` | 1G | |
| `/pg_temp` tmpfs | 1024m | 临时表/排序走内存 |

### 5.4 扩展

- `pgvector` — 向量搜索（`chunks_vec` 表，HNSW + cosine）
- `uuid-ossp` — UUID 生成
- `timescaledb` — 日志库 Hypertable 分区（仅 `aid_work_logs` 启用）

### 5.5 连接串示例

```bash

# 测试环境
```

### 8.1 工作区瘦身：sparse-checkout 排除非运行目录（2026-09-02）

三套环境的仓库均配置了 git sparse-checkout（服务器 git 2.17.1，用老式三件套配置），`git pull` / `git reset --hard` 时以下目录不再落到工作区：

```
.agents/ .claude/ .codebuddy/ .pytest_cache/ .zcode/ docs/ ext/ openspec/ plans/ test_uploads/ tests/
```

> ⚠️ `deploy/` **必须保留**在检出列表中：容器 ENTRYPOINT 是 `gunicorn -c deploy/gunicorn.conf.py`（经 `.:/app` 挂载读取）、镜像构建 COPY `deploy/fix_tmp.sh`、更新脚本 `./deploy/agent*_update.sh` 与备份 cron `deploy/backup_postgres.sh` 都依赖它。

> ⚠️ **`plans/` 是运行时可写目录，排除后必须预创建**（2026-09-03 agent3 启动事故教训）：
>
> `plans/` 不仅是文档目录，还是 `PlanManager` 的运行时持久化目录（计划 MD 文件写入 `plans/`）。sparse-checkout 排除它之后，`git read-tree -mu HEAD` 会把 `plans/` 下被跟踪的文件从工作区删除；若目录内没有未跟踪的运行时文件残留（agent3 即如此），**整个目录会随之消失**。下次应用启动时 `PlanManager` 尝试 `mkdir /app/plans`，而容器以 `gosu appuser`（uid 1000）运行、`/var/www/agent3` 属主为 1001，无权创建目录 -> `PermissionError` -> gunicorn worker 无法 boot，容器 crash 循环。
>
> **修复与预防**：在三套环境各执行一次（属主对齐 gunicorn 运行身份 uid 1000 gid 999）：
>
> ```bash
> sudo mkdir -p /var/www/agent3/plans   # agent / agent2 已幸存，可 ls 确认
> sudo chown 1000:999 /var/www/agent3/plans
> ```
>
> 预创建的目录及其中的运行时文件均为未跟踪状态，sparse-checkout 与后续 `git pull` 不会触碰，配置稳定。agent（生产）的 `plans/` 属主本就是 1000:999，即此模式。

配置方式（新 clone 的服务器需重新执行一遍）：

```bash
cd /var/www/agent   # agent2 / agent3 同理
git config core.sparseCheckout true
printf '/*\n!/.agents/\n!/.claude/\n!/.codebuddy/\n!/.pytest_cache/\n!/.zcode/\n!/docs/\n!/ext/\n!/openspec/\n!/plans/\n!/test_uploads/\n!/tests/\n' > .git/info/sparse-checkout
git read-tree -mu HEAD
```

回滚：`git config --unset core.sparseCheckout && rm .git/info/sparse-checkout && git read-tree -mu HEAD`。

遗留事项：sparse-checkout 只影响工作区，`.git` 对象库中仍有这些目录的历史 blob；如需彻底清除，需在维护窗口用 `git clone --filter=blob:none` 重 clone（参照 qbweb3.1 项目《服务器仓库瘦身》文档 §4）。

### 快速更新脚本流程（agent_update.sh / agent2_update.sh）

1. `git fetch --all && git reset --hard origin/master`
2. 前端编译（`node:22-alpine` 容器内 `npm install && npm run build`）
3. `docker compose -f docker-compose.{prod,test}.yml down`
4. `docker compose -f docker-compose.{prod,test}.yml up -d --force-recreate --wait`
5. 修复容器内 `/tmp` 权限（`chmod 1777 /tmp` 或 `mount remount`）
6. 增量安装 `requirements.txt` 新增依赖
7. 清理已移除的 `zhipuai` 包并修复 `pyjwt` 版本冲突

> 排查线上问题时，按本节路径直接读取日志与数据，避免绕路。

### 10.1 容器日志在宿主机直接读取

3 套环境的容器内 `/app/log` 均通过 volume 挂载到宿主机项目目录的 `log/` 子目录（见 §4.4），**无需 `docker exec` 进容器**，直接在宿主机读取：

| 环境 | 容器名 | 容器内路径 | 宿主机路径 |
|------|--------|-----------|-----------|
| 生产 | `aid-agent-api` | `/app/log` | `/var/www/agent/log` |
| 测试 | `aid-agent-api2` | `/app/log` | `/var/www/agent2/log` |
| 在线开发 | `aid-agent-api3` | `/app/log` | `/var/www/agent3/log` |

uploads / storage 挂载对照（compose 中为绝对路径）：

| 环境 | 容器内 uploads / storage | 宿主机路径 |
|------|--------------------------|-----------|
| 生产 | `/app/uploads` / `/app/storage` | `/var/www/qb3_upload/agent_uploads` / `/var/www/qb3_upload/agent_storage` |
| 测试 | `/app/uploads` / `/app/storage` | `/var/www/qb3_upload/agent2_uploads` / `/var/www/qb3_upload/agent2_storage` |
| 在线开发 | `/app/uploads` / `/app/storage` | `/var/www/qb3_upload/agent2_uploads` / `/var/www/qb3_upload/agent2_storage`（与测试共用） |

常用命令（宿主机）：

```bash
# 直接 tail 生产日志（无需进容器）
tail -f /var/www/agent/log/aid-work-agent.log

# 临时主题日志（tlog，调试某主题时单独落盘到 log/temp/）
ls /var/www/agent/log/temp/

# scp 拉取日志到本地
scp ubuntu@124.222.3.254:/var/www/agent/log/aid-work-agent.log ./
```

### 10.2 数据库本地直连

数据库可在本机（WSL）用 psql 直连（宿主机 `5433` 映射到容器内 `5432`，见 §5.3）。4 个库对应关系：

| 库名 | 环境 | 用途 |
|------|------|------|
| `aid_work_agent` | 生产 | 生产主库（业务数据） |
| `aid_work_logs` | 生产 | 生产日志库（`obs_traces` / `obs_spans` / `obs_scores`，含 TimescaleDB） |
| `aid_work_agent2` | 测试 | 测试主库（业务数据，在线开发共用） |
| `aid_work_logs2` | 测试 | 测试日志库 |

```bash
# 本机直连生产日志库
psql "postgresql://aid_user:***@124.222.3.254:5433/aid_work_logs"

# 本机直连测试主库
psql "postgresql://aid_user2:***@124.222.3.254:5433/aid_work_agent2"
```

> 用户名/密码与库的对应关系见 §5.1，真实密码见服务器 `.env`（此处打码），**不要写入文档或代码**。

### 10.3 按 trace_id 读取日志

用户提供 `trace_id` 时，应到**对应环境的日志库**（`aid_work_logs` / `aid_work_logs2`）读取：`obs_traces` 存请求主记录，`obs_spans` 存各步骤明细。

```bash
# 生产：查 trace 主记录（输入/输出/状态/耗时/成本/错误）
psql "postgresql://aid_user:***@124.222.3.254:5433/aid_work_logs" \
  -c "SELECT trace_id, session_id, tenant_id, user_id, status, duration_ms, total_tokens, error_message FROM obs_traces WHERE trace_id = '<trace_id>';"

# 生产：查该 trace 的步骤明细
psql "postgresql://aid_user:***@124.222.3.254:5433/aid_work_logs" \
  -c "SELECT span_type, name, model, prompt_tokens, completion_tokens, status, error_message FROM obs_spans WHERE trace_id = '<trace_id>' ORDER BY start_time;"
```

- 测试环境同理，把库名换成 `aid_work_logs2`、用户换成 `aid_user2`
- 平台级 ERROR 错误日志（含完整堆栈）在**主库**的 `log_error` 表（`WRITE_LOG_ERROR=true` 时写入），不在日志库
- 日志库表结构见 [init-postgres-logs.sql](init-postgres-logs.sql)

## 11. 故障排查

> **文件/存储排查总则**：排查租户文件、附件落盘、存储迁移等问题时，统一
> `docker exec aid-agent-api sh -c '...'` 进**本项目容器**读（例如
> `docker exec aid-agent-api sh -c 'ls -la storage/tenants/'`）。
> **容器内 appuser 身份能正常访问文件是必要且充分的判据**——应用本身即以该身份
> 读写 storage；**宿主机 ubuntu 身份能否访问文件是不必要、也不充分的**，不作为
> 判据（storage 走 docker volume 挂载，见 §4.4，宿主机路径与容器内路径不一致，
> 一律以容器内路径为准）。另注意：`/home/ubuntu/repos/aid` 是**另一个项目**
> （容器 `aid-api-1`）的路径，与本项目无关，排查时勿混用。

### 11.1 容器无法启动

```bash
docker logs aid-agent-api --tail 100
# 常见原因：
# - .env 未配置或字段缺失
# - 端口冲突（检查 8000/8001 占用）
# - 依赖问题：docker compose -f docker-compose.prod.yml build --no-cache
```

### 11.2 Nginx 502

```bash
docker ps | grep aid-agent-api          # 容器是否运行
curl http://localhost:8000/health       # 端口连通性
sudo tail -f /var/log/nginx/error.log   # Nginx 错误日志
```

### 11.3 Gunicorn Worker 启动失败

```bash
docker logs aid-agent-api 2>&1 | head -100
# 常见原因：
# - LLM API Key 未配置导致 lifespan 初始化失败
# - /dev/shm 不可用（注释 gunicorn.conf.py 中的 worker_tmp_dir）
```

### 11.4 API 请求超时

```bash
docker stats aid-agent-api              # 资源使用
# .env 临时调大：WORKER_TIMEOUT=300
# nginx.conf 临时调大：proxy_read_timeout 300s
```

### 11.5 文件上传失败

```bash
ls -la /var/www/qb3_upload/agent_uploads/
sudo chown -R www-data:www-data /var/www/qb3_upload/agent_uploads/
sudo chmod -R 755 /var/www/qb3_upload/agent_uploads/
df -h   # 检查磁盘空间
```

### 11.6 Playwright / Chromium 启动失败

```
报错：Permission denied: '/tmp/...'
```

根因：Debian trixie-slim 上游变更导致 `/tmp` 默认 mode=755。处理链：
1. docker-compose 已挂载 `tmpfs /tmp mode=1777`（首选）
2. `fix_tmp.sh`（容器 entrypoint 兜底）
3. 运行时手动修复：`docker exec -u root aid-agent-api chmod 1777 /tmp`

### 11.7 数据库连接耗尽

```bash
# 查看当前连接数
docker exec -it aid-postgres psql -U aid_user -d postgres \
  -c "SELECT datname, count(*) FROM pg_stat_activity GROUP BY datname;"

# 强制断开某库所有连接（谨慎）
docker exec -it aid-postgres psql -U aid_user -d postgres \
  -c "SELECT pg_terminate_backend(pid) FROM pg_stat_activity WHERE datname='aid_work_agent' AND pid <> pg_backend_pid();"
```

更完整的排查清单见 [DEPLOYMENT.md](DEPLOYMENT.md) §故障排查 与 [README.md](README.md) §故障排查。
