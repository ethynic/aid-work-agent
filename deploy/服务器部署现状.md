## 2. SSH / SFTP 连接

| 项目 | 生产（新） | 测试/开发（旧） |
|------|-----------|----------------|
| IP / 端口 | `129.211.65.243` / **`10167`**（22 已关闭） | `124.222.3.254` / `22` |
| 用户名 | `ubuntu` | `ubuntu` |
| 认证方式 | SSH 密钥（**已禁用密码登录**，root 仅 prohibit-password） | SSH 密钥（公钥已写入 `authorized_keys`） |

**私钥位置**：本仓库 `deploy/ssh_key`（已加入 `.gitignore`，不入库）。
每台开发机的密钥可能不同：首次使用时把分配给你的私钥放到该路径并
`chmod 600 deploy/ssh_key`，找不到时向运维/管理员索取。

**生产机 SSH 加固落点**（2026-09 迁移时配置）：

- `/etc/ssh/sshd_config`：单行 `Port 10167`（先双端口并行验证后再删除 22）
- `/etc/ssh/sshd_config.d/49-disable-password.conf`：`PasswordAuthentication no`、`KbdInteractiveAuthentication no`、`PermitRootLogin prohibit-password`
- **陷阱**：`sshd_config.d` 是**首个匹配生效**（非后覆盖），cloud-init 的 `50-cloud-init.conf` 会抢占 `PasswordAuthentication`，加固文件必须用更小的序号（49-）才能先生效
- `ssh.socket` 已禁用，改用独立 `ssh.service`（避免 socket 激活忽略 Port 配置）

常用命令：

```bash
# 生产服务器（注意 -p 10167）
ssh -p 10167 ubuntu@129.211.65.243 "sudo docker ps | grep aid-agent-api"
scp -P 10167 ubuntu@129.211.65.243:/var/www/agent/log/aid-work-agent.log ./

# 旧服务器（测试/在线开发）
ssh -i deploy/ssh_key ubuntu@124.222.3.254 "docker ps | grep aid-agent-api2"
sftp -i deploy/ssh_key ubuntu@124.222.3.254 <<'EOF'
cd /var/www/agent2/log
ls
get aid-work-agent.log
quit
EOF
```

> sftp 只能列目录/传文件；执行命令必须用 `ssh`。

## 3. 整体架构

```
互联网用户
    ↓ HTTPS (443)
Nginx（新生产服务器 129.211.65.243 宿主机）
    ├── 静态文件 frontend/dist        → 直接返回
    ├── /api/*                        → 反代 localhost:8000（aid-agent-api 容器）
    ├── /uploads/*、/storage/*        → 宿主机文件系统
    └── /t/{tenant}/(wecom|dingtalk|feishu|wecom_kf)/callback → 反代 localhost:8000

新生产服务器 Docker（compose: docker-compose.prod.yml，单环境）
    ├── aid-agent-api         → Gunicorn(6 workers) → 8000
    ├── aid-agent-background  → 定时调度/后台任务（同镜像）
    ├── aid-redis             → redis:7.4-alpine（自建容器，仅容器网络）
    └── aid-postgres          → TimescaleDB pg16，对外 10864（另有独立 postgres compose）

旧服务器 124.222.3.254（测试 / 在线开发，Docker 多环境）
    ├── aid-agent-api2  (测试)      → 8001
    ├── aid-agent-api3  (在线开发)  → 8004
    ├── aid-postgres → 5433 → aid_work_agent2 / aid_work_logs2
    └── Redis（腾讯云托管 172.17.0.7:6379，测试/开发用）

DNS（2026-09-15 已切换）
    └── agent.aidingyi.cn  → 129.211.65.243
        （agent1.aidingyi.cn 为迁移验证期临时域名，已弃用）
```

**外部回调端点登记**：

| 端点 | 用途 | 备注 |
|------|------|------|
| `/t/{tenant}/(wecom|dingtalk|feishu|wecom_kf|wecom_personal_rpa)/callback/{config_id}` | IM 渠道消息回调 | 每配置独立凭证 |
| `/api/wechat-mp/callback/{config_id}` | 微信公众号服务器配置回调（公众号内容入知识库 WP4，产品版 2026-09-14） | 走 `/api/*` 反代，无需单独 nginx 配置；每配置独立 token（服务端生成）；GET=URL 验证回显 echostr，POST=事件受理（明文+安全模式 AES）；诊断期环境变量 `WECHAT_MP_CALLBACK_TOKEN` 逻辑已移除 |

**凭据加密主密钥（2026-09-15 起）**：渠道敏感字段 Fernet 主密钥统一由 `src/core/secret_crypto.py` 加载，优先级 `settings.app.secret_key` → 环境变量 `APP_SECRET_KEY` → 环境变量 `RPA_SECRET_KEY`。**`APP_SECRET_KEY` 优先级高于 `RPA_SECRET_KEY`，部署前需确认生产 env 未占用该名**（若被占用为其他值，会导致存量 RPA/wechat_mp 密文全部解密失败）。

**Volume 挂载**（与旧机生产一致）：

- `/var/www/agent:/app` — 整个项目目录挂载，代码更新后重启容器即可生效

> ⚠️ **`plans/` 是运行时可写目录，排除后必须预创建**（2026-09-03 agent3 启动事故教训）：
>
> `plans/` 不仅是文档目录，还是 `PlanManager` 的运行时持久化目录。sparse-checkout 排除后若目录内无未跟踪运行时文件残留，**整个目录会消失**。容器以 uid 1000 运行、项目目录属主不一致时 `mkdir` 报 `PermissionError` → gunicorn worker 无法 boot，容器 crash 循环。
>
> **修复与预防**（属主对齐运行身份 uid 1000 gid 999）：
>
> ```bash
> sudo mkdir -p /var/www/agent3/plans
> sudo chown 1000:999 /var/www/agent3/plans
> ```

配置方式（新 clone 的服务器需重新执行）：

```bash
cd /var/www/agent   # agent2 / agent3 同理
git config core.sparseCheckout true
printf '/*\n!/.agents/\n!/.claude/\n!/.codebuddy/\n!/.pytest_cache/\n!/.zcode/\n!/docs/\n!/ext/\n!/openspec/\n!/plans/\n!/test_uploads/\n!/tests/\n' > .git/info/sparse-checkout
git read-tree -mu HEAD
```

回滚：`git config --unset core.sparseCheckout && rm .git/info/sparse-checkout && git read-tree -mu HEAD`。

## 11. 读取日志与数据速查

> 排查线上问题时，按本节路径直接读取日志与数据，避免绕路。**先分清环境**：生产问题到新机（129.211.65.243），测试/开发问题到旧机（124.222.3.254）。

### 11.1 容器日志在宿主机直接读取

容器内 `/app/log` 通过 volume 挂载到宿主机项目目录的 `log/` 子目录，**无需 `docker exec` 进容器**：

| 环境 | 服务器 | 容器名 | 宿主机路径 |
|------|--------|--------|-----------|
| 生产 | 新机 | `aid-agent-api` | `/var/www/agent/log` |

常用命令：

```bash
# 直接 tail 生产日志（新机，无需进容器）
ssh -p 10167 ubuntu@129.211.65.243 "tail -f /var/www/agent/log/aid-work-agent.log"

# 临时主题日志（tlog，调试某主题时单独落盘到 log/temp/）

# scp 拉取生产日志到本地
scp -P 10167 ubuntu@129.211.65.243:/var/www/agent/log/aid-work-agent.log ./
```

### 11.2 数据库直连与表分布

| 库名 | 服务器 | 用途 |
|------|--------|------|
| `aid_work_agent` | 新机 | 生产主库（业务数据、`log_error` 错误日志） |
| `aid_work_logs` | 新机 | 生产日志库（`obs_traces` / `obs_spans` / `obs_scores`，TimescaleDB） |
| `aid_work_agent2` | 旧机 | 测试/在线开发主库 |
| `aid_work_logs2` | 旧机 | 测试/在线开发日志库 |

直连方式见 [postgres.md](postgres.md) §4（测试库公网 5433 可直连；生产库走 SSH 隧道）。

### 11.3 按 trace_id 读取日志

用户提供 `trace_id` 时，应到**对应环境的日志库**读取：`obs_traces` 存请求主记录，`obs_spans` 存各步骤明细。

```bash
# 生产：查 trace 主记录（新机容器内 psql）
sudo docker exec -it aid-postgres psql -U aid_user -d aid_work_logs \
  -c "SELECT trace_id, session_id, tenant_id, user_id, status, duration_ms, total_tokens, error_message FROM obs_traces WHERE trace_id = '<trace_id>';"

# 生产：查该 trace 的步骤明细
sudo docker exec -it aid-postgres psql -U aid_user -d aid_work_logs \
  -c "SELECT span_type, name, model, prompt_tokens, completion_tokens, status, error_message FROM obs_spans WHERE trace_id = '<trace_id>' ORDER BY start_time;"
```

- 测试环境同理（旧机），把库名换成 `aid_work_logs2`
- 平台级 ERROR 错误日志（含完整堆栈）在**主库**的 `log_error` 表（`WRITE_LOG_ERROR=true` 时写入），不在日志库
- 日志库表结构见 [init-postgres-logs.sql](init-postgres-logs.sql)

## 12. 故障排查

> **文件/存储排查总则**：排查租户文件、附件落盘、存储迁移等问题时，统一
> `sudo docker exec aid-agent-api sh -c '...'` 进**本项目容器**读（例如
> `sudo docker exec aid-agent-api sh -c 'ls -la storage/tenants/'`）。
> **容器内 appuser 身份能正常访问文件是必要且充分的判据**——应用本身即以该身份
> 读写 storage；**宿主机 ubuntu 身份能否访问文件是不必要、也不充分的**，不作为
> 判据（storage 走 docker volume 挂载，宿主机路径与容器内路径不一致，
> 一律以容器内路径为准）。

### 12.1 容器无法启动

```bash
sudo docker logs aid-agent-api --tail 100
# 常见原因：
# - .env 未配置或字段缺失（改 .env 后未 force-recreate 也属此类）
# - 端口冲突
# - 可写目录属主不对：新机 gosu appuser(uid 1000)，log/storage/plans 需预创建并 chown 1000:999
# - 依赖问题：docker compose -f docker-compose.prod.yml build --no-cache
```

### 12.2 Nginx 502

```bash
sudo docker ps | grep aid-agent-api       # 容器是否运行
curl http://localhost:8000/health         # 后端连通性
sudo tail -f /var/log/nginx/error.log
```

### 12.3 Gunicorn Worker 启动失败

```bash
sudo docker logs aid-agent-api 2>&1 | head -100
# 常见原因：
# - LLM API Key 未配置导致 lifespan 初始化失败
# - /dev/shm 不可用（注释 gunicorn.conf.py 中的 worker_tmp_dir）
# - log/plans 等运行时目录缺失或属主错误（见 §9.1 plans/ 事故）
```

### 12.4 API 请求超时

```bash
sudo docker stats aid-agent-api          # 资源使用
# .env 临时调大：WORKER_TIMEOUT=300
# nginx conf 临时调大：proxy_read_timeout 300s
```

### 12.5 文件上传失败

```bash
ls -la /var/www/qb3_upload/agent_storage/
df -h   # 检查磁盘空间
```

### 12.6 Playwright / Chromium 启动失败

```
报错：Permission denied: '/tmp/...'
```

根因：Debian trixie-slim 上游变更导致 `/tmp` 默认 mode=755。处理链：
1. docker-compose 已挂载 `tmpfs /tmp mode=1777`（首选）
2. `fix_tmp.sh`（容器 entrypoint 兜底）
3. 运行时手动修复：`sudo docker exec -u root aid-agent-api chmod 1777 /tmp`

### 12.7 数据库连接耗尽

```bash
# 查看当前连接数
sudo docker exec -it aid-postgres psql -U aid_user -d postgres \
  -c "SELECT datname, count(*) FROM pg_stat_activity GROUP BY datname;"

# 强制断开某库所有连接（谨慎）
sudo docker exec -it aid-postgres psql -U aid_user -d postgres \
  -c "SELECT pg_terminate_backend(pid) FROM pg_stat_activity WHERE datname='aid_work_agent' AND pid <> pg_backend_pid();"
```

### 12.8 迁移相关踩坑速查

以下坑在 2026-09 迁移中踩过，重建/再迁移时必读（详见 [生产环境部署.md](生产环境部署.md) §1.3）：

| 坑 | 处理 |
|------|------|
| TimescaleDB 跨版本 restore 失败（hypertables 全丢） | 用与源库相同版本镜像（2.27.2-pg16），目标库先 DROP + CREATE 空库再全量 pg_restore |
| `docker cp` 静默失败（Docker 29） | 改用 `cat file \| docker exec -i <容器> sh -c "cat > file"` stdin 流式写入 |
| 改 `.env` 后容器仍用旧值 | `docker compose restart` 不重读 env_file，必须 `up -d --force-recreate` |
| Docker Hub 拉不动 | `/etc/docker/daemon.json` 配腾讯云内网镜像 `mirror.ccs.tencentyun.com`（新机已配） |
| rsync `-e "ssh -i ..."` 报错 | 用 `/root/.ssh/config` Host 别名（新机 root 已配 `oldprod` → 124.222.3.254） |
| nginx `limit_conn_zone already bound` | 多份 conf 重复定义全局 zone，仅保留一份 |
| Worker `PermissionError: log/agent` | 可写目录被 rsync/git 排除后缺失，宿主机预创建并 chown 1000:999 |

更完整的排查清单见 [DEPLOYMENT.md](DEPLOYMENT.md) §故障排查 与 [README.md](README.md) §故障排查。

## 13. 仿真环境（staging，agent1.aidingyi.cn）

> 设计文档：[../docs/system/simulation-env-design.md](../docs/system/simulation-env-design.md)。用途：复现生产 bug——一键同步指定租户的生产数据到仿真库，配合 `SIMULATION_MODE` 副作用门控，与生产同机混部但相互隔离。

### 13.1 部署事实速查

| 项目 | 值 |
|------|------|
| 目录 | `/var/www/agent1/`（代码 = 生产工作区 rsync + cherry-pick 仿真提交；含 .git） |
| 容器 | `aid-agent-api1`（镜像 `aid-agent-api:latest` 与生产共用），端口 `8010:8000` |
| compose | `/var/www/agent1/docker-compose.sim.yml`（仅 api 服务，**无 background 容器**，物理消除定时外呼） |
| 数据库 | 同实例新库 `aid_work_agent1` / `aid_work_logs1`，专用账号 `aid_sim_user`（两库 OWNER）；生产侧同步用只读账号 `aid_readonly` |
| Redis | 共用生产 `aid-redis` 实例，`REDIS_KEY_PREFIX=aid-agent1` 隔离 |
| 附件 | 共享挂载生产 `/var/www/qb3_upload/agent_storage|agent_uploads`（删除由 SIMULATION_MODE 门控跳过） |
| 副作用门控 | `SIMULATION_MODE=1`：SMTP/通知 dry-run、租户附件磁盘删除跳过、启动日志横幅 |
| Nginx | `/etc/nginx/conf.d/agent1.aidingyi.cn.conf` + 白名单 `/etc/nginx/snippets/sim_whitelist.conf`（⚠️ 必须放 snippets/，放 conf.d/ 会污染 http 层拦掉生产） |
| 日志 | `/var/log/nginx/agent1_access.log` / `agent1_error.log`；应用日志 `/var/www/agent1/log/` |
| 资源限额 | mem 4g / cpus 1.5 / `WORKERS=2`，`restart: "no"`（按需启停，不随机自启） |
| 凭据 | DB 密码存 `/var/www/agent1/.db_passwords`（600）；`.env` 由生产派生（600） |

### 13.2 常用操作

```bash
# 启动 / 停止（默认停）
cd /var/www/agent1 && docker compose -f docker-compose.sim.yml up -d
cd /var/www/agent1 && docker compose -f docker-compose.sim.yml stop

# 改 .env 后必须重建（restart 不重读 env_file）
docker compose -f docker-compose.sim.yml up -d --force-recreate

# 一键同步指定租户（在 243 上，生产库只读 + 渠道凭证自动置空）
sudo /var/www/agent1/deploy/sync_tenant_to_sim.sh --tenant <tenant_id> --wipe --redis --dry-run
sudo /var/www/agent1/deploy/sync_tenant_to_sim.sh --tenant <tenant_id> --wipe --redis

# 代码更新（生产已更新后）：rsync 差量 + cherry-pick 仿真提交
sudo rsync -a --exclude '.env' --exclude 'log/' --exclude '.git' /var/www/agent/ /var/www/agent1/
cd /var/www/agent1 && git cherry-pick <仿真提交> && docker compose -f docker-compose.sim.yml restart api
```

### 13.3 注意事项

- **同步后渠道凭证为空**：`tenant_channel_configs.config='{}'`、`verified=0`——仿真环境调试渠道需在前台重新配置测试渠道应用。
- **健康检查**：`curl http://localhost:8010/health`；启动横幅「⚠️ 仿真环境（SIMULATION_MODE=1）」出现即门控生效。
- **git 状态**：agent1 的 master 与远程分叉属预期（含生产未推送提交 + 仿真 cherry-pick 提交），勿在 agent1 内直接 pull/rebase。
- 生产 `/var/www/agent` 更新后需同步到 agent1（见上），两边代码差异 = 仿真门控提交。
