## 1. 发布生产时调整 .env 运行槽位与每槽内存上限

**对应提交**：`701da4dd`（监控「Runner 负载」卡片新增总槽位展示，读取 `AGENT_RUNNER_WORKER_SLOTS`）等监控改版批次（`ba39ccdc` / `a6b21ccc` / `f2815f5d` / `f4916355`）

**Why**：2026-11-10 测试环境已完成槽位调优（agent2 扩 4 槽、agent3 降 1 槽，均设每槽内存 1g），但生产 243 的 `/var/www/agent/.env` **未设置**任何 `AGENT_RUNNER_WORKER_*` 变量，当前生效值为 compose 默认：1 槽、每槽内存上限 6g。发布监控改版后「总槽位」按默认 1 显示，与实际期望容量不符；需在发布时一并作出容量决策并写入 `.env`。

**操作**：编辑 `/var/www/agent/.env`，新增（或调整）：

```bash
AGENT_RUNNER_WORKER_SLOTS=<槽数>
AGENT_RUNNER_WORKER_MEMORY=<每槽内存上限，如 1g>
```

然后 `docker compose -f docker-compose.prod.yml -f docker-compose.agent-runner.yml up -d runner-worker` 应用（replicas 变化会自动增减容器）。

**决策参考**（2026-11-10 现状）：

- 生产宿主 4 核 CPU / 15G 内存（available 约 9.9G），同机还运行 agent1 仿真栈（`aid-runner-worker1` 独立项目，互不影响但共享宿主资源）
- 测试环境先例：agent2 4 槽 + 每槽 1g、agent3 1 槽 + 每槽 1g（每槽 CPU 限额默认 1）
- 测试环境教训：agent2 库 `max_connections=80`，4 槽满载理论需 4×(15+2)=68 连接 + API/background 存量，多槽并发时需关注 DB 连接预算；生产发布时按生产库 `max_connections` 同口径核算
- 每槽内存上限若维持 6g，多槽名义上限会超过宿主物理内存（上限不预留、峰值并发电才会触发），需按生产任务画像权衡

**验证**：`docker ps` 中 runner-worker 容器数 = `AGENT_RUNNER_WORKER_SLOTS` 且全部 healthy；监控页「Runner 负载」卡片「运行中 / 收尾 / 总槽位」的总槽位值与 `.env` 一致。

## 2. 发布生产时为对话容器配置百度检索双出口代理（WEBSEARCH_BAIDU_PROXY）

**对应提交**：`daa80168`（web_search.py 多代理轮换 + 失败出口 10 分钟熔断回直连，百度风控治理）

**Why**：服务器 IP 被百度动态风控时检索须走外部出口。双出口基础设施 2026-11-11 已就绪并验证：151（办公网出口 `180.169.235.0/24`）与 46（博物馆宽带出口 `123.158.82.107`）两条 SSH 反向隧道分别落 243 宿主回环 **18080 / 18081**，forwarder（socat）已绑 `172.20.0.1:18080/18081`（**243 的 docker 网关是 172.20.0.1，勿照抄 254 的 192.168.48.1**）。生产容器未配 env 前检索直连，撞风控时无代理兜底。测试 254（agent2）已同日完成同款配置并 e2e 验证（轮换交替生效、零 errors），生产发布时按测试先例落地。

**操作**：编辑 `/var/www/agent/.env`（agent1 栈为 `/var/www/agent1/.env`），新增：

```bash
WEBSEARCH_BAIDU_PROXY=http://leadproxy:<151密码>@172.20.0.1:18080,http://leadproxy:<46密码>@172.20.0.1:18081
```

- 逗号分隔两出口即启用轮换；密码只从各出口服务器 tinyproxy.conf 取（151: `~/lead-search-proxy/tinyproxy.conf`、46: `D:\lead-search-proxy\tinyproxy.conf`），不落任何仓库文档
- 仅 agent / agent1 两套栈的**对话执行容器**需要该 env（api / background / runner-api / runner-worker）

然后 `docker compose ... up -d` 重建对应容器（**改 .env 必须 compose up -d 重建，restart 不重读 env**）。

**验证**：
1. 宿主双落点各归其位：`curl -x http://leadproxy:<对应密码>@127.0.0.1:18080 https://ifconfig.me` 应返回 180.169.x、`:18081` 应返回 123.158.82.107
2. 容器内 env 已是逗号分隔双值：`docker exec aid-agent-api printenv WEBSEARCH_BAIDU_PROXY`
3. e2e：aid-agent-api 内 `python` 走 `web_search.search(..., engine='baidu')` ×3，真实结果且 errors 为空；查 `web_search._baidu_warm_cookies` 与轮换序列（`_next_baidu_proxy()`）确认两出口交替

## 4. 定期低峰重启 runner-worker 容器（agent 与 agent1 两套栈都要）

**对应提交**：`477cb413`（任务收尾 gc + malloc_trim 钩子、RSS 水位自动 recycle）。定期重启是兜底手段，不依赖该提交代码。

**Why**：2026-11-12 agent2 实测确认 worker 常驻进程存在**内存棘轮效应**——跑完 1M 行 Excel 任务后 worker RSS 停在约 315MB（基线约 87MB），25 分钟不回落（pymalloc arena 与 glibc 堆释放后不归还 OS）。单个 worker 只进不出，长期运行下历史峰值水位变常态占用，多容器叠加会逼近 cgroup 上限甚至挤占宿主内存。收尾 gc/trim 钩子缓解大部分回落，RSS 水位监控在逼近上限且空闲时自动 recycle；定期重启覆盖二者之外的残留（水位未到阈值但已抬高、页缓存、长周期碎片）。

**操作**：在低峰期（建议每周一次，凌晨 03:00~05:00 任选）对两套栈的 runner-worker 容器执行滚动重启：

```bash
# agent 栈（243 生产 / 254 测试）
ssh <host> "docker restart \$(docker ps -q --filter name=runner-worker)"

# agent1 栈（243 生产同机运行，独立项目 aid-runner-worker1）
ssh <host> "docker restart \$(docker ps -q --filter name=agent1-runner-worker)"
```

- 逐台重启即可（容器间无依赖）；重启会丢掉该容器 poll 队列中未领取的领取权，租约与 DB 状态兜底恢复，空闲时段执行无业务影响
- 诺度 30 私有云按其拓扑如有 runner-worker 同样执行；无则跳过
- 重启后确认全部容器 healthy

**验证**：`docker ps` 两套栈 runner-worker 容器全部 healthy；重启后任一 worker RSS 回到基线水位（`docker stats --no-stream` 单容器 < 200MB 量级）；重启时段无任务被中断（agent_runner 表无 interrupted 增量）。

## 5. 发布生产时将 Postgres `max_connections` 80/120 -> 200

**对应提交**：`deploy/docker-compose.postgres.yml`（compose `command` 内 `max_connections` 参数，发版窗口随本条目一并修改提交；80->120 先例见 `595527d4`，[plan-runner-capacity-load-separation.md](plans/plan-runner-capacity-load-separation.md) 3.1）

**Why**：2026-11-13 容量评估定版：生产库连接数决定并发执行上限的兜底资源（真闸门在应用侧槽位×连接池，DB 连接数是最后防线）。当前 compose 默认 120，agent2 测试环境已有登记风险——4 槽满载理论需 4×(15+2)=68 连接 + API/background 存量约 40 ≈ 108 接近触顶（[服务器部署现状.md](服务器部署现状.md) 2026-11-10 条目）；生产槽位决策（条目 1）落地后同样逼近。16G 宿主机 / PG 容器 6G 上限下 200 是安全上界：每连接成本 ≈ 基础后端 2-3MB + work_mem 16MB×排序/哈希节点数，200 连接较 120 约多耗 200-250MB，容器 6G 内余量充足（shared_buffers 1GB + maintenance 512MB + 辅助进程 ~300MB 之外仍有 ~3.5G 活跃查询余量，池懒加载、全员活跃排序是病态上界不现实）。

**操作**：

1. 修改 `deploy/docker-compose.postgres.yml` `command` 中 `max_connections=120` -> `200`（仓库提交后各服务器 pull）
2. 生产 243（与测试 254 如同配置）执行 `docker compose -f docker-compose.prod.yml -f docker-compose.agent-runner.yml -f docker-compose.postgres.yml up -d postgres`——**`max_connections` 是启动参数，reload 无效，必须重建 PG 容器生效；重建有秒级 DB 中断，全部服务重连，务必在发版窗口低峰执行**
3. 诺度 30 不适用：其混部口径独立（容器 4G、Java 压缩 -Xmx 后腾出的内存预算、`max_connections=40`），如需调整另行走其容量评估，不随本条目

**验证**：

1. `docker exec <postgres 容器> psql -U <用户> -c "SHOW max_connections;"` 返回 200
2. PG 容器内存 `docker stats --no-stream` 无异常抬升（预期较 120 基线多 200-250MB 量级，仅在连接真实建立后渐进增长）
3. 无连接获取报错：发布后观察 `log_error` 表与主日志 24h，无 `too many clients already` / FATAL 53300
4. 满载演练（可选）：4 槽重任务并发时段查 `SELECT count(*) FROM pg_stat_activity;`，水位留 ≥30 余量
