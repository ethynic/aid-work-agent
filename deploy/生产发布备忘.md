## 1. 发布生产时调整 .env 运行槽位与每槽内存上限

**对应提交**：`701da4dd`（监控「Runner 负载」卡片新增总槽位展示，读取 `AGENT_RUNNER_WORKER_SLOTS`）等监控改版批次（`ba39ccdc` / `a6b21ccc` / `f2815f5d` / `f4916355`）

**Why**：2026-11-10 测试环境已完成槽位调优（agent2 扩 4 槽、agent3 降 1 槽，均设每槽内存 1g），但生产 243 的 `/var/www/agent/.env` **未设置**任何 `AGENT_RUNNER_WORKER_*` 变量，当前生效值为 compose 默认：1 槽、每槽内存上限 6g。发布监控改版后「总槽位」按默认 1 显示，与实际期望容量不符；需在发布时一并作出容量决策并写入 `.env`。

**操作**：编辑 `/var/www/agent/.env`，新增（或调整）：

```bash
AGENT_RUNNER_WORKER_SLOTS=<槽数>
AGENT_RUNNER_WORKER_MEMORY=<每槽内存上限，如 1g>
```

然后 `docker compose -f docker-compose.prod.yml -f docker-compose.agent-runner.yml up -d runner-worker` 应用（replicas 变化会自动增减容器）。

**决策参考**（2026-11-10 现状）：

- 生产宿主 4 核 CPU / 15G 内存（available 约 9.9G），同机还运行 agent1 仿真栈（`aid-runner-worker1` 独立项目，互不影响但共享宿主资源）
- 测试环境先例：agent2 4 槽 + 每槽 1g、agent3 1 槽 + 每槽 1g（每槽 CPU 限额默认 1）
- 测试环境教训：agent2 库 `max_connections=80`，4 槽满载理论需 4×(15+2)=68 连接 + API/background 存量，多槽并发时需关注 DB 连接预算；生产发布时按生产库 `max_connections` 同口径核算
- 每槽内存上限若维持 6g，多槽名义上限会超过宿主物理内存（上限不预留、峰值并发电才会触发），需按生产任务画像权衡

**验证**：`docker ps` 中 runner-worker 容器数 = `AGENT_RUNNER_WORKER_SLOTS` 且全部 healthy；监控页「Runner 负载」卡片「运行中 / 收尾 / 总槽位」的总槽位值与 `.env` 一致。

## 2. 发布生产时为对话容器配置百度检索双出口代理（WEBSEARCH_BAIDU_PROXY）

**对应提交**：`daa80168`（web_search.py 多代理轮换 + 失败出口 10 分钟熔断回直连，百度风控治理）

**Why**：服务器 IP 被百度动态风控时检索须走外部出口。双出口基础设施 2026-11-11 已就绪并验证：151（办公网出口 `180.169.235.0/24`）与 46（博物馆宽带出口 `123.158.82.107`）两条 SSH 反向隧道分别落 243 宿主回环 **18080 / 18081**，forwarder（socat）已绑 `172.20.0.1:18080/18081`（**243 的 docker 网关是 172.20.0.1，勿照抄 254 的 192.168.48.1**）。生产容器未配 env 前检索直连，撞风控时无代理兜底。测试 254（agent2）已同日完成同款配置并 e2e 验证（轮换交替生效、零 errors），生产发布时按测试先例落地。

**操作**：编辑 `/var/www/agent/.env`（agent1 栈为 `/var/www/agent1/.env`），新增：

```bash
WEBSEARCH_BAIDU_PROXY=http://leadproxy:<151密码>@172.20.0.1:18080,http://leadproxy:<46密码>@172.20.0.1:18081
```

- 逗号分隔两出口即启用轮换；密码只从各出口服务器 tinyproxy.conf 取（151: `~/lead-search-proxy/tinyproxy.conf`、46: `D:\lead-search-proxy\tinyproxy.conf`），不落任何仓库文档
- 仅 agent / agent1 两套栈的**对话执行容器**需要该 env（api / background / runner-api / runner-worker）

然后 `docker compose ... up -d` 重建对应容器（**改 .env 必须 compose up -d 重建，restart 不重读 env**）。

**验证**：
1. 宿主双落点各归其位：`curl -x http://leadproxy:<对应密码>@127.0.0.1:18080 https://ifconfig.me` 应返回 180.169.x、`:18081` 应返回 123.158.82.107
2. 容器内 env 已是逗号分隔双值：`docker exec aid-agent-api printenv WEBSEARCH_BAIDU_PROXY`
3. e2e：aid-agent-api 内 `python` 走 `web_search.search(..., engine='baidu')` ×3，真实结果且 errors 为空；查 `web_search._baidu_warm_cookies` 与轮换序列（`_next_baidu_proxy()`）确认两出口交替
