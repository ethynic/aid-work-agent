# 并行会话 Git 协作纪律

> **适用范围**：多个 AI 会话（或人 + 会话）同时在本仓库工作区并行作业的场景。git 工作区与 index 是**整个目录共享**的，stash / reset / rebase / checkout / restore 等全局状态操作会波及**所有**会话的未提交改动，不分会话。
>
> **背景**：2026-11-10 会话 A 推送被拒后 `git stash push` 收走会话 B 的 5 个未提交文件再 rebase，B 侧感知「工作区被重置冲掉」（pop 恢复无损失，但属越权触碰他方改动）。本规范把并行场景的纪律固化。

## 纪律

1. **勤提交，缩小脏区窗口**：非平凡任务在自己的分支上勤提交（自有分支提交无害，后续可 squash/rebase 整理）；master 提交仍须用户确认（见 [AGENTS.md Git 提交规范](../../AGENTS.md#git-提交规范)）。脏工作区存活时间越长，被并行全局操作误伤的概率越高。
2. **全局状态操作前先盘点他方改动**：执行 stash / reset / rebase / checkout 前，若工作区存在**不属于本任务**的改动，先询问用户处置方式，**不得直接 stash**。
3. **推送被拒（他人并发推送）**：工作区干净才自行 `git pull --rebase`；含他方改动则停下询问。
4. **只暂存本任务文件**：`git add` 逐个点名，禁止 `git add -A` / `git add .`（重申 AGENTS.md 规范第 3 条）。
5. **误丢兜底**：先查 `git stash list` 与 `git reflog`，stash/reflog 几乎不会真丢；不要慌，更不要凭记忆重建改动。

## 已否决方案

`git worktree` 隔离不作为默认方案（2026-11-10 用户试用后裁决：维护成本高、新目录需重装依赖）。确有强隔离需求时由用户主动提出，不要反复推荐。
