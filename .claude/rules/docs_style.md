# 文档写作规范

> **适用范围**：本项目所有 Markdown 文档（`docs/`、`subagents/`、`src/skills/` 下的 SKILL.md、根目录 README 等），以及代码中的中文注释。规范的制定背景见「3. 箭头/破折号字符陷阱」。

---

## 1. 箭头符号：统一使用 Unicode 箭头 `->`

本项目文档中的流程指向、映射关系、状态流转，**统一使用 Unicode 箭头 `->`（U+2192）**，禁止使用 ASCII 双连字符箭头 `->`。

**例外**：
- 代码块内的代码（SQL、Python、shell 等可执行内容）按代码自身语法写，如 Python `->` 返回类型注解、shell 重定向等不受本条约束
- 引用外部系统的原始输出/报错信息时保持原样

## 2. 破折号：统一使用 Unicode 长破折号 `--`

中文文档中的插入语/解释性破折号，**统一使用 `--`（两个 U+2014 em-dash）**，禁止用 ASCII `--` 充当中文破折号。

**例外**：
- Markdown 结构语法必须用 ASCII：frontmatter 分隔线 `---`、表格分隔线 `|---|`、YAML 中的 `--` 选项、URL 中的双连字符
- 代码块内的代码按代码语法写

## 3. 箭头/破折号字符陷阱（编辑文档必读）

**问题**：Unicode `->`（U+2192）与 ASCII `->`、Unicode `--`（U+2014×2）与 ASCII `--` 在渲染后**视觉上完全相同**，肉眼无法区分。后果：

1. 用 Edit 工具编辑文档时，old_string 中的箭头/破折号字符与文件实际字符不一致，报「String to replace not found」，且极难排查（看起来明明一样）
2. 同一份文档中两种写法混用，grep/统计口径被污染
3. AI 辅助写作时输出字符不确定（时而是 ASCII、时而是 Unicode），会在编辑过程中反复触发第 1 类失败

**编辑已有文档时的强制流程**：

1. **先探测、后编辑**：写 old_string 前，先用命令确认目标位置的字符实际是什么：

   ```bash
   # 查看文档中箭头字符构成（U+2192 显示为 →）
   python3 -c "
   s = open('<文件>', encoding='utf-8').read()
   print('Unicode 箭头:', s.count(chr(0x2192)), 'ASCII 箭头:', s.count('->'))
   print('em-dash:', s.count(chr(0x2014)))
   "
   ```

2. **old_string 精确匹配实际字符**：如果不确定，用 Python 脚本 + `chr(0x2192)` / `chr(0x2014)` 显式构造字符串做替换，或做多变体匹配（同时尝试 ASCII 和 Unicode 两种形式）

3. **新写内容一律用 Unicode**：新插入的段落、表格、流程图中，箭头写 `->`（U+2192）、破折号写 `--`（U+2014×2），保持与文档主流一致

**排查口诀**：Edit 报「字符串未找到」且目标文本"看起来完全正确"时，99% 是箭头/破折号字符不一致，先跑上面的探测命令，不要反复重试同样的 old_string。

## 4. 其他文档约定

- 文档语言为中文；代码标识符、命令、文件路径保持英文原样
- 流程图（Mermaid / ASCII 图）中的节点流向同样使用 `->`（U+2192）
- 需要登记到 `docs/ideas.md` 的文档，遵循 CLAUDE.md「文档登记规范」
