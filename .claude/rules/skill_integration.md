# 外部技能包整合规范

> **适用范围**：将从第三方系统（workbuddy、豆包等）探索成熟的技能包整合进本项目的全部工作。典型场景：第三方技能出新版/增量更新后的合并、全新技能包的首次移植。
>
> **背景**：pptx-vi-gen 技能经 2026-10-21 整体移植、2026-10-22/10-23 三轮上游合并实践后沉淀本流程。三轮中反复出现的风险是「上游更新覆盖我方补丁」（sysClr 修复被上游回退）与「上游结构调整导致接口口径变化」（CLI 入口被上游移除），本规范将其固化为主要流程节点。

---

## 1. 接收与盘点

1. 技能包落到临时目录（如 `/mnt/temp/<skill_name>`），先整体浏览结构：`SKILL.md`、核心包目录、verify/示例/资源文件、requirements 清单。
2. 与我方现有技能目录做结构比对：

   ```bash
   diff -rq <临时目录> src/skills/<skill>-<ver>/
   find <临时目录> -type f | sort   # 上游完整文件清单
   ```

3. 识别三类差异，分别处理：
   - **内容更新**：包内模块改动 -> 常规合并
   - **结构调整**：上游增删文件、移动入口（如 CLI 入口移除改为包 API 调用）-> 决定我方布局是否跟随，**默认保持我方布局不跟随**，只做内容合并
   - **资源变化**：新增字体/模板/示例等大文件 -> 评估仓库体积与运行必要性后按需引入

## 2. 补丁与陷阱清单核对（合并前必做）

1. 从项目记忆（MEMORY.md 及其指向的记忆文件）与 `docs/ideas.md` 对应条目取出**我方补丁清单**。该清单是历轮整合沉淀的核心资产，没有它每轮都要重新踩坑。
2. 对清单中每个补丁逐个判断（三选一，把结论写回记忆）：
   - **需重移植**：上游仍缺或已回退（如 pptx-vi-gen 的 sysClr 取 lastClr，上游反复回退成读 val）
   - **被上游新方案取代**：上游用更好的方式解决了同一问题（如 Linux 字体路径补丁被随包字体分发取代）——补丁作废并从清单移除
   - **不适用**：补丁在我方 CLI/文档层，上游更新根本不会碰到（如路径 fail-fast、role 校验）——跳过即可
3. **上游 bug 修复对照**：我方修过上游未修的 bug，逐个检查上游新版是否也修了：
   - 上游仍未修 -> 重新移植我方修复
   - 上游已修 -> 对比实现，取更优者，避免双份逻辑

## 3. 合并策略

| 内容 | 策略 |
|------|------|
| 核心包代码 | 用上游版本整体覆盖，再叠加我方补丁（先覆盖后补丁，避免 diff 噪音） |
| 我方目录布局 | 保持不变（如 scripts/ CLI 入口层是我方加的，上游没有） |
| CLI/胶水脚本 | 我方维护，仅在上游 API 签名变化时适配；新能力按需暴露开关（如 --embed-fonts） |
| SKILL.md | 保持我方结构与调用口径（skill_execute + scripts/），采纳上游新章节，version 递增 |
| references/usage.md 等参考文档 | 通常整文件采纳上游，再适配我方特有段落 |
| 资源文件（字体/模板/示例） | 上游 verify 脚本依赖的资源一并引入，保证验证可独立运行；纯演示性大文件按需取舍 |
| __pycache__ 等 | 不入库；注意陈旧 pyc 可能因权限删不掉（容器 root 产生），源码 mtime 变化后 Python 会自动忽略，不影响功能 |

**版本号**：SKILL.md frontmatter version 按上游语义递增（上游大功能更新 -> 次版本号 +1），保持可追溯。

## 4. 验证（三层各有分工）

1. **我方单测**：`./scripts/dev_test.sh tests/unit/test_<skill>.py -p no:cacheprovider -q`，确认既有断言不回归。
2. **上游自带 verify**：第三方包常带自验证脚本，全部跑一遍——它们覆盖上游作者的意图，能发现我方合并引入的偏差。
3. **CLI 端到端冒烟**：在容器内（`docker exec aid-agent-api`）用最小 content 走一遍完整命令，确认 stdout JSON 结构、我方特有路径（如无模板兜底、fail-fast 拒绝）行为正常。

验证注意：
- 容器内运行时注意工作目录与相对路径资源（demo content 引用的图片按 `cwd -> PROJECT_ROOT -> test_uploads` 顺序解析）
- 未覆盖的验证缺口（如真实 PowerPoint 观感、真实模板全链路）如实登记，不声称已验证
- 涉及新增 LLM/Embedding 调用点的技能，按 [billing_audit.md](./billing_audit.md) 自检查

## 5. 登记与闭环

1. **docs/ideas.md**：更新对应条目（首次整合新增条目），说明追加本轮合并内容与验证结论，状态按实际推进（待提交部署 / 部分完成等）。
2. **项目记忆**：更新记忆文件——这是下轮整合的输入，必须包含：
   - 更新后的**我方补丁清单**（含每个补丁的三选一结论）
   - 上游 bug 修复的对照状态（上游修没修）
   - 已过时补丁（防止下轮误移植）
   - 已知限制（如 replace_text 跨段落命中 0 需 set_text 兜底）
   - 验证状态与缺口
3. **提交**：按 Git 提交规范执行（fetch -> 确认无冲突 -> commit -> push），提交信息注明「合并上游 YYYY-MM-DD 更新」与本轮核心变化。

## 6. 首次移植新技能包的额外事项

首次移植（非增量合并）额外确认：

- [ ] 技能与现有工具/技能的**边界划分**（哪个诉求归哪个技能，写入 SKILL.md「不要使用本技能」）
- [ ] 目录布局决策：新建 `src/skills/<name>-<version>/`，含 SKILL.md（YAML frontmatter + 触发词）
- [ ] 第三方特定依赖剥离（路径、环境、专有服务），我方容器环境可独立运行
- [ ] 注册与发现验证（SkillRegistry 加载、skill_execute 调用、白名单层级配置）
- [ ] 新建 `tests/unit/test_<skill>.py` 基础单测（注册发现/端到端/非法输入）
- [ ] 商业授权核查：随包分发的字体/图片/模板的许可证（如 SIL OFL 1.1 可商用分发）
