# 三智能体开发流程

针对非平凡的代码开发任务（新功能、Phase 开发、重构、多文件 bug 修复），按本流程**串行**执行三个独立智能体，把问题拦截在合并前，避免"自己写的自己测"盲区。完整流程在**独立 worktree + 功能分支**上进行：每阶段通过即提交推送，合并回主分支前由用户人工把关。

## 为什么需要这个流程

凡是"合并即上线/部署"的项目，一旦合入的代码有 build 错误或启动错误，服务/应用直接挂掉。本流程通过三个**独立**智能体的串行校验把问题拦在合并前：

- **开发智能体**：写代码 + 单测，自测通过
- **测试智能体**：独立跑测试 + 回归 + 启动安全检查，修明显问题（不复用开发的判断）
- **CodeReview 智能体**：独立审查，修必要问题（不复用前两者判断）

三个智能体**串行执行，后一个等前一个完成才启动**，每个独立验证。

## 何时使用 / 何时简化

| 任务类型 | 流程 |
|---------|------|
| 新功能 / Phase 开发 / 多文件改动 / 触及启动链路 | ✅ 完整三智能体流程（worktree + 功能分支） |
| 单文件 bug 修复（含测试） | 🔧 开发 + 测试两步（CR 可选），当前工作区直接做 |
| 单行修复 / typo / 纯文档 | ⚡ 直接改，自测即可 |
| 紧急 hotfix | ⚡ 直接改 + 自测 + 提交，事后补 CR |

**判断标准**：改动是否触及启动链路（入口文件、调度器、配置加载、依赖清单）或多模块？是 → 完整流程。

## Git 工作区策略

完整流程在独立 worktree + 功能分支上进行：**阶段成果即时提交推送，合并主分支前用户人工把关**。

1. **建 worktree + 分支**（步骤 0 执行）：
   - 分支名清晰表达本次开发内容：`dev/<任务简述>`（如 `dev/user-auth`、`dev/fix-startup-crash`）；项目已有分支命名规范（`feature/` 等）则从其约定。
   - worktree 放仓库旁，目录名避免含 `/`：`git worktree add ../<repo名>-<任务简述> -b dev/<任务简述>`。
   - 若当前已在某个功能分支的 worktree 中，直接使用，不重复创建。
   - 建好后**先装依赖/构建**（`npm install`、`cargo fetch` 等）——worktree 不共享主工作区的 `node_modules`/`target`，不装依赖后续测试必挂。
2. **每阶段通过后**：主控者亲自核验该阶段成果（抽查重跑测试），然后 commit 并 `git push origin <分支>`；仓库无 remote 则跳过 push。commit/push 由主控者执行，智能体不做。commit 前用 `git status` 确认只暂存本次任务相关文件，排除无关 untracked 文件；message 写清阶段与内容，遵循项目规范。
3. **合并回主分支**（master/main）：**必须**等用户人工审核代码 + 线下验证通过、明确说"合并"后才执行（见步骤 5）。主控者绝不自动合并。
4. **简化流程**（两步/直接改）在当前工作区直接进行，不建 worktree；提交仍遵循"用户明确说'提交'才提交"。

---

## 步骤 0：准备（主控者执行）

1. 读取相关设计文档和现有代码，理解需求和既有模式。
2. 若需求不明确或有多种实现方式，用 AskUserQuestion 澄清后再开工。
3. 建立任务 todo list。
4. 探测项目技术栈（决定后续"启动安全检查"用什么命令，见末尾"技术栈命令速查"）。
5. 探测项目是否有自己的**代码评审准则文档**（常见位置：`docs/reviews/`、`.claude/rules/`、`AGENTS.md` 引用的评审规则）。找到则记下路径，供步骤 3 挂载给 CR 智能体——项目准则优先于本技能默认审查重点。
6. 按"Git 工作区策略"建 worktree + 功能分支，装好依赖，向用户报告分支名与 worktree 路径。

---

## 步骤 1：开发智能体

用 `Agent` 工具（subagent_type: `general-purpose`）启动，prompt **自包含**：

- **worktree 绝对路径**（智能体只在 worktree 内工作，不碰主工作区）
- 需求背景、要实现什么
- 关键技术事实（已验证的入口点、命名约定、配置位置等，避免智能体重复探索）
- 约束：
  - 遵循既有代码风格（注释语言、命名、错误处理范式）
  - 配置变更要所有相关文件**同步**（如 settings + config 同一字段名一致）
  - **测试先行（TDD 裁剪版）**：行为逻辑（新功能核心逻辑、bug 修复）必须先写测试、**先看到它失败**（Red），再写实现到刚好通过（Green）——先看到失败才证明测试真的在测新行为，杜绝镜像实现式空测。**bug 修复必须先写复现测试**。一次只写一个测试，只写让它通过的最少代码，不过度设计；**严禁删除/禁用/弱化断言来让测试变绿**（测试只能因需求变化而改）。配置、纯样式、文档、探索性代码不强制先行，但测试最终须补齐且验证真实行为
  - 测试覆盖核心路径（命中/未命中/异常/边界）
  - 自测全绿
  - **不提交、不 push**（提交由主控者在阶段核验后统一做）

**报告必须包含**（主控者按此模板验收，并原样转交下一棒）：

```
改动文件：新增 <...>；修改 <...>；删除 <...>
实现要点：<关键设计决策，≤5 条>
测试：位置 <...>；命令 <...>；结果 <X 通过 / Y 失败>
已知风险：<自认不稳的地方 / 未覆盖场景>
```

主控者核验 → commit + push → 交接给测试智能体。

---

## 步骤 2：测试智能体（开发完成且自测通过后启动）

用 `Agent` 工具启动，prompt **自包含**：

- **worktree 绝对路径** + 开发智能体的报告（按模板原样转交）
- 要求：
  1. 跑新功能测试
  2. **回归测试**：跑改动模块全量 + 相邻模块，确认没破坏既有功能
  3. **启动安全检查**（关键，避免服务挂）—— 按项目技术栈选命令（见末尾速查表），至少覆盖：
     - 语法/编译检查
     - import/依赖加载检查（新增符号能正确导入）
     - 配置加载检查（若触及配置）
     - 前端 build（若有前端改动）
  4. 自己读一遍实现，查明显 bug（拼写错、异常未隔离、参数未参数化等）
  5. 修**明显的**问题（import 错、SQL 错、签名不匹配、断言被弱化），修复最小化、外科手术式；**结构性问题（需改设计/接口/数据结构）不修**，报告主控者
  6. 预先存在/环境问题（缺可选依赖、需真实外部服务的 e2e）记录但不修
  7. 修复后**重跑**相关测试确认绿
- 约束：**不提交、不 push**
- **报告必须包含**：

```
新功能测试：<命令> → <结果>
回归：<范围> <命令> → <结果>
启动安全：<逐项命令> → <逐项结果>
修复清单：<修了什么、为什么>
未修清单：<问题> <原因>
结论：<是否全绿 + 启动安全>
```

主控者核验 → commit + push → 交接给 CR 智能体。

---

## 步骤 3：CodeReview 智能体（测试全绿且启动安全后启动）

**启动门禁**：主控者亲自核验测试报告，确认**全绿 + 启动安全**后才能启动 CR。测试未通过或结果存疑时不得启动，**绝不为了省时间让测试与 CR 并行**——CR 阶段可能触发修复回路改动代码，并行的测试结论会立刻失效，审查的 diff 也不是最终 diff。

用 `Agent` 工具启动，prompt **自包含**：

- **worktree 绝对路径** + 改动文件列表（含前两棒报告摘要）

**CR 是只读评审者：只报告问题，不修代码。** 修复统一由开发智能体执行，保证评审者独立于实现者。

- **审查重点（技术面，按严重度）**：
  1. 正确性 bug（P0/P1）：逻辑错误、SQL 错、属性/字段名错、签名不匹配
  2. 资源/安全：注入（字符串拼值）、连接泄漏、异常未处理致崩溃
  3. 并发/异步：阻塞调用混入异步路径、竞态、循环/资源误用
  4. 启动安全（P0）：import 是否破坏启动链路、循环依赖、懒加载是否正确
  5. 配置一致性：多处配置字段名/默认值是否一致
  6. 测试质量：是否真断言了正确行为，还是 mock 过度变成空测
- **评审纪律**：
  1. **证据链**：每条发现 = 代码位置 + 可发生的触发条件 + 影响 + 最小修正方向；明确区分**已证实缺陷 / 合理风险 / 个人偏好**，不把不可达的假设场景当缺陷
  2. **过度防御也是问题**：重复校验、静默兜底、任意阈值、为不可达场景增加的限制要指出
  3. **范围审查**：实现是否超出设计授权、是否夹带与任务无关的改动
  4. **按影响分级**：命名、格式、可选优化不作为阻断项；P2/nit 只记录
- 要求：
  1. `git diff` 看全部改动 + 读新文件全文，沿真实调用链核对
  2. 按严重度（P0 > P1 > P2 > nit）输出发现列表
  3. 严格但公平，不编造问题
- 若步骤 0 探测到项目评审准则文档：prompt 附上路径，要求 CR 以项目准则为准绳审查，与本技能默认审查重点冲突时以项目准则优先
- 约束：**只读，不修改任何文件、不提交、不 push**
- **报告必须包含**：

```
发现列表：<严重度> <file:line> <触发条件> <影响> <最小修正方向> <已证实缺陷/合理风险/个人偏好>（逐条）
结论：<是否可合并；若有 P0/P1 单列清单>
```

**P0/P1 修复回路**：主控者把 P0/P1 回炉开发智能体修复 + 定向自测 → 开发报告修复内容 → CR 复核受影响部分确认修复有效 → 主控者核验 → commit + push。P2/nit 记录在案，不阻断本次交付。

---

## 步骤 4：全部完成——终检与报告（主控者亲自做，不委托智能体）

三个智能体都通过后：

1. **编译/import 终检**（自己跑一遍，不盲信报告）：关键启动路径能编译/导入；前端 build（若有前端改动）
2. **全量测试兜底**：在 worktree 跑一次全量测试（覆盖修复回路的改动）
3. 确认所有改动已 commit 并 push 到功能分支
4. **向用户报告**：分支名、worktree 路径、commit 列表、三阶段结果摘要
5. **提醒用户**："请人工审核代码并线下验证；确认没问题后告诉我'合并'，我再合并回主分支。" —— 到此停下，不自动合并

---

## 步骤 5：合并回主分支（仅当用户明确确认后执行）

1. `git fetch origin`，确认主分支状态；若主分支有新提交，先按项目习惯 merge/rebase 功能分支并解决冲突
2. 有 PR 平台（GitHub/GitLab）：push 分支、建 PR，把链接交给用户
3. 否则：本地合并到主分支（建议 `--no-ff` 保留分支历史，或按项目习惯），push
4. 清理（默认**不**主动做，用户要求时才做）：`git worktree remove <路径>`、`git branch -d <分支>`

## 失败与升级路径

1. **修复边界**：测试智能体只修外科手术式问题（CR 不修代码，见步骤 3）。发现需要改设计/接口/数据结构才能解决的结构性问题 → 不修，报告主控者；主控者决定回炉开发智能体重做，或与用户确认方向。
2. **P0/P1 修复回路**：CR 只读报告，主控者回炉开发智能体修复并定向自测，CR 复核受影响部分，主控者在步骤 4 用全量测试兜底。修复若涉及多文件结构性改动 → 回到测试智能体做一轮独立回归。
3. **迭代上限**：完整流程（开发→测试→CR，含修复回路的往返）最多 **2 轮**。第 2 轮结束后仍有 P0/P1 问题未解决 → 停止流程，向用户报告现状与卡点，等用户决策，不自动重试。

---

## 关键原则

1. **串行不并行**：后一个智能体等前一个完成才启动；**测试全绿是启动 CR 的硬前置**，测试与 CR 绝不并行（理由见步骤 3 启动门禁）。
2. **独立判断**：每个智能体不复用前者的结论，自己验证。
3. **启动安全优先**：触及入口/调度器/配置/依赖清单的改动，提交前必须验证能启动。
4. **主控者兜底**：智能体报告后，主控者亲自核验测试数和编译/import，不能盲信。
5. **只在 worktree 内工作**：三个智能体都不碰主工作区。
6. **评审与实现分离**：CR 只读评审、不修代码，修复统一回炉开发智能体；测试智能体仅限修本阶段测出的明显小问题并重跑验证。
7. **提交分层把关**：功能分支上每阶段验证通过即 commit+push（成果即时固化、远程有备份）；**合并主分支必须用户人工审核 + 线下验证后明确确认**，绝不自动合并。

## 技术栈命令速查（启动安全检查用）

先探测项目根的清单文件确定技术栈，再选命令。多语言项目（如 Rust 后端 + 前端）需对每部分都跑。

| 技术栈 | 探测标志 | 编译/语法检查 | 测试 |
| --- | --- | --- | --- |
| **Rust** | `Cargo.toml` / `Cargo.lock` | `cargo build`（或 `cargo check` 更快） | `cargo test` |
| **Node/TS** | `package.json` / `tsconfig.json` | `npx tsc --noEmit`（TS）；`npm run build`（前端） | `npm test` / `npx vitest` / `npx jest` |
| **Python** | `pyproject.toml` / `requirements.txt` / `setup.py` | `python -c "import ast; ast.parse(open('<file>',encoding='utf-8').read())"` | `python -m pytest` |
| **Python import 检查** | — | `python -c "from <module> import <新符号>"` | — |
| **Go** | `go.mod` | `go build ./...`；`go vet ./...` | `go test ./...` |

> 涉及容器化部署的项目（如 `docker ps` 能看到运行中的开发容器），对应命令需加 `docker exec <容器名>` 前缀在容器内执行；优先使用项目自带脚本（如 `./scripts/dev_test.sh`），不要绕过。

## 输出

每步完成后向用户简要汇报：当前在哪一步、结果如何、下一步是什么。全部完成后给出完整总结（分支名、commit 列表、验证结果、等待合并确认）。
