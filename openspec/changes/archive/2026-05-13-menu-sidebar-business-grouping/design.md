## Context

`MenuSidebar.vue` 当前通过 `currentBusinessPages` computed 属性决定展示哪些业务菜单。该属性依赖 `props.currentSubagentId` 或路由参数 `currentSubagent`——当两者均不存在时（如非对话页面），返回空数组，业务数据区域完全不渲染。

业务菜单数据来自 `filteredAvailableSubagents`，每个数字员工对象包含 `business_pages` 数组。当前仅展示匹配数字员工的菜单，其余隐藏。

## Goals / Non-Goals

**Goals:**
- 业务菜单始终可见，按数字员工分组展示
- 多数字员工场景下，当前会话关联的数字员工菜单自动展开，其余折叠
- 单数字员工场景下，仍以分组形式展示（保留上下文标识）
- 非会话页面所有分组默认折叠
- 路由变化时重置展开状态
- 数字员工名称优先使用 `display_name`

**Non-Goals:**
- 不修改业务菜单的数据结构（`BusinessPage` 接口不变）
- 不修改业务页面的路由定义
- 不引入新的 API 或后端变更
- 不持久化用户的展开/折叠状态到 localStorage
- 不改动菜单以外的区域（历史会话、知识库入口等）

## Decisions

**1. 分组渲染 vs 平铺渲染**
- **选择**：按数字员工分组渲染，每组可独立折叠
- **理由**：用户已能识别数字员工名称（对话界面有展示），分组结构清晰；平铺会导致菜单过长且失去归属关系

**2. 展开状态由路由驱动，不持久化**
- **选择**：展开状态由 `currentSubagent` 计算决定，路由变化时重置
- **理由**：实现简单，且"当前数字员工展开"是唯一有意义的默认状态；用户手动展开其他组只是临时浏览，刷新后重置为路由驱动状态符合预期

**3. 无业务菜单的数字员工隐藏**
- **选择**：`business_pages` 为空的数字员工不渲染分组
- **理由**：避免空分组浪费空间并造成困惑

**4. 单数字员工仍使用分组**
- **选择**：即便只有一个数字员工，也显示为可折叠分组
- **理由**：统一视觉结构，保留"这些菜单属于某数字员工"的上下文；与多数字员工场景代码路径一致

## Risks / Trade-offs

| 风险 | 缓解措施 |
|------|----------|
 多数字员工且每个都有较多菜单时，分组折叠后仍需逐个点开查找 | 该方案已优于"完全隐藏"；未来可考虑添加搜索或收藏功能 |
| 路由变化导致用户手动展开的分组被意外关闭 | 接受此行为——非持久化是设计决策，且路由变化通常意味着上下文切换 |
| `display_name` 字段在某些场景不存在 | 降级使用 `name`，已在模板中处理 |
