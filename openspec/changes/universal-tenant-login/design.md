## Context

当前系统支持两种模式：
1. **演示模式** (`DEMO_ENABLED=true`)：`/` 路由返回简单JSON，用户可通过任意手机号+888888登录
2. **SaaS模式** (`SAAS_ENABLED=true`)：租户通过 `/t/{tenant_id}` 访问，但租户ID为长格式（`tenant_{uuid4_hex[:12]}`），难以记忆

当演示模式关闭时，`/` 路由仅返回JSON，缺乏用户引导。租户用户需要知道完整的租户ID才能访问系统，这增加了使用门槛。

**发现的问题**：后端 `/` 路由实现存在 bug（Internal Server Error），修复成本较高。因此采用前端实现方案，绕过有问题的后端路由。

## Goals / Non-Goals

**Goals:**
1. 提供统一的租户入口门户，关闭演示模式后引导用户进入正确租户
2. 引入短租户代码（4-8位字母数字）替代长租户ID作为用户友好标识
3. 保持向后兼容，现有租户自动生成默认租户代码
4. 确保租户代码全局唯一，避免冲突（在应用层检查）
5. 提供简单的租户代码验证和重定向机制
6. **绕过后端 `/` 路由的 bug**，通过前端实现租户入口功能

**Non-Goals:**
1. 不改变现有租户认证流程（仍使用手机号+验证码）
2. 不修改租户内部权限系统
3. 不提供租户代码自助注册（仍由平台管理员创建）
4. 不实现租户子域名映射（如 `alibb.yourapp.com`）
5. **不修复后端 `/` 路由的 bug**（采用前端绕行方案）

## Decisions

### 1. 租户代码格式与存储
- **格式**：4-8位大写字母数字组合（`[A-Z0-9]{4,8}`）
- **存储**：在 `tenants` 表新增 `tenant_code` 字段，无数据库唯一约束
- **唯一性**：在Python应用层检查唯一性，提供更好的错误提示和并发控制
- **大小写**：数据库中存储为大写字母，用户输入时支持大小写混合，系统自动转换为大写进行验证
- **默认值**：现有租户生成 `t` + `tenant_id` 后5位（如 `tenant_a1b2c3d4e5f6` → `TD4E5F`）
- **保留代码**：避免使用 `ADMIN`、`DEMO`、`TEST` 等保留词

**Rationale**：4-8位提供更多灵活性，允许使用更长但更有意义的代码（如公司全称缩写）。应用层唯一性检查提供更好的用户体验和错误处理。存储为大写但支持大小写不敏感验证，提升用户体验，避免因大小写输入错误导致的登录失败。

### 2. 入口页面实现方案（关键变更）
- **触发条件**：前端通过 `VITE_DEMO_ENABLED` 环境变量控制，当 `false` 时显示租户入口页面
- **实现位置**：前端 Vue 应用实现 `TenantEntry.vue` 组件，而非后端返回 HTML
- **验证方式**：前端基础格式验证 + 后端 `/api/tenant/enter` API 存在性验证
- **重定向**：验证成功后前端跳转到 `/t/{tenant_id}`
- **后端依赖**：仅依赖 `/api/tenant/enter` API，不依赖后端 `/` 路由

**Rationale**：后端 `/` 路由存在 bug（Internal Server Error），修复成本高且风险大。前端实现方案：
1. 完全绕过后端 bug
2. 依赖关系清晰（仅 `/api/tenant/enter` API）
3. 用户体验与原始设计完全一致
4. 易于切换（改环境变量即可切回演示模式）

### 3. 前端路由结构
```
GET  /                    → 根据 VITE_DEMO_ENABLED 选择组件
                             true: ChatContainer.vue (演示模式)
                             false: TenantEntry.vue (租户入口)
POST /api/tenant/enter    → 租户代码验证和重定向URL返回（后端不变）
```

**Rationale**：保持后端 API 不变，仅调整前端路由逻辑。演示模式开关从前端环境变量控制，与后端配置解耦。

### 4. 数据库迁移策略
- **新增字段**：`ALTER TABLE tenants ADD COLUMN tenant_code TEXT`
- **索引**：`CREATE INDEX idx_tenants_tenant_code ON tenants(tenant_code)`（非唯一索引，仅提升查询性能）
- **唯一性检查**：在Python应用层实现，提供更好的错误处理和并发控制
- **默认值生成**：单次UPDATE语句为所有现有租户生成唯一代码
- **回滚方案**：可删除字段，不影响核心功能

**Rationale**：最小化数据库约束，将业务逻辑放在应用层，提供更好的用户体验。

### 5. 管理界面集成
- **租户创建表单**：添加必填的 `tenant_code` 字段，实时验证唯一性
- **界面提示**：表单显示提示"4-6位字母数字组合"，实际支持4-8位以提供灵活性
- **租户编辑页面**：支持修改租户代码（需重新验证唯一性）
- **租户列表**：显示租户代码列

**Rationale**：管理员需要管理租户代码，提供完整CRUD支持。界面提示保持简洁（4-6位），实际支持更宽范围（4-8位）以适应不同需求。

## Risks / Trade-offs

### 风险与缓解措施
1. **租户代码冲突** → 创建时实时验证唯一性，提供冲突提示
2. **现有租户迁移失败** → 提供手动修复脚本，支持批量更新
3. **租户代码泄露导致未授权访问** → 租户代码仅作为入口标识，仍需租户内认证
4. **性能影响** → 为 `tenant_code` 字段添加索引，确保查询效率
5. **后端 `/api/tenant/enter` API 不可用** → 测试该API确保可用，这是前端方案的唯一依赖

### 权衡
- **简单性 vs 功能性**：选择简单表单而非完整登录页面，聚焦核心需求
- **灵活性 vs 一致性**：固定4-6位格式而非可变长度，简化验证逻辑
- **用户体验 vs 安全性**：租户代码公开可见，但结合租户内认证保证安全
- **前端实现 vs 后端修复**：选择前端绕行方案，避免修复复杂的后端 bug，但增加前端复杂度
