## ❌ 卡住的硬阻塞：会话列表视觉定位不可靠

### 现象

按用户指定的方案 B（搜索框 → 输入"文件传输助手" → 截图 → 视觉定位搜索结果 → 点击进入会话），链路在最后一步"定位搜索结果中第一项"上彻底失败：

| 模型 | 用户实测反馈 |
|------|-------------|
| qwen3-vl-plus | 点击落在了「行政合同归档 智能体 沟通」会话上，且把会话里的一张图片放大了 |
| qwen-vl-max | 点击落在了「企业微信团队」的 5.0.9 版本新功能介绍上 |

两次都是「进入了错误的会话」。

### 根因分析

用 4-5vl 外部模型分析真实搜索结果列表，实际顺序是：

| 位置 | 名称 | Y 坐标 |
|------|------|--------|
| 1 | 白月何曾照…加满 | ~94 |
| 2 | 白月何曾照… | ~167 |
| 3 | 新朋友 | ~247 |
| **4** | **文件传输助手（目标）** | **~414** |
| 5 | 微信 | ~493 |
| 6 | 测试 | — |

而 Qwen VL 返回的 `conversation_item` 元素中：
- 要么 `conversation_name` 字段把别人标成了「文件传输助手」
- 要么 bbox 的 Y 坐标整体偏移到了别人那一行

`QwenVisionLocator.MatchElement` 的 Pass 1 是「role 严格匹配 + conversation_name 包含关键字」——模型自报家门叫"文件传输助手"，我们就信了，但模型报错了。

### 结论

**Qwen VL（plus 和 max 都）在企微会话列表上不可靠**。这不是 prompt 工程或缓存策略能解决的问题，是模型能力上限。

## 🎯 明天的下一步选择

| 方案 | 思路 | 成本 |
|------|------|------|
| **A. OCR + 文字定位** | 用 PaddleOCR / Tesseract 截图识别"文件传输助手"四个字，直接拿文字 bbox 的中心点点击。比 Qwen VL 在密集中文列表上稳得多。 | 中（需引 OCR 引擎） |
| **B. UIAutomation API** | 企微是 Electron，但 WeWorkWindow 类下面有部分 UI Automation peer。用 `System.Windows.Automation.TreeWalker` 找名为"文件传输助手"的 ListItem。 | 高（很多 Electron 控件不暴露 AutomationPeer） |
| **C. 改 prompt 让模型只返回 bbox + 文字 OCR** | 让 Qwen VL 只做 detection（bbox + OCR text），把"哪个是文件传输助手"交给代码用 OCR 文字精确匹配。 | 低 |
| **D. 几何定位** | 搜索结果列表项行高固定（约 60-70px），第一项顶部 Y 已知。算式：`firstItemY = searchBoxBottom + margin`，然后 `targetY = firstItemY + rowIndex * rowHeight`。 | 极低，但脆弱（依赖企微版本） |

**推荐 A 或 D**：
- A 最稳，OCR 是中文场景的成熟技术
- D 是 fallback，跟视觉定位并行——视觉命中就走视觉，视觉失败走几何
