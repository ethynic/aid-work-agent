## 1. 运行环境前提

| 项 | 要求 | 检查方式 |
|----|------|---------|
| 操作系统 | Windows 10/11（推荐 Windows Server 2019+ 或 Win11 物理机/云桌面） | `winver` |
| .NET SDK | .NET 8 SDK，含「Windows 桌面」工作负载（net8.0-windows） | `dotnet --version` 显示 8.0+ |
| 屏幕分辨率 | 固定 **1920×1080**（设计 §6.1 强制） | 设置 → 显示 |
| DPI 缩放 | **100%**（设计 §6.1 强制） | 设置 → 显示 → 缩放 |
| 企业微信 | PC 客户端，先验证再升级（设计 §6.1） | 企微「关于」查版本号 |
| 远控方式 | RDP / 向日葵 / VNC 之一，需支持「断开后会话不注销」（见 §7） | 远控软件设置 |
| 桌面会话 | 保持可见桌面，禁止锁屏后继续自动化（设计 §6.1） | 见 §7、§8 |

**首次准备**：

1. 安装 .NET 8 SDK。
2. 把企微 PC 客户端装到固定路径，登录一次确认能用。
3. 关闭所有会抢占焦点的工具（输入法弹窗、自动更新、杀软全屏扫描）。
4. 企微设置里关闭「关闭窗口时退出」「自动锁屏」「消息弹窗抢焦点」等。

## 2. 探测工具用法

### 2.1 一句话

```powershell
# 在 clients/wecom-personal-rpa/ 目录下
powershell -File scripts/run-probe.ps1
```

脚本会自动 `dotnet run --project src/Client.Probe -c Debug`，把探测结果写到：

- `clients/wecom-personal-rpa/probe-report.yaml`（结构化报告）
- `clients/wecom-personal-rpa/probe-screenshots/`（截图）

### 2.2 常用参数

| 参数 | 说明 |
|------|------|
| `--window-class <name>` | 企微主窗口类名候选（默认 `WeWorkWindow` / `WeComMainWnd` / `TXGuiFoundation`），可多次提供，最前者优先 |
| `--qr-region <x,y,w,h>` | 二维码区域，相对主窗口左上角；不提供则截整个主窗口供人工框选 |
| `--template <path>` | 发送按钮模板 PNG；准入阶段先从真实截图裁出来，再带这个参数重跑 |
| `--template-threshold <0..1>` | 模板匹配置信度阈值，默认 0.85 |
| `--out <path>` | 报告输出路径 |
| `--screenshots-dir <dir>` | 截图输出目录 |
| `-h` / `--help` | 显示帮助 |

### 2.3 典型流程

```powershell
# 第一次：默认参数，拿环境基线 + 主窗口 + UIA 控件树
powershell -File scripts/run-probe.ps1

# 看 probe-report.yaml：
#   - env.resolution / env.dpi_scale 是否 1920×1080 / 1.0
#   - main_window.class_name 是不是命中了（没命中看 main_window.top_window_candidates）
#   - uia_tree 里有没有 EditControl / ButtonControl 候选

# 第二次：带 --window-class（若默认没命中）
powershell -File scripts/run-probe.ps1 -ProbeArgs @("--window-class", "WeWorkWindow")

# 第三次：带 --qr-region（从第一次的二维码截图里量出来的相对坐标）
powershell -File scripts/run-probe.ps1 -ProbeArgs @("--qr-region", "520,240,200,200")

# 第四次：带 --template（先把发送按钮裁成 assets/templates/send_btn.png）
powershell -File scripts/run-probe.ps1 -ProbeArgs @("--template", "assets/templates/send_btn.png", "--qr-region", "520,240,200,200")
```

### 2.4 安全说明（重要）

探测工具**只读**：

- 只读环境指标、窗口句柄、UIA 控件树；
- 只用 `CopyFromScreen` 截屏存 PNG；
- 只调 `OpenCvSharp.MatchTemplate` 算置信度；
- 只验证 `SetForegroundWindow` → `GetForegroundWindow` 是否一致（焦点夺取）。

**绝不**调用 `SendInput` / `keybd_event` / 剪贴板写入，不会向企微发送任何字符或粘贴，不会触发误发（设计 §10.3：误发 0 容忍）。第 3 项「Win32 SendInput 验证」中的真实粘贴、点击发送动作，留到正式开发阶段在受控环境里做（见 §4）。

## 3. 验证项 2：UIA 可见性

### 3.1 目的

确认 FlaUI/UIA3 能稳定识别企微主窗口、输入框、会话标题、消息区元素。这是三层自动化策略的第一层（最稳）。

### 3.2 成功标准（计划 §0 / 设计 §10.1）

> FlaUI 能稳定识别主窗口、输入框、部分会话元素。

### 3.3 失败处理

> 坐标 + OpenCV 前置为主策略（即放弃 UIA，退化到 Win32 坐标 + 模板匹配）。

### 3.4 探测

```powershell
powershell -File scripts/run-probe.ps1
```

看 `probe-report.yaml`：

| 字段 | 判定 |
|------|------|
| `main_window.found = true` | 主窗口定位 OK |
| `main_window.class_name` | 实测类名（回填 `main_window.class_name`，见 §9） |
| `main_window.visible = true` 且 `is_foreground = true` | 窗口可见且可置顶 |
| `uia_tree` 数组非空 | UIA 能枚举控件 |
| `uia_tree[*]` 里能找到 `type=EditControl` 且 `automation_id` 非空 | 输入框 / 搜索框可用 UIA 定位 |
| `uia_tree[*]` 里能找到 `type=ButtonControl` 且 `name` 非空 | 发送按钮可用 UIA 定位 |

### 3.5 人工确认（探测工具 dump 到 80 个控件，需人工挑）

1. 打开 `probe-report.yaml`，找 `uia_tree` 区块。
2. 找「编辑」控件（`type` 含 `Edit`）：
   - 位于主窗口**左上角搜索区**（`rect` 接近窗口顶部的 Edit）→ 这是搜索框，记下 `automation_id`。
   - 位于主窗口**底部输入区**（`rect` 接近窗口底部的 Edit）→ 这是消息输入框，记下 `automation_id`。
3. 找「按钮」控件（`type` 含 `Button`）：
   - `name` 含「发送」的 → 记下 `name`（回填 `controls.send_button.name`）。

> 控件树 dump 截断到 80 个（防止企微主窗口上千控件拖死）。如果挑不出来，手动用 [Accessibility Insights for Windows](https://accessibilityinsights.io/) 或 FlaUI inspect 工具看完整树。

## 4. 验证项 3：Win32 SendInput

### 4.1 目的

确认窗口置顶、粘贴文本、点击发送这条链路在固定环境下可稳定执行。

### 4.2 成功标准（计划 §0 / 设计 §10.1）

> SendInput 在固定窗口下能稳定发送文本。

### 4.3 失败处理

> SendInput + OpenCV 在固定环境下仍无法稳定执行文本发送，则**暂停 PC RPA 开发**（计划 §0 准入失败规则）。

### 4.4 探测（仅焦点，不发输入）

```powershell
powershell -File scripts/run-probe.ps1
```

看 `probe-report.yaml` 的 `sendinput` 区块：

| 字段 | 判定 |
|------|------|
| `sendinput.brought_to_foreground = true` | `SetForegroundWindow` 返回成功 |
| `sendinput.foreground_handle == sendinput.expected_handle` | 焦点夺取一致 |
| `sendinput.can_focus = true` | **焦点夺取达标**，SendInput 前置条件成立 |

### 4.5 真实粘贴 / 点击发送（受控人工验证，探测工具不做）

> 这一步**故意**不放进探测工具——它要向企微真实发送字符，有误发风险，必须在受控环境、由运维手动确认目标和时机。

受控验证清单（在运维准备好后单独做）：

1. 企微登录自己的测试账号，建一个**只有自己的「文件传输助手」会话**（不会打扰任何真人）。
2. 用 Client.Automation 的 `WeComAutomation.SendText`（已实现，编译通过）对一个写死的文本做粘贴 + Enter。
3. 人工确认：消息出现在文件传输助手、内容正确、无重复。
4. 重复 10 次，全部成功 → SendInput 链路达标。
5. 任一失败 → 检查：远控是否断开 / 前台锁进程 / 输入法抢焦点 / 剪贴板被其它程序占用。

> 受控验证的代码骨架在 `src/Client.Automation/WeCom/SendMessageService.cs`，但当前依赖占位节点常量；必须先把 §3、§5、§6 的回填做完，再跑这一步。

## 5. 验证项 4：模板匹配

### 5.1 目的

确认 OpenCvSharp 能在固定窗口 region 稳定识别发送按钮、搜索框、二维码区域。

### 5.2 成功标准（计划 §0 / 设计 §10.1）

> OpenCvSharp 可在固定窗口 region 稳定识别发送、搜索、二维码区域。

### 5.3 失败处理

> 调整窗口基线或放弃 PC RPA（计划 §0 准入失败规则）。

### 5.4 探测

#### 5.4.1 先裁模板

1. 运行一次 `run-probe.ps1`，拿到 `probe-screenshots/wecom_full_*.png`（主窗口全屏截图）。
2. 用画图 / Snipping Tool 裁出：
   - 发送按钮（右下角输入区附近）→ 存为 `assets/templates/send_btn.png`
   - 搜索框图标（如果有显式图标）→ 存为 `assets/templates/search_box.png`
3. 模板尺寸要**严格小于**主窗口截图，否则 `MatchTemplate` 直接返回未命中。

#### 5.4.2 带模板重跑

```powershell
powershell -File scripts/run-probe.ps1 -ProbeArgs @("--template", "assets/templates/send_btn.png")
```

看 `probe-report.yaml` 的 `template_match` 区块：

| 字段 | 判定 |
|------|------|
| `template_match.score` | 实测置信度（0..1） |
| `template_match.threshold` | 阈值（默认 0.85） |
| `template_match.hit = true` | **达标**：发送按钮可被模板匹配稳定定位 |
| `template_match.point` | 命中坐标（模板左上角在源图中的位置） |

#### 5.4.3 二维码区域

```powershell
powershell -File scripts/run-probe.ps1 -ProbeArgs @("--qr-region", "520,240,200,200")
```

- 第一次不提供 `--qr-region`，脚本会截整个主窗口。
- 从截图里量出二维码区域的相对主窗口左上角的 `x,y,w,h`，再带参数重跑。
- 看 `probe-report.yaml` 的 `qr.screenshot_path` 和 `qr.region`，确认截图里能看到完整二维码。

### 5.5 多企微版本注意

企微不同版本的按钮图标 / 颜色 / 位置可能变化。模板匹配要做到「稳定」，至少要在 2 个企微版本上验证 `score >= 0.85`。做不到 → 不要纯靠模板，必须叠 Win32 坐标降级（见 `wecom_nodes.yaml` 的 `fallback` 链）。

## 6. 验证项 5：登录态检测

### 6.1 目的

区分 4 种登录态：已登录 / 未登录（待扫码） / 二维码过期 / 账号异常。

### 6.2 成功标准（计划 §0 / 设计 §10.1）

> 已登录、未登录、二维码过期、账号异常可区分。

### 6.3 失败处理

> 不进入开发（计划 §0 准入失败规则）。

### 6.4 探测

探测工具第 4 步用启发式（搜索框存在 → Online；二维码/登录关键词存在 → NeedLogin；其它 → Unknown）给出**初步**判断，看 `probe-report.yaml` 的 `login_state` 字段。

4 种状态的完整验证需要**人工制造场景**：

| 状态 | 怎么制造 | 预期 `login_state` |
|------|---------|-------------------|
| 已登录 | 企微正常登录，显示主窗口 | `Online` |
| 未登录（待扫码） | 企微退出登录，停在扫码页 | `NeedLogin` |
| 二维码过期 | 扫码页停留超过二维码有效期（一般几十秒到几分钟） | `NeedLogin`（保守，需人工确认二维码失效提示文本） |
| 账号异常 | 企微被风控 / 密码改了 / 多端登录被踢 | `NeedLogin` 或弹错误框（需人工观察） |

> 探测工具目前**不能**自动区分「二维码过期」和「待扫码」——企微的失效提示文本随版本变化，需运维在 §3 的 UIA 控件树里找到失效提示文本，回填后才能区分。这是已知保守点，不影响准入 Go/No-Go（只要能区分 Online vs NeedLogin 即可进入开发，二维码过期在正式版由 MessageWatcher 轮询补充判断）。

## 7. 验证项 1 + 6：标准环境与桌面保活

### 7.1 标准环境固定

| 项 | 要求 | 探测确认 |
|----|------|---------|
| 分辨率 | 1920×1080 | `probe-report.yaml` → `env.resolution = [1920, 1080]` |
| DPI | 100% | `env.dpi_scale = 1.0` |
| 锁屏 | 否 | `env.locked = false` |
| 企微进程 | 在跑 | `env.wecom_processes` 非空 |
| 磁盘 | > 5GB | `env.disk_free_gb` |

> 任一项不达标，先改环境（设置 → 显示改分辨率 / DPI），再重跑探测。**禁止**用代码「适配」非标准环境——企微窗口在不同分辨率/DPI下坐标全漂，模板也跟着错位，会直接误发。

### 7.2 桌面会话保活（核心难点）

RPA 依赖**可见的交互式桌面会话**。锁屏、远控断开、用户注销都会让 SendInput 失效。这一项**不依赖探测工具**，用下面的人工检查清单。

## 8. 桌面保活验证清单（人工，不依赖探测工具）

> 这一节对应计划 §0 第 6 项「验证交互式会话保活：远控断开、重启、锁屏检测」。

### 8.1 远控方式选型

| 方式 | 会话保活 | 推荐度 |
|------|---------|--------|
| 物理机 + 显示器常亮 | 永久保活 | 最稳（首选生产环境） |
| 云桌面（阿里云/腾讯云 Windows） | 断开客户端后会话保留 | 推荐 |
| RDP（远程桌面） | 默认断开→会话保留；但锁屏会让 SendInput 失效 | 可用，需配「不锁屏」 |
| 向日葵 / TeamViewer | 镜像当前会话，断开后会话保留（取决于被控端是否锁屏） | 可用 |
| VNC | 取决于实现，部分 VNC 断开后 Session 0 无 GUI | 慎用 |

### 8.2 检查清单（每项都要在目标机器实测一次）

- [ ] **远控连接建立后**，企微主窗口可见、能用鼠标点。
- [ ] **远控客户端关闭**（不是注销，只是关掉客户端窗口），等 5 分钟后重连：
  - [ ] Windows 没注销（任务栏还在、企微还在托盘）。
  - [ ] 企微主窗口仍可见（可能需要点托盘图标恢复）。
  - [ ] 运行 `run-probe.ps1`，`env.locked = false`、`main_window.found = true`、`sendinput.can_focus = true`。
- [ ] **Windows 重启**（`shutdown /r`），开机自启后：
  - [ ] 企微自动启动并显示主窗口（或停留在扫码页）。
  - [ ] 交互式会话恢复（不是 Session 0 服务态）。
  - [ ] 运行 `run-probe.ps1`，全部步骤通过。
- [ ] **锁屏测试**（手动按 Win+L）：
  - [ ] 运行 `run-probe.ps1`，`env.locked = true`。
  - [ ] 解锁后重跑，`env.locked = false`，全部步骤恢复通过。
  - [ ] **结论**：锁屏期间禁止发送任何 action（客户端必须自动暂停）。

### 8.3 不达标怎么办

- 远控断开后会话注销 → 换云桌面 / 物理机方案（设计 §6.1、计划 §0 失败规则）。
- 锁屏频繁 → 配置电源管理「从不睡眠」「从不关闭屏幕」+ 组策略「禁止锁屏」。
- 重启后企微不自启 → 配开机自启（计划 §5 第 44 项）。

## 9. 翻译字段回填：probe-report.yaml → wecom_nodes.yaml

探测通过后，把 `probe-report.yaml` 的实测值翻译到节点配置。**注意**：项目里有两份 `wecom_nodes.yaml`，结构不同——

| 文件 | 结构 | 谁加载 |

### 9.2 坐标换算示例

假设 `probe-report.yaml`：

```yaml
main_window:
  window_rect: [100, 80, 1200, 800]   # x, y, w, h
uia_tree:
  - type: EditControl
    automation_id: "msg_input"
    rect: [500, 760, 600, 40]          # 屏幕绝对 x, y, w, h
```

则消息输入框相对主窗口左上角的点击偏移：

```
click_offset.x = (rect.x + rect.w / 2) - window_rect.x = (500 + 300) - 100 = 700
click_offset.y = (rect.y + rect.h / 2) - window_rect.y = (760 + 20) - 80 = 700
```

回填到 `src/Client.Automation/assets/wecom_nodes.yaml`：

```yaml
controls:
  message_input:
    automation_id: "msg_input"
    click_offset:
      x: 700
      y: 700
```

## 10. 准入 Go/No-Go 决策

> 复述计划 §0 准入失败规则。任何一条触发 → 不进入正式开发。

### 10.1 Go（可进入正式开发）

全部满足：

- §3 UIA 至少能识别主窗口（若控件不可识别，已确认坐标 + OpenCV 能前置为主策略）。
- §4 SendInput 焦点夺取达标（`sendinput.can_focus = true`），且人工受控粘贴 / 发送 10 次全部成功。
- §5 模板匹配置信度 ≥ 0.85（至少 2 个企微版本）。
- §6 登录态至少能区分 Online vs NeedLogin。
- §7 环境基线全达标（1920×1080 / DPI 100% / 不锁屏 / 企微在跑）。
- §8 桌面保活清单全过（远控断开 / 重启 / 锁屏后交互式会话可恢复）。
- 节点常量已按 §9 回填到 `src/Client.Automation/assets/wecom_nodes.yaml`。

### 10.2 No-Go（暂停 / 换方案）

| 触发条件 | 处理 |
|---------|------|
| SendInput + OpenCV 在固定环境下仍不稳定执行文本发送 | **暂停 PC RPA 开发**，重新评估运行环境和自动化可行性 |
| 桌面会话无法稳定保活（远控断开 / 锁屏 / 重启后会话丢失） | **先解决运行环境**（换云桌面 / VNC / 物理机），不写业务代码 |
| 出现无法可靠检测的误发风险（焦点夺取失败、目标会话歧义无法消除） | **不进入正式开发**（误发 0 容忍，设计 §10.3） |

### 10.3 准入失败后的回退

参见 [plans/plan-wecom-personal-rpa.md](../../../plans/plan-wecom-personal-rpa.md) 「风险与回退」表：

- PC 自动化不稳定 → 暂停开发，重新评估运行环境和自动化可行性。
- 误发 → 停止上线，强化绑定和发送前确认。
- 桌面不稳定 → 更换云桌面 / VNC / 物理机方案。
- 账号异常 → 停止该账号托管，复盘频率和环境。
