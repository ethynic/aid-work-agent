# 企微客服 20 用户并发演示 sync_msg 限频（45009）事故复盘

> 2026-10-12 排查定案。现象：2026-10-11 10:00-10:10，租户 `tenant_af2eefa4594d` 组织内部演示，约 20 个用户同时通过企微客服（wecom_kf）使用智能体，反馈"比平时慢很多"。

## 1. 结论速览

| 项 | 结论 |
|----|------|
| 用户感知 | 演示开始阶段首批消息端到端等待 **1-3 分钟**（正常约 10-15s），积压排空后（~10:04-10:05）恢复正常 |
| 根因 | **微信官方 `sync_msg` 接口限频 errcode=45009**，叠加代码两处缺陷：并发拉取无去重、失败后无重试 |
| DeepSeek API | 排除。高峰 LLM span p50=2.3s vs 平时 1.4s（轻微升高），无 429/超时 |
| 服务器性能/带宽 | 排除。处理耗时 p50=5s 无劣化，错误日志仅 45009，纯文本消息无带宽压力 |

## 2. 量化对比（消息处理开始 -> 回复发出）

| 时段 | n | avg | p50 | p90 | max |
|------|---|-----|-----|-----|-----|
| 10-11 10:00-10:10 演示 | 41 | 6.2s | **5s** | 10s | 22s |
| 10-10 16-21 点（平时） | 23 | 7.1s | 5s | 10s | 36s |
| 10-09 10-13 点（平时） | 66 | 15.4s | 8s | 29s | 128s |

处理本身不慢；慢在"用户发出 -> 开始处理"的拉取排队段。数据来源：`log/temp/微信客服回调.log` + 主日志（`消息处理开始` / `回复发送成功` 配对）。

## 3. 时间线还原

```
10:01:12  约 20 个用户同时扫码进入，1 秒内 21 个 enter_session 事件回调
          每个回调 -> 新建独立后台任务 -> 立即调 sync_msg（同一秒多任务并发、无去重）
10:01:22  触发微信限频 errcode=45009 "Too many requests"
10:01:22 ~ 10:02:09  约 47 秒内 30 次拉取全部失败（每次回调新任务又立即撞限频）
10:02:30  一次成功拉取返回积压 31 条
10:02:32 ~ 10:04+  串行处理 ~4-5s/条排空积压
10:04 后  延迟恢复正常
```

## 4. 根因链条

1. **触发条件**：20 用户同时进入是压测级场景，日常 1-3 人不会触发；演示/营销活动必然复现
2. **放大点 1（并发无去重）**：`_process_tenant_wecom_kf_messages` 由每个回调各起一个 `asyncio.create_task`，同一 `open_kfid` 无锁/合并，并发 `sync_msg` 直接耗尽微信限频配额
3. **放大点 2（失败即放弃）**：`channel_routes.py` 收到 45009 后直接 `return`，无指数退避重试，只能等下一个回调再拉——而下一个回调又立刻撞限频，形成持续失败
4. **雪崩效应**：积压 31 条串行排空（每条含 LLM 往返），首位用户等待 = 限频窗口 + 排队位置 x 单条耗时

## 5. 修复方案（2026-10-12）

| 项 | 内容 |
|----|------|
| 限频重试 | 45009（及可重试的微信错误码）任务内指数退避重试（2s/4s/8s，上限若干次），不再依赖下一个回调 |
| 拉取去重 | 同一 `open_kfid` 已有拉取任务在跑时，新回调不再起新任务（Redis 锁 + 完成后标记，防止丢消息）；进行中的任务重入拉取循环兜底新消息 |
| 效果预期 | 并发进入时只保留一个拉取循环，QPS 钳制在限频阈值内；偶发 45009 自动重试恢复，消息延迟从分钟级回到秒级 |

## 6. 排查方法备忘

- 计费/审计表 `chat_records`（wecom_kf source）只有单条处理耗时（duration_ms），**不含拉取排队延迟**，不能用它回答"用户感知慢多少"
- 端到端感知 = `log/temp/微信客服回调.log` 的 `消息处理开始` 与主日志 `回复发送成功: reply_to={external_userid}` 按用户配对计算
- 微信 45009 详情可凭日志中 hint 串到 `open.work.weixin.qq.com/devtool/query` 查询
