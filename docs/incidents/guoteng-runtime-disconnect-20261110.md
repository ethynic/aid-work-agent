# 国腾 Runtime 断联与重复配对调查

2026-11-10，时间均为北京时间。客户机补采显示，11 月 5 日 16:19 的最后一段正常通信紧邻 Windows 进入睡眠，同日 16:52 从低功耗恢复后，16:54 已出现自动启动失败。11 月 9 日 14:20 再次从低功耗恢复，14:24 又自动启动失败。当天 16:33 客户手动尝试重新配对，随后活动 HTTP `requested` 被后台续接。恢复原 HTTPS 身份后，Windows 启动项标识误用仍阻断执行。现场已恢复原设备，17:15 生产验证连续心跳。首次恢复失败的内部阶段和首笔 HTTP 记录的输入来源仍缺日志。

## 复盘结论

这次连续出现两个可独立阻断恢复的客户端缺陷。**反复请求配对由残留事务引起；恢复原身份后仍不能启动由旧执行停稳核验引起。** 后者是现场最后一道阻断，也可能与 11 月 9 日较早的启动失败有关；首份诊断只记录通用事件，无法把那次失败归因于同一个分支。

**为什么会重发配对。** Main 启动、检查连接或定时器读到活动名 `clean-registration.bin`，发现阶段是 `requested`，就按协议 3 用同一注册请求身份发 `POST /pair`，自动续接不带新配对码。保存的 HTTP 地址打到生产 TCP 80，Nginx 在应用之前返回 301。客户端拒绝跳转，并把这种明确重定向归入普通网络故障，每 10 秒用相同地址再试。它还在服务端尚未确认替换前切换到空目录、阻断原设备启动。覆盖安装和 `/Clean` 会保留这份跨版本记录。文件时间记录了本轮 16:33 切换目录及重写的时间，无法确定最初写入时间。

16:33 的人工操作、首条 301 和本地文件时间吻合。最符合证据的解释是该次手动尝试在本机留下了仍处于活动位置的 `requested`，后续由 Runtime 自动重发；目前无法区分该次创建新事务还是在同一目标上接续一个更早的请求。0.0.37 的实际顺序是退出 Main 管理的旧 Host、分配空目录、保存 `requested`、发配对请求；服务端成功响应后才安装新身份、尝试启动执行。现场已换目录且已发到网关，因此本轮失败落在 HTTP 301，未进入配对成功后的执行检查。原目录里的「待核对」是回到原身份后仍无法启动的另一个阻断。

**为什么恢复原身份后还不能执行。** 实际 Windows 启动时间晚于原执行标记，但 native `BootIdentifier` 对比相同，当前 Windows 会话和旧执行会话不同。0.0.37 将启动项 GUID 当作开机实例标识，因此错过跨启动恢复分支，同一启动项正常重启也可能持续待核对。要保留进程停稳和未知业务不重放的边界，同时用正确证据做判断。详见[启动结构原始分析](https://geoffchappell.com/studies/windows/km/ntoskrnl/inc/api/ntexapi/system_boot_environment_information.htm)及[Microsoft 启动项说明](https://learn.microsoft.com/en-us/windows-hardware/drivers/devtest/boot-options-identifiers)。

## HTTP 地址从哪里进入重试

| 0.0.37 入口 | 实际行为 |
| --- | --- |
| 新配对进入落盘分支 | 表单只去首尾空白，preload 和 Main 透传提交值。Core 接受 HTTP 和 HTTPS，只去尾部斜杠，保存 `input.server`。新提交 HTTPS 与已有 HTTP 地址比较不相等，会归档旧事务，用 HTTPS 创建新事务。 |
| 点击「重试连接」，或 Main 启动、定时恢复 | 连接诊断先调用 `resume()`，再验证活动设备身份。恢复读取已保存的 `r.server`，忽略配对表单当前内容。若事务还没有目录，先退出旧 Host、切换目录并重写同一事务，再发送请求。 |
| 旧事务正在恢复时提交新 HTTPS | 界面控制器可在忙时提前返回。若调用已到 Main，`reconfigure()` 也可在读取旧记录、比较地址之前返回「正在配置连接，请等待完成」，新地址不会替换旧记录。 |
| 提交与旧记录相同的地址 | Main 先无配对码续接旧请求。301 被折叠为网络错误，未命中可用新码替换的错误分支。旧请求仍活动，新码不会发出。 |

用实际交付 Main、Core、Windows DPAPI 和本地 HTTP/TLS 端点做并发回放。在 HTTP 请求返回 301 前保持 `diagnose()` 运行，此时提交 HTTPS，Main 返回忙，磁盘仍为原 HTTP 事务，端点只收到不带码的旧请求。结束诊断后再次提交相同 HTTPS，TLS 端点收到带新码的新请求，旧事务归档，活动记录清除。该验证直接调用交付 Main，界面忙态来自源码核对。

现场文件已确认保存了 HTTP。重定向发生在请求发出之后，也不会回写事务地址。此前的 TLS 中间层夹具始终保留 HTTPS，不能解释这份现场文件。**0.0.37 可以在客户拿到并复制 HTTPS 的同时继续使用旧 HTTP，但一笔已进入新建分支的 HTTPS 提交不会写成 HTTP。** 当前文件写入时间与首条 301 同秒，能对上目录分配后重写，也能对上新请求直接发出。现场缺少表单 IPC 的协议值、是否命中忙态或续接分支、首请求是否带码，尚无法在「当次已有 HTTP 记录并续接」和「当次新建 HTTP 记录」之间定案。11 月 9 日 14:24 的自动启动失败已越过活动事务门禁，也缺证据支持同一个可读的活动 HTTP 文件从 11 月 5 日一直存在。

## 待核对的触发、历史行为和影响

1. **运行标记何时留下。** Host 每次 start 在接纳执行前写 `host-running.json`，运行时保留，正常 stop 在确认资源退出后删除。现场标记写于 11 月 5 日 11:39:54，对应最近一次成功 start，此后生产同来源仍有领取和连续心跳。写入时间是启动记录，不能当作故障时间。正常清理未完成可留下该文件，例如进程被强制结束、突然断电或 stop 未证实停稳。16:33 的替换路径若仍有 Main 所管旧 Host，会走强制退出，可能保留标记；当时是否还有该进程未知，而且这次替换晚于 14:24 的首次自动启动失败。
2. **本次为何清不掉。** 客户重启后 Windows 启动时间晚于旧标记，受保护证明与原目录匹配，`rebootOnly=false`，但辅助器仍读出与标记相同的启动项 GUID，当前会话又不同。跨启动分支和同会话 Job 核验分支都未通过。现场连续五次 stop 的 `previous-execution-not-confirmed-stopped` 对应此分支；`code=0` 是管理回执格式，操作终态仍为 `reconciling`。真实交付 Host 用当前 native GUID、不同会话的受保护 v2 标记复现，登录自启拒绝，手动 start 和 stop 均为待核对，标记保留，本地端点收到零心跳、零领取。
3. **过去重启是否能清掉。** 10 月 9 日首版独立 Host（`f1087289`）已将残留标记视为待核对，且无执行所有权时 stop 直接拒绝。10 月 12 日（`ebd8120e`）加入 Windows Job 及开机证明，已使用同一 `BootIdentifier`。10 月 30 日（`63bce640`）才让无所有权的 stop 再尝试核验。正常退出能清标记，同会话下成功核验 Job 也能恢复；发现标记后的重启从来没有保证能清除。旧测试换的是模拟 GUID，未验证同一启动项的真实重启。
4. **不重启会挡什么。** 这次是整个 Host 的 `reconciling`。只要停稳证据仍不满足，0.0.37 没有自动到期放行，`start` 不会启动该设备的心跳和领取循环。后续分配给这台设备的 Runtime 任务都受影响，其他设备及纯云端任务不受此状态直接影响。如果只是单个任务结果未确认，仍需按任务身份保留结果与防重放证据，它与整个 Host 的启动门禁是两层状态。

整改边界纳入现有[连接与旧执行恢复设计](../system/runtime-plugin-host-architecture-design.md#16-连接与旧执行恢复整改2026-11-10)。配对 301 这类已知失败应结束自动续接、保留原身份，下次新注册由用户发起。请求已送出但结果未知时，才按同一事务有限核对，避免服务端已登记却再创建设备。Host 确认未进入执行且已清理的失败应正常结束；资源已停稳后可以恢复新执行，单个旧任务结果未知仍保留核对和防重复执行。全设备门禁只用于确实无法确认受管资源已停稳且新执行可能冲突的阶段。

以发行源码 `07e5d428` 做隔离回放。既有 HTTP 待续接事务遇到重定向异常时进入 CONNECTING，并阻止原执行启动。明确提交 HTTPS 会替换不同地址的旧待续接事务，没有把新输入降级成 HTTP。另模拟自动启动操作失败，原启动函数报错退出，没有再次发出 start。实现在正常配对开始时即退出旧 Host 并换目录，失败的新配对会阻止原执行自动恢复。自动启动失败日志只记录事件名，且由管理状态读取、启动失败等多个分支共用，无法用回放确定客户命中了哪一支。

### 事务来源与设备 ID 核对

`clean-registration.bin` 由 2026-10-14 提交 `7d12e94e` 引入，是桌面 Runtime 的协议 3 事务文件。更早的 CLI 和协议 2 UI 不写这个文件。它存于跨安装版本保留的 `installation-v2` 根目录，目的是在服务端已注册但客户端丢失响应时续接同一请求。缺口是 `requested` 无到期字段，恢复时没有先确认当前有效的原设备身份和待处理目标是否一致，导致旧事务可反复接管启动。

记录含创建时写入的 `request.runtime_version`，不含 EXE/UI 版本和业务创建时间。已扩展只读脚本，同时读取原文件和恢复脚本隔离的备份，输出 `writerRuntimeVersion` 和文件最后写入时间。用真实 DPAPI 隔离备份验证可读到 0.2.23；该 Core 至少由 0.0.34–0.0.37 共用，单靠它不能区分安装包。文件时间可能是分配连接目录后重写的时间。留存生产日志中，同来源在 10 月 30 日曾有 35 次配对 301，随后成功配对；11 月 5 日又成功注册并使用当前设备，同一配置根成功注册会归档此前事务。现有证据无法把这批旧流量和现场文件认定为同一事务。

0.0.37 正常成功流程是 `requested → paired → installed → completed-registration-*.bin`；新注册入口会先归档此前活动事务，并生成新的注册 ID。普通启动和重连读取已有事务，不能创建新的 `requested`。11 月 5 日是最后一次成功配对，11 月 9 日 16:33 的手动尝试没有成功。之前按「11 月 5 日之后没有新配对操作」推测是更早的残留，现由用户向客户复核的时间线替代。只读脚本追加 `matchesCompletedRegistration`，在本机比较活动或隔离文件与已完成回执的注册 ID，只输出匹配结果。DPAPI 夹具验证相同、不同及无法比较三种结果。

协议 3 注册 ID 为随机 UUID，事务内容不含时间戳。首次创建记录与首次分配连接目录分别落盘；后者会通过临时文件写入后替换原文件，因此当前文件创建时间不保证等于最早发起时间。当前 `homeAllocated=true` 且持续 HTTP 301，普通重试既不会再次分配目录，也不会更新该记录。只读脚本新增当前或隔离文件的创建、最后写入时间，已分配目录创建时间，以及按注册 ID 精确匹配的最早 `previous-registration` 归档最后写入时间。Windows DPAPI 夹具验证活动文件及隔离备份均可采集，时间更早但注册 ID 不同的归档被排除。此前客户输出未采集这些字段。现有生产同源最早配对 301 是 10 月 30 日 13:11:59，入口无法证明属于同一事务。

## 已确认的行为

- **运行中的重试有效。** `PollLoop` 用原服务地址和凭据分别重试心跳和任务领取，失败退避 1–30 秒，成功后重置。设备鉴权 401 才会走凭据失效并停止循环的分支。附件没有 401 或凭据撤销后停止循环的日志。网页离线按最后活跃时间计算，超过 30 秒无心跳即可显示离线。
- **11 月 2 日的 404 应先查请求经过的入口。** 正常 Runtime 鉴权找不到有效设备返回 401；心跳处理器在已鉴权但更新不到设备行时可以返回带“设备不存在”的 404，普通领取处理器没有对应的 404 分支。入口日志也记录了同期其他来源的 404。现有日志缺具体上游标识，无法归因于某次发版或某台上游。
- **截图状态指向配对恢复阶段。** 匹配截图文案的 UI 将“正在完成连接，请稍候”绑定到待处理连接诊断。另一行“企业服务暂时不可连接”对应 Main 的 `CONNECTING` 分类，来源为配对恢复过程中捕获的网络错误或 HTTP 5xx。详情的“暂不可读取”表示 UI 未取得活动 Runtime 目录的服务地址。正常运行中的心跳失败会显示离线。截图反映当时执行已停止，可能处在待完成注册并已切到新目录的阶段，无法确定它是第一次断联前的状态，还是已点击重新配对之后的状态。
- **设备撤销与配对码有效期。** 协议 3 在有旧设备凭据或指定替换关系时，注册新设备的同一事务会撤销旧设备。已配对设备鉴权按有效设备凭据和 `active` 状态核验，配对码有效期只约束注册。
