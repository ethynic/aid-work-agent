## 调查结论

这台电脑遇到了两个独立的阻断。**第一次离线发生在手动重新配对之前。** 11 月 5 日和 9 日均有低功耗恢复后自动启动失败的记录，最早失败的内部阶段因日志缺失无法还原。11 月 9 日客户看到离线后手动尝试了一次重新配对。此后 Runtime 持续使用一条保存了 HTTP 地址的未完成配对事务，导致原 HTTPS 设备目录被空目录抢占。服务端收到的持续配对流量来自 Runtime 自动续接。

恢复原设备目录后，仍然离线。**现场确认此时是 Host 的旧执行「待核对」阻断了启动。** 0.0.37 把同一 Windows 启动项可以复用的标识作为开机实例判断。现场已经重启，标识仍相同，当前会话又不同于旧执行会话，导致两条停稳核验分支均未通过。Host 因此没有启动心跳和任务领取循环。现场核验真实重启、旧会话无进程及受保护台账后，归档旧执行标记，原设备恢复在线。整个过程沿用既有凭据和配对身份。

## 问题一 · 失败配对抢占原连接并循环请求

0.0.37 的 Main 用 `clean-registration.bin` 保存活动配对事务。协议 3 允许用同一注册请求身份找回丢失的服务端回执。`requested` 表示当前没有可安装的成功回执。启动、点击「重试连接」及定时恢复都会先续接该事务。续接沿用文件里的服务地址和请求身份，无需新配对码。已有 `paired` 回执则进入本机安装和验证。正常成功配对会完成归档，归档文件不参与这一循环。覆盖安装及 `/Clean` 在交付版复现中都能保留活动文件。 [Main 恢复入口](../../clients/agent-desktop/electron/runtimeCleanConnection.ts#L60) · [事务记录](../../clients/agent-tool-runtime/src/cleanRegistration.ts#L63)

旧流程在服务端确认成功前就退出受管 Host、切换到空的连接目录。保存的 HTTP 地址到达生产 80 端口后，Nginx 在转给应用前返回 301。客户端拒绝跳转，把这个结果归类为网络异常，Main 随即再次使用原地址续接，约 10 秒一次。结果是旧 HTTPS 身份资料仍在上一目录，应用一直停留在「连接中／未配对／执行已停止」，正常执行循环没有启动。配对请求发生在 Main，运行中的心跳重试发生在 Host，两者是不同路径。 [目录切换](../../clients/agent-desktop/electron/runtimeCleanConnection.ts#L81) · [请求重定向策略](../../clients/shared/local-tool-host-core/src/legacy/apiClient.ts#L219) · [运行心跳](../../clients/shared/local-tool-host-core/src/legacy/pollLoop.ts#L143)

**HTTPS 与 HTTP 的证据边界。** 客户收到并复制的是 HTTPS 地址。交付包源码和真实 TLS 回放均显示，进入新建分支的 HTTPS 输入会原样保留协议。交付版也复现了另一条路径：旧 HTTP 事务恢复时提交新的 HTTPS，界面或 Main 会先返回忙，旧请求照常重发，新的地址未进入写入路径。现场文件的 HTTP 值已确认。首次表单实际进入 Main 的值、忙态分支及首笔请求是否带码缺少日志，因此尚无法判定当次手动操作新建了 HTTP 事务，还是触发了已有事务的续接。16:33 文件时间与首条 301 同秒，能确定它在该轮处于活动状态。该文件曾因分配目录重新写入，现有时间也不能证明最初创建时间。

**旧版本残留的范围。** 此文件是协议 3 的桌面 Runtime 事务记录。现场记录中的写入组件版本为 `0.2.23`，该 Core 被多版安装包共用，单靠此值无法定位 EXE 版本。11 月 5 日的 HTTPS 成功回执与 11 月 9 日活动事务的注册 ID 不同。11 月 9 日这轮失败与客户确认的手动尝试吻合，没有证据表明该活动事务从 11 月 5 日起就一直存在。

## 问题二 · 旧执行待核对阻断整台设备

Host 在开始执行时写 `host-running.json`，确认正常停止后清理。该文件在非正常退出或未能证明停止时会保留。0.0.37 的 v2 运行标记与本机 DPAPI 保护的进程台账绑定。Host 使用 native `BootIdentifier` 变化作为跨启动停稳依据。该值相同的时候，只有当前 Windows 会话与旧执行会话一致，且受管 Job 核验通过，才能走同会话恢复。现场标记绑定原目录且可读，`rebootOnly=false`、`bootMatchesMarker=true`、`sessionMatchesHost=false`，所以两条分支都走不通。五次 stop 的 `code=0` 只是管理回执格式，终态仍为 `reconciling`。 [停稳核验](../../clients/agent-tool-runtime/src/processSupervision.ts#L68) · [Host 启停](../../clients/shared/local-tool-host-core/src/management.ts#L409)

这个保护原意是避免旧插件进程仍在操作桌面时启动第二份执行。本次实现把无法核验旧执行与设备是否可通信绑在了一起，影响该设备全部后续插件任务。登录恢复读取 `reconciling` 后在发出 `start` 前退出，等待不会让标记自动过期。0.0.37 这条登录恢复失败后仅记录通用事件并显示窗口。只要 Host 本身仍在运行，普通网络异常会按原地址和凭据自动退避重连。连接诊断可以单独发一次心跳，生产偶尔看到 200 仍可能没有任务领取循环。 [登录恢复](../../clients/agent-desktop/electron/runtimeStartup.ts#L39) · [连接诊断](../../clients/agent-tool-runtime/src/connectionDiagnosis.ts#L41)

## 现场临时恢复

现场处置分两步，先恢复原配对，再核实旧执行已经停稳。写入操作使用与 Runtime 相同的 Windows 用户，实际恢复时通过托盘退出 Runtime。第一次脚本返回 `RUNTIME_STILL_RUNNING` 时在写入前中止，随后在进程退出后重新执行。

1. **只读检查。** 用 `check-runtime-pairing.ps1` 查看当前指针、活动配对事务、各目录身份、已完成回执、运行标记和管理操作状态。用 `collect-runtime-disconnect-timeline.ps1` 对照旧目录日志、Desktop 日志及 Windows 电源事件。实际定位到活动目录为空、上一目录有原设备 HTTPS 配置及有效的本机凭据，且生产原设备仍有效并被选定。
2. **隔离失败事务并恢复指针。** `restore-runtime-original-device.ps1` 仅在待处理事务指向当前空目录，且上一目录的设备编号、HTTPS 服务地址、受保护凭据和已完成回执一致时执行。它保留当前指针备份 `current.pre-recovery-*.json`，把 `clean-registration.bin` 移到 `quarantined-clean-registration-*.bin`，再切回上一目录。过程中没有联网配对或改写原凭据及业务数据。实际返回 `original-device-restored`，复查 `pending=missing`，原设备显示在 `active-home`，配对 301 停止。重新打开后仍为「待核对」，继续下一步。
3. **核验并归档旧执行标记。** `recover-runtime-execution-marker.ps1` 先只读验证原设备、指定旧标记和匹配的 DPAPI 进程台账，核对实际 Windows 启动时间晚于旧标记，且与 System 中完整启动事件一致。确认原执行会话无进程、Runtime 已退出，并复核文件未被改动后，才显式应用。脚本将 `host-running.json` 归档为 `host-interrupted-*.json`，保留进程台账、原配对凭据、已有任务数据及未知执行的核对记录。无法证实完整启动或停稳时，脚本会拒绝写入。该处置按现场设备和标记证据限定。
4. **恢复后核对。** 重新打开 Runtime，以原身份运行。生产以同一设备记录连续更新的心跳确认上线，并核对仍选定、无新增设备。已有任务中可能已经执行、结果不明的动作继续保留原事实。

上述脚本名用于识别当时的现场工具。报告以文字保留核验条件、实际改动和结果。

## 交付包复现与诊断缺口

验证使用实际 0.0.37 交付模块、Node `22.23.3`、Windows DPAPI、随包 native 辅助器和隔离 HTTP/TLS 服务。不同场景分开验证。

| 对照 | 观测结果 |
| --- | --- |
| 原 Host 仍在，短时断网后恢复 | 实际挂起再恢复进程，并注入心跳 503。原身份自动恢复心跳、领取，零配对。 |
| 同会话旧 Host 已退出，台账可核验 | 真实运行标记及 Job 台账可以核验停稳，随后同一设备恢复心跳和领取。 |
| 旧标记会话与当前不同、native 标识相同 | 用实际 native 和受保护旧会话夹具，`describe` 与 `getState` 均成功，状态为 `reconciling`。自动恢复不发 start，手动 start 也不能上线。观察窗口内零心跳、零领取、零配对。 |
| Host 握手失败对照 | 让另一个 Host 持有同目录租约，新的 `describe` 直接失败，未进入 `getState`。这条路径可与上面的「待核对」明确区分。 |
| 活动 HTTP `requested` 与有效 HTTPS 身份并存 | 交付版只在启动恢复时发出无新配对码的 HTTP `/pair`。出现 301 后重复发送。显式提交 HTTPS 并进入新建分支时，实际发到 TLS 端点。 |

隔离环境只有一个可用 Windows 会话。实际挂起、真实 Job 和模拟跨会话输入分别验证了对应分支。真实第二会话、系统级睡眠及快速启动的完整组合未在隔离环境重跑。11 月 5 日及 9 日最早两次自动启动失败均只有通用事件，现场 11 月 10 日确认的「待核对」解释了恢复阶段的持续阻断，无法回填早先两次的内部失败阶段。

首次诊断包只从活动目录采集，空目录导致其中没有 Runtime 日志。恢复原目录后的包虽然读到约 226 KB 原始日志，1844 行未进入诊断投影，最终只导出 5 条 Desktop 事件。启动握手、状态读取、执行停稳、配对续接及心跳恢复缺少可区分事件，因而需要补充现场只读脚本与生产访问记录。扩大同一目录的导出时间窗口无法补回缺失证据。 [诊断入口](../../clients/agent-desktop/electron/runtimeLogs.ts#L63) · [日志投影](../../clients/shared/local-tool-host-core/src/legacy/logDiagnostics.ts#L128)

## 留档事项

- 客户现场原身份和连续心跳已恢复。现有资料支持低功耗状态切换在自动启动失败之前，缺少突然断电、系统崩溃或首次握手失败的直接证据。现场只确认这一台设备命中两层阻断。
- 遇到同类情况时，先区分正常运行心跳、单次诊断心跳和配对请求，再区分 Host 握手失败与握手成功后的待核对。现场可按原身份、任务领取和回执分别记录恢复结果。
- 如旧版后续需要专项维护，可以沿两处已复现缺陷独立处理。明确失败的配对不继续重发，原身份留在活动位置。执行恢复依赖真实受管进程停稳证据，旧动作结果未知时保留事实。诊断需能区分这两条路径并覆盖可信上一连接目录。
- 本次主分支归档范围为事故报告和索引。国腾恢复分支中的客户端、后台、数据库及打包试验改动没有纳入本次合并。
