# 正式服：excel_process同步读取膨胀工作表阻塞全部Runner调度

日期：2026-11-05；下文时间均为北京时间。状态：完成只读诊断，未修复、提交、部署或重跑客户任务。本文为本次事故唯一诊断文档，保留事实、证据限制及最小修复建议；不包含用户原话、表格正文或凭据。

## 1. 结论

正式服一个`excel_process`全文读取调用占住了多个会话共用的Runner事件循环。从14:12:55左右到15:05人工重启，后续任务可正常接单入库，却不能进入执行。已核验12个请求、11个用户、5个租户受到排队影响；最早请求等待37分15秒。

这里的`excel_process`是Python工具名，不是每个会话独享的Excel操作系统子进程。当前生产为一个Runner worker Python进程，`asyncio.run → asyncio.create_task(self.execute(row))`在同一个事件循环中调度会话；`concurrency=4`表示最多4个并发协程任务，不是4个隔离线程或进程。

异常工作簿仅73,762字节，但四个工作表都有接近104万行的空白/样式尾行。`ExcelProcessTool._handle_read`在async方法中直接调用同步`read_excel_document`，后者按巨大矩形范围逐格访问，并在循环内反复计算`max_column/max_row`。它既阻塞事件循环，也可能因创建空白Cell持续放大CPU和内存使用。事件循环占用后，其他会话、认领循环、续租和协程超时均无法正常调度。

根因是**异常表范围放大计算量 + 同步重活未隔离出事件循环 + 多会话共用执行循环**。不是不同用户的会话状态串了，也不是4个槽位都被正常任务占满。缺少被终止进程的实时线程栈，精确停在哪一轮Python循环未现场采样；但请求、路由、checkpoint、文件结构及同SHA源码已形成一致证据链。

## 4. 源码调用链与架构误区

已核对生产与当前本地源码SHA256一致：

| 文件 | SHA256 |
|---|---|
| `src/services/agent_runner/worker.py` | c1099ad95cedc345fb6cb8f784eb5a64d07931e4de99931d2fad8f7b8cd365f9 |
| `src/tools/executor.py` | c6b4b014048613f55e73a366609ecf39b168b90e293ff45a2ffc1bbd38789953 |
| `src/tools/excel/excel_process_tool.py` | c9e255a77481b333bd46ec283592afd916834ed8dbe9cf73059711ba9ea609b3 |
| `src/tools/excel/excel_reader.py` | 8c3fbe7d8a6e6b102609c38a8a1b1be3b96eab70d7b3a516b6968a707d3c7e7e |

1. `worker.main/run_worker`只调用一次`asyncio.run`。`RunnerWorker.run`在同一循环中用create_task启动各会话。线上配置concurrency=4、heartbeat_seconds=10、lease_seconds=30；相关环境变量没有覆盖这三个值。当前进程清单也显示生产worker为单个Python进程；多个辅助线程不等于每个会话有独立执行线程。
2. `ToolExecutor.execute`直接`await tool.execute(**parameters)`；await只在被调用方真正让出控制权时才允许其他协程调度，不会自动把同步函数变成线程执行。
3. `ExcelProcessTool.execute → await handler → _handle_read`，有range或include_formulas走同步read_sheet，否则直接`read_excel_document`；本次range为空，走后者，没有`asyncio.to_thread`。
4. `read_excel_document`用普通模式load_workbook，先`_extract_sheet_data_doc`，再为全部sheet调用`_format_sheet_to_text_doc`。这些函数按max_row/max_column遍历矩形；`sheet.cell`还会为原本未存储的空白位置创建Cell。
5. `_extract_sheet_data_doc`每行重新读取`sheet.max_column`；格式化函数同样在循环中重复读范围。openpyxl的这些property需要从已加载Cell集合求最大值，不是常数时间计数器；随着空格被实例化，重复求范围继续放大耗时。即便仅将范围缓存一次，104万空白行的展开问题依然存在。
6. 认领、各任务、心跳、取消/超时都在同一事件循环。同步循环占用后，“空余并发槽”仍无法接新任务；心跳和协程超时同样不能抢占。主API多Gunicorn worker或提高Runner concurrency不能修复这条同步阻塞链。

可见的同源风险：ExcelProcess的to_md/export/modify/format/merge/convert等处理器也有直接同步调用；结构化模板填充已单独使用to_thread，不能据此认为整个Excel工具已异步隔离。开发应按实际同步处理边界补齐，而非重写路由或新增全套执行框架。

## 5. 最小修复建议（待开发，非本次实施）

1. **先修假异步边界。** 将Excel同步读取/写入/格式化等真正阻塞的处理移出事件循环，复用已有to_thread方式和上下文传递；异步路由LLM仍正常await。不要把整套异步工具再包入第二个事件循环，也不新增每用户Agent进程/队列。
2. **同时修异常维度算法。** 全文读取应按真实存储/有效数据范围处理，避免因样式尾部创建百万空行Cell；缓存行列边界、复用读到的数据，保留必要坐标与格式语义。相同目的的读取逻辑尽量复用，不让两个入口继续各留一份旧算法。只改线程而不改算法仍可能耗尽线程和内存；只改算法而不移出事件循环仍会让正常大任务干扰其他会话。
3. **范围请求按范围执行。** 用户只读一个sheet/区域时，不额外全文格式化所有工作表；输出预览和完整结果分开时准确说明，不能静默丢数据或把样式尾部当真实业务行。对于真实超大数据按既有读取/分块能力返回明确结果，不简单禁止客户文件。
4. **工具级可回收隔离。** 用户进一步要求单个计算卡死时其他Runner仍可执行；推荐将Excel这类同步重活放入独立、可终止的计算子进程，由父协程异步等待，限制其并行数量及自身CPU/内存消耗，异常时只回收该调用的进程。to_thread可先消除事件循环直阻塞，但不是最终的硬资源隔离，取消/超时也不能杀掉已运行线程。复用已有子进程等待与回收能力，不以全平台调度重建为前提；单纯wait_for、提高并发或扩大超时不能解决本次根因。具体检测/回收边界见第7节。
5. **健康观察反映真实调度。** 现有worker healthcheck只pgrep进程，无法识别“进程活着、循环卡住”。复用现有心跳/租约及排队时间观察调度停滞，补必要告警与阶段耗时，不新造一套监控平台，不盲目自动重放可能有副作用的任务。

必要验证只围绕实际影响：脱敏复现百万样式尾行、一个Excel读取期间其他会话/心跳/认领持续推进、真实范围/单sheet和原内容语义不丢、取消后不错误宣称后台线程已停止。不要在正式服重跑阻塞样本，也不要求重验所有历史客户端。

## 7. 追加：如何发现并限制单个卡死计算（用户11月5日追问）

### 7.1 当前为什么没及时察觉和回收

- worker健康检查只有pgrep。Python还活着就继续healthy，不能发现主事件循环没有调度。现有restart=unless-stopped也不会仅因容器变成unhealthy就自动重启。
- 每10秒续租、30秒租约都依赖同一个事件循环；`reap_expired`同样由`RunnerWorker.run`调用。循环被同步读取卡住后，检查者和被检查者一起失去运行机会，数据库时间过了不等于会自动执行回收SQL。
- CPU高是线索，不宜单独当卡死判据：合法计算也会高CPU，死锁/同步IO可能低CPU。需要同时看主循环活性、租约新鲜度、认领是否推进和工具执行阶段。
- 本次没有历史CPU采样，已证明的是同步循环阻塞及跨会话排队；不能把“所有CPU核都被占满”写成现场监控已确认的数值事实。

### 7.2 最小方案：计算隔离、调用级回收、外部检查

| 层 | 推荐行为 | 故障影响范围 |
|---|---|---|
| Excel计算 | 保持异步路由/调度；把同步读写计算放到可终止子进程，父进程异步等待 | 计算进程卡住，父事件循环仍可调度其他会话及续租 |
| 调用级资源/时间 | 对该类计算设置合理的并行数、内存及CPU时间上限，父进程设置单次计算等待期限；到限回收该进程及其拥有的子进程，等待退出 | 仅本次工具失败，返回结构化原因；原Runner保留成果，可解释、缩小读取范围或继续其他步骤，不无限原样重试 |
| worker活性检查 | 由现有健康检查的独立进程或既有运维监控检查主循环活性/既有租约及排队进展，检测逻辑不能仍放在被检查的循环里 | 在遗漏同步阻塞时及时发现并告警；针对真正失活worker的重启属于最后兜底，不能每个工具超时就重启全worker |

实现可复用项目已有`asyncio.create_subprocess_*`、异步communicate及`src/core/subprocess_owner.py:stop_process_group_async`的原进程组回收方式（现有skill执行已消费）。Excel是首批接入点，整体工具隔离范围按第8节收敛；不重做Runner或新增调度服务，外部工具接口保持兼容。

资源限制要区分含义：CPU时间预算限制累计计算量，CPU配额限制占用速率，内存限制防止单次计算无限扩张；nice优先级和线程数量都不是硬配额。限制共享Runner容器只能保护同机其他服务，不能替代工具级隔离，否则容器整体超限仍会波及内部所有会话。具体额度按工具用途、服务器余量及受影响样本确定，不先硬编码统一阈值或引入每用户资源管理平台。

单次计算期限只约束本机工具执行，不给整个后台Agent任务或前端订阅加统一超时；异步LLM/用户等待等按原机制处理。数据落盘采用已有输出/结果登记方式，子进程被回收不代表文件已成功生成；不交付半成品，也不推断有副作用调用可盲目重放。

外部检查应观察主循环实际推进，不能另起独立线程不停续心跳、将卡死主循环伪装成健康。复用当前进程/执行归属和持久状态；确需兜底重启时，后续按现有checkpoint、租约及原回执恢复，不把任务一律从头重放。不会因新健康检查强制旧Runtime/CLI升级，本批针对服务端内置Excel计算。

### 7.3 验证与范围

优先完成第5节异常范围算法修复，同时验证工具级子进程和检测。只需针对实际风险补足：让一个Excel计算子进程持续运行/超限，核对另一个会话、认领及心跳仍正常；超时/取消后该计算进程确实退出，资源释放；模拟worker主循环失活时独立检查能够发现。合法长任务在持续推进时不得仅因CPU高被误杀。

本节是诊断建议的细化，未实施代码、配置或自动重启策略。新增隔离应先做受影响范围验证，部署仍等待用户明确指令；不新增大量全平台验收门禁。

## 8. 追加：统一覆盖业务工具，而非只保护Excel

如果目标是“任意业务工具卡死不能阻塞Runner调度”，则所有业务工具都应纳入统一、可回收的执行边界，Excel只是本次故障及首批落地点。仅修几个已知重工具不能形成架构保证：HTTP/搜索等工具即使定义为async，内部仍可能误用同步SDK或出现CPU循环，不能只靠async标记判定已隔离。

推荐沿现有工具分发/执行入口集中处理执行边界，而非让每个工具自己写一套进程、超时、取消及结果回传：

| 实际职责 | 建议边界 |
|---|---|
| 服务端业务工具主体，如文档、数据分析、搜索、HTTP及扩展工具 | 由统一执行层放入独立于Runner调度的可回收进程；并发、资源限制、超时/取消和退出回收统一处理 |
| 已在Runtime、CLI、技能脚本或浏览器执行进程中运行的工作 | 复用已有外部执行边界，补其可观测/回收能力；云端代理只做轻量异步提交及观察，不为形式统一重复嵌套隔离 |
| ask_user、等待/暂停、计划及委派等与Engine状态有关的控制部分 | 保留原Runner唯一状态所有权，轻量编排不能搬进子进程后直接修改父进程内存；其中包含的实际计算、同步IO或技能执行仍按对应边界移出 |

这里按实际职责划分，**不能将整个`ToolControlSet`注册表当作不隔离白名单**：其中还装配了skill_execute等真实工作入口，控制适配与执行主体需要区分。现有`ToolExecutionContext`包含LLM gateway等活对象，也不能直接pickle整个工具实例、事件循环或数据库连接；隔离执行应沿可信调用上下文传递必要参数，使用原有身份、模型配置、用量及结果归属，不能扩大权限或重复登记费用。具体适配须在开发前核对，不能把“统一丢进ProcessPoolExecutor”当作已经完成设计。

工具进程可复用，不要求每次调用新建进程或每个用户长期独占进程。需要避免同一个计算进程同时承载多次业务调用后又发生共享阻塞；一个卡死调用只占其执行单元，到限回收/替换该单元，其他单元和Runner继续运行。总体并行数仍按机器资源有限配置，正常排队与卡死长期不释放要区分。进程隔离本身不等于CPU/内存硬配额或权限沙箱，仍需第7节资源及活性检查。

落地顺序：先修异常表范围并切断Excel对主循环的直阻塞，同时设计/接入统一业务工具执行边界；再按现有工具类别完成剩余入口适配及相关验证。所有业务工具是覆盖目标，不等于一次性重写每个工具，也不需要引入Celery、分布式队列或每用户容器。保留现有Runner持久状态、外部工具接口及已交付Runtime/CLI兼容；单工具失败仍局部处理，原任务可根据已有事实继续。本文仅更新方案，未获得也未执行代码修改或部署授权。

## 9. 追加：当前单机并发口径（11月5日只读核实）

| 项目 | 当前事实 |
|---|---|
| 正式服机器 | 4个逻辑CPU，约16GB内存（free显示15480MiB），同机还有API、数据库及仿真等服务 |
| 正式Runner | 一个worker进程，concurrency=4；worker容器内存上限6GiB，无CPU quota/NanoCpus限制 |
| 同时占执行槽的根Runner | 当前配置最多4个，模型/工具等待但执行尚未park时仍占槽；这是配置上限，不是压测得到的硬件极限 |
| 等待用户/暂停 | 持久park后execute返回、释放执行槽；历史会话、在线用户和排队请求不等于正在占槽的Runner数 |
| 现场资源快照 | worker约0.25% CPU、332MiB内存；只是采样瞬间，不能据此推算满载容量 |

当前可明确回答“最多同时执行4个根Runner，其余排队”，不能说“只能4个用户在线”，也不能把单线程异步等同于每次只处理1个请求。子执行/工具还可能在根任务内部并发，4也不是模型请求或OS线程总数。

现有[Runner计划M7](../plans/plan-agent-runner-service.md)记录过本地真实API/worker、假LLM近零延迟和隔离测试库的1.30 runner/s；文档明确不能外推生产承载。尚未找到当前正式服配真实模型、混合业务和修复后工具隔离的有效容量结果，不承诺可提高到多少。

吞吐近似为“并发槽数÷平均占槽时长”：仅作算例，4槽、平均30秒约8次/分钟，平均60秒约4次/分钟；不含持续排队及其他瓶颈，也不是活跃用户容量承诺。大量模型/HTTP等待的轻任务与Excel/PDF/浏览器重任务须分别测量，CPU、内存、DB事务及模型侧限流都会影响结果。

调大concurrency或扩进程前先修本次阻塞；随后在隔离/测试环境按实际业务逐级施压，观察排队、响应分位数、主循环活性、资源及错误率，得到该机型的运行配置。此次没有发起压测或更改并发配置。
