# Runtime协议3配对持续500：迁移水位跳过注册字段

日期：2026-10-14。修复进度及发布边界见[干净安装计划Phase7](../plans/plan-runtime-clean-install.md)。

## 事实

用户自行发布agent2后，r13客户端视频显示“企业服务暂时不可连接，网络恢复后会自动继续”，设备仍未配对。服务器仓库为`a805eb24`，API容器已更新且healthy；22:33起配对日志约每10秒记录一次“设备配对失败，事务未提交”。本次助手只读检查，无服务器、数据库写入或客户机清理。

API容器及宿主机均包含协议3的`2026-10-14 17:00:00`迁移，`DB_UPDATE_SKIP`未启用。数据库`_db_update_applied.last_datetime`却为`2026-10-14 18:00:00`，启动21:52日志显示“数据库更新无新增块”。`local_tool_devices`的`registration_id`、`registration_request_hash`、`registration_code_hash`全部缺失，`uq_lt_devices_registration`索引也不存在；旧替换关系三列存在。

## 原因与限制

迁移执行器只应用`block.datetime > last_datetime`。原17:00迁移被18:00水位过滤，协议3第一次查询注册ID即无法执行；客户端将HTTP500归为暂时连接故障并重试，造成视频里的误导提示。18:00水位的历史来源本次未核实，不假定它应回拨，也不能通过重装客户端改变服务端表结构。

开发验证使用完整新建数据库，已经有协议3列；既有迁移单测使用低于新块的时间，没有覆盖目标存量库水位高于新增块。这是交付前未核对目标迁移水位的漏项。

## 修复

保留原17:00历史块，追加22:45幂等补偿，创建同样三个可空字段及部分唯一索引。新增回归模拟真实18:00水位、只运行新四条DDL、已应用水位不重复执行；独立真实PostgreSQL验证旧结构/部分迁移和已有设备数据保留。协议、客户端、设备选定和任务归属均不更改，r13无需重新安装。

若本轮原配对从未提交，受保护的重试意图不保存OTP，旧网页码也可能已过期；数据库补齐后应生成一次新配对码重新提交，而不是反复安装或点击刷新。

补偿已在本地准备，服务器执行必须由用户当场明确授权；本次不自动提交或发布。持久诊断及500误导网络提示尚未在本次改动中解决，不宣称已新增这项能力。
