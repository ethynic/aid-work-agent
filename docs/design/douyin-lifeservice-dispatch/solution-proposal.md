# 抖音来客订单同步与门店微信播报系统 私有化部署解决方案

> 版本：v1.0（商务报价评审稿，报价与工期为建议值，签约前可调整）
> 日期：2026-09-06
> 面向对象：客户决策层与 IT 负责人
> 关联调研：《抖音本地生活订单→门店微信群推送系统 私有化部署可行性评估》（docs/research/douyin-lifeservice-order-wechat-group-dispatch-research.md）

## 1. 项目背景与目标

商家在抖音（直播/短视频挂载团购券）售卖线下服务，顾客购买后到对应门店核销使用。当前依赖第三方 SaaS 完成订单同步与门店群播报，存在数据外流顾虑。本项目为商家建设一套**部署在其内部网络**的私有化系统，实现：

1. **订单同步**：自动获取抖音来客的团购订单、买家信息、门店与商品数据，无需人工导出；
2. **门店播报**：订单产生后自动将"顾客 + 商品 + 订单号 + 门店"信息推送到订单对应门店的微信群，支持预约提醒；
3. **核销闭环**：支持系统内核销操作与核销状态同步，统计各门店核销率；
4. **经营看板**：门店/商品/时段维度的订单量、金额、核销率实时看板；
5. **数据自主**：全部数据落客户自有服务器，手机号等敏感信息加密存储。

一期聚焦抖音来客（本地生活服务类团购）；抖店（实物商品，快递发货）作为二期扩展预留（配货/发货提醒等场景）。

## 2. 总体方案设计

### 2.1 业务闭环

```
抖音直播/团购成交 → 抖音来客订单 → 【本系统】增量同步
      → 商品/门店 映射路由 → 门店微信群播报（订单信息 + 预约提醒）
      → 顾客到店 → 核销（系统操作或来客核销后同步）→ 核销率统计
      → 经营看板（订单量/金额/核销率/门店对比）
```

### 2.2 系统架构（客户内网部署）

```
┌────────────────────────── 客户内网 ──────────────────────────┐
│  Web 管理后台（Vue3）    ←→    API 服务（Python FastAPI）      │
│                                    │                          │
│   同步 Worker ── 轮询抖音来客接口（仅出网，无需公网入站）        │
│   推送引擎（事件→模板渲染→路由→通道适配→重试）                  │
│   PostgreSQL（主数据/订单/客户/推送记录，PII 加密）              │
│   Redis（队列/缓存/分布式锁）                                   │
│   [可选] Windows 播报节点（微信客户端自动化，见 §3.3 通道 C）     │
└──────────────┬───────────────────────────┬───────────────────┘
               │ 出网 HTTPS                 │ 出网
        抖音开放平台/来客接口          企微 API /（可选）微信客户端
```

要点：
- **纯出网架构**：抖音订单采用授权后增量轮询，无需在客户防火墙上开放公网入站端口；
- **Docker Compose 一键部署**，提供备份、升级、监控告警与运维手册；
- 敏感信息（手机号）落库加密、界面按角色脱敏、操作全程审计。

### 2.3 多门店与路由模型

- 门店档案 ↔ 抖音来客门店（POI）绑定；
- 抖音商品（SKU）→ 门店 的映射规则（含默认门店兜底）；
- 门店 → 播报群绑定（一店一群或多群）；员工账号归属门店，数据按门店隔离。

## 3. 对接方案设计

### 3.1 抖音来客（一期核心）

- **接入路径**：商家自研应用。商家在抖音来客「店铺管理 → 服务应用授权 → 商家自研服务」入驻抖音开放平台，创建应用并授权本系统，数据仅在商家自有店铺范围内，与私有化部署模式匹配；
- **数据范围**：门店（POI）、团购商品/SKU、订单列表与详情（增量）、核销状态、退款状态、买家昵称/联系方式；
- **核销**：支持本系统调核销接口直接核销；同时在来客后台人工核销的订单会同步回来，保证两边一致；
- **手机号说明（重要）**：平台对买家联系方式有隐私保护策略，实际返回明文手机号还是脱敏/虚拟号，需在启动后第一周用真实店铺授权验证（M0 验证项）。若为脱敏号，播报模板自动降级为"尾号 + 到店补录"模式，顾客到店报手机号后由门店在系统内补录归档。

### 3.2 抖店（二期预留，非一期范围）

抖店开放平台对商家自研应用支持成熟（订单/物流/发货接口齐全）。二期扩展"配货发货提醒包"：订单事件 → 仓库/门店内部群播报（新增订单、待配货、已发货、异常件），可选回写发货状态。

### 3.3 微信播报通道设计（通道矩阵）

微信群机器人能力存在平台硬限制，我们按群性质设计三条通道，系统内统一为"通道适配器"，可按群配置、随时切换：

| 通道 | 适用群 | 原理 | 自动化程度 | 合规/风险 |
|------|--------|------|-----------|----------|
| **A. 企微群机器人（Webhook）** | 门店**员工群**、仓库/配货群、管理层群（企微内部群） | 企微官方机器人接口 | **全自动实时**，20 条/分钟 | 官方合规，零风险 |
| **B. 企微客户群（含顾客的群）** | 顾客在群的官方路径 | 企微"客户联系"：入群欢迎语（全自动）+ 客户群群发 API | 欢迎语全自动；群发每群每天约 1 条、需员工在企微端确认 | 官方合规，但**无法做到每单实时刷屏** |
| **C. 微信客户端自动化（RPA）** | 存量**个人微信群**（顾客群） | 自研微信桌面端自动化引擎在真机上以门店机器人号发送 | 全自动实时，可支持 @机器人 查订单等**群内互动**（差异化能力） | 非官方通道，存在账号风控风险；采用真机+真人号+低频播报策略降低风险，机器人号与主号隔离 |

> 说明：普通微信群与含顾客的企微外部群，官方均不支持添加"群机器人"（企微机器人仅限企微内部群；个人微信无官方机器人机制），因此"实时推送到顾客所在的普通微信群"业界均通过通道 C 类方案实现。我们建议：**内部协同群一律走通道 A（合规全自动）；顾客群默认通道 B（合规档），如需对齐竞品"每单实时播报"体验，加购通道 C（体验档）**，由客户知情选择。

可选增强：微信客服（企微）1v1 向顾客本人发送订单/预约提醒（合规、点对点、不进群）。

### 3.4 可选外围

短信提醒兜底（需报备签名模板）；云打印核销小票；门店地图定位展示。

## 5. 开发计划

### 5.1 里程碑（合同生效 T0 起，总日历约 14 周）

| 阶段 | 内容 | 工期 | 交付物/出口标准 |
|------|------|------|----------------|
| M0 启动与验证 | 双方立项；客户完成抖音开放平台入驻与授权申请；**真店 PoC：验证订单/手机号/核销接口实际范围**；细化需求与模板文案 | 第 1–2 周 | PoC 报告、需求规格书（双方签字） |
| M1 基础平台 | 部署框架、账号权限、门店与映射配置中心 | 第 3–5 周 | 后台可登录、门店/映射可配置 |
| M2 订单链路 | 抖音来客同步 + 订单中心 + 客户中心 | 第 5–9 周（依赖权限审批，多数与 M1 并行准备） | 真实订单进系统、核销状态一致 |
| M3 播报链路 | 播报引擎 + 通道 A/B（+C 若选购） | 第 8–11 周 | 真实订单自动播报到指定群 |
| M4 看板与打磨 | 数据看板、报表导出、整体联调 | 第 10–12 周 | 看板指标与来客后台对账一致 |
| M5 部署与试运行 | 客户内网正式部署、培训、2–3 周试运行陪跑、验收 | 第 12–14 周 | 验收报告、全套文档移交 |

团队配置：后端 2 人、前端 1 人、测试 0.5 人、项目经理 0.5 人（合计约 4 人，高峰 4 人）。

### 5.2 验收标准（摘要）

- 真实订单从成交到群播报延迟 ≤ 3 分钟（通道 A/C）；
- 订单同步与抖音来客后台对账差异率 ≤ 0.5%（T+1 核对）；
- 看板核心指标与来客后台误差 ≤ 1%；
- 系统可用性 ≥ 99.5%（试运行期）；手机号等敏感字段落库加密抽查通过。

### 5.3 客户侧配合事项

提供抖音来客商家账号并完成自研应用授权；提供企业微信管理员（开通自建应用）；提供内网服务器（建议 8 核 16G 起，Docker 环境）及出网白名单（抖音开放平台、企微 API 域名）；指定门店配合 UAT；如选购通道 C，提供播报用微信号与一台可长开 Windows 电脑。
