# 企业微信定时消息发送设计

状态：设计决策已逐项确认（2026-11-10），待开发。[开发计划](../../plans/plan-wecom-scheduled-send.md)

定时消息发送在[监控配置首次启动发送（P0）](wecom-conversation-operations-design.md#921-监控配置首次启动发送p0)真机验收通过后进入开发。

## 已明确的需求

用户配置企业微信群聊或单聊、发送时间和确定的消息内容。系统按配置主动发送，触发与是否收到新消息无关。

## 现有能力

- 企微代理任务由新消息触发，使用所选智能体和任务指令回答，已有会话目录及设备与账号绑定。[现有代理任务设计](wecom-conversation-operations-design.md#9-企业微信代理任务新消息触发回答2026-11-08设计待开发)
- 现有 Scheduler 支持按时触发，企微日报已经通过该入口派发专用任务。[共同集成契约](../../system/runner-desktop-runtime-integration-contract.md)
- 现有企微 Runtime/CLI 支持通过 `wecom_message_send` 发送消息，原发送链路包含本地记录核验与结果不明时的只读对账。[发送契约](wecom-proxy-task-contract.md#1-唯一写入者与身份边界)

## 决策 1：配置名称与共用队列

状态：已确认（2026-11-10）。

- 两类配置分开管理。现有功能称为「监控配置」，新增功能称为「定时消息发送」。页面入口见决策 16。
- 定时消息发送和监控回复共用企微设备的执行队列，串行使用设备。发送时间到达后，定时消息优先于尚未开始的监控回复执行。

## 决策 2：到点时设备正在执行监控工作

状态：已确认（2026-11-10）。

已经开始的监控工作执行完本次占用，再让出设备。到点的定时消息在下一次派发时优先执行，其间不开始新的监控工作。设备繁忙时，实际发送时间可能晚于计划时间。

## 决策 3：错过计划时间后的补发范围

状态：已确认（2026-11-10）。

尚未开始发送的消息，距计划时间不超过 10 分钟（含第 10 分钟）时可以补发。超过 10 分钟跳过本次，执行记录标为「已过期」。设备忙碌或离线都使用同一个时间上限。

## 决策 4：首版发送时间规则

状态：已确认（2026-11-10）。

首版支持三种规则：指定日期和时间发一次、每天固定时刻发送、每周勾选星期几并在固定时刻发送。

## 决策 5：一条配置可选择的会话数

状态：已确认（2026-11-10）。

一条配置可以选择一个或多个群聊和单聊，按同一时间规则向各会话发送同一份内容，每个会话单独记录发送结果。不同会话要发不同内容时，分别建立配置。

## 决策 6：首版支持的消息内容

状态：已确认（2026-11-10）。

首版支持预先填写的固定纯文本，允许换行。到点原样发送保存的内容。图片、文件、@提醒和动态变量留待后续扩展。

## 决策 7：到点由谁发起发送

状态：已确认（2026-11-10）。

由调度流程把到期消息交给共用队列，轮到时调用现有企业微信发送工具。配置无需选择智能体或填写提示词，发送流程按保存的正文执行。

## 决策 8：发送设备和企微账号如何绑定

状态：已确认（2026-11-10）。

创建时绑定「本地工具」当前选定的设备和它登录的企微账号，目标会话从该账号的目录选择。创建后固定使用该设备和账号。原设备离线或切换企微账号时，在补发窗口内等待原组合恢复。

## 决策 9：发送结果不明时如何处理

状态：已确认（2026-11-10）。

以原发送工具回执为依据。文本发送成功回执带有本机库核验结果 `verification='local-record'`。未取得明确回执且发送动作可能已经发生时，沿原发送调用走只读对账。仍无法确定时，将该会话本次结果标为「发送结果未确认」，不自动重发。[现有回执与对账逻辑](../../../src/local_tools/wecom_flow.py)

## 决策 10：确认未发送的临时失败是否重试

状态：已确认（2026-11-10）。

发送工具返回明确失败后，本会话本次记为失败，日志记录失败原因和调用诊断编号，队列继续执行后续项目。尚未发起发送时，仍可按决策 3 在窗口内等待设备可用。

## 决策 11：多条定时消息到期时的队列顺序

状态：已确认（2026-11-10）。

同一队列里，已到期的定时消息按计划发送时间从早到晚执行。计划时间相同时，按配置创建顺序执行。一条配置的多个会话依次发送。

## 决策 12：暂停时如何处理已排队的消息

状态：已确认（2026-11-10）。

暂停取消本配置中尚未开始发送的消息。已经开始发送的消息继续等待回执或对账。恢复后从下一次计划时间开始。

## 决策 13：启用中的配置能否直接编辑

状态：已确认（2026-11-10）。

启用中的配置不可编辑。用户须先暂停，才能修改会话、正文或时间规则。保存修改后由用户恢复，按新的下一次计划时间执行。

## 决策 14：新配置保存后的初始状态

状态：已确认（2026-11-10）。

新配置保存后处于「已暂停」，由用户手动启用。

## 决策 15：发送时间使用哪个时区

状态：已确认（2026-11-10）。

首版统一按北京时间（`Asia/Shanghai`）填写和执行，页面在时间字段旁标注「北京时间」。

## 决策 16：定时消息发送的页面入口

状态：已确认（2026-11-10）。

在「企业微信 Agent」内增加「定时消息发送」入口，与「监控配置」同级。进入后管理定时发送配置和执行记录。

## 决策 17：复用现有调度器判断到期

状态：已确认（2026-11-10）。

复用现有后台调度器计算发送时间和发现到期项。到期后交给企微共用队列派发。服务端重启后仍以原计划时间计算 10 分钟补发窗口。

## 决策 18：执行时只看队列顺序

状态：已确认（2026-11-10）。

执行器按共用队列顺序取下一项。调度器在定时消息到期时按决策 1 和 11 将它排在尚未开始的监控工作前，执行器取队首时无需再扫描定时配置。已开始的工作按决策 2 执行完再释放占用。

## 决策 19：同一次发送如何避免重复入队

状态：已确认（2026-11-10）。

以「配置、计划发送时间、目标会话」确定唯一的发送记录。同一次计划发给同一个会话只建一条记录。服务重启或调度器重复发现同一到期项时，继续处理原记录。已开始发送但回执不明时，按决策 9 处理原调用。

## 决策 20：执行记录显示哪些信息

状态：已确认（2026-11-10）。

按每次计划发送时间查看各目标会话的结果，显示会话名、计划时间、实际开始发送时间（未开始时留空）和状态。失败、过期或发送结果未确认时，显示简短原因与可复制的诊断编号，便于查日志。

## 决策 21：删除配置后是否保留执行记录

状态：已确认（2026-11-10）。

配置采用软删除。删除后停止计划派发，从配置管理 UI 隐藏。保留原配置的关联标识供历史发送记录引用，历史仍可从执行记录查看；已开始的发送继续等待回执或对账。

## 决策 22：定时发送计划存在哪里

状态：已确认（2026-11-10）。

沿用企微日报的专属计划模式，把发送计划保存在现有 `scheduled_tasks` 中，标明为「企微定时消息发送」类型。由企微专用页面管理，普通定时任务列表不显示这类配置。到期后按决策 17 交给企微共用队列。

## 决策 23：排队状态和发送结果是否使用同一条记录

状态：已确认（2026-11-10）。

每次计划发送的每个目标会话保存一条专用执行记录。从排队到终态更新同一条记录，页面也从这里查历史。监控继续使用现有批次记录，两类记录由同一派发器按共用队列顺序处理，无需额外复制一份通用队列表。

## 决策 24：什么时候算已开始发送

状态：已确认（2026-11-10）。

以服务端授权设备执行本次发送的时刻为界。排队和设备领取后尚未取得发送授权的，都可以被暂停取消或在超时后跳过。授权前核对配置状态和 10 分钟截止时间；已授权的发送继续等待回执或对账。执行记录的开始时间取授权时间。

## 决策 25：结果未确认时后续消息是否继续

状态：已确认（2026-11-10）。

原发送动作还可能占用设备时，等待它释放。确认设备已空闲后，后续消息按队列顺序继续发送，原消息继续走只读对账。对账结论只更新原执行记录。

## 决策 26：定时发送采用什么计费口径

状态：已确认并修订（2026-11-10）。

定时消息发送按目标会话的单条消息计价，默认 0.5 积分。Portal 提供平台级单价配置，仅平台管理员可设置；存在有效配置时按配置值，未配置时按默认值。此单价适用于定时消息发送。定时、排队和只读对账不额外收费，也没有生成正文的模型费用。

## 决策 27：是否占用普通定时任务名额

状态：已确认（2026-11-10）。

定时消息发送不占用普通定时任务的启用名额。普通定时任务列表和启用数量统计采用同一范围。

## 决策 28：队首消息通过哪条链路执行

状态：已确认（2026-11-10）。

轮到定时消息时，企微派发器按保存的目标和正文，经现有受信 Runtime 通道直接调用绑定设备上的企微 CLI 发送命令。发送动作不创建 Runner，也不调用模型。调用生命周期、授权时点、回执、重启恢复及旧端兼容按共同集成契约落实。

## 决策 29：什么结果才扣发送积分

状态：已确认（2026-11-10）。

每个目标会话仅在发送得到确认时扣一次积分。失败、取消、过期和仍未确认的发送不扣费；只读对账后来确认发送成功时，按同一条发送记录结算一次。

## 决策 30：以哪个时点的单价结算

状态：已确认（2026-11-10）。

服务端授权设备执行该条发送时，锁定当时的 Portal 单价并保存在执行记录里。收到回执或后续对账确认后，按原记录的单价结算。Portal 改价只影响之后取得发送授权的消息。

## 决策 31：发送前发现积分余额不足怎么处理

状态：已确认（2026-11-10）。

对启用积分计费的租户，在授权发送时按锁定单价检查当前余额。余额不足以支付本条时记为「失败 · 积分不足」，队列继续处理后续项目。充值后不补发本次。

## 决策 32：如何接入现有 Runtime 发送授权

状态：已确认（2026-11-10）。

复用 Runtime 领取任务后、启动 CLI 前已有的开始确认接口（`/started`）。服务端只对定时发送在这一步核对配置、截止时间和余额，并在首次确认成功时锁定单价和开始时间。Runtime 收到成功响应才启动 CLI。现有接口请求和响应格式保持兼容，原有工具按原规则运行。旧客户端能否参与定时发送，以实际交付版本验证为准。

## 执行链路与数据归属

1. **配置。** 企微专用入口以当前登录用户建立 `scheduled_tasks` 专属计划，固定租户、配置归属用户、设备、企微账号与稳定会话标识，保存正文和北京时间规则。新配置先暂停；启用、暂停、编辑和软删除沿上述决策执行。Portal 平台单价从现有平台管理鉴权入口配置，权限由后端核验。
2. **到期。** Scheduler 以原计划时间生成逐会话执行记录。唯一键是配置 ID、计划时间与稳定会话标识。记录固化本次会话、设备、账号与发送正文，供重启和历史查询使用。到期入队与推进计划进度须保证重启后既不漏发也不重复入队。尚未开始的记录超过原定时间 10 分钟后结束为过期。
3. **派发。** 同一设备的监控与定时发送共用现有企微设备协调机制，由同一处取队首并取得设备占用。监控工作开始后执行至释放占用。调度器负责把到期发送排在未开始的监控工作前。每条定时发送记录绑定原本机调用，轮到时经 Runtime 调用 `wecom_message_send`，不提交 Agent Runner。
4. **授权。** Runtime 先领取，再调用 `/started`。该请求对定时发送在同一状态迁移内核验原记录与租户、用户、设备、账号和目标绑定、配置状态、截止时间及余额，首个成功迁移锁定单价与开始时间。暂停、过期或积分不足均发生在授权前。开始确认的网络重投使用同一调用，保留原授权事实。
5. **收敛。** 以原 CLI 回执为发送证据。明确失败即结束本条。结果不明时原发送不重放，设备释放后队列继续。只读对账必须绑定原发送记录和可验证的原回执定位符。完全缺失定位证据时先使用可验证的迟到回执，仍无证据则保留未确认，不能用同文案猜测发送成功。
6. **结算。** 成功回执与对账确认走同一记账入口，以原发送执行记录作为唯一扣费依据，使用授权时锁定的 Portal 单价。必须防止普通企微工具计费路径对同一条定时发送再扣一次。执行记录可查原计划、目标、开始时间、结果与诊断编号，软删除后的配置仅保留历史关联。
