## P10 图片与文件时间线及按需读取（2026-10-30，设计草案）

2026-10-31实施更新：本节方案已在master源码实现，验收以计划P10记录为准；标题保留原草案日期用于链接。仅支持本地已有缓存的图片和UTF-8文本片段，不宣称已安装新版插件或完成真实Web/生产验收。

### 只读实证与能力边界

本机当前微信单聊的新消息类型101为图片、102为文件。调查时旧CLI将二者返回非文本占位；本轮源码已识别并支持按需展开。类型102的field2可读出文件名，field3为远端资源引用；类型101的field3/field26分别命中高清缓存和缩略缓存的映射key。当前账号`CacheMapping`目录的SQLite映射表包含`type/key/file_name/last_modify_time/file_md5`，可将原消息资源引用精确关联到`Cache/Image`下的实际文件，不必每轮递归扫描文件系统，也不靠时间相近猜测图片归属。文件样本在`Cache/File`，大小和内容摘要与消息记录一致，可直接按UTF-8读取。

本轮图像样本存在1080×2400的可读JPEG缓存及210×467的JPEG缩略缓存，已打开高清缓存核实。缓存图像大小/摘要可能不同于消息原始资源元数据，本样本不能以“消息MD5等于缓存文件MD5”作为图片可读的必要条件；使用消息资源key与缓存映射关联，实际检测文件格式/可读性。缓存映射声明的摘要如何使用尚待确认，不凭空固化新校验门禁。这里只证明本机样本可直接读取，不概括所有版本、未下载附件或所有图片均有明文缓存。远端地址可能含访问参数，禁止直接返回给模型或写入日志；原始样本、账号、真实文件内容和私有路径不进入仓库。

### 时间线默认轻量，理解内容按需展开

保留原消息的`msg_id`、时间、发言人/平台、方向与顺序。图片/文件使用`kind=image|file`，正文给可读占位，并附最小附件元数据：文件名（有证据时）、格式、大小、可用性；图片尺寸区分已验证缓存与原始资源，不能混称。尚未查看时不伪造图片描述或文档摘要。未缓存或格式暂不支持只标注该附件，不影响其他消息与游标读取。

仍保留现有三业务工具。原会话读取新增可选`attachment={message_id,offset?,max_bytes?}`，复用会话稳定标识与`msg_id`定位，不创建附件ID数据库或新工具集合。省略或null沿普通时间线；指定附件时只返回该附件、不返回/推进时间线cursor，不能与cursor/resolve_only混用。文本offset为字节位置，默认0，max_bytes默认4096、上限8192；next_offset可原样续读，不截断UTF-8字符。共同契约2.12已登记；旧object-only和新nullable MCP schema沿原能力协商，缺新能力仅影响附件展开。

| 内容 | 默认时间线 | 按需读取结果 |
|------|------------|--------------|
| 图片 | 图片消息、可用尺寸、是否已有缓存；不自动逐张识图 | 读取可用清晰缓存，单张最多5MiB；通过真实图片内容交给视觉模型。当前未实现裁剪/远端下载，不以本机路径字符串代替视觉输入 |
| 文本/Markdown文件 | 文件名、大小、可用性 | 本地按UTF-8字节窗口读取，返回text/offset/next_offset/has_more；需要时逐段续读，小文件可完整覆盖 |
| 大文档 | 同样只给附件信息，不自动通篇转换、摘要 | 当前UTF-8文本可按字节续读，不全文件装内存；PDF/Office等暂返回unsupported，目录/页码/搜索不属于本轮已实现能力 |

Agent先结合相邻聊天判断是否需要附件：例如客户发图并问“这种情况怎么办”，应展开这条图后回答；历史无关附件不随每次轮询重复展开。文件预览/分页优先本地处理，不先调用模型通篇总结。初版不默认解包压缩文件、逐页识别扫描件、运行宏或执行附件中的指令。

### 云端理解、成本与恢复

CLI负责附件识别、本机定位与局部读取，Runtime负责现有受权调用与实际内容传输，Runner沿原任务推理/用量机制决定是否进一步读取。服务器无法访问客户机绝对路径；图片需经当前任务的资源接收路径进入服务器资源空间，再复用已有`AttachmentAssembler`/`runner_image`与模型装配能力。本轮已将私有标准MCP图片块经原OperationResult/Runtime outbox传输，在LocalToolAdapter正常/恢复结果出口消费并注册ImageRegistry/ImageRef，再复用AttachmentAssembler保存原owner副本。ModelAdapter仅在最新完整工具批次后临时加入真实多模态输入，并保留之后的用户补充；SSE图片引用本身不作为模型看见图片的证据。未新增上传API、附件服务、队列或恢复框架。

同一消息/同一内容的已读取结果优先复用原调用结果或现有任务资源；重启恢复沿原invocation/checkpoint及游标，附件读取不触发业务重发。持久状态保留内容引用、已读片段位置和必要理解结论，不塞完整Base64或反复重附整份文件。后续模型上下文压缩沿现有机制；仅新增owner副本标记source=local_attachment并随既有compaction回收不再被消息/恢复结果引用的项，不影响初始用户图片。原Device invocation/outbox仍保留单次有界图片传输字段作为原回执，公开工具结果/SSE/模型checkpoint只有ImageRef或owner引用；不承诺仅保存引用即可免除再次模型视觉用量，真实用量仍沿原模型计费。

定位失败、文件未下载、缓存被清理或暂不支持均作为单附件结果，保留原消息身份和可行恢复提示；不让整段时间线失败，也不靠无限重试卡住任务。优先本地已有资源；按需获取尚未缓存内容的下载/UI路径另行实证，初版不假定有缓存、更不直接把私有URL交给模型自行请求。

旧Runtime/旧插件保持现有文本读写能力，不强制升级、不将缺少附件支持作为会话读取拒绝条件。新增字段可选，旧输入不改义；正式共同接口变动实施前登记唯一写入者与兼容方案。历史非文本游标锚点继续沿P9按text=null，附件元数据/正文展开不改变旧读取基线，不影响普通文本发送对账。

实施计划及验收边界见[本地库计划P10](../../plans/plan-wecom-cli-localdb.md#p10-图片与文件时间线及按需读取2026-10-30设计草案)。本节已完成源码实现、匿名跨层与模型输入验证；实际现用客户端尚未安装新版插件，不宣称已完成真实Web多模态或真实模型计费验收。提交与推送按用户后续授权执行；未安装、部署或恢复监听。

## 1. 定位与目标

本地库是会话读取、待回复快照与监控增量的唯一数据通道。读聊天记录按 conversation_id 查询，返回精确时间和 sender_id 方向；未读/待回复按最后发言方判断，监控按数据库水位读取增量。这三个入口不调用 UI/OCR，不切换会话或清角标。文本、图片、文件发送及 UI 搜索/选择保留各自设计，不受本节修改。

## 2. 本地库版本准入与失败语义（2026-11-06 修订）

`wecom_read_session` 的稳定 `session`、日期和旧 `target_name`/账号绑定 `target_ref`，以及 `wecom_unread_list`、`wecom_watch_poll`，每次从当前进程确认版本并依据已有 validated/stale 矩阵、算法/库指纹、账号与快照准入。未配置 doctor 状态或状态为 `ui(compat/transient)` 时也尝试本地库；`forced=true` 只覆盖落盘状态选择，绝不绕过实际版本矩阵与身份校验。旧无账号 ref 拒绝读取，提示重新搜索或使用目标名称。显式 `channel=ui` 返回 `VERSION_UNSUPPORTED`；旧 `max_pages` 参数返回 `INVALID_ARGUMENT`。

版本不支持、密钥不可得、快照不稳和其它本地库失败返回真实错误码，不返回 OCR 猜测内容；有游标的失败保留原游标语义，不重置水位。监控本轮失败另返回 `db_unavailable=true`、保留 DB 水位，下一轮可重试。取消、身份变化和目标歧义照原错误独立上报。`logs/localdb.log` 继续记录本地库尝试、成功和扫描失败；不再记录这三个入口“回退 UI”的假成功。doctor 仍提供版本/密钥/环境诊断与原状态文件，但状态不再决定这三个读取入口是否使用 UI。

关注集合继续沿现有契约：未传 `focus` 为全部，空数组非法；会话名或账号绑定 ref 在本地库中消歧，单个 focus 失败列入 `failed` 而不推进其水位。新关注绑定 `{account, conversation_id}` 后只按身份轮询；首次基线为当前最大消息 ID，存量待回复由调用方先读快照。监控水位保存在 `localdb-watch-state.json`，按账号/库代际与消息锚点核对；失败轮不推进。CLI watch 按轮获取并释放原互斥，不在间隔期间持锁。

### 3.3 可信快照与 WAL 校验协议（评审 v3 修正判定规则，实验逻辑不可照搬）

实验版直接解密 WAL 并重算校验和，且未处理 WAL 重用旧尾帧——生产协议如下。**WAL 有效前缀规则与 SQLite 自身读 WAL 语义一致：首个校验和链断裂或 salt 不匹配的帧即前缀终点；WAL 重用后保留的上一代尾帧（salt ≠ 当前头）属正常现象，不得据此判定 reset 或重试**（评审 v3 合成验证：SQLite 3.45.3 checkpoint 后写入一条记录，22 帧中 21 帧为旧代尾帧，integrity=ok）。

```
捕获（支持条件：捕获窗口内无 WAL reset 且无撕裂页写入）：
  1. 预读源 WAL 头 H0（salt-1/2、文件序号）与基线（源 WAL size S0、源主库 size D0）
  2. 复制主库（D0 字节）→ 复制 WAL（按当时实际大小）
  3. 复读源 WAL 头 H1 与 size S1：要求 H1 == H0 且 S1 ≥ 已复制 WAL 字节数，
     主库 size 与 D0 一致（或增长可归因且重试）；任一不满足 → 整体重试（N 次小退避）
  说明：窗口内 checkpoint 回填不改变 WAL 头，帧仍在有效前缀内，重放幂等，属支持条件内；
  checkpoint+reset 会改写头，由 H0/H1 比较捕获——**reset 判定只依据头比较，不依据尾帧 salt**
快照 WAL 判定（对密文）：
  4. 从帧 0 起验证累计校验和链（自 WAL 头校验和起链，对帧头前 8B + 帧页密文复算）
  5. 首个链断裂或 salt 不匹配的帧 = 有效前缀终点（旧代尾帧按此自然截断，正常处理）
  6. 有效前缀内只回放到最后一个提交帧（帧头 dbsize>0），其后丢弃
解密与验收：
  7. 页 1 密钥先知验证（快速失败）→ 整库解密 → PRAGMA integrity_check
失败语义：
  8. 重试后仍不可得 → SNAPSHOT_UNSTABLE，不返回半解密结果，不推进 watch 水位
```

**诚实边界**：以上是"支持条件下的捕获 + 尽力检测"，不宣称数学意义的一致性证明；stat 比较、帧校验和、integrity_check 三者组合的证明力以 P0/专项验证为准（**冻结点：C7 实现前必须完成判定规则验证**），不为此堆叠自研锁协议。

测试覆盖：无 WAL、空 WAL、正常重用旧尾帧、并发 checkpoint、捕获窗口内 reset、坏校验和链、截断、未提交尾帧。

**P0 实测注记（2026-10-14；普通样本已验证，专项验证待完成——评审 v5 收窄）**：H0/H1 头比较在真机普通样本通过（8 文件 1.28MB 复制窗口仅 6ms）；真实 message.db-wal 6 帧中 **4 帧为旧代尾帧**（旧 salt 恰为新 salt−1，与评审合成验证一致），有效前缀 2 帧含 1 提交帧——证明捕获流程在该样本可运行、旧代尾帧必须显式按代处理（实验 decrypt_full 依赖 SQLite 自行忽略旧代帧，语义靠侥幸，不可照搬）。**尚不能证明**并发 checkpoint、捕获期间 reset、截断/撕裂场景下协议仍正确或可靠拒绝——按任务 1.4 场景表完成专项验证（含失败场景验证"不返回不可信结果、不推进水位"）后，方冻结生产捕获规则。

### 3.4 密钥存储与生命周期（评审 v3 修正复用来源与失效范围）

**当前账号归属修正（2026-10-15，独立测试与 CR 通过）**：CEF 日志只定位候选目录，不再凭行时间、进程启动时刻或 TTL 确认账号。只读勘察发现本机不同 WXWork 进程同时持有不同账号的 `Data/message.db`，故不能枚举全进程后任选账号。复用操作驱动的主窗口选择规则（可见主窗口中面积最大，最大面积并列则歧义），轻量登录探针返回该窗口所属 PID；Python 专用 `active-account <pid>` 原语只查询这个进程的磁盘文件句柄路径，唯一 `Data/message.db` 所在目录为直接归属证据。无匹配、多目录、权限失败或枚举不完整均不确认，禁止回退历史日志背书。强证据存在时直接选择对应目录，不受 CEF 缺失/冲突、mtime 或长时间在线影响。查询不读取库内容或进程内存、不提权，不新增常驻进程；每次调用重新查询，不跨登录上下文缓存。CEF 跨文件候选统一按行级事件时间排序，未知时间只作弱候选。矩阵准入始终定向读取该主窗口 PID 的实际 FileVersion；仅在缓存密钥不能复用、确需扫描时才定向核验其他候选 PID，只有同一已确认版本可参与，主窗口进程优先。由此保留多进程找钥能力，不把密钥位置限制在主窗口进程。

验证：独立测试 `npm test` 419/419（34 文件、无跳过），Python 全量 98 项（97 通过、1 个非 Windows 分支跳过），typecheck/build、PS1 解析通过；独立合成 WXWork.exe 的真实 CLI 验证唯一账号、多账号拒绝、同 PID 换账号、零句柄拒绝 4/4，重复查询无句柄数增长，定向版本探测返回该辅助映像的实际版本。主控独立 CR、亲自 typecheck 与 dist doctor/datadir import 检查通过，未修改实现。

证据边界：已只读核对唯一主窗口 PID 与唯一消息库路径一致；同 PID 登出/切号后句柄释放及锁屏窗口探测仍须任务 1.14 真机验收，不能把本次静态勘察写成三态验证完成。进程创建时刻仅保留诊断，不参与身份准入。

**方案：DPAPI 本地安全存储，不做独立守护进程**。复用来源：wecom-cli 当前**没有**现成 DPAPI 实现——serverProxy 注释已准确说明 DPAPI 缓存取消、改用环境变量静态 token（非过时注释，评审 v4 勘误）；移植来源为 **weixin-cli `src/security/dpapi.ts`**（单文件、PowerShell ProtectedData、零 npm 依赖，P0 已验证打包可行）。

- **存储**：密钥经 DPAPI（用户作用域）加密存 `%LOCALAPPDATA%\AidWorkAgent\wecom-cli\localdb\key.bin`；明文只在单次调用进程内存与 TS→py stdin 管道。不落日志、不进命令行参数、不进业务返回值、不入库文档、不进 git。
- **绑定**：`{account user_id, data_dir, matrix 条目指纹}` 三元组，任一变化即失效。
- **复用**：doctor 与运行时**默认先核验复用已有密钥**（页 1 先知，毫秒级），无效/缺失才发起全量扫描——doctor 深检不每次全扫。
- **身份与登录态分开（本轮修正）**：操作主窗口进程持有的唯一消息主库路径用于**账号身份归属**；Config.cfg/CEF 仅作候选与诊断，不能独立证明身份或登录状态；缓存密钥能解旧文件，页 1 核验成功 ≠ 当前已登录。登录状态以轻量登录探测原语判定（从 probe 抽取登录判定核心，**不带交互桌面会话门禁**，避免把 UI 门禁带回本地库路径）；无法确认登录或账号时明确报告，不靠缓存密钥继续读旧账号数据。
- **失效**：**仅页 1 密钥核验明确失败**才删除存储的密钥；快照失败、模式失败不归因密钥、不删已验证密钥。退出登录/账号切换/版本变化按身份与登录证据判定。负缓存主要针对**实际扫描失败**并区分原因；已知密钥失效后在允许的登录态下允许重取，负缓存只节流重扫、不阻断恢复。**WXWork PID 变化单独不作为失效依据**。
- **登录证据（P0 候选证据调查完成；判定规则待专项验证，评审 v5 勘误）**：**账号身份、当前登录状态、密钥有效性是三个独立判断**——缓存密钥能解旧文件（DPAPI 缓存尤其不代表当前登录），页 1 核验成功只证明密钥对密文有效，**不证明当前已登录**；退出登录清除的是客户端内存中的密钥，不会使已保存密钥失去解密能力。Config.cfg 登录键（`DbKeyVerKey`/`LoginCompanyId`/`HasEverLoginKey`/`kPollCorpMessageSyncKey` 活跃同步游标/`LastStorageBackupTimeKey`）、文件活跃 mtime、WXWork 进程存在均为**辅助信息，不单独作硬门禁**（退出登录后可能残留，闲置/锁屏时可能无活动）；主窗口标题仅"企业微信"无账号信息。当前登录状态以**登录探测原语（任务 1.10）交付并完成三态验证（已登录→退出但进程仍在、同 PID 切号、锁屏）为准**；未登录或账号无法确认时明确拒绝，不靠缓存密钥读旧账号数据。注意：Config.cfg 是外层 latin-1 字节 + 内层 GBK 值的复合结构，不能按单层 GBK JSON 解析。

## 4. 各能力设计

### 4.1 read-session 本地库通道

- **定位与消歧**：target_ref/target_name → 会话名 → conversation_id。user_table 的 name/别名/备注名精确匹配；多候选 → `TARGET_AMBIGUOUS`（data 附候选）；外部联系人"@微信"后缀对齐现有约定。**target_ref 账号绑定**：新签发 ref 携带账号标识，账号不匹配直接 `TARGET_REF_STALE`。**legacy ref（无账号字段）在 DB 路径一律返回 `TARGET_REF_STALE`，不执行读取**——调用方重新 search 或显式传 target_name 表达按当前账号定位的意图；UI 读取路径已停用。
- **分页与水位（基元已按 P0 实测冻结，2026-10-14）**：
  - 首次读取默认最近 **100 条**（`limit`；旧 `max_pages` 已停用）。
  - **水位/游标基元 = `message_id`**（AUTOINCREMENT 主键=入库序）。证据限定（评审 v5）：message_id 即 rowid 别名，"0 逆序"是同一字段的单调性验证，**不是企微写入策略的独立证明**；"覆盖迟到同步"准确表述为——**迟到消息以新记录插入并取得更大 message_id 时，被增量查询覆盖**（库内 2 例迟到均如此，且均为系统类消息）；**不覆盖原地更新已有记录**（v1 限制，不建变更捕获系统），也不能仅凭当前样本断言所有同步路径都用自动分配 ID——P1b 手机端联调确认。cursor 在 message_id 空间，绑定 `{account, conversation_id, 格式版本, 水位基元代际}`；**不用 send_time（实测为秒级且系统消息可迟到回退）也不用 sequence 做游标**。
  - 同秒消息展示排序以 `server_id`/`sequence` 决胜（实测同秒 7.7%，sequence 同秒递增）；`send_time` 秒级仅用于展示与 since_days 过滤。**入库顺序**（游标推进）与**发送时间顺序**（展示）分开使用。
  - 水位绑定**数据库代际**——库重建/替换/序列回退触发基线重建；空洞无害（cursor 语义按 ≤水位，实测 1 空洞/197）。
  - **游标 = 本批次已返回记录在增量顺序（message_id）上的末端**（本批次最大 message_id）；展示排序（send_time）不改变游标位置，不推进到尚未返回的扫描结果（评审 v4 案例：入库 31 的 send_time 10:00、入库 32 为 09:59 时，按时间展示数组末项是 31，若据数组末项设游标会漏 32——游标只认增量顺序末端）。
  - `since_days`：按本地库 `send_time >=` SQL 过滤（秒级换算）。
  - 残留限制（明示）：不承诺覆盖未测的手机端实时落库延迟（P1b 联调补测）；不建全历史去重账本。
- **消息契约**：`{side, kind?, text, time?}` 不变 + 增量可选 `msg_id`、`parse_trusted`；`time` 精确、`side` 由 sender_id 判定；时间升序（展示序）。
- **v1 仅文本，非文本占位、不触发 OCR 补读**：占位 + kind 标注；需要非文本内容时调用方按现有附件接口显式读取；无法解析的类型保持占位，不自动截图/OCR。
- **失败边界**：本地库错误返回原码，不以 UI 内容代替；增量游标不因失败推进。

### 4.2 unread / watch 本地库通道（待回复检测为主要用途）

- **核心判定**：会话**最后一条可参与回复判定的消息**发送方为对方 → 待回复（角标消失仍可发现，比角标贴合自动回复目标）。tool 描述以"待回复检测"为主要用途。
- **系统/控制消息最小过滤（评审 v5）**：P0 已确认存在系统/控制类记录（ct=1017/38/31 等）——待回复判定只统计**已确认可参与判定的类型**，已确认的系统/控制类型（按 P0 观察样本归纳的最小排除表，P3 全量表再扩）**不参与最后发言方计算**：既不能制造新待回复（自己回复后的系统提示不得重新触发），也不能清除已存在的待回复（对方消息后的系统提示不得顶掉判定）。系统记录仍保留在读取/事件结果中，只是不触发自动回复。
- **watch 增量独立于待回复判定**：返回水位以来全部新消息，附每会话最后发言方辅助标记。
- **返回结构**：`channel=local-db`、`judgment_basis=last_sender`；不返回角标 OCR 快照。
- **水位**：按 §4.1 水位规则；不可信快照不推进水位；**有 limit 只推进到已返回消息**。
- **关注集合契约（P1b/P2 前冻结 schema）**：
  - **关注身份 = 建立关注时一次性解析的持久标识**：入参 target_ref（5 分钟有效，**建立时验证并解析**）或 target_name，统一解析为 `{account, conversation_id}` 交给调用方随水位保存；**后续轮询只使用已解析会话身份，不复用短期 ref、也不每轮重新 search**（否则 ref 过期或引入 UI 操作，损失本地库独立性）。新的独立请求仍按 ref 原有 5 分钟规则验证，不全局取消有效期。无需长期 token/订阅服务/通用身份框架。
  - 语义：未传 = 全部会话；传空数组 = `INVALID_ARGUMENT`；**新增关注会话的基线 = 加入时刻的当前水位**（只看之后的新消息）。
  - **新增关注初始化（评审 v4）**：建立关注时对该会话执行一次待回复快照检查（复用 unread/read-session 流程），加入前已存在的待回复消息经现有流程交消费侧处理；watch 仍从当前水位只出增量，不回放历史，CLI 内不新增 AI 回复循环。初始化调用归属 = 调用方（Runner 建立关注流程）。
  - **单目标解析失败返回部分结果**（失败项进 `failed`，不推进其水位）；CLI 参数、MCP schema、返回事件与旧字段兼容方式列入开发计划。
- **watch 本地库失败行为（v1 决策，评审 v4）**：DB 不可用 → 本轮返回明确不可用（水位保留、日志记录），**不自动落 UI 兜底**——UI 消息无 msg_id，跨通道结果无法去重且会污染水位语义。read-session 与 unread_list 也不再自动回退 UI。
- **群会话解析**：conversation_id `R:` 前缀；群名→conversation_id 经 session.db `conversation_table`（P0 实测可行，name 无唯一索引需防重）；Y: 应用号等无法解析显示名的会话显式降级为 id 展示（P0 实测 2/17）。
- **watch 持锁修正（P2，评审 v4 简化）**：现有 CLI watch 全程持有跨进程互斥（含轮询间隔），堵死"监控 + AI 回复"场景。**v1 最小修正 = 按轮获取/释放既有互斥**（轮询间隔不持锁），**CLI 与 MCP 轮询路径的锁入口一并核对对齐**（MCP handler 外层也有统一互斥，只改 CLI 会造成锁策略不一致）。"DB 读取绕过 UI 锁"**延后**：共享状态（水位/密钥/模式文件）的多进程读改写需要串行协调，原子替换只防半截文件不防覆盖；确有需要再专项定义，不提前建读写锁/多采集器/复杂调度。集成验证：**watch 运行期间能完成一次 send**。
- 轮询形态：v1 关注会话适度频率轮询；独立采集进程为后续可选优化（§11）。

### 4.3 message-send 本地库核验（评审 v3 修订）

- **时间基准（已实测冻结）**：库内 `send_time` 为**秒级**（P0 实测 1.7e9 量级）；核验采用**发送前基线**：记录当前 message_id 水位，发送后出现匹配的新记录（更大 message_id）即命中——规避秒级精度与迟到回退问题，不做同文本并发关联机制。
- **核验依据**：基线之后的新记录 ∧ 方向=本人（sender_id 比对）∧ conversation_id 匹配 ∧ **可信正文**（parse_trusted=true）全等。
- **核验语义（2026-11-05 修订）**：**message_table 无发送状态字段**（flag 为与方向无关的位标志；`send_failed_unnotified` 表存在但恒空）——本地记录只能证明"客户端已记录该出站消息"，非服务端回执。本地库基线可用时仅唯一可信正文匹配 → success/applied + `data.verification='local-record'`；未命中、歧义或核验失败 → `EXECUTION_UNKNOWN`，不能用气泡前缀覆盖数据库不匹配。无本地库基线的旧路径沿原 UI/OCR 结果。**success/applied 不代表对方已收到/已读**。
- **接线**：PS 发送驱动**发送动作与核验分离**。TS 编排在本地库路径发送完成后只读核验，未确认保留原凭据供 `send-status` 再查，不重入发送阶段；无本地库基线的旧路径仍沿原驱动内 OCR 核验。超时/取消后不得重入发送阶段，未知效果不自动重发。
- **后续结构化 @ 核验边界**：当前 `send-messages` 将 mention 片段标为不可信，纯文本 receipt v1 继续全文精确匹配。增加真正的 @ 发送时，发送参数与新凭据须携带被提及成员的稳定 ID；本地库解析完整的正文片段与 mention ID 后，逐段核对，允许显示名和已证实的格式变化，不用整体文字相似度猜测另一条消息。新匹配规则只用于新凭据，不能把历史 `unknown` 重新解释为 `confirmed`。
- 图片/文件消息 v1 不做库内核验，直接走 OCR 气泡核验。

### 4.3.1 不确定发送的只读对账（2026-10-26，W4）

- 每次核验重新确认账号、本人映射、源库fileIdentity和schema；基线包含原行legacy anchor。严格校验目标会话、基线后ID、本人sender、可信全文全等。按50条分页，单快照最多20页，达到上限明确unknown；只有完整扫描中的唯一匹配可确认，多个匹配unknown。结果仅含页数、行数、不可信数及原因枚举，不记录消息原文。

- 在已有每阶段`send-*`证据目录保存不可覆盖的`send-receipt.dpapi`，复用DPAPI CurrentUser；账号、会话、基线/锚、源代际、文本和时间窗仅在密文中。文件写入、flush、close成功且进度事件发出receipt ID后才调用发送驱动；open(wx)成功后write/flush/close被捕获失败由保存函数清理自己创建的文件，open碰撞不删既有文件，自清失败的unknown/receipt ID/失效失败诊断穿透派发前错误包装；凭据写失败则明确未派发。导航重入阶段各有凭据，最终结果/错误附最后阶段ID。无需增加全局ledger、恢复队列、计时器或Runtime outbox。已知未派发（checkpoint取消/进度失败）、navigate_required或发送驱动明确写前拒绝时立即删除本阶段凭据，删除成功才允许继续导航；第二阶段保存前清掉旧ID。失效删除失败立即停止并返回unknown及receipt_invalidation_failed，不能称已退役；timeout、驱动内取消及unknown保留凭据。只读对账返回confirmed前再检查原凭据存在，避免用已失效的内存副本误确认。
- `send-status --receipt-id <ID>`为CLI只读恢复入口，共用相同核验代码，不调用UI/OCR、搜索/切群或发送。未观察到、歧义、上限、账号/代际/锚失效、凭据丢失/损坏/不可解密均不推断未发送、不自动重发；可稍后再次只读对账。已确认只代表客户端记录，不代表服务端送达/已读。本地库路径不再调用 `VerifyOnly` OCR 兜底。

### 4.3.3 配置智能体持续群聊接线（2026-10-26）

## 5. doctor 深检（首跑定基调）

现有 `doctor` 只读门禁检查保留，新增 local-db 深检段（`--localdb` 显式触发；state 缺失时 CLI 建议运行）。**doctor 同时报告两个独立就绪块**（本地库就绪 / UI 就绪，§2）：

```
引导阶段（不产出模式，保持/重置 unset）：
1. 安装检测（运行进程/exe 路径/版本）→ 未安装：安装引导，终态
2. 登录态（进程 + 轻量登录探测原语）  → 未登录：登录引导（need_login 复用 probe 二维码），终态
深检阶段（必产出模式）：
3. 数据目录定位（账号↔目录交叉核验） → 失败：目录未生成/日志暂缺等 → ui(kind=transient)；版本路径模式不符 → ui(kind=compat)
4. 版本 vs 矩阵（以运行进程 executable 为准）→ unknown/broken：ui(kind=compat) + 原因
5. 指纹预检                          → 失败：ui(kind=compat) + 原因
6. 密钥步骤：先核验复用已有密钥（页 1 先知），无效/缺失才试扫
                                     → 失败：ui(kind=transient)（可自愈，§2 状态表）
   （keyscan 是全链路唯一接触进程内存的步骤：只读观察，无注入/无写/无提权，分钟级带进度）
7. 可信快照 + 整库解密 + PRAGMA integrity_check   → 失败：ui(kind=transient)
   （页 1 先知只是密钥快速验证机制；冒烟验证范围 = 整库 integrity + 查询计数）
8. 查询冒烟（conversations 计数）                 → 失败：已确认 schema 不支持 → ui(kind=compat)；其他 → ui(kind=transient)
   （分类依据是错误事实而非步骤编号，评审 v4）
→ 全过 → mode=db（密钥入 DPAPI 存储）；任一深检不过 → ui + kind + 原因。
  结论写 localdb-state.json + mode_decided 日志。
```

语义统一说明：引导阶段（1-2）不产出模式（保持/重置为 unset），深检阶段（3-8）**每次必产出 db/ui 之一**；kind 按具体错误事实分类（§2 原则），上表步骤仅列**典型归类**——同一一步骤可能因原因不同落不同 kind（评审 v5：目录暂缺=transient 但路径模式不符=compat；查询冒烟的 schema 不符=compat 但环境错误=transient）。瞬时类经负缓存到期运行时单次探测自愈（§2 状态转移表）或重跑 doctor。**登录状态以轻量登录探测原语判定**（从 probe 抽取登录判定核心，不带交互桌面会话门禁，避免把 UI 门禁带回本地库路径）；账号身份、当前登录状态、密钥有效性是三个独立判断（§3.4），不能互相代替。

## 6. 新版本接入 runbook（维护者工作流）

版本升级信号（运行进程 exe 版本 / 安装目录新版本子目录 / WXWorkUpgrader 活动）→ 维护者流程：

1. 跑 doctor 深检 / validate：静态指纹（不碰进程）→ 常量指纹（exe 内 sAlT/LCG）→ 动态冒烟（keyscan → 可信快照 → integrity_check）。
2. 静态指纹不符或动态冒烟失败 → 走 REA 逆向流程。实验包 `EVIDENCE.md` + `iterations/` 踩坑决策树是标准操作手册。
3. 产出：新算法/扫描策略实现 + **独立来源固定测试向量** + 矩阵条目。
4. 真机冒烟通过 → 条目置 `validated` 随代码提交发布。

小版本未登记表示尚未复核，不等于已证明不兼容。维护者先只读比对结构指纹，再以既有方案的精确版本候选执行上述动态验证；算法未变时只新增该版本条目，不复制实现、不对相邻未知版本通配放行。2026-10-27 的 5.0.13.6005 复核记录见开发计划 P6。

### 6.1 显式外部联系人约束（2026-10-27）

`@微信`后缀及已签名contact ref的`微信联系人`副标题是调用方约束，须保留到本地resolve，不再先剥后缀而混入内部同名人。共享native resolve的`--external-only`在当前账号快照中核对本人corp、候选corp和外部关系表；只排除明确内部同名人，不以无会话/关系缺失代替内部证据。未知/矛盾元数据明确失败，多外部同名继续拒绝，未指定约束保持原行为；外部关系只证明外部，不能泛称识别了所有微信用户类型。

## 7. 测试与清理（评审 v2 新增）

**测试**：
- **独立来源固定测试向量**：加密/解密自往返只能证明实现自洽，不足以证明兼容——按 sqlite3mc `cipher_wxaes128.c` 参考实现独立生成固定向量（密钥/页号/明文 → 密文字节）入库为 fixture，C7 解密必须消费独立向量而非仅自往返。
- 场景覆盖：WAL 损坏（坏帧/reset/截断/未提交尾帧）、迟到同步、同名目标消歧、账号切换、取消（AbortSignal 中断扫描/复制的清理）。
- protobuf：严格解析失败后递归找出的可解码字符串**不能无条件视为正文**——标 `trusted=false`；发送核验仅使用可信正文；读取结果保留该标注。

**清理（评审 v3 修订）**：
- **只清理可确认无活动所有者的目录**：watch 持锁修正后多进程并存是常态，单纯按目录年龄删除可能误删另一调用的有效产物——目录内写 owner 标记（pid + 启动时间），清扫时校验进程存活，存活的跳过。
- finally 清理保留；补充**取消路径**（AbortSignal）的子进程退出与清理顺序（先终止 py 子进程再删目录）。
- 清理失败记日志并在结果 data 报告（cleanup_failed），内容限定必要信息（目录名/原因），不含消息内容或敏感路径。
- `logs/localdb.log` 设轮转/保留上限（大小分段），防长期 watch 逐轮日志无限增长。
- 明文产物目录遵循既有 artifact 权限规范（用户 profile 下、不对其他用户开放）。
- 密钥文件（DPAPI 后）损坏/不可解 → 视同失效，走重扫。

## 8. 安全与合规

- 仅支持本机当前登录账号自己的数据；唯一进程接触点是 keyscan 的只读内存观察（`OpenProcess(PROCESS_VM_READ)`，无注入/无写/无提权），doctor 文案明示该步骤。
- 原始库文件只复制不改；快照与解密产物用毕即删 + 遗留清扫（§7）；密钥仅 DPAPI 存储与进程内存/stdin 流转，不落日志、不进命令行参数、不进返回值（返回 only 消息内容与会话元数据）。
- redaction 层兜底：驱动输出与日志中的 32-hex 密钥样式串强制脱敏。

## 12. 本地库群列表与时间线查询（2026-10-22）

用户确认：直接查询 local-db，避开视觉搜索；历史取最近 N 条，再按发送时间从早到晚展示。

- `list-groups [--query <关键词>] [--limit N]` / `wecom_group_list`：从当前账号 session 库 `conversation_table` 列出本机已同步的 R: 群，包括无消息群；关键词为群名的字面子串（%/_ 不作通配符），过滤、按会话 ID 去重后按名称和 ID 稳定排序再限制数量。默认 100，返回 `{channel,groups:[{name,conversation_id}],count,has_more,scope}`；不宣称覆盖企业全部群或实时成员资格。
- `read-group --target-name <群名> [--limit N] [--from-time <时间>] [--to-time <时间>]` / `wecom_group_read`：群名精确匹配，仅在 R: 群内消歧，同名不同群明确 `TARGET_AMBIGUOUS`；默认最近 100 条。时间边界均包含，时间格式为带时区 RFC3339（秒精度），或 `YYYY-MM-DD HH:mm:ss`（固定 Asia/Shanghai，UTC+08:00）。范围内超过 limit 时取最近 N 条，`has_more=true` 明示截断；无匹配消息成功返回空数组。
- Python 新增独立 `query --task groups/history`。history 在 SQL 中按 `send_time DESC,message_id DESC` 选取 N+1 条，再输出升序；仅接纳有效非负整数秒时间，异常时间记录数量显式返回。输出保留 `sender_id/send_time` 和既有解析可信标记，非文本仍占位。现有 `messages` 水位游标和 watch 语义不变。
- 2026-10-22 真机结构证据（5.0.12.6018）：`session.conversation_table` 使用 `con_numeric_id INTEGER` 与 `id TEXT`，名称为 `name TEXT`；`id` 同时含 R:/S:/Y: 及其他系统会话前缀。旧实现只认 `conversation_id/conv_id`，全样本前缀推断会因系统条目失败；新增已实证的 `id TEXT` 候选，原显式列名优先，不用数值内部ID替代会话ID。未知 schema 仍拒绝；本次只登记结构与形态统计，不登记实际账号、群ID或聊天内容。
- 两个 operation 复用 `admitLocaldbVersion/prepareDecryptedDbs`、当前主窗口账号直接证据及本人 user_table 映射；返回前复核账号/PID/目录及源库文件身份，失败不回退 UI。查询结束/取消/异常均清理解密产物，清理失败显式返回。
- 本批唯一写入者为本任务主控（Python 驱动及其测试委托开发角色）；仅增加 Provider 工具，不修改 Runtime core、Device API、binding、授权或共同 wire。既有 OperationResult 和 manifest major 不变，工具列表及 schema_digest 由 toolDefs 同源推导，旧工具输入和语义保持兼容；本地 MCP 生产/消费联调验证新工具发现与调用。

验收：字面关键词、limit、空群/同名群/缺失 schema、迟到入库和同秒消息、时间边界/非法时间、账号变化/取消/清理、CLI/MCP 注册一致性；真机查询指定群“新劳务云系统项目沟通群”最近 100 条及时间范围，正文仅在本机受忽略的验收目录保存，不写入日志或提交。

### 12.1 群消息用户名与提及恢复（2026-10-22）

用户以三张截图要求补齐发言人用户名、`@成员`、`@所有人`，包括带引用前文的回复。复用P4群历史通道，不扩展图片/附件内容解析。

结构实证（5.0.12.6018）：type=2 的根字段1可重复，每项是按顺序排列的片段；片段字段1为varint类型，字段2为负载。类型0负载的字段1是UTF-8文字；类型5负载字段1为uint64用户ID，字段2为显示名，ID=0代表所有人。真机本批5条content_type=0也使用相同有序片段，其中1条含提及；history对type0先识别原顶层单字段UTF-8包装，再处理有序片段，两种已知格式兼容。截图中的引用是普通文字片段（引用作者/文字及分隔线），没有独立可信身份字段；按原文保留，不从引用文字猜测作者ID，也不把引用文字内的字面@当结构化提及。旧“递归取最深最长字符串”会丢兄弟片段，需在history专用解析中替代。

- history新增完整varint/wire解析，按片段原序拼接文字和`@显示名`；同一消息多次提及原样保留。缺字段/未知类型/损坏UTF-8或protobuf明确`trusted=false`，已识别片段可保留并标示缺口；不静默挑一段冒充完整正文。未知片段用占位表示，`mentions_complete=false`；识别状态独立保存，不以占位文案判断，合法正文即使与占位文案同文也不能被重复或丢失。
- history输出新增`sender_name: string|null`、`sender_name_source: user_table|unresolved`及`mentions:[{kind:user|all,user_id:string,name:string|null,name_source:message|user_table|unresolved}]`、`mentions_complete:boolean`。所有ID继续是字符串，ID=0以`kind=all`表达。提及优先保留消息内历史显示名，缺名时按ID补当前用户表姓名；找不到保留ID及未知提示，不能按同名反查身份。
- 发言人按`user_table.id`精确批量取`name`，只查询本批发言者/提及的ID；不枚举输出通讯录。缺失/空名/冲突不猜，`naming_incomplete=true`明示。群名片并非本批已确定来源，不擅自套用。人工输出与查看文件优先显示姓名，未解析姓名显示未知及ID；JSON始终保留原ID和解析可信标记。
- 仅改变`query history`投影及群读取适配；原`extract_content/_message_row/_message_anchor/query messages/watch`保持语义，避免历史展示增强使已持久化游标失效。新增输出字段属Provider兼容增量，旧输入/OperationResult/共同wire不变，MCP描述和同源digest随实现同步。

验收包括：纯文字、多段/多成员/所有人/仅提及、中文与emoji、同名不同ID、大uint64、缺名及冲突、引用前文加@和较短回复、未知/损坏片段、排序与时间范围保持；对照用户截图中的“是的@周亚清”“@周亚清 表名是这个：t_bank”“@段勇波 @邵昆”和“@所有人”逐项真机核对。真实载荷仅在受控解密快照内检查，清理和账号复核沿用P4，不把原始blob/凭据写入日志或文档。

## 13. 单聊与群聊的发言人平台识别（2026-10-27）

目标：让智能体直接知道每条消息由微信用户还是企业微信用户发送，从而按任务要求服务客户，同时保留同事发言作为上下文。平台识别属于CLI数据层；是否回复属于智能体的任务策略。开发安排见[计划P8](../../plans/plan-wecom-cli-localdb.md#p8-发言人平台识别)。

### 实施说明（2026-10-27）

当前实现已统一单聊、群聊和发送核验读取的sender_id/name/platform投影。按原sender_id关联同一快照user_table：已核实的微信虚拟corp映射wechat，本人当前企业映射wecom；缺资料或其他企业返回unknown，不凭external关系推断平台。真实来源核验覆盖官方微信单聊与内部成员；缺少外部企微真人样本，未对该类作肯定映射。群聊混合身份的业务逻辑由合成库验证，不替代真人混合群验收。没有新增平台拒发门禁，调用方依任务决定是否回复。

元数据补齐不改变原消息ID/正文/历史标记。batch的unknown_messages提供原消息精确recovery_cursor，Runner以原invocation私有offset和固定扫描位置接回；消息已滑出最近窗口仍可核验，不重新当新消息。来源缺失只影响该条，不停止其他已识别客户。版本及恢复证明见[共同契约2.11](../../system/runner-desktop-runtime-integration-contract.md)及[P8进度](../../plans/plan-wecom-cli-localdb.md#p8-发言人平台识别)。下方事实表保留为实施前基线。

### 13.1 实施前能力与实际缺口

| 路径 | 现有代码事实 | 缺口 |
|------|--------------|------|
| 单聊本地库read-session / watch | Python行有sender_id，TS的normalizeMessages仅保留self/peer等消息字段 | 归一结果丢失发送者ID，没有平台分类 |
| 群read-group / group-poll | 按sender_id补sender_name，保留结构化mentions | 姓名和提及可用，但没有微信/企微平台字段 |
| P7外部联系人消歧 | corp_id与external_user_relation_v3排除明确内部同名候选 | 只证明外部关系，不能区分微信与外部企业微信 |
| 显式微信单聊发送 | 当前原生标题的微信标识用于该目标发送核验 | 不等于所有群成员、每条群消息已获得平台身份 |

必须区分两个维度：`wechat / wecom`是账号平台；内部/外部是相对当前企业的关系。外部企业微信用户也属于外部联系人，不能统一标成微信。腾讯云官方[ExternalContact数据结构](https://main.qcloudimg.com/raw/document/product/pdf/1318_53205_cn.pdf)也分别描述这两种外部联系人类型；该服务端结构仅佐证概念，不能套作桌面本地库字段定义。

已知本地user_table、external_user_relation_v3及微信相关表存在，但尚未验证可直接关联消息sender_id的平台类型字段。字段名、空企业名、关系status/stranger_type及未解析PB片段都不能作为已证实的平台含义。原实验只有已核实的微信单聊与内部同名样本，不足以验证混合群和外部企微分类。本节是设计，不宣称原生类型映射已实现。

### 13.2 最小结果契约

沿用现有扁平消息结构，补齐以下字段；不再另建嵌套sender对象：

| 字段 | 语义 |
|------|------|
| sender_id: string \| null | 消息原始发送者稳定ID；单聊归一不再丢失，群沿用现有字段 |
| sender_name: string \| null | 按ID取得的显示名；群既有sender_name_source保持 |
| sender_platform: wechat \| wecom \| unknown | 微信、企业微信、当前数据不足；每条消息独立标注 |
| side: self \| peer | 原有自己/对方方向，含义不变；peer不等于微信用户 |

同一群内，微信客户为wechat，内部同事和其他公司的企微成员均为wecom。同名不同ID分别解析；群名称、引用作者、@对象不决定实际发送者平台。系统消息继续按原system/kind处理，不增加机器人等平台枚举。平台缺失只使该条unknown，不能让整批读取失败；缺姓名也不影响已有可靠平台结论。

### 13.3 识别来源与实现边界

1. 先用一个真实混合群的微信用户、本企业企微用户、外部企业企微用户核验本地元数据，找出平台类型及其与sender_id的确定关联。同平台单聊复用该映射。字段语义与ID关联均须有客户端原生身份对照，不能因两个旧样本恰好命中就冻结算法。
2. 优先复用既有只读快照查询，批量查询本次返回消息中的不同sender_id，并在TS公共归一处输出同一契约。仅内部明确身份可直接确定wecom；外部关系本身不足以确定平台。默认不逐条查询、不扫描全通讯录、不增加跨轮持久缓存。
3. 若本地库没有可靠类型，单独核验现有客户端原生联系人/成员资料能否按稳定ID补齐。只有身份对应明确时才可作为补充来源；群名片或名字中的字面“@微信”不算。此来源需额外设计确认后再实现，不把每轮切UI、OCR或点击成员变成DB轮询前置步骤。无法取得时返回unknown并说明覆盖范围，不能承诺全量准确。

首次实现不强制接入服务端API，不新增客户凭据、身份中心、数据库表、后台同步服务或置信度打分。服务端API若未来使用，需先解决与桌面sender_id的映射，不能直接混用不同ID域。

### 13.4 工具与智能体用法

用户后续已要求收敛为三个Agent业务工具，以[CLI主设计§12.5～12.7](wecom-cli-design.md#125-工具与状态的收敛选择)为准；下面group-poll/watch等表示内部能力复用及旧版本兼容，不要求它们继续各占一个Agent工具。

- 复用现有read-session、群历史、group-poll、watch的消息输出及相同身份解析函数；context_messages与new_messages都带平台。MCP与Runtime透传结果，云端工具说明明确平台值和unknown含义。unread-list仍是会话发现/待回复线索，不把整个混合群标成一个平台，也不把会话未回复判断当作客户身份。
- 智能体用正常读取工具取得全体发言。对“只回复来自微信用户”的任务，仅新的wechat发言触发客户回复；wecom发言保留为上下文，例如同事已经解答的问题。自己出站、系统消息和启动历史沿原处理规则，不因补平台字段而重放。
- unknown不能冒充客户；本轮可跳过该条自动回复，继续处理已识别客户，并对实际影响覆盖的缺口作一次说明。可能需要服务的未识别消息保留msg_id及处理结论于任务既有checkpoint，身份补齐后再判断，不静默视作已回复，也不另建身份待办服务。首次不新增必调的身份工具、每条确认弹窗或让整项任务暂停的身份门禁。
- 平台分类不等于发送许可。用户可明确要求回复企微成员；“被@是否必须回复”服从当前任务要求，不由CLI增加永久限制。默认读取不按平台删除消息，不新增wechat专用轮询工具或过滤参数。
- 既有目标定位、游标、设备绑定与发送对账继续复用；本字段只说明发言人平台，不解决正式Runner外部单聊增量/目标绑定等已记录缺口，也不替代这些工作。

### 13.5 共同接口检查点与验证范围

本节登记候选“消息发言人平台结果增量v1”；原OperationResult和共同wire envelope保持。生产端唯一事实来源为WeCom Provider的native查询与公共归一，MCP/Runtime/云端代理负责消费和透传，不各自按名字重新分类。实施前按[共同契约C12](../../system/runner-desktop-runtime-integration-contract.md)核对结果结构、工具描述与实际消费者，登记负责人及既有release/schema_digest更新；若实测需要改变共同schema，再同步版本和生产/消费实现，不为本次文档修订虚升协议版本。

兼容：旧消息结果缺sender_platform时，消费侧按unknown解释，不能默认为wecom或wechat；旧消费者可忽略新增字段。旧消息ID、解析、排序、水位和锚点算法不变，姓名/平台元数据的补齐不使原游标失效，不触发旧消息重新回复。身份只在当前账号的数据来源内关联，不建立跨账号全局姓名缓存。

验收只覆盖实际业务：混合群三类成员与同名不同ID、两种平台单聊、缺失成员资料时局部unknown、各消息通道结果一致及MCP/Runtime字段不丢失；再验证智能体只以微信新消息为回复触发且保留同事上下文。每轮批量取不同发送者，不增加每条UI操作；记录实际耗时，避免拖慢已有DB轮询。真实样本不足时明确标注未验收，不以构造夹具宣称完成真实平台识别。无需为此新增权限体系或穷举与本功能无关的故障组合。

## 14. 稳定会话发送的本地库准入（2026-11-06）

`wecom_message_send(session,text)` 先经本地库把 `session` 解析为当前账号的会话 ID。此后 doctor 动态状态缺失、处于 UI 兼容态或版本记录滞后时，仍沿与强制会话读取相同的进程版本矩阵和库指纹准入，建立该 ID 的发送前基线；准入并不跳过实际版本、账号及快照检查。发送前本地库不可用则明确报未发送，不降级到驱动内 OCR 成功判定。按 Enter 后仅用原加密凭据与本地出站记录对账，未知保持 unknown，绝不自动重发。旧 `target_ref` / `target_name` 入口保留原兼容分派。
