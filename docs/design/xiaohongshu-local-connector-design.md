# 小红书本机连接器设计

2026-11-16 · Windows 用户设备。关联 [连接中心](../system/connection-center-design.md) 与 [开发计划](../plans/plan-xiaohongshu-local-connector.md)。

## 使用流程

1. 员工在连接中心选择「小红书」，使用当前已配对并选定的 Runtime 设备。界面标出目标设备，扫码与打开动作均在该设备执行。
2. 点击「扫码登录」。插件以专用 Profile 打开有界面 Chrome，在小红书原网页显示官方二维码，等待用户用小红书 App 扫码。已登录时直接显示小红书首页。页面只回显结果和下一步，网页登录由用户完成。
3. 点击「打开小红书」。设备复用同一 Profile 访问小红书首页并核对网页登录状态。Chrome 或 Runtime 重启后，正常保留的 Profile 仍可使用。若网页明确要求登录，提示用户重新扫码。页面异常或未核实的状态分别报告。

本期范围是扫码、保存网页会话和带身份打开网页。线索、内容发布和客服分别按后续功能设计。连接按当前 AID 租户、用户和设备区分。换设备需要重新登录。

## 实现

- 复用已配对的 Runtime 及可信 MCP Provider 的包、能力上报、领取和结果回传。连接中心调用业务配置 API，经现有 LocalInvocationService 下发固定动作。打开任务无需建立聊天、调用模型或设置公开代理工具。服务端从认证用户和所选设备计算 Profile 键，不接收浏览器路径、URL 或客户可指定的 Profile 键。
- Provider 通过 Playwright 与本机已安装的 Chrome 建立有界面上下文。每个 Profile 对应用户目录中独立路径，由 SHA-256 索引，连接器只使用自己的目录。它保持自己的窗口供扫码和浏览，经 Runtime 管理，既可复用已有窗口，也可在再次启动时从 Profile 恢复，不接管日常 Chrome。浏览器启动前遇到已有归属未明的 Profile 占用，报告占用并请用户关闭对应窗口。
- 扫码只操作小红书首页可见的登录入口，使用官网 `.login-modal .qrcode-img` 的显示与加载结果判断二维码已出现。打开动作以固定的 HTTPS 小红书首页为目标。小红书网页的公开导航组件在认证分支渲染 `li.user.side-bar-component` 下的个人页链接，设备用该可见入口确认登录状态。
- 二维码直接由小红书网页渲染。云端只保存固定业务动作、匿名 Profile 键和状态回执。Chrome 自身管理 Profile 的浏览数据和登录 Cookie。页面不得返回二维码、Cookie、浏览器地址或站点存储。扫码前退出窗口或遇站点异常时，可以从原入口重试。

2026-11-16 探测：Windows 有界面 Chrome 使用全新临时上下文打开首页，发现可见的 `.login-modal` 与 `img.qrcode-img`。WSL2 Docker 无头 Chromium 访问首页返回 200，未发现可点击的登录入口或二维码。同一开发镜像临时加 Xvfb、以有界面模式运行 Chromium 后可以看到二维码。上述探测均未扫码。用户决定采用本机 Chrome，按设备与 AID 身份隔离会话。
