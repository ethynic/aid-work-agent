# 小红书本机连接器设计

2026-11-16 · Windows 用户设备。关联 [连接中心](../system/connection-center-design.md) 与 [开发计划](../plans/plan-xiaohongshu-local-connector.md)。

## 使用流程

1. 员工在连接中心选择「小红书」，使用当前已配对并选定的 Runtime 设备。界面标出目标设备，扫码与打开动作均在该设备执行。
2. 点击「扫码登录」。插件以专用 Profile 打开有界面 Chrome，在小红书原网页显示官方二维码，等待用户用小红书 App 扫码。已登录时直接显示小红书首页。页面只回显结果和下一步，网页登录由用户完成。
3. 点击「打开小红书」。设备复用同一 Profile 访问小红书首页并核对网页登录状态。Chrome 或 Runtime 重启后，正常保留的 Profile 仍可使用。若网页明确要求登录，提示用户重新扫码。页面异常或未核实的状态分别报告。

本期范围是扫码、保存网页会话和带身份打开网页。线索、内容发布和客服分别按后续功能设计。连接按当前 AID 租户、用户和设备区分。换设备需要重新登录。

## 实现

- 复用已配对的 Runtime 及可信 MCP Provider 的包、能力上报、领取和结果回传。连接中心调用业务配置 API，经现有 LocalInvocationService 下发固定动作。打开任务无需建立聊天、调用模型或设置公开代理工具。服务端从认证用户和所选设备计算 Profile 键，不接收浏览器路径、URL 或客户可指定的 Profile 键。
- Provider 通过 Playwright 与本机已安装的 Chrome 建立有界面上下文。每个 Profile 对应用户目录中独立路径，由 SHA-256 索引，连接器只使用自己的目录。它保持自己的窗口供扫码和浏览，经 Runtime 管理，既可复用已有窗口，也可在再次启动时从 Profile 恢复，不接管日常 Chrome。浏览器启动前遇到已有归属未明的 Profile 占用，报告占用并请用户关闭对应窗口。
- 扫码只操作小红书首页可见的登录入口，使用官网 `.login-modal .qrcode-img` 的显示与加载结果判断二维码已出现。打开动作以固定的 HTTPS 小红书首页为目标。小红书网页的公开导航组件在认证分支渲染 `li.user.side-bar-component` 下的个人页链接，设备用该可见入口确认登录状态。
- 二维码直接由小红书网页渲染。云端只保存固定业务动作、匿名 Profile 键和状态回执。Chrome 自身管理 Profile 的浏览数据和登录 Cookie。页面不得返回二维码、Cookie、浏览器地址或站点存储。扫码前退出窗口或遇站点异常时，可以从原入口重试。

2026-11-16 探测：Windows 有界面 Chrome 使用全新临时上下文打开首页，发现可见的 `.login-modal` 与 `img.qrcode-img`。WSL2 Docker 无头 Chromium 访问首页返回 200，未发现可点击的登录入口或二维码。同一开发镜像临时加 Xvfb、以有界面模式运行 Chromium 后可以看到二维码。上述探测均未扫码。用户决定采用本机 Chrome，按设备与 AID 身份隔离会话。

## 指定主页线索与首条私信

2026-11-19 · 来源账号是待浏览的公开主页。操作者使用连接中心已登录的专用 Chrome，按主页 URL 逐个读取。网页截图仅用于解释交互。真实页面用隔离登录态核实了账号主页的笔记卡片、图文/视频共用的评论区域、评论者头像链接，以及主页「发消息」弹出的同源会话页。

| 插件动作 | 输入与输出 |
| --- | --- |
| `xiaohongshu_list_notes` | 主页链接、数量上限 → 笔记 ID、规范 URL、标题及页面显示的点赞数 |
| `xiaohongshu_list_comments` | 来源主页链接、笔记 ID、数量上限 → 可见文本评论、评论 ID、评论者昵称和规范主页 URL，以及是否完整 |
| `xiaohongshu_open_conversation` | 评论者主页链接 → 打开原生私信会话，核对对方稳定 ID；回传昵称、页面显示的小红书号和会话是否可编辑 |
| `xiaohongshu_send_first_message` | 评论者主页链接、确定正文和来源 → 仅在确认为目标首条且页面允许时发送一次，记录实际发送账号、收件人、来源笔记和评论、正文、联系理由、时间和结果 |

浏览、字段抽取、判定网页是否可操作、私信和本机发送事实由小红书 CLI 实现。待浏览账号清单、客户定义、按哪些评论判为线索、消息措辞和成果汇总属于任务编排层。线索依据取评论明示的需求，与产品及客户画像对照。网页内容仅作数据。首条发送完成后停在原生会话供人工接手。

只读抓取有界滚动，支持已展开的回复并准确标识截断。保留规范 HTTPS 小红书 URL 作为来源标识。示例笔记的规范链接直接打开会跳到 404，复核时用来源主页与笔记 ID，通过主页内的笔记卡片重开。带站点导航令牌的链接只在受管浏览器中使用，Cookie 留在本机。无有效登录、验证码和页面形态不可确认分别报告。私信采用网页实际限制，以稳定收件人标识核对目标。若会话已有沟通、网页阻止、账号不符或无法确认会话与结果，交人工。首次点击前按已登录账号及收件人持久化单次发送预留。调用方传入已核对的发送账号 ID。发送动作使用网页原生快捷键。只有当前会话对应的己方消息正文匹配，且页面收到服务端确认后渲染出正数存储编号，才记已发送。只有本地临时编号、失联或回执不明确均记待人工核对，禁止重试自动发送。本机发送记录保存在当前 Windows 用户的 `%LOCALAPPDATA%/AidWork/Xiaohongshu/FirstMessages`。结构化回执区分未发、已发送、待人工核对，并注明已确认发送但本机终态记录未能确认的情况。真实写入验收需要指定可控收件账号。

小红书官方要求使用合规获客工具并禁止使用自动化脚本进行违规营销或规避监管。用户提到的陌生人窗口按实际页面提示处理，不以固定文案、次数或切换账号绕过限制。见[聚光专业号合规说明](https://ad.xiaohongshu.com/next_help/docs/cfa457375a0dffd3bd04453f42b9731e)。

### 爱定义科技线索筛选配置（初稿）

依据用户提供的《爱定义科技 · 企业级 AI 智能体 V5（2026）》PDF 第 1、7、9、13–27 页。爱定义科技提供企业级 AI 员工与定制落地，能结合企业数据、既有系统、SOP 和文档模板执行重复流程，提供公有云按使用计费和私有化部署两种合作方式。以下筛选规则放在社媒智能体业务配置，供首轮试跑校准。

| 判定 | 评论证据 | 示例 |
| --- | --- | --- |
| 明确线索 | 评论表达企业或团队的具体工作痛点或项目，能对应产品能力，并明确询问方案、接入、部署、报价或希望交流 | 「我们有几家门店，客服每天重复回答报价，能接企业微信和公司的产品资料吗？」 |
| 人工复核 | 有可能对应产品的业务问题，但使用主体、需求或联系意愿不明确 | 「想让 AI 自动整理每周经营报表，有什么方案？」 |
| 跳过 | 通用工具使用、个人学习、求提示词、泛赞同、求职或同行推广，缺乏企业应用意图 | 「怎么设置 Pro？」 |

首批优先覆盖客服销售、内部知识问答、办公和报表流程、企业系统集成、私有化部署。招聘、采购、法务、生产等场景在留言有具体业务证据时也可命中。每条候选保留评论证据、对应企业场景和判断理由。同一评论者多次出现时合并证据并保持一个首联候选。报价、效果数字和联系方式不自动写入首条私信。首句围绕对方明确提到的工作场景，询问一个相关问题，后续由人工承接。
