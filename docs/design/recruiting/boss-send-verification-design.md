## 3. 验证原则与状态

各操作拥有自己的确定性 verifier；本期不先建通用插件框架。共同约定：目标绑定、动作前基线、动作后证据、观察范围、失败原因、证据级别。LLM 使用证据解释结果，不以自由推理改写执行终态。

1. 点击进入可能提交阶段前标记 `may_have_started`（在点击调用之前，避免点击已生效但调用抛错）。没有调用发送且能证明未提交：effect=none；输入草稿变化单独说明。
2. 可能提交后，只有符合本操作完整后置条件才返回 applied。断连、取消、超时、解析异常、会话漂移均为 unknown，不自动重发。
3. UI 气泡出现只证明客户端可见效果；未经平台状态证据验证不得说“对方已收到/已读”。识别不到失败标记不等于已证明没有失败，状态解析须有受支持且真机验证的结构。
4. 批量 greet 已完成项加当前 unknown 项分别保留，停止余下写操作，不把整批折算成全部成功/失败。

## 4. send 详细方案（替代前案 S1）

### 4.1 观察模型与发送前条件

抽取共享消息解析，读取工具复用，但发送验证使用更严格的结果：`readable / reason / container_count / target / messages / coverage / editor_state`。缺主文档、父链、属性、唯一容器或目标身份时，不返回“可读空列表”。class 按 token 匹配；一条气泡按容器聚合正文，保留原文，不用 trim/字符覆盖率作为真发送全等证据。

目标须绑定当前设备/页面会话及可验证候选人上下文；姓名只能是显示线索。send_to 对照打开结果，send_current 冻结入口会话，输入后和每轮观察复验。稳定候选人 ID 是否可从当前 DOM 取得待只读取证；无法区分同名或会话切换时阻断。这里不实现独立 resolve-probe 命令，但不能因此省略本次动作的目标核验。

发送前定位唯一编辑器，限定该子树读取 contenteditable 碎片或 input 值；有既存草稿时停止并说明，不盲目追加或清空。输入后确认正文按已验证的渲染规则一致，再紧邻点击采集消息尾部基线。换行、连续空格、emoji、零宽字符按真机样本建立明确规则；不支持时在点击前拒绝，不静默规范化用户正文。dry-run 暂不改变现有行为，但只能声称输入探测，不能充当真发送门禁。

**正文比较口径**：保留用户原文和解析原文；比较使用有版本的、基于样本验证的表示转换，不要求不同 DOM 表示逐字节相同。可验证后统一 CRLF/LF、将明确的 BR 节点还原为换行；不得全局 trim、折叠空格、删除零宽字符或做未经验证的 Unicode 归一。必须取证：首尾空格、连续空格、空行/多行、普通 emoji、带 ZWJ 的组合 emoji、零宽字符，以及 DOM 分片/实体表示。每类记录“输入原文→编辑器解析→气泡解析→比较规则→支持/不支持”；加反例证明有业务差异的两段正文不会被合并判等。既有历史样本可只读分析，缺少的输入/发送样本须在授权测试中补齐，不能称为只读取证完成。

### 4.2 什么算“本次新消息”

`afterCount > beforeCount` 和 `identical_bubbles_before` 仅作辅助信息。历史懒加载可增加数量、虚拟化可减少数量、DOM 重建可重编号，均不能单独证明本次新增。

优先采用真机确认稳定的消息 ID/服务端状态关联。若无稳定 ID，可仅在已验证的连续尾部视图内，利用有序尾部锚点、同一目标、正文全等、me 方向和本次点击后的新增位置联合确认；重复锚点、历史插入、虚拟化重排、基线丢失、手工并发发送导致无法归因时 unknown。不得把 DOM nodeIndex 当跨快照 ID，也不得向正文添加追踪字符。

成功还须满足：新增气泡无发送中/失败状态，编辑器恢复为空，支持的状态结构可识别。缺一项则继续观察或 unknown。即便通过也只声称“已在 BOSS 客户端核实发送”，不声称接收方送达。若真机不能提供可靠状态或归因证据，本方案不能宣称达到 §11.6 门禁，应记录缺口再讨论，不用计数方案降级冒充验证成功。

**预定分支，避免取证失败后无路可走**：

取证首先判断是否有发送中/失败或其他可靠提交确认信号，以及乐观气泡后失败如何体现；只有 `status-read`/已读结构，不能据此推断未读气泡的提交状态。未在样本中看到失败标记属于证据缺口，不等于平台无失败状态。若既不能识别失败/待发送，也无替代可靠证据排除乐观渲染的不确定性，则进入 C；反复观察同一气泡或延长等待不能单独将 C 升为 B。

- A：有可靠消息 ID 和状态，使用强关联路径。
- B：没有稳定消息 ID，但尾部关联及 UI 状态结构可验证，使用本节联合证据，`scope=client_ui`。这已经是允许的实现路径，不要求证明服务端送达；与 A 使用相同验收门禁。
- C：连本次新增归因或 UI 状态都无法可靠判断，只记录 `verdict=inconclusive` 和实际观察，保留 unknown，不自动重发。可先完成解析、阶段处理、证据透传与提示词修正，但发送自动确认不得发布或宣称修好；不回退旧 strings 判成功。若要进一步降低成功证据标准，须另行明确改变产品语义，不能靠提示词兜底绕过。

取证与开发可并行准备：现有脱敏快照/fixture 足以开展解析接口、异常阶段和透传契约测试；特定页面选择器及成功判定的定稿依赖真机证据。

### 4.3 有界轮询与异常

建议首延 500ms、间隔 800ms、单调时钟总预算 8s，参数待真机校准。总预算包含 snapshot 耗时；每次采集使用剩余预算，取消/超时后停止发起新观察，处理晚到结果，不重入写操作。复用既有桌面锁覆盖定位、输入、点击和验证，不在每轮释放锁；桌面锁不能排除人工干预，发现目标/页面漂移立即 unknown。

未知原因明确区分：`baseline_unreadable / target_changed / history_unstable / pending / failure_marker / editor_not_empty / observation_timeout / transport_lost / cancelled_after_submit`。输入状态为 `empty / nonempty / unreadable`，不能用碎片“没找到”冒充 empty；文案描述观察事实，不推断“更可能未发出”后引导重发。

## 5. 重复消息与只读自查（修正 S2/S4）

不按相同正文硬拦截正常业务消息。可返回 `identical_bubbles_before`，但它表示当前观察范围内历史同文数量，不代表全量历史，也不是幂等键。不要声称用户已明确批准前案中的所有产品取舍；本条为待讨论的设计建议。

提示词拟修改为：

> effect=unknown 时禁止自动重试该写动作。先进行有界只读核对，使用 boss_read_chat 检查目标和消息；只有能与本次动作关联、且具备有效成功状态的新消息证据，才能说明已核实。仅看到历史同文消息、没有看到目标消息、读取失败或覆盖不全，都维持未知。必要时可用 boss_open_chat 进行既有授权内的会话导航，但它有界面点击和潜在草稿风险，不是纯 snapshot 读取；目标不唯一或导航会影响草稿时停止。仍无法核实时请用户核对，不自动补发。无论是否读回，均不得声称对方已收到或已读，除非有相应证据。

建议最多两次读回，总观察预算 10s（含已有工具调用截止）；无法安全取消工具时不得叠加调用。当前 read_chat 只有姓名、正文、粗粒度时间和 read，未提供完整归因证据，因此第一批提示词不能单独靠“最后一条相同”把 unknown 升为成功。后续如补读回证据，需明确关联原 invocation；只读工具成功不等于原发送账本成功，不直接篡改原终态。账本核销另行设计。

第一批的正常场景可用性主要由 verifier 保证，不把提示词读回当作降低 unknown 的承诺。第二批增加恢复关联可行性评估：read_chat 的 invocation_id 标识的是本次读取，不是原发送，更不是 BOSS 消息 ID。需要显式关联 `source_send_invocation_id`、同租户/设备/目标、原发送基线和写入时间窗，以及新增消息/状态证据；仅时间相邻或正文相同只能辅助诊断。先评估证据可用性和结果保存路径，再决定是否实施自动核对，不以弱关联直接改变原发送终态。

## 6. greet 第二批方案（替代 S3）

同一目标卡片从“打招呼”变为“继续沟通”作为候选后置条件，须绑定目标身份和原卡片上下文，并确认前后变化；位置容差只辅助匹配，不单独判成功。原按钮消失、列表总数减少、同名卡片或邻近已有“继续沟通”均不足。卡片消失/重排无法归属时 unknown；不继续点击下一人。付费墙/确认弹层与部分完成明细保留；采用同样的有界观察与提交后异常规则。需覆盖定向和非定向路径，不能保留另一条不可靠成功捷径。

## 7. 证据契约与接线范围

保持 MCP 输入 schema 不变，新增输出 `data.verification`，建议包含：`version / method / verdict / scope=client_ui / reason / target_match / baseline_readable / bubble_before / bubble_after / new_message_evidence / editor_state / message_state / elapsed_ms / identical_bubbles_before / phase`。缺失字段不推断为通过；target_match 只在有实际身份证据时为真。未知/失败同样携带已取得证据，不存整页 DOM、凭据或不必要的聊天原文；审计引用遵守现有租户权限及脱敏规范。

必须同时修改 executor 成功/结构化异常、send_to、send_current 的 data 构造及公共 catch 白名单传递。提交后结构化异常显式映射 EXECUTION_UNKNOWN、effect=unknown、retryable=false，不靠中文关键字；隔离其他工具的取消语义，避免全局改动。成功已取得后不因随后取消改成 none。

服务端目前 data 通用透传，目标是不改服务端业务代码；须做 executor→operation→runtime→数据库 result_json→proxy 的端到端契约验证，覆盖成功/未知/取消/断连/迟到回执。若存在证据过滤或状态改写再按证据扩展范围，不能预先保证“服务端零改动”。v1 证据不能冒充自动任务 v2 的完整验证凭证。

## 8. 测试与发布门禁

离线 fixture 必须验证错误成功判定被拒绝：旧同文/预览文本/历史加载增量/等数量虚拟化替换/多容器/同名切会话/邻卡换位/乐观气泡后失败/编辑器残留/状态不可读/重复正文/多行空格 emoji/跨快照节点重编号/人工并发。正向覆盖稳定新消息与延迟落地。注入点击已生效但抛错、采集挂起、截止前后取消、回传丢失，断言不重发且 effect 不变为 none；时钟可注入，不靠真实 sleep。

独立测试与 CodeReview 在实施时按项目 dev-workflow 执行；本轮仅文档审核不触发三智能体开发流程。不预填“修改两个测试”或固定绿测数量，按真实 fixture 清单及意图区分补测。保留 read_chat 回归、两发送入口证据透传、其他写工具公共异常路径兼容和启动/typecheck 必要检查。

真机门禁：仅用另行明确授权的 BOSS 测试对象；本轮 SSH 日志核对授权不包含试发。同文连续发送、长会话历史加载/虚拟化、失败与恢复、超时/点击后崩溃、断网、同名/切会话、多行与输入状态均须核实。先记录可采集稳定身份、消息状态及新增关联证据的可行性，再开发具体选择器；门禁不通过不得宣称 P0′ 完成。灰度保留停用路径，不能以回退旧 naive 校验作为可靠发送降级。

### 8.1 可用性与正确性量化验收

固定客户端版本和预先登记的用例集，在明确授权的测试账号/会话上至少进行 20 次正常发送，send_to 与 send_current 各不少于 10 次，至少两轮独立运行。覆盖普通文本、连续相同正文、长会话已稳定尾部及已声明支持的正文类型。测试对象授权未给定时不执行发送。

- 正常集直接由 verifier 返回 applied 的比例 ≥95%；其余 ≤5% 必须逐例解释，未知算未通过单例，不得以事后人工确认计入 applied。发送前拒绝也计未通过，不通过缩小分母提高比率。20 次最多允许 1 次非 applied。
- 正常集需要用户人工核对的比例 ≤5%，单列 verifier unknown、前置拒绝、读回和人工介入数量；这衡量主诉是否改善。
- 所有 applied 必须经测试人员/独立证据核实目标、正文及客户端发送状态，错误 applied 为 0；自动重复发送为 0。不能以 verifier 自报充当真值。
- 单次写后验证耗时不超过配置的 8s 预算（含采集）；超时返回 unknown，迟到观察不重启写动作。两发送入口分别报告比例与耗时，不能合并掩盖一条路径退化。
- 故障集独立于正常集，不计入上述分母；所有预定故障/歧义用例均须符合阶段与证据预期，可能提交且证据不足者必须 unknown、不重试。故障若在预算内恢复且取得完整证据，可以 applied，不能笼统要求所有故障必然 unknown。

“正常 applied≥95%”允许少量 unknown，与“unknown 只允许故障场景”并不等价，本设计采用前者，不同时写互相矛盾的标准。每次非 applied 都要定位，无合理说明或存在确定性误判缺陷则阻止发布，即便总比例合格。20 次是最小工程验收样本，不是生产成功率 ≥95% 的统计证明。发布后在首个累计 100 次受支持正常调用窗口复核，再滚动监控；不足 100 次如实标注样本不足。任一错误 applied/自动重发立即停止扩大发布，正常非 applied 超过 5% 暂停扩量并排查，保留全部异常，不事后挑样本。

### 8.2 环境与动作边界

已登录的调试 Chrome 所在设备、连接入口和可观察会话是实际所需信息；有既有授权且可访问时，纯 snapshot 观察无需机械再要一次权限。只有 SSH 查服务器日志不能推定已具备访问任意桌面的范围和入口。缺少环境时先登记具体缺项，继续不依赖真机的工作；本轮文档评审无需用户现在提供环境。输入、切会话、滚动和发送要分别标注，不能统称只读；真实试发需明确测试对象、文案及次数范围，现有充分授权应复用。

授权适用范围由主控在真机操作前统一核对，在开发计划登记环境、允许动作、授权来源、核对人和日期；执行者按清单操作。主控核对不新增用户审批门槛，已有明确授权直接沿用，仅缺失/歧义部分向用户询问。当前尚未完成桌面环境及试发范围登记，不将文档修订视为试发授权。

## 9. 监控与登记修正

监控按时间窗口、租户、设备和可取得的客户端版本分组，分列 succeeded/unknown/failed/cancelled；基于 verification.reason 分析原因。unknown 率下降须同时抽样核实成功真值，避免漏报增多造成假改善。版本缺失单列，不猜测版本。

```sql
BEGIN READ ONLY;
SELECT tool_name, state, count(*)
FROM local_tool_invocations
WHERE tool_name IN ('boss_send_to', 'boss_send_current', 'boss_greet')
  AND created_at >= '2026-08-01' AND created_at < '2026-09-05'
GROUP BY tool_name, state ORDER BY tool_name, state;
COMMIT;
```

上例为有界运维查询；§1 历史复核无起始日期，两个口径不要混用。
