# 营销 App 智能外呼代理：技术可行性调研

日期：2026-09-05。状态：公开资料调研完成，客户平台与真机能力未验证。

**用户补充后的约束**：系统疑似“云图”（产品身份未确认）；安卓机型由我们选；不依赖厂商技术支持、呼叫 API 或 SIP；App 按钮与表单由 GLM-5.3-Flash 看截图定位，安卓接口执行。本项目确定采用第 3 条路线；下面的厂商集成路线仅保留为技术对照，不是前置工作或推荐实施范围。

关联：[详细设计](../design/marketing-call-agent-design.md) · [验证与开发计划](../plans/marketing-call-agent-plan.md)。

## 1. 结论与建议

需求可以拆成四个独立能力：发现线索、沿原链路发起呼叫、AI 双向通话、回填原 App。最难的是双向通话音频和业务关联，自动点击只是其中一环。**不必限定为一台安卓手机，更不应把两台手机互开免提作为正式交付基础。**

通用技术路线对照（本次实际执行第 3 条）：

1. 原平台提供呼叫控制、双向媒体、录音和反馈接口：优先直接集成，保留平台业务链路。
2. 平台提供部分接口：API 负责可用部分，安卓 RPA 补足界面操作，音频走平台或外部音频桥。
3. 平台没有接口：指定安卓销售手机保留账号、SIM 和拨号动作；边缘电脑通过有线耳麦音频桥接替销售听说，RPA 回填。这是当前信息下的首选验证方向，并非已验证兼容性。
4. 两台手机声学耦合：仅证明 AI 能与真实电话对话；如果最终必须使用，需封闭夹具、独立控制通道和专项验收。

本项目沿原 App 的正常拨号流程运行。按用户明确的设计前提，云图自行录音并关联销售和客户，其实现作为黑盒，不纳入我们的研究、控制或验收；我们只验证正确线索/销售上下文、双向通话与反馈保存。Agent 自留音轨是独立的非权威参考，不能上传云图。

## 2. 现有呼叫链路的可能解释

用户描述的事实：App 获得线索；点击拨号按钮后进入系统拨号；目标号码不同于客户真实号码；通话后 App 有录音与反馈入口。

以下是待验证假设：

| 模式 | 典型行为 | 对方案的影响 |
|---|---|---|
| AXB 隐私号 | 销售 A 拨 X，平台依据 A-X-B 绑定接通客户 B | 同一个 X 可复用，不能当客户唯一标识；必须使用绑定的 A |
| AXN/分机号 | A 拨 X 或 X 加分机，平台选择目标客户 | 需保留后拨号、DTMF、绑定有效期与上下文 |
| 平台接入号 | 平台先接听 A，再呼叫 B | A 接通不等于 B 接通；开场白不能只由手机通话计时触发 |
| 双呼/回拨 | App 创建任务，平台分别呼叫销售与客户 | 需要接听销售腿，而不是固定执行外拨逻辑 |
| 自有 VoIP | App 或配套组件承载媒体 | 需要供应商 SDK/媒体接口，系统拨号盘的观感不足以定性 |

AXB 的工作方式有官方产品依据，但不能据此判断该客户使用了阿里云或某一种具体模式。[阿里云号码隐私保护功能](https://help.aliyun.com/zh/pnp/product-overview/features)

调查时记录一次人工测试的完整时间线：点击、号码绑定、系统拨号、平台提示音、客户响铃、客户接通、双方说话、挂机、反馈出现。优先使用客户授权测试账号与内部测试号码。

## 3. 安卓权限与音频边界

安卓官方说明区分“采集麦克风”和“采集电话上下行”：通话上下行采集涉及预装特权应用及 `CAPTURE_AUDIO_OUTPUT` 等条件。普通安装应用获得麦克风权限，不代表能拿到电话下行；无障碍服务的音频采集条件也不应解释为通用蜂窝通话录音权限。[Android 音频输入共享](https://developer.android.com/media/platform/sharing-audio-input)

默认拨号应用可通过 `InCallService` 管理通话界面、状态和音频路由；该接口并不提供普通应用任意读取和注入蜂窝通话 PCM 的通用通道。成为默认拨号器还会改变手机使用方式，需单独兼容测试。[InCallService](https://developer.android.com/reference/android/telecom/InCallService)

屏幕录制的 AudioPlaybackCapture 面向满足使用类型和捕获策略的播放音频，不是电话音频桥。不能将“录屏有声音”当作能实时获取电话双方声音的证明。[Android 播放音频捕获](https://developer.android.com/media/platform/av-capture)

因此：ADB、Appium、无障碍用于操作；电话音频单独解决。Root、系统签名、定制 ROM、厂商 Audio HAL 可能提供更深能力，但需要设备厂商合作和逐版本验证，且读取成功仍不代表注入成功。这个业务量下不建议将其作为 MVP 前置条件。

## 4. 各接入路线比较

| 路线 | 原 App 关联保留条件 | 音频质量潜力 | 主要成本/风险 | 建议 |
|---|---|---|---|---|
| 原平台双向媒体 API | 同一业务任务/销售席位和录音链 | 高 | 供应商开放程度、报价、媒体方向 | 首选 |
| 原平台 SIP 席位/机器人接入 | 平台支持席位映射并承载录音 | 高 | 呼叫路由、编码、NAT、转人工 | 优先调查 |
| 安卓 RPA＋有线音频桥 | 原账号/SIM 发起，平台继续录音 | 中高，待测 | 配件电气兼容、音频路由、UI 漂移 | 无接口时首选验证 |
| 安卓＋HFP 硬件桥 | 原手机作为音频网关 | 中，待测 | 配对、SCO、驱动和断连恢复 | 有线不可行时备选 |
| 厂商特权方案 | 厂商开放上下行及注入 | 依设备 | OEM 绑定、升级维护 | 特殊采购路线 |
| 双手机免提 | 原手机正常拨号 | 低且环境敏感 | 回声、啸叫、自激、串音、轮次误判 | 演示/最后备选 |
| 新购云外呼直接拨客户 | 需迁移绑定、录音、归属及写回 | 高 | 未必知道真号，也未必保留原系统功能 | 不满足当前目标的默认路线 |

SIP 是会话接入方式，不自动等于供应商允许机器人呼叫。录音回调只提供通话后的文件，也不等于实时媒体接口。单向监听或录音流不能满足 AI 发声，需要双向注入能力。

Asterisk 的 ARI External Media 提供媒体导出与注入机制，可作为供应商允许 SIP 对接后的适配层；它本身不会赋予平台接入权限，也不会让原 App 自动出现录音。[Asterisk External Media](https://docs.asterisk.org/Development/Reference-Information/Asterisk-Framework-and-API-Examples/External-Media-and-ARI/)

## 5. 有线音频桥的实际含义

销售手机把桥接设备当有线耳麦：电话下行从耳机输出送到电脑输入，电脑把 TTS 经适配电路送入手机外接麦克风。这条路线保留真实蜂窝通话，由外部设备接替人耳和人嘴。

它不是“一根普通 AUX 线”。手机端需要耳麦检测、CTIA 接线和麦克风电气匹配；电脑输出需要衰减、隔直和必要的隔离，避免线路电平直接进入麦克风端。左右声道不可随意短接。3.5 mm 耳麦规范提供引脚和电气基础，不能替代特定机型通话测试。[AOSP 耳麦配件规范](https://source.android.com/docs/core/interaction/accessories/headset/plug-headset-spec)

没有 3.5 mm 接口时，测试支持输入输出的 USB-C 音频适配器。仅支持耳机播放的转接头不合格；USB-C 音频、充电与 ADB 共用接口时，还要验证 Hub/PD 组合，不能假设同时可用。优先借用现有设备、先验证再采购。

HFP 备选中销售手机是 AG（Audio Gateway），桥接设备必须能做 HF（Hands-Free）。普通手机蓝牙配对、A2DP 音乐播放或通用 USB 蓝牙适配器都不保证这种角色和媒体能力。[Bluetooth SIG HFP 规范](https://docs.bluetooth.com/download/hfp_v1-10_showing_changes_since_hfp_v1-9/?tmstv=1765934392)

## 6. 双手机免提为何难以可靠运行

手机 A：蜂窝电话免提。手机 B：运行自研全双工音频客户端，经网络连接 AI，通常不需要再打一通蜂窝电话。

客户声音：A 扬声器 → 空气 → B 麦克风。AI 声音：B 扬声器 → 空气 → A 麦克风。B 同时可能录到自己的 TTS，A 的通话回声消除和 B 的回声消除又相互影响。两部手机的 AGC、降噪可能吞掉轻声或重叠语音。

仅按“AI 说话时关闭识别”可减轻自激，但会丢掉客户打断和拒绝。正式系统至少需要播放参考信号、AEC、双讲检测、固定音量与位置，以及独立于语音的通话控制事件。不能让手机 B 从“你好”判断是哪位客户或通话是否结束。

若坚持验证，应使用独立声学隔离通道/夹具，先做半双工基线，再评估全双工；必须测试机器人说话时客户插话、附近有人说话、平台提示音、断网和 A 挂机。未通过时停止扩展，不能通过降低验收标准宣称可生产。

## 7. 模型与现有工程能力

实时 ASR＋受控文本对话＋流式 TTS 更适合本项目“话术与问题流程稳定可预测”的要求。端到端语音模型可作为并行候选，但必须验证逐句证据、打断一致性和话术约束。

百炼已有实时语音交互文档及 VAD 模式。具体模型、区域、工具调用、输入输出格式和取消语义应在实施时锁定版本测试，不从产品宣传推断服务等级。[Qwen 实时模型文档](https://help.aliyun.com/zh/model-studio/realtime)

仓库当前 `src/tools/asr/speech_to_text_tool.py` 是最长 60 秒短音频的一句话识别工具，不能直接当实时电话 ASR。`src/llm/gateway.py` 可评估复用文本模型网关；调度、租户、审计能力可复用，但新的实时媒体服务和设备控制仍需开发。

## 8. 业务与数据边界

客户获得线索不自动证明可无限频次自动营销。上线前确认线索授权用途、联系时段、拒绝名单、录音告知、供应商线路规则与数据处理约定。产品开场明确企业与智能助手身份，不冒充具体销售本人。拒绝后立即停止当前营销并更新抑制名单。

个人信息保护法对自动化决策商业营销的便捷拒绝方式、委托处理等作出规定；其适用方式应由客户合规负责人结合具体业务确认。本方案将其落实为拒绝机制、最小字段、访问控制和可配置留存，而非仅添加文案。[个人信息保护法官方全文](https://www.samr.gov.cn/wljys/gzzd/art/2023/art_3ef1e889c1e644d4b65b5f5c7f432386.html)

## 9. 尚不能下结论的事项

- 客户平台是否采用 AXB，谁提供线路，拨号按钮是否创建临时绑定。
- 实际机型是否支持稳定外部耳麦双向通话与同时充电/控制。
- 能否通过安卓状态和音频判断客户接通，以及通过界面识别反馈变化。
- 4000 多通是拨打尝试、接通次数还是线索数，是否含重拨。
- 反馈填写是否触发分配、工单、佣金或下一轮自动联系。

这些均由下一阶段的验证矩阵给出证据，不以公开资料替代现场测试。平台不暴露的业务 ID 不强行获取，采用设计中的本地身份与界面证据关联。

## 10. GLM 截图定位选型补充

已在 Z.ai 官方组织发布的模型卡确认 GLM-5.3-Flash 是原生多模态模型，提供图文输入示例。因此按用户要求作为首选视觉定位模型；但具体商业 API 的账号可用性、图像限制、坐标输出准确性和延迟仍需实测，模型卡不能证明 App 点击成功率。[官方模型卡](https://huggingface.co/zai-org/GLM-5.3-Flash)

截图像素到点击坐标必须有明确变换。DPI 影响布局，不是唯一坐标比例：完整截图、模型缩放图、裁剪图、显示旋转和键盘状态都必须记录。执行遵循“截图 → 模型返回目标框 → 几何变换 → 页面前置条件校验 → 单步点击 → 新截图验证”。ADB 是可用的设备控制基础；需要用户授权调试连接，且具体设备的输入和截图能力要先测试。[Android ADB](https://developer.android.com/tools/adb)
