# 企业微信群接入自研 Agent 自动问答调研

> 调研日期：2026-10-22。范围：官方机器人接入机制与项目现状；未创建机器人、未联调、未开发或部署。

## 1. 结论

**有官方机制：企业微信「智能机器人 → API 模式」可以连接自研 Agent，在群内成员 @机器人后接收问题并回复，也支持与机器人单聊。** 腾讯云官方接入文档明确列出这两种交互场景，并提供 WebSocket 长连接和 URL 回调两种接入方式。[1][2]

需要先分清群和机器人类型：

| 场景 | 本次结论 | 边界 |
|---|---|---|
| 内部员工群，成员 @机器人提问 | 可通过智能机器人 API 对接自研 Agent | 还需配置可见范围、成员身份映射并做真实账号验证 |
| 群内普通消息，无人 @机器人 | 不能按智能机器人接口具备全群监听能力来设计 | 已核验的群交互是 @触发；不能承诺自动读取全群上下文 |
| 含个人微信客户的外部群 | 当前不能按这条官方智能机器人路线承诺可接入 | 官方集成资料列出的企微通道范围为内部群和内部员工私聊，不支持外部群；未完成企微帮助中心原文直接核验 [4] |
| 普通群机器人 Webhook／消息推送 | 适合向群发送通知，不构成双向问答入口 | 不能拿通知 Webhook 当作用户问题回调接口 [5] |

因此，若需求是内部员工群答疑，可以继续进入设计；若需求是客户外部群直接自动应答，需要另行评估，不能将内部群能力直接外推。

## 2. 自研 Agent 怎样接入

建议先验证 WebSocket 长连接：

```text
内部群成员：@业务助手 + 问题
  → 企业微信智能机器人
  → 自研渠道适配服务（WebSocket 接收消息）
  → 可信身份映射、会话定位、调用现有 AgentRunner
  → Agent 的模型 / 知识库 / 已授权工具
  → 适配服务将结果回复到原群
```

这里的机器人是企业微信中的消息入口，问答逻辑由我们自己的服务决定。企业微信团队已公开 `@wecom/aibot-node-sdk`，提供连接认证、消息事件、流式回复、心跳和重连等能力，不要求采用某个指定的 Agent 框架。[3]

| 接入方式 | 配置 | 适用判断 |
|---|---|---|
| WebSocket 长连接 | Bot ID、Secret；服务主动连接企微 | 建议首轮验证使用，无需给接收端配置公网回调地址 |
| URL 回调 | 接收消息 URL、Token、EncodingAESKey；实现校验与消息加解密 | 已有公网回调设施时可评估 |

同一机器人两种方式不能同时生效；腾讯云文档说明长连接同一时间只允许一个有效连接。多副本部署时应确保连接归属唯一，不能每个 worker 同时连接同一个机器人。[1]

这不是要求用户安装 Node.js：SDK 是自研服务的可选实现工具，项目也可按官方协议在既有后端栈实现。采用哪种方式应在正式设计时决定。

## 3. 最小验证路径与需验证的边界

1. 由有权限的账号在企微管理后台「安全与管理 → 管理工具 → 智能机器人」创建机器人，选择 API 模式、长连接，获取 Bot ID 与 Secret；客户端也有工作台入口。[1][2]
2. 配置机器人的可见范围，将其添加到内部测试群；至少用创建者以外的一个普通员工账号提问，确认目标用户确实可用。
3. 用一个独立测试接入进程连接企微，先验证收消息与原群回复，再接现有 AgentRunner。凭据只通过既有安全配置存储，不写入文档或日志。
4. 先限定文本问答：验证 @触发、无 @消息、单聊、两人并发、跨群隔离、重复消息与断线重连。
5. Agent 耗时较长时先回复处理中状态，再流式更新最终结果；官方 SDK 有中间回复与结束回复接口。流式时限、主动发送窗口及频率应按选定模式的最新协议实测，不混用不同接口的限额。[2][3]

以下属于后续设计建议，而非已实现能力：

- 用可信机器人配置映射租户，用企微发送者身份映射业务用户；不能将所有群成员当作管理员或机器人创建者。
- 会话必须区分机器人、群与用户；是否共享群上下文需明确决定，个人历史与凭据不能随群回复暴露。
- 以消息唯一标识去重，防止重连或重复投递导致重复执行业务操作。
- 对群内回复只使用当前群成员可见的数据；知识问答先行，业务写操作沿用现有权限与确认规则。

## 4. 本项目现状

本次只读核查发现：

| 位置 | 当前代码事实 | 与本需求关系 |
|---|---|---|
| `src/channels/wecom/adapter.py` | 使用 Corp ID、Agent ID、应用 Secret；解析 XML 应用回调，调用应用消息发送接口 | 是企微应用渠道，不能仅换凭据就当成智能机器人渠道 |
| `src/services/wecom_bot.py` | 提供群 Webhook 的文本、Markdown 通知发送 | 可用于通知；没有智能机器人用户问题接收链路 |
| `src/channels/wecom_kf/` | 微信客服渠道 | 不能当作客户群原地问答接口 |
| 企微个人号 RPA 渠道（已清退删除） | 个人账号 RPA 及客户端动作投递 | 是另一条技术路线，不能等同官方智能机器人 API |

在 `src/channels/` 与 `src/services/wecom_bot.py` 范围内检索 `aibot`、官方长连接地址和相关接口路径，未发现智能机器人 API 接入实现；不将这一局部检索表述为已穷尽所有代码。

若进入开发，应新增智能机器人渠道适配，沿用项目现有 AgentRunner、身份、会话与交付机制，不另建 Agent 推理循环。涉及本地设备执行时继续遵守 [Runner / Desktop / Runtime 集成契约](../system/runner-desktop-runtime-integration-contract.md)。

已有[招聘通知设计](../design/recruiting/recruiting-interview-notify-design.md)的“群机器人单向”描述针对 Webhook 通知，仍适用于其原场景，不能解释成企业微信完全没有双向机器人。旧[微信客服设计](../channel/wecom_kf/wecom_kf_design.md)背景出现群聊措辞，也不能据此承诺微信客服 API 支持客户群原地回复。

本轮仅形成调研报告并登记研究索引，不建立已获开发授权的任务或开发计划。正式进入功能设计后，再补设计与开发计划并登记 ideas。

## 5. 证据与局限

已直接读取的主要资料是企业微信团队官方 SDK 和云厂商自己的接入文档。企业微信开发者站原文通过网页读取工具返回无法打开，浏览器又因站点安全策略阻止访问；未绕过该限制。搜索结果中的镜像只用于定位文档入口，不作为本报告核心技术结论的依据。

关于外部群，[4] 是阿里云自身集成的范围说明；腾讯官方 WorkBuddy 产品文档也明确含微信用户的群暂不能拉入其机器人，但该产品还有“仅主人可用”等自身限制，不能将这些限制一概套用于自研 API 机器人。[6] 因此本报告保留“不能承诺外部群可用”的边界；上线前仍应由实际企业账号核查企微最新群类型与机器人能力。

未验证项：当前企业是否开放创建权限、目标群类型、成员可见范围、普通成员与创建者差异、端到端问答、断线恢复及生产并发。文档可行性不等于本项目已经支持。
