# 抖音电商飞鸽客服接入 Agent 可行性深度调研

> 调研日期：2026-08-19
> 调研对象：抖音商城/抖店消费者在飞鸽咨询商家时，由企业自有 Agent 自动接待，并在必要时转人工
> 文档性质：公开资料可行性研究，不构成抖音电商接口授权承诺
> 结论有效期建议：3 个月；拿到开放平台控制台实际权限或平台书面答复后立即更新

## 1. 执行摘要

### 1.1 核心结论

**可以做，但不是注册一个普通抖店应用后即可调用的通用公开 API。** 抖店开放平台已经公开展示了“第三方客服”“客服机器人”“客服实时消息”等权限包/场景包，以及飞鸽消息推送开关、客服工具执行和直接转人工工具。这些证据说明平台存在供第三方客服系统或机器人接入的正式技术链路。

但是，公开的飞鸽 API 目录没有通用的“拉取会话列表、读取消息、发送任意文本”接口；2024 年官方 FAQ 还明确写过 `doudian_pigeon_ConversationMsg` 未开放。较新的接口与权限包表明平台后来至少开放了受控接入能力，但消息协议、发送回复接口、机器人身份绑定、准入条件等核心文档没有对未登录公众完整公开。因此当前应把可行性定级为：

| 判断项 | 结论 | 置信度 |
|---|---|---:|
| 飞鸽能让 AI 自动接待购前、购后咨询 | 能，官方产品已支持 | 高 |
| 飞鸽支持知识不足、问题模糊或超权限时转人工 | 能，官方协议明确说明 | 高 |
| 第三方系统可获得客服实时消息 | 存在受控权限包和开通 API | 中高 |
| 第三方 Agent 可直接发送回复 | 技术链路应当存在，但公开目录未给出完整发送契约 | 中 |
| 普通自研商家应用可自助申请上述权限 | 未证实，更可能需要定向准入/服务商审核 | 中高 |
| 本项目现在即可无审批上线 | 不能 | 高 |
| 通过飞鸽桌面端 RPA 绕过审批是否推荐 | 不推荐作为生产方案 | 高 |

### 1.2 推荐决策

首选路线是申请“**三方客服 / 客服机器人 + 客服实时消息**”正式能力，拿到文档和测试店后做一个两周 PoC。Agent 负责低风险问答、订单/物流查询和标准售后引导；退款承诺、赔付、改地址、投诉、法律/舆情、高金额操作及低置信度问题转真人。

如果平台只允许使用官方“飞鸽智能客服”，则采用“**官方机器人承接消费者会话 + 本系统提供知识、工单、质检、话术和人工辅助**”的降级方案，而不是绕过平台控制会话。

## 2. 业务边界：消费者到底在哪个系统聊天

抖音商城订单相关的商家客服会话由电商客服系统“飞鸽”承载。抖音小程序的 `tt.openEcIm` 只负责把用户跳转到抖店客服页面，不是服务端收发消息 API；开放平台能力清单也说明电商品牌客服整体统一使用飞鸽。因此本项目应接入的是“抖店开放平台 + 飞鸽”，不是抖音开放平台的普通私信、视频评论或小程序客服。

这几个概念不能混用：

| 能力 | 是否解决本需求 | 说明 |
|---|---:|---|
| 抖音号私信/评论 | 否 | 不等同于抖店买家飞鸽会话 |
| 小程序 `tt.openEcIm` | 否 | 只打开客服 UI，不向服务端开放消息 |
| 飞鸽官方智能客服 | 是 | 平台自带机器人，可自动接待和转人工 |
| 飞鸽第三方客服/客服机器人权限 | 是，目标路线 | 让外部客服系统/Agent 进入正式会话链路 |
| 飞鸽插件 | 部分 | 可嵌入客服工作台、辅助人工或调用客服工具，不等同于接管消息 |

## 3. 官方证据链

### 3.1 平台官方 AI 已证明业务闭环成立

[《飞鸽智能客服服务协议》](https://lf3-static.bytednsdoc.com/obj/eden-cn/522eh7lpqubqbd/%E9%A3%9E%E9%B8%BD%E6%99%BA%E8%83%BD%E5%AE%A2%E6%9C%8D%E6%9C%8D%E5%8A%A1%E5%8D%8F%E8%AE%AE.pdf)明确写明：

- AI 可自动应答购前及购后咨询；
- 可回答商品、营销、发货物流、订单、售后、会员等问题；
- 在商家授权下可处理退换修赔、修改订单地址、开票等需求；
- 知识不足、问题模糊或超出权限时会自动转接人工；
- 商家可在“智能客服—服务概览—转人工配置”设置规则；
- 商家仍需配置人工客服，并对答案、数据和合规负责。

这证明用户希望的产品形态符合飞鸽自身支持的服务模式，真正的不确定点仅是“是否允许企业自有 Agent 使用第三方接口进入同一链路”。

### 3.2 开放平台存在第三方客服专属权限

官方公开接口页显示多组非普通应用权限：

1. [`pigeon.updatePushUser`](https://op.jinritemai.com/docs/api-docs/188/6016)：为店铺开启/关闭飞鸽消息推送。权限包含“飞鸽—客服实时消息”“三方客服—客服机器人”，场景包也包含“客服实时消息”。
2. [`pigeon.GetPigeonToolList`](https://op.jinritemai.com/docs/api-docs/188/7668)：获取飞鸽客服工具，返回值包含 `DIRECT_SWITCH_HUMAN`，同时还有催拍、商品推荐、退款、换货、售后、物流等工具。
3. [`pigeon.ISVToolEventPreCheck`](https://op.jinritemai.com/docs/guide-docs/api-test?interfaceId=7596)：检查指定会话中 ISV 客服工具是否可执行及其频控。
4. [`pigeon.ISVExecuteTool`](https://op.jinritemai.com/docs/api-docs/188/7670)：执行 ISV 客服工具，说明第三方系统可以在会话上下文执行平台认可的客服动作。
5. 飞鸽 API 公开目录还包含客服在线日志、工单通知、登录参数交换，但没有展示通用文本消息发送 API。

上述组合足以证明第三方客服生态不是猜测。特别是 `updatePushUser + 客服实时消息` 代表存在消息进入外部系统的链路，`DIRECT_SWITCH_HUMAN` 代表转人工是平台原生动作，而非 Agent 自己虚构状态。

### 3.3 为什么不能直接宣布“接口已完全开放”

[官方 FAQ《如何对接店铺消息到飞鸽会话消息接口？》](https://op.jinritemai.com/docs/question-docs/96/6260)在 2024-03-08 的回答是：`doudian_pigeon_ConversationMsg` 尚未开放、暂不支持对接。它与较新的“客服实时消息”权限并不一定矛盾：

- FAQ 可能描述当时的普通开发者开放状态；
- 新能力可能只对通过“三方客服/客服机器人”准入的应用开放；
- `updatePushUser` 只是开通店铺推送，真正的消息事件文档可能登录后或签约后可见；
- 收消息、发送消息、转人工可能分别属于消息推送、私有协议和 OpenAPI，不一定出现在同一公开目录。

所以严谨表述是：**平台具备正式能力并留下公开接口证据，但本项目能否获得权限仍需平台审核确认。** 在拿到实际权限之前，不应承诺上线日期或全量功能。

## 4. 可能的正式接入链路

```text
抖音买家（商品页/订单页进入客服）
        ↓
飞鸽会话系统
        ↓ 客服实时消息推送（受控权限）
接入网关：验签、幂等、顺序整理、快速 ACK
        ↓
会话编排器：店铺/买家/订单上下文 + 风险策略
        ↓
Agent：知识检索、订单/物流/售后查询、答案生成
        ↓
发送回复协议（待平台提供正式契约）
        ↓
飞鸽展示给买家

转人工条件触发
        ↓
ISVToolEventPreCheck → ISVExecuteTool(DIRECT_SWITCH_HUMAN)
        ↓
飞鸽人工队列/指定客服组
```

消息接收端应遵循抖店通用[消息推送接入指南](https://op.jinritemai.com/docs/tmp/153/99)：2 秒内先返回成功、异步处理；平台可能重推且可能乱序，因此必须按 `msg_id` 幂等、按会话重排，不能在 Webhook 请求中同步等待大模型。

### 4.1 与现有项目的适配

本项目已有企微客服等渠道、会话串行化、主 Agent/子智能体、知识库、人工转接和多租户基础，建议把飞鸽实现为新渠道适配器：

- `DouyinPigeonChannel`：验签、消息规范化、ACK、出站回复；
- `PigeonConversationRouter`：以 `shop_id + conversation_id` 作为会话隔离键；
- `PigeonContextProvider`：按授权查询订单、商品、物流、售后；
- `PigeonHumanHandoff`：调用平台原生转人工工具并保存转接状态；
- `PigeonPolicy`：敏感动作、超时、置信度、用户情绪和连续失败规则；
- 租户凭证必须加密，日志不得记录 access token、手机号、地址等明文。

不要先按公开页面猜测字段写生产代码。应先拿到消息样例、发送契约和沙箱/测试店，再冻结内部消息模型。

## 5. Agent 与人工的职责边界

### 5.1 建议 Agent 自动处理

- 商品参数、尺码、库存、活动规则等有权威知识来源的问题；
- 已付款订单状态、发货时效、物流节点查询；
- 标准退换货政策解释和操作引导；
- 发票、地址修改等低风险流程的说明；
- 识别问题并收集人工所需信息；
- 使用平台已授权且可回滚/可审计的客服工具。

### 5.2 必须或建议转人工

- 用户明确要求真人；
- 连续两次未解决、低置信度、知识冲突或无法识别订单；
- 投诉、辱骂升级、媒体/监管/律师、食品药品安全、人身伤害；
- 退款、赔付、补差价、优惠承诺超过阈值；
- 修改地址、取消订单等不可逆或临近履约动作；
- 平台工具预检查不通过、接口异常或权限不足；
- 涉及敏感个人信息、账号异常、欺诈风险；
- 任何 Agent 试图编造物流、政策、库存或承诺的场景。

转人工时要把会话摘要、订单号、用户诉求、已执行动作、风险标签和推荐处理方式一起交给真人，避免用户重新描述；Agent 随即停止自动回复，直到收到平台明确的“机器人重新接管”事件或人工主动结束。

## 6. 准入和商务申请清单

建议由商家主体或拟成为服务商的主体，通过抖店开放平台工单、开放平台商务和飞鸽智能客服渠道同时询问，问题要具体到权限名称：

1. “三方客服—客服机器人”权限包是否接受新服务商申请？自研商家应用能否申请？
2. “飞鸽—客服实时消息”场景包的准入条件、应用类型、保证金、收费和审核周期是什么？
3. 是否提供买家消息接收事件的完整字段、消息顺序、撤回、图片/卡片/订单消息协议？
4. 第三方机器人发送文本、图片、卡片和客服工具结果分别使用什么接口？
5. 如何绑定店铺、客服账号和机器人身份？同一会话由机器人和真人切换的状态机是什么？
6. `DIRECT_SWITCH_HUMAN` 是否支持指定技能组/客服组？转接失败如何处理？
7. 是否有沙箱、测试店、白名单或灰度环境？消息推送是否支持回放？
8. 是否允许使用第三方大模型，数据能否离开抖店云，是否要求抖店云部署或安全测评？
9. 消费者个人信息的字段脱敏、留存期限、跨主体委托处理和删除要求是什么？
10. 是否要求应用上架服务市场；如果只服务自有店铺，是否可创建自用型应用？

申请材料建议提前准备：营业执照和开发者认证、产品说明、数据流图、隐私政策、个人信息委托处理说明、等保/安全能力、回调域名、稳定性与限流方案、人工兜底机制、模型安全策略、测试店和目标日会话量。

## 7. 两周 PoC 建议与验收门槛

### 阶段 0：权限验证（阻塞项）

在任何正式开发前完成以下硬验证：

- 控制台确实可见并批准“客服实时消息”和“客服机器人”权限；
- 收到一条真实测试买家消息；
- 通过正式接口回复一条文本；
- 成功执行一次 `DIRECT_SWITCH_HUMAN`；
- 人工接管后机器人不再抢答，人工结束后可恢复。

任一项不成立，都不能进入生产开发。

### 阶段 1：只读问答 PoC

- 仅 1 个测试店、1 个测试客服组；
- 只回答商品、订单状态、物流和政策；
- 不自动退款、不赔付、不改地址；
- 低置信度和异常全部转人工；
- 保存消息 ID、模型版本、知识证据、回复、转人工原因和耗时审计记录。

### 建议验收指标

| 指标 | PoC 门槛 |
|---|---:|
| Webhook ACK P99 | < 1 秒 |
| 消息丢失 | 0 |
| 重复发送 | 0（幂等生效） |
| 人工接管后 Agent 抢答 | 0 |
| 高风险问题自动执行 | 0 |
| 转人工成功率 | ≥ 99% |
| 有证据答案准确率 | ≥ 95%（人工抽检） |
| 无答案时编造率 | 0 |

## 8. 替代方案评估

| 方案 | 可行性 | 推荐度 | 说明 |
|---|---:|---:|---|
| 正式三方客服/客服机器人接口 | 高但需准入 | 首选 | 唯一适合规模化 SaaS 和多店铺运营的路线 |
| 飞鸽官方智能客服 | 高 | 强降级方案 | 不能完全使用自有 Agent，但最快、最合规，原生转人工 |
| 飞鸽插件 + Agent 辅助人工 | 高 | 推荐过渡 | Agent 推荐话术/摘要/查单，由真人确认发送，风险低 |
| 服务市场已有客服厂商二次集成 | 中 | 条件推荐 | 需确认厂商是否提供合法开放 API 和数据处理协议 |
| 飞鸽桌面端 RPA 自动收发 | 技术上可能 | 不推荐生产 | UI 变化、掉线、并发、封控、消息错位和合规风险高 |
| 抓包调用私有接口/Cookie 复用 | 不应采用 | 禁止 | 未授权接口、账号安全和个人信息风险不可接受 |

如果官方拒绝第三方机器人权限，最合理的产品调整是“Agent 辅助坐席”：在飞鸽插件或自有工作台生成建议回复、检索订单和知识、生成摘要，真人一键确认发送。它仍能显著降低客服成本，而且未来拿到权限后可平滑升级为自动接待。

## 9. 主要风险

1. **准入风险**：权限可能只给签约客服服务商或平台邀请对象。
2. **接口完整性风险**：能收消息不等于能发任意回复；能转人工不等于能指定队列。
3. **平台规则风险**：客服响应率、禁用词、营销承诺、售后时效均可能影响店铺评分和处罚。
4. **并发与顺序风险**：Webhook 重推、乱序、买家连续发消息会导致重复或上下文错配。
5. **个人信息风险**：订单、地址、手机号和聊天记录属于敏感经营/个人数据，必须最小化访问、加密、脱敏和审计。
6. **模型风险**：错误承诺、虚假物流、误导售后会直接形成商家责任。
7. **人工交接风险**：没有严格所有权状态机时，最容易出现 Agent 与真人同时回复。

## 10. 最终建议

项目值得推进，但应把第一里程碑定义为“**拿到飞鸽第三方客服准入并完成五项硬验证**”，而不是直接开始开发完整渠道。

推荐顺序：

1. 立即提交平台工单并联系飞鸽/开放平台商务，申请三方客服、客服机器人、客服实时消息；
2. 同时用官方飞鸽智能客服验证业务规则、知识库和转人工策略；
3. 权限未下来前，只设计平台无关的内部会话模型和安全策略，不猜测私有协议；
4. 权限获批后用单测试店完成收、发、转人工、人工接管、恢复五项 PoC；
5. PoC 通过再编写正式设计和开发计划，按渠道适配器接入现有 Agent 平台。

一句话结论：**抖音电商具备让第三方 Agent 参与飞鸽客服并转人工的官方能力基础，但属于受控生态能力；能否落地取决于“三方客服/客服机器人 + 客服实时消息”的准入，而不是单纯的技术开发。**
