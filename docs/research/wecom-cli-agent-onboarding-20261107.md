# 多智能体接入 WeCom CLI 回复能力调研

> 2026-11-07。范围：本机 WeCom CLI/Runtime 读发，不等同于企业微信应用或微信客服官方渠道。仅核对当前源码及 agent2 的只读配置；未修改智能体定义、部署、启动自动监听或发送消息。

## 结论

底层调用链已经通用：选定智能体 profile → Agent 工具装配 → 用户选定的本地设备 → Runtime → WeCom MCP Provider。不同智能体无需各写一套企微 CLI 适配器。然而“给某个智能体开通企微回复”目前仍靠逐个编辑其工具与技能列表，没有企微能力预设、会话到智能体的自动路由配置或完整接入验收。因此“在线电商客服”的接入是**通用底座上的手工配置**，不能当作可复制的完整标准。

agent2 的只读快照：7 个启用的自定义智能体定义中，仅 `after-sales`（在线电商客服）显式包含企微工具。它采用 `tools.inherit=false`，`additional` 为 `http_api`、`knowledge_base_search` 和四个企微工具；`skills.allowed` 为 `after-sales-core`、`after-sales-api`、`lead-management`，**没有** `wecom-conversation`。第四项目录工具是 W30 真机验收发现漏配后手工补入数据库。此前五轮群聊实验的回复原文由主控逐轮预设，只证明读发/回读链路，未检验智能体自主业务答复或业务资料是否存在。

## 当前实际链路与边界

| 环节 | 已有机制 | 对接入的含义 |
|------|----------|--------------|
| 智能体定义 | 管理界面分别选择工具和技能；`inherit=false` 时仅注册显式工具。租户副本沿用父定义的工具/技能 | 给一个智能体加工具不需要改 CLI；修改共享父定义会影响其租户副本，不能当成单租户授权 |
| 工具目录 | WeCom 模型工具为 `wecom_session_directory`、`wecom_read_session`、`wecom_read_sessions`、`wecom_message_send` | 其他 CLI 命令和图片/文件发送不等于当前模型可见工具 |
| 设备与能力 | 设备按租户和用户单选；必须 active、在线、具有 WeCom Provider。目录搜索另需 `wecom_session_directory_search` 能力 | 同一用户的多个智能体可复用其设备；不同用户要各自配对。配置了工具也不能替代设备就绪检查 |
| 技能 | `wecom-conversation` 已提供唯一名称检索、游标与 unknown 不重发说明，但没有声明 `requires_tools` | 选此 Skill 不会自动补齐四工具；目前必须同时手工选择工具和 Skill |
| 业务能力 | 智能体自己的提示词、模型、知识库及业务工具独立于企微读发 | 不要把“在线电商客服”的 `http_api`/`knowledge_base_search` 原样复制给所有智能体 |
| 消息触发 | Web/任务选中 profile 后可用企微工具读取、持续轮询并回复；CLI 本身只是本机执行器 | 仅勾选四工具不会让来消息自动触发某个智能体；需要明确启动任务、目标和回复范围 |

## 现在可执行的标准配置流程（人工配置）

1. **选智能体和业务资料**：确认目标智能体已启用，所属租户/用户可用，原提示词、知识库和业务工具能独立回答该类问题。若只想给某一租户开通，先核对它是不是共享父定义的副本；现有副本不能单独覆盖父定义的工具/技能，不能为单租户需求直接改共享父定义。
2. **开通模型工具**：由平台管理员在“智能体定义”的工具配置中保留原业务工具，并明确加入上述四个企微工具。新建专用智能体优先 `inherit=false` 并列出所需工具。不要把 `inherit=true` 当作企微开关，它会继承其他业务工具；已有智能体切换继承模式前须保留原工具清单。
3. **加入企微使用 Skill**：在同一智能体的技能列表加入 `wecom-conversation`，保留原业务 Skill。当前 Skill 没有自动补工具元数据，需核对工具和技能两项都已保存。
4. **确认设备**：执行用户在“本地工具”选择自己的在线 Runtime，确认 WeCom 插件已启用、企微登录且本地库可用。需要目录搜索时，设备须上报 `wecom_session_directory_search`；本次验收组合为 Runtime 0.0.39 + WeCom 0.2.10。工具在配置界面出现或模型可见，不单独证明本机可执行。
5. **明确任务范围再运行**：在 Web 选择该智能体，说明目标会话、只回复哪些人/消息、是否持续监控及停止条件。首次按完整名称经目录确认唯一，再读会话；后续复用返回的稳定会话标识和游标。一个会话不要同时交给两个独立自动回复任务，避免双方各自发送。
6. **自主问答验收**：让成员发一个需要该智能体业务资料的问题，不预写回复文案；确认它确实调用了所需业务工具或知识、读到原消息、只发送一条自身生成的答案并通过本地库回读。再验错名/同名、增量游标、停止任务和发送结果 unknown 时不重发。客户端落库不代表对方收到或已读。

这个流程能让**已由用户启动的 Web/持续任务**使用相同企微 CLI 回复。当前没有“只把某企微会话绑定到某智能体，来消息就自动创建/唤醒任务”的通用配置入口；现有企微会话页的日报计划也不是自动回复路由。企业微信应用和微信客服渠道另走 `tenant_channel_configs.subagent_type` → 渠道适配器 → Runner，不经过本机 WeCom CLI，不能把它们的绑定设置误当成本流程。

## 建议的最小产品化方向（未实施）

- 先把上面的人工流程做成管理端的**企微回复能力预设**：一次选择四工具和 `wecom-conversation` Skill，保存前展示被影响的共享父定义/租户副本；同时检查目标用户设备的实际 Provider 与目录搜索能力。不要靠勾选项假定插件已安装，也不要自动复制其他智能体的业务工具。
- 只有当产品需要“无需在 Web 发起任务，企微来消息即自动分配智能体”时，另设计会话到 profile、用户、设备及回复范围的显式绑定与唯一负责人。沿用现有 Runner 持续任务/恢复链路，不在 CLI 内新建模型或第二套消息调度。
- 产品化前补一轮**不预设文案**的真机业务验收；此前五轮实验不能充当这一项的通过证据。

本报告是现状核查与配置建议，不表示上述预设或自动路由已实现；若决定开发，先更新既有企微设计并制定开发计划，登记到 ideas 索引。
