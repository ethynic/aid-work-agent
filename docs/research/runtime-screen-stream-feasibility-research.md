# Runtime 桌面实时画面：技术可行性调研

调研日期 2026-11-23，2026-11-24 按评审修订并补充单机验证结果。基线为 `runtime-optimization` 分支提交 `98a9153f`。本文回答「能否把 Runtime 电脑的桌面实时画面显示到客户网页」以及「用什么技术做」，不涉及实施。结论为**技术可行**：隐藏窗口能采集、720p 能编码、浏览器能播放，这些已有单机证据；**客户网络能不能直连还没有证据**，需要两台电脑和真实跨网络的验证（见第 6.2 节）。

配套文档：[技术设计](../system/runtime-screen-stream-design.md) · [开发计划](../plans/plan-runtime-screen-stream.md) · [交互原型](../design/prototypes/runtime-screen-stream-prototype.html)（浏览器直接打开）。

## 1. 结论

| 需求 | 结论 | 采用技术 | 把握度 |
| --- | --- | --- | --- |
| Runtime 画面实时显示到网页 | 可行 | WebRTC：Runtime 端采集后经点对点连接发给浏览器 | 单机已验证：10 分钟稳定，Chrome、Edge 能播放 |
| 服务器只转交建连信令 | 可行 | 服务器只转交双方的十几条握手消息，画面不经过服务器 | 单机已验证：建连时约 24 KB，传画面期间独立的信令中转进程每 10 秒只经手约 0.5 KB，与视频码率无关 |
| 由客户在网页发起才建立连接 | 可行 | 无会话时 Runtime 不采集、不建连；会话由网页请求创建 | 高 |
| 同一台电脑不可用并提示 | 可行 | 先建立不含画面的连接，Runtime 比对观看端地址；确认不是本机才采集，无法确认也不采集 | 单机已验证观看端在本机的情形；另一台电脑上的情形待验证 |
| 720p | 可行 | 1280×720、15 帧、码率上限 2.5 Mbps，H.264 硬件编码 | 单机已验证 |
| 嗅探局域网并直连 | 可行，有条件 | WebRTC 自己探测候选地址，走哪条线路以实际连接结果为准 | 没有跨机证据。单机验证发现 Runtime 默认被 Windows 防火墙拦截入站，而浏览器只公布 mDNS 名字（见 4.3） |
| 信令断开后要停 | 可行 | 画面租约：Runtime 连续 30 秒收不到服务器确认就自己关闭采集 | 单机已验证：停止续期后约 20 秒内关闭 |
| 有些网络打不通 | 明确的结果 | 连不上就是「当前网络无法直连」，不做中转 | 真实成功率未知，需要跨网络测试 |

一条硬约束直接决定方案取舍：**主服务器公网出口只有 5 Mbps**（[后端规范 · 下载接口规范](../../.claude/rules/backend_dev.md)）。720p 画面走服务器中转至少要 2～3 Mbps，一路就会占掉一半以上。所以只做点对点，画面不经服务器。

另一条约束决定握手指令走哪条路：**Runtime 的设备凭据只存在 Host 子进程里**，界面进程和网络渲染进程都拿不到（[共同契约](../system/runner-desktop-runtime-integration-contract.md) C02、C08）。所以握手指令必须由 Host 用设备身份与服务器通信，采集窗口只管建连、采集和收发画面。

## 2. 现状（代码事实）

| 组成 | 现状 | 对本功能的影响 |
| --- | --- | --- |
| Runtime 壳 | Electron 43.1.0，关窗收托盘；主窗口权限处理器一律拒绝，未使用 `desktopCapturer`，未设置 `backgroundThrottling` | 需要新增一个独立的隐藏采集窗口，只在会话期间存在，不能放宽主窗口的权限 |
| Runtime Host | 独立 Node 22 子进程，经私有 IPC 与壳通信；管理请求参数限制为不超过 4096 字符的字符串 | 握手描述（SDP）有几千字符，不能走现有管理通道，需新增专用 IPC 消息类型 |
| Runtime 与服务器 | 只有 HTTP：心跳每 5 秒一次，任务领取为 20 秒长轮询；设备接口用 Bearer 令牌 | 可以原样承载信令，无需新增长连接；心跳响应可以顺带给画面续期 |
| 设备记录 | 表 `local_tool_devices`，能力存于 `capabilities_json`；不记录设备来源地址；设备列表接口刻意不下发能力原始内容 | 需要新增一个明确的「支持实时画面」投影字段 |
| 服务端 | FastAPI，Gunicorn 以 uvicorn worker 运行（3～6 个）；跨请求数据必须放 Redis 或数据库 | 会话状态放数据库即可，多个 worker 之间天然共享 |
| 网页 | Vue 3 加自研 Base* 组件；设备入口在「本地工具」页的设备表格；没有使用过 WebRTC | 入口放在设备行操作列，观看用大弹框 |
| 已有画面类功能 | 「服务端浏览器」只读画面：服务器把 JPEG 帧经 WebSocket 推给网页 | 帧全部过服务器，同样受 5 Mbps 限制，不适合桌面连续画面；其状态条样式可作为参考 |

## 3. 技术选型

### 3.1 画面传输

| 方案 | 做法 | 判断 |
| --- | --- | --- |
| **WebRTC（选用）** | 浏览器与 Electron 自带的实时音视频引擎，双方直接建连，自带加密、拥塞控制和码率自适应 | 浏览器零依赖；画面不过服务器；两端都是 Chromium 内核，兼容性问题少 |
| 服务器转发图片帧 | Runtime 截图后上传，服务器经 WebSocket 或 SSE 推给网页 | 每秒 15 帧 720p 图片约 7～18 Mbps，远超服务器带宽，延迟也高。只在现有低帧率浏览器画面里合适 |
| HLS 等直播协议 | 推流到媒体服务器再分发 | 延迟数秒起，需要媒体服务器，画面过服务器 |
| RDP、VNC | 系统级远程桌面协议 | 需要开启系统远程桌面或自建网关，浏览器不能直连，也不满足点对点 |
| 自研 UDP 传输 | 自己实现打包、加密、拥塞控制 | 重复实现 WebRTC 已有能力，不建议 |

### 3.2 Runtime 端采集与发送

| 方案 | 做法 | 判断 |
| --- | --- | --- |
| **Electron 采集窗口（选用）** | Runtime 内新建一个隐藏窗口，用 `getDisplayMedia` 采集主屏幕，交给同窗口内的 `RTCPeerConnection` 发送；编码由 Chromium 完成 | 不引入原生依赖；代码量小；只在有会话时创建窗口。单机 10 分钟验证稳定 |
| Node 原生采集 | Host 进程内用原生接口采集（DXGI 或 Windows Graphics Capture），再接 `node-datachannel` 等库发送 | 要新增原生采集模块、编码器和 WebRTC 库，工作量和维护风险都大得多。不采用 |

单机验证（Electron 43.1.0）摸清了四件事：

- 采集窗口申请的权限名是 `media`，不是 Electron 文档里写的 `display-capture`。请求详情里 `mediaTypes` 为空，并带请求页面地址，可以据此把放行范围收窄到采集页。
- 必须注册 `setDisplayMediaRequestHandler` 并在其中指定主显示器，否则 `getDisplayMedia` 立即报不支持。旧式 `chromeMediaSource` 写法报找不到设备，已不可用。
- 隐藏窗口保持默认后台节流时 90 秒内也没有降速。
- 默认协商出来的是 VP8 软编码；把 H.264 排到首选之后走英伟达硬件编码，渲染进程的占用从约 6% 降到约 2.5%（单核口径）。

### 3.3 信令通道

握手消息很少：一次会话只有邀约、应答、若干地址候选和状态通知，合计十几条小消息。

| 方案 | 优点 | 代价 | 判断 |
| --- | --- | --- | --- |
| **HTTP 轮询加会话表（选用）** | 复用现有设备通道和登录态；会话存数据库，多 worker 天然共享；不占长连接；不受代理超时和进程回收影响 | 每一跳增加约 0.5 秒延迟；Runtime 要等到下一次心跳（最长 5 秒）才知道有请求 | 信令量太小，不值得为此引入长连接 |
| WebSocket | 实时；服务端已有先例，nginx 已配升级头 | 两个连接可能落在不同 worker，要接 Redis 发布订阅；要处理断线重连、浏览器端票据鉴权、进程回收；Runtime 端还需新增 WebSocket 客户端 | 列为后续优化，首版不做 |
| SSE 推送加 HTTP 提交 | 网页到服务器方向实时 | Runtime 到服务器方向仍要另想办法，跨 worker 同样需要发布订阅 | 不单独采用 |

时延的大头不在信令：从点击到出画面，等心跳最长 5 秒，单机实测建连、确认设备、采集、首帧合计 1.7～2.7 秒。要提速应先解决心跳等待。

### 3.4 穿透与线路

只有直连，按先成功者选路：

| 线路 | 条件 | 画面路径 | 延迟 |
| --- | --- | --- | --- |
| 局域网直连 | 两端在同一网段，能互通内网地址 | 内网直达 | 通常 20 毫秒以内 |
| 点对点直连 | 双方路由器允许「打洞」（锥形 NAT） | 两端公网地址直达，不经服务器 | 30～80 毫秒 |

STUN 只帮两端发现自己的公网映射地址，不转发画面。有些网络组合本来就打不通，例如两端都是对称 NAT（企业防火墙和手机网络上常见）。这种情况就是「当前网络无法直连」，产品把它当作明确的结果，不设服务器中转；中转是否做另行立项。

国内网络还有一点：浏览器默认使用的公共 STUN 服务器在国内不可达或很慢，需要自建 STUN。单机验证时本机能连上几个国内的公共 STUN 服务，采集端由此得到了公网映射候选。

## 4. 关键难点

### 4.1 同一台电脑怎么识别

要求：同一台电脑时直接提示不可用，不能传出任何画面。几种思路：

| 思路 | 问题 |
| --- | --- |
| 比对双方公网出口地址 | 只能当线索。同一局域网里所有电脑出口相同，分不出「同一台」和「同网段的另一台」；同一台电脑上浏览器走了代理时，两端出口还可能不同 |
| 浏览器上报本机内网地址或主机名 | 浏览器没有这种接口；WebRTC 会把内网地址替换成随机的 `.local` 名字 |
| 回环探测（初稿方案，已放弃） | 网页请求本机 `127.0.0.1` 上的 Runtime。它依赖浏览器对「公网页面访问本机地址」的权限，用户拒绝时读不到应答，下不了结论。初稿把这种情况当作「另一台电脑」继续，评审指出这是漏洞 |
| **先建连，再比对观看端地址（选用）** | 连接建立后才有地址可比，所以连接里不能带画面：先建一条不含画面的连接，确认不是本机之后才开始采集。连接统计里对端地址是隐藏的，判定只能靠地址候选加解析 |

选用方案的做法见设计文档 4.2 节。要点是三种结果：确认同机、确认非同机、无法确认，只有确认非同机才采集。证据只有三样，都来自地址候选：网页内网候选解析出的地址（mDNS 名字交给 Runtime 的系统解析器）、网页的公网映射地址、Runtime 自己的公网映射地址。连接统计用不上：浏览器不提供对端的实际地址。

同网段靠「解析出的地址不是本机」放行，跨网络靠「两端公网映射地址不同」放行，证据不足一律无法确认。**这两条放行路径都还没有真实设备的证据**，见 6.2 节。

### 4.2 浏览器「本地网络访问」权限

Chrome 142 起（本机当前为 Chrome 158、Edge 156）对「公网页面访问本机或局域网地址」增加了权限弹窗，Edge、Firefox 跟进。对本功能的影响现在只剩一处：公网 HTTPS 页面连接内网地址时，浏览器可能询问用户；不允许时局域网直连用不了，同一网络下点对点通常也连不上，结果就是「当前网络无法直连」。

单机实测的浏览器行为（Chrome 157、158，Edge 156）：

- 从回环地址或内网地址打开的页面访问本机回环服务不被拦截、不弹权限，把三个本地网络权限（`local-network-access` 及拆分出的 `local-network`、`loopback-network`）设为拒绝也不影响。
- 内网地址的 HTTP 页面里这三个权限恒为「拒绝」且无法授予。
- Chromium 对 WebRTC 连接内网地址的权限门控在官方状态页上仍为「提案」。本机上回环和内网来源的页面在各种权限设置下候选都不变，未发现门控；公网来源无法在本机实测。

企业管理员可以通过浏览器策略为站点预先放行，部署文档里要写明。

### 4.3 局域网直连的现实条件

单机验证把实际情况摸清了：

- 拿到屏幕采集权限的 Runtime 采集窗口公布的是**真实内网地址**，所以浏览器连接 Runtime 不需要 mDNS。
- 浏览器页面出于隐私只公布 **1 个 mDNS 名字**。Runtime 要主动连到浏览器，必须先解析这个名字，或者等浏览器的探测包先进来。
- 未签名的程序第一次监听端口时，Windows 会弹出防火墙提示：点「取消」会留下一条入站阻止规则，点「允许访问」才是放行。测试程序两种状态都出现过（见 6.1）。Chrome 和 Edge 的安装程序则给自己加了一条只放行 UDP 5353 的「mDNS-In」规则。
- Windows 的系统解析器能解析浏览器注册的 mDNS 名字：本机验证中 Chrome、Edge 和 Electron 的候选名都解析成了这台电脑自己的网卡地址。这条路不需要管理员权限。**只验证了同一台电脑上的名字**；另一台电脑上的名字能不能解析，需要两台电脑时验证。

所以同网段直连按三层争取，逐层退让：安装器在可提权时为 Runtime 添加与 Chrome 相同的规则；不可提权时由 Runtime Host 用系统解析器解析出真实地址再交给采集窗口；两者都不成立时界面提示在防火墙提示里点「允许访问」；仍然连不上就提示无法直连。跨网络的点对点不受这个问题影响，出站流量会在各自防火墙上打开回包通道。

### 4.4 锁屏、多显示器与缩放

- 锁屏和系统安全桌面（UAC 弹窗、登录界面）下采集不到画面。Runtime 已有锁屏检测（`OpenInputDesktop`），可以复用来通知网页「已锁屏，画面暂停」。
- 首版只采主显示器。高分屏按 720p 等比缩放，文字会变小，观看端提供原始大小和全屏。
- 远程桌面会话断开后控制台可能被锁定，同样表现为锁屏。

### 4.5 安全与隐私

- 画面由 WebRTC 强制端到端加密，服务器只能接触到握手描述。
- 采集只在「确认观看端不是本机」之后开始。确认是本机、无法确认、无法直连时全程不采集。同机浏览器单独走另一条出口时有一个接受的例外，见设计 4.2。
- 画面走点对点，服务器失联时媒体仍会继续传，所以由 Runtime 按画面租约自己限时停止：连续 30 秒收不到服务器的确认就关闭采集。这只管实时画面，不影响其他 Agent 任务。
- 发起权限：只有配对该设备的账号本人，且设备在线并上报了本功能能力。同一台设备同一时间只允许一个查看窗口。
- Runtime 端在窗口和托盘持续显示「正在远程查看」，本机可随时停止或拒绝。
- 只看不控：不传键盘鼠标，Runtime 不获得任何来自网页的输入。
- 查看不占用桌面锁、不产生工具调用、不计费，不影响正在执行的 BOSS 等任务。
- 保留审计：谁在何时查看了哪台电脑、判定结果、走的哪条线路、何时因何结束。

### 4.6 与设备心跳、Agent 任务的关系

现有代码里有两条硬约束，决定了画面这一路必须自己兜住：

- 服务端的心跳处理是一个整体，任何一步出错都返回 500（[设备接口](../../src/local_tools/api.py)的 `runtime_heartbeat`）。
- Runtime 只在心跳成功之后才补传旧回执；心跳失败就标记离线并退避重试（[Host 轮询循环](../../clients/shared/local-tool-host-core/src/legacy/pollLoop.ts)的 `heartbeatLoop`）。

画面会话的通知和续期挂在心跳上，所以：服务端把画面会话的查询放在设备更新之后单独做并限时，出错不影响心跳成功；Runtime 把画面会话逻辑放在主循环之外的独立流程里，异常不外抛。这样画面查询出问题时，任务领取、任务租约、回执补传照常，只是画面 30 秒后按租约停止。细节见设计文档 4.4 节。

和 Agent 任务并行方面，代码上没有任何共享状态：插件进程、任务租约、结果补传与画面互不相干。2026-11-25 做了一次单机模拟并行实测（见 6.1 节「与插件工具并行」一行）：用验证程序的本机自测模式提供采集负载，同时运行已安装的微信插件里群聊总结在本机读微信窗口的那一步，开采集只慢 0.3～1.1 秒，12 次全部完成，编码器没有出现 CPU 受限。设计上定了任务优先、但能降画质就不停观看：编码器在 CPU 跟不上时自动降帧；任务运行中持续受限就降低画质继续观看，降低后仍然受限才停止观看（设计 4.5）。这只是一台高配电脑、一种工具的结果：判断「受限」的信号是否可靠、时长是否合适，以及降低画质能不能解除受限，要在性能弱的机器上用真实任务校准（Phase 4）。

## 5. 与现有契约的关系

本功能新增以下共同接口，按[共同契约](../system/runner-desktop-runtime-integration-contract.md)第 8 节需在实施前登记检查点（草案见设计文档第 9 节）：

| 接口 | 性质 | 旧端行为 |
| --- | --- | --- |
| 设备心跳能力新增 `screen_stream_v1` | 加性 | 旧 Runtime 不上报，功能对它不可用，其余不变 |
| 心跳响应新增 `screen_stream` 支持标记和 `screen_session` 通知；传画面期间每次心跳都带当前会话 | 加性，可选字段 | 旧 Runtime 忽略 |
| 新增设备侧信令接口、用户侧会话接口 | 新路由 | 不调用 |
| Host 状态新增 `screen` 字段、管理接口新增 `screen.stop` | 加性 | 旧界面忽略；schema 与 fixture 同步更新 |

不改动任务领取、许可、回执、恢复和计费链路。

## 6. 验证结果与剩余项

验证在一台 Windows 电脑上完成：i7-14700KF（20 核 28 线程）、RTX 4090、单显示器 2560×1440，Electron 43.1.0（Chromium 150），Chrome 157 与 158，Edge 156。验证程序在 `spikes/runtime-screen-stream-poc/`（用法见其 [README](../../spikes/runtime-screen-stream-poc/README.md)），画面只在隐藏窗口或本机浏览器之间传输，不显示、不落盘，输出只有数字和类型。

**单机实测只证明采集、编码、播放和判定逻辑成立，不能证明客户网络能直连。** 验证里两端配的是同一个 STUN 服务，但两端在同一台电脑上，选中的始终是内网路径，**还没有跑过真正的跨网络打洞**。

### 6.1 已验证

| 编号 | 结论 | 实测数据 |
| --- | --- | --- |
| P1 隐藏窗口采集与稳定性 | 通过 | 不可见窗口里 `getDisplayMedia` 约 0.6 秒完成采集。连续 10 分钟 1280×720，平均 14.8 帧，最低 14 帧，丢包 0，丢帧 0，两次合计 0.67 秒的轻微停顿 |

| P1 采集方式与权限 | 只能用 `getDisplayMedia`；权限名是 `media` | 不注册请求处理器直接报不支持；旧式写法报找不到设备；屏幕采集申请的是 `media`，`mediaTypes` 为空 |
| P1 地址候选 | 采集窗口公布真实内网地址；浏览器页面只公布 1 个 mDNS 名字 | 采集窗口在 3 个网络接口上各得到 1 个 UDP 候选。Chromium 不采集回环地址候选 |
| 先建连后采集 | 可行，不需要重新协商 | 先建不含画面的连接，确认之后才采集并用 `replaceTrack` 接上。30 秒 14.8 帧、零丢包，路径无中转。首帧比先采集的顺序晚约 0.25 秒 |
| Runtime 只主动连出 | 可行 | 让验证程序按产品里的做法运行：本机不监听任何端口，只主动连接一个独立的信令中转进程取送信令。Chrome 158 经它观看正常，H.264 720p 15 帧，30 秒无卡顿，路径无中转 |
| 同机判定 | 观看端在本机时判为同机，不采集；没有证据时不放行 | 连接建立后 0.1～1.2 秒给出结论（规则 1），采集始终没有开始。本机没有公网映射地址时，名字解析不出落到无法确认，不会误放行。用开关模拟「另一台电脑」和「解析不出名字」，前者按规则 2 开始采集，后者按规则 4 不采集；这两条只验证了判定之后的动作。四条规则另用构造的地址单测了 21 种组合 |
| 规则 2、规则 3 的真实证据 | **没有** | 同网段另一台电脑的名字能否被本机解析、跨网络时两端的公网映射地址是否不同，都需要真实设备。旧版规则依赖连接统计里的对端地址，而浏览器从不提供，等于跨网络永远放行不了；新版已改为只用明文可见的候选 |
| 直连失败 | 不采集，会话按时结束 | 两端不交换地址时连接建立不起来，采集始终没有开始；30 秒建连超时后 Runtime 结束会话，观看页随即收到结束原因。另外发现：完全没有候选地址时 ICE 自己不报失败，超时必须由会话自己计时 |
| 画面租约 | 到期后自行关闭 | Runtime 停止联系服务器后，采集在最后一次联系之后 20.1～20.2 秒关闭（租约设为 20 秒），观看页收到结束原因。本机信令和信令中转两种模式各验一次 |
| P6 建连时延 | 点击到首帧 1.7～2.7 秒 | 先采集的旧流程是 1.0～1.8 秒。多出的是先建连、再确认设备这一步。经信令中转、Runtime 靠定期取信令得知有请求时，从打开观看页到首帧约 6.5 秒，其中约 4.6 秒在等 Runtime 的下一次定期取信令（对应产品里等心跳） |
| 互通 | 真实浏览器能正常观看 | Chrome 157、158 与 Edge 156 都以 14～15 帧解出 Electron 发出的 H.264 720p 画面，选中的路径没有中转 |
| 服务器带宽 | 不随视频码率增长 | 经独立的信令中转进程观看 30 秒：建连时中转约 24 KB，传画面期间中转进程每 10 秒经手约 0.5 KB，同期视频约 0.7～0.9 Mbps |
| 浏览器权限 | 回环地址和内网地址打开的页面访问本机回环服务不被拦 | 默认状态和权限设为允许或拒绝时都一样，见 4.2 |
| 防火墙 | 未签名程序首次监听端口会触发 Windows 防火墙提示 | 早先记录到这个测试程序有两条入站阻止规则；2026-11-24 复查时同一程序的两条规则（TCP、UDP 各一条）是入站放行。验证程序不改防火墙，何时被改成放行未知 |
| 系统解析器 | 能解析本机浏览器注册的 mDNS 名字 | 解析结果是这台电脑自己的网卡地址。只验证了同一台电脑 |
| 对端离开的检测 | 只靠连接状态较慢 | 网页离开后几秒内 Runtime 侧报告断开，10 秒后报告失败，并在那时关闭采集，合计约 12～16 秒。设计里网页正常关闭时会先发结束信令，不用等这么久；这一条验证程序没有实现 |
| 观看页的一个坑 | 不能预先加只收通道 | 预先加的通道在协商时没有被复用，画面落在另一条通道上，帧在解码但画面出不来。要用 `ontrack` 给的轨道 |
| 与插件工具并行（2026-11-25，单机模拟） | 开采集时工具只慢不到 1 秒，编码器不受限 | 验证程序 `pair` 模式提供采集负载（发送和接收都在本机，比实际略重），同时调用已安装的微信插件 0.1.3 的群聊时段总结，只取它在本机读微信窗口的那一步（不配服务器地址，读完后在本地停住，不联网、不计费）。每次都从微信在后台开始，用户没有键鼠操作时才执行。不开采集 4 次：18.8～19.6 秒，平均 19.1。开采集 8 次：硬编码 3 次平均 19.5，软编码 3 次平均 19.4，硬编码加画面持续变化 2 次为 19.5 和 20.8；合计平均 19.6。12 次全部完成。传画面期间帧率始终约 15 帧，`qualityLimitationReason` 全程不是 `cpu`。整轮占用：硬编码约 0.35 个核心，软编码约 0.35 个核心，画面持续变化时 0.4～0.48 个核心。**没有经过 Runtime 的任务链路，也没有在性能弱的电脑上测**；降低画质的接口没有验证。受限原因当时是用验证程序的临时副本采样的，验证程序本身从 2026-11-25 起在摘要里记录 |

| 三、直连失败（跨机复核） | 单机已通过，另一台电脑上再确认一次 | 同第一组 | 网页提示无法直连；Runtime 未采集或已关闭采集；服务器不留残留会话 |
| 同机判定的真实证据 | 同网段靠什么放行（规则 2），跨网络靠什么放行（规则 3） | 并入第一、第二组；验证程序摘要里的 `rule` 和 `evidence` 给出判定用的规则和当时手里的证据 | 第一组：规则 2 放行且采集在判定之后；名字解析不出时为规则 4。第二组：规则 3 放行；STUN 不通时为规则 4。同机始终不采集（浏览器单独走另一条出口的例外除外，见设计 4.2） |
| 与任务并行 | 经 Runtime 的完整链路：先观看后派任务、任务中开观看、停止观看、仅画面信令失联时，任务是否照常；性能弱的电脑上资源不足时能否靠降低画质继续观看 | 真实的插件任务和 Windows 真机；另需一台性能较弱、没有硬件编码的电脑（单机模拟的结果见 6.1 节） | 任务照常领取、执行、续租、上报，不暂停、不取消、不重跑；资源不足时先降帧，持续受限则降低画质继续观看，降低后仍持续受限才停止观看 |
| 画面不拖累心跳 | 画面会话查询失败时心跳是否照常成功；画面停止是否影响任务 | Phase 1、Phase 2 完成后做故障注入 | 心跳成功、设备在线、回执补传照常；只关画面 |

| 锁屏与显示器 | 锁屏、UAC、远程桌面断开时的画面；多显示器；其他缩放比例 | 锁屏需要用户在场时触发一次；多显示器需要第二块屏幕 | 锁屏时画面停止更新且提示正确 |

## 7. 需要用户决定或安排的事项

2026-11-24：设计上的几项（只做点对点、接受 5 秒唤醒、Runtime 端无需确认、只有配对账号本人可看、首版主显示器 15 帧）已确认按默认执行。交互原型待确认。验证还需要三样条件：

1. 一台同网段的第二台电脑，用来做第一组验证。
2. 跨网络测试环境，以及一个两端都能访问的信令入口和一个自建 STUN，用来做第二组验证。信令入口和 STUN 的部署需要你指示。
3. 一个公网 HTTPS 测试页：部署到 agent3（需要你授权），或者同意在本机用浏览器策略临时把本机地址标记为公网（会改动浏览器设置，验证后恢复）。

另有一件遗留事项需要你确认：这台电脑的防火墙里，测试用的 `electron.exe` 现在是两条入站放行规则（TCP、UDP）。如果不是你有意保留的，验证结束后可以删掉；删除需要管理员权限，由你决定。
