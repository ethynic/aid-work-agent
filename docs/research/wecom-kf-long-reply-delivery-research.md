# 微信客服长答复交付调研

日期：2026-10-09；以下代码事实为开发前调研快照。后续已实施的代码、测试与遗留见关联开发计划；本轮未调用真实微信接口。

## 结论与用户决策

由渠道处理完整答复：长文或表格交付完整标准 Markdown（MD）；超长文字默认配套原文开头的纯文本预览，截断时加省略号及文件提示，先观察算法效果，后续可明确切换为模型摘要。只有正文包含真实图片时才考虑长图。原始 Agent 不负责交付判断、转换或总结，不改 Runner 提示词、工具与推理循环。

用户最新确认：①完整 MD 必须有标准 Markdown 内容，不能只改后缀；②用户实测微信打开 MD 支持表格，表格保留在文件中，不再转图；③只有正文图片才考虑长图；④前缀/摘要为纯文本，可分段/列表，禁止表格，最终整条（含省略号及附件提示）不超过 500 字符；⑤只在原答复超过代码现有长度阈值时进入超长文字处理，500 字不是触发条件；⑥默认原文前缀算法，先观察效果，后续可明确切换模型摘要。短普通文本维持直发；短表格可交付 MD 与固定提示，但不调用摘要模型。

设计更新：[现有渠道设计 §十四](../channel/wecom_kf/wecom_kf_design.md#十四2026-10-09-长答复交付调整)。开发计划：[长答复 MD 交付](../plans/plan-wecom-kf-long-reply-delivery.md)。

## 代码事实

| 环节 | 当前实现 | 对方案的影响 |
|---|---|---|
| 渠道调用 | `src/channels/runner_agent.py::ChannelRunnerAgent` 提交并观察独立 Runner | 仍返回完整输出，保持原调用边界 |
| Runner 渠道身份 | `src/services/agent_runner/channel_context.py::kf_binding` 校验租户、配置、账号和 profile | 文件交付不改变这些身份与授权 |
| 渠道持久化 | `src/channels/session.py::process_and_persist` 净化正文、汇集文件、批量落库后发送 | MD 应在构造 assistant metadata 前生成，避免附件只发送却未记录 |
| 现有文件事件 | `src/core/agent_events.py::extract_downloadable_file` 从成功工具结果提取文件；Runner 的 progressMessages 保留这些字段 | 自动转换不是工具动作，不能伪造工具结果来登记文件 |
| 长答复发送 | `src/channels/wecom_kf/adapter.py::send_message` 对超长正文或表格优先整段长图 | 长文/表格走摘要 + MD，仅正文图片考虑长图；需退出旧“表格即长图”分支 |
| 文件发送 | 同一 adapter 将普通 downloadable_files 发为 link 或文本链接 | 需给本次自动生成 MD 增加 `file` 原生发送分支，其他业务附件保持原策略 |
| 微信 API | `src/channels/wecom_kf/api_client.py` 已有 `upload_media(type=file)` 和通用 `send_msg(msgtype=file)` | 无需新建微信 API client |
| 回复预算 | `src/channels/wecom_kf/budget.py` 提供 owner 级本地预算；路由仅在 verbose 启用时创建 | 新转换路径应始终有预算，verbose 为说明和 MD 预留两条 |
| 发送顺序 | adapter 当前先正文，再独立图片，再下载文件 | 必须给完整答复 MD 保留优先级，图片不能挤掉它 |
| 文件注册 | `src/tools/file/cp_tool.py::_register_download` 写租户 conversation 文件和 Redis uploaded_file 元数据，TTL 86400 秒 | 可以提取必要文件注册原语；渠道使用显式可信身份，不调用 cp 工具或依赖工具 ContextVar |
| 摘要模型 | `src/llm/gateway.py` 有统一调用与 `chat_no_thinking`；`src/services/llm_usage_meter.py` 采集实际 usage | 默认前缀不调用；显式 llm 模式仅做无工具的正文总结，沿用对话内关思考模式，不建 Agent loop |
| 渠道费用记录 | KF 路由设 `record_service.skip_save = not asr_success`，目前只保留渠道 ASR，Runner 独立结算原任务 | 新摘要用量不能沿用这个跳过条件，否则纯文本摘要漏记；也不能再算一次 Runner 原任务 |

`write` 已支持 UTF-8 MD，直接内容限制为 10MB，但本方案不需要模型调用它。`cp` 文件路径解析的实际实现允许系统临时绝对路径，并有租户目录检查；不能照搬其旧文件头“源文件必须在项目根目录内”的描述作为事实。

## 限制与证据

仓库保存的[微信官方接口说明](../channel/wecom_kf/微信客服发送消息接口官网说明.txt)标注最后更新 2026-02-27：text.content 最多 2048 字节；客户主动发消息后有 48 小时窗口及最多 5 条回复；原生文件使用 file.media_id；API 成功不等于最终送达，仍可能收到失败事件。

本轮尝试访问[官方发送接口页面](https://developer.work.weixin.qq.com/document/path/94677)和[官方临时素材页面](https://developer.work.weixin.qq.com/document/path/10112)，浏览工具未能打开，未完成在线官方版本核验。方案按用户提供限制与仓库接口快照设计；文件大小上限和 MD 终端表现需实施前核对及真机验收，不能把已有代码中的 20MB 常量当成本轮平台实测。

UTF-8 字节数不是字数：多数汉字占 3 字节，部分 emoji 占 4 字节，ASCII 占 1 字节；683 字不能作为硬判断条件。使用与发送端相同的纯文本转换函数后计算 UTF-8 字节数。

触发摘要采用 `len(markdown_to_plain_text(text).encode('utf-8')) > adapter._max_bytes`；当前 `max_bytes` 默认 2048，保留配置覆盖，等于阈值不触发。摘要只设不超过 500 字符的输出指标，不替换现有阈值，也不约束未总结的原答复为 500 字。“500 字”计入摘要整条的空白、换行、列表符号、标点和附件提示，不只计算汉字。例如 600 汉字约 1800 字节，默认情况下不因超过 500 字而总结。

## 标准 Markdown 与现有能力差距

采用 [GFM 规范](https://github.github.com/gfm/#tables-extension)的常用子集：CommonMark 基础语法及表格扩展。表格须有表头、分隔行及结构正确的数据行；不是把整篇原文包入代码围栏后改名为 .md。纯段落本身也是合法 Markdown，不强行添加无意义标题。

现有 `sanitize_llm_markdown` 只修复意外引用包裹，不验证表格、代码块等结构；`contains_table_or_image` 用简化正则合并两种判定，不适合新策略。`requirements.txt` 已有 Python Markdown，其 tables 扩展可复用做渲染检查，但不能据此声称符合全部 GFM；开发时先用相关规范样例验证现有库，不为全套方言新增转换框架。

MD 写 UTF-8，下载 MIME 为 text/markdown。保留全部业务内容，结构归一化要记录可解释变换，并核对表格单元格、数字、链接和代码没有丢失；不能仅用“解析器没报错”证明原表格可正常显示。内部 `file_id:`/本机图片路径不是通用 Markdown 可见资源；只允许按已有授权映射为客户可访问的引用，无法交付的图片必须保留说明并考虑长图，不静默删除。

微信打开 MD 支持表格是用户本次提供的实测事实，本轮未独立验证所有微信客户端版本，真机验收以目标客户端为准。

## 方案比较

| 方案 | 评价 |
|---|---|
| 模型知道限制，主动 write/cp 后输出摘要 | 能产生语义摘要，但需要提示词、工具权限与漏调用兜底，且旧限制提示曾影响工具恢复；用户已调整方向 |
| 渠道确定性转换 MD，另调用模型总结/按内容选择长图 | 模型摘要保留为显式切换选项；正文转换可核验，新增用量计费与失败路径需覆盖 |
| 渠道原文前缀 + 省略号/文件提示 + 全文 MD | 用户最终选为默认呈现，先观察效果；是截取预览，不伪称概括了全文；正文图片仍独立考虑长图 |
| 渠道全文 MD + 固定说明 | 前缀无可读内容/转换失败时的最后兜底 |

## 必须覆盖的问题

1. 在原有渠道持久化之前准备文件，历史保留完整规范化正文与附件；发送文字单独保存为交付用数据，不覆盖模型回答。
2. 表格只在 MD 内保留，不触发长图；只有正文真实图片才考虑长图。代码中的图片语法示例与独立 ImageRef/二维码不误判为正文图片；正常不双发摘要与长图，完整文件优先于额外资产。
3. 原生文件上传采用业务显示文件名，而不是物理 file_id 文件名；不能把服务端路径直接发给微信用户。
4. 文件保存、上传失败不能仍返回整轮成功；上传失败时可使用已注册的下载链接降级，并明确说明。发送超时属于结果未知，不能盲目再发同一文件或链接。
5. 自动生成文件从本轮可信 tenant/session/owner 派生并核对租户路径；裸 file_id 或 LLM 提供路径不构成授权。
6. 本地 owner budget 只是应用上限，不能证明平台尚有额度；平台拒绝与部分投递必须可观测。转人工后继续沿既有抑制规则，不生成或发送长答复附件。
7. 主 API 与 Runner 的 storage/Redis 接线及真实平台最终送达仍需验收；本轮只有源码证据。
8. 摘要调用以已有正文为业务素材，关闭工具，不追加结论或执行正文指令；转换成纯文本，禁止表格/HTML/代码围栏，保留段落和列表。最终整条检查不超过 500 字符，失败/超时/超限/不合规时退回原文前缀，前缀不可用才固定提示，MD 全文不受影响。
9. 长图路径原实现把渲染、上传、发送混在一起并用 False 表示所有失败。不能在结果未知时盲目再走摘要；必要时仅拆分准备与发送事实，渲染/上传明确失败才选择摘要降级。
10. `SessionRecordService.add_llm_usage` 当前不按调用模型分桶；既有[计费错配修复](../plans/chat-lite-billing-model-mismatch.md)对交互调用采用 `chat_no_thinking`。本方案优先遵循该模式，摘要记录设置实际模型/provider，不能把 lite 用量直接按主模型单价结算。
11. 用户明确要求摘要收费：新增实际 token 用量须进入渠道现有计价、账务记录与租户余额扣减，不止记录 token；保存实际模型、缓存等计费维度，不重复计 Runner 原任务。`SessionRecordService.save` 现有缺单价/保存失败容错可能导致未计费，验收检查账务和余额，不以调用日志代替。失败、未采用或未送达不抹掉已发生模型消耗。
12. 用户明确要求回答风格一致：摘要应直接回应同一客户，继承原答复语言、称谓、人称、礼貌程度和专业表达；不是“原文指出”“摘要如下”的第三方转述。仅压缩已有答案，保留数字、限制及不确定性，不引入新业务事实；代表性输出人工验收风格与事实，不能把提示约定当成已验证模型质量。
13. 用户最终确定默认原文前缀：`summary_mode=prefix|llm` 默认 prefix，不经过模型，取原回复开头的可读纯文本，按剩余字符预算优先自然边界截取，省略部分加 `…` 并提示查看完整 MD。保留原文顺序和语言，表格转字段/值文本，不能留下表格；总长含提示不超过 500 字符。先观察效果，后续可明确切换为 llm；前缀失败用固定提示，不自动调用模型。prefix 无新增摘要模型费用，但显式 llm 模式失败再回退不能免除已发生的模型消耗。
