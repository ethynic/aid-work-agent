# agent3 Runner 端到端混合负载实验（2026-11-06）

## 范围与方法

从本机脚本向 `https://agent3.aidingyi.cn` 发起真实 HTTPS 请求（DNS 指向 `124.222.3.254`），经宿主机 Nginx 的 `/api/` 反代到 `aid-agent-api3:8000`，再由主 API 访问内网 `aid-runner-api3:8091`。脚本为每个样本创建独立会话、提交 Runner、轮询终态，并每约 5～9 秒采样业务库中的 `attempt`/`worker_id`/执行起点及容器 CPU、内存和数据库连接。脚本见 [`scripts/agent3_runner_load.py`](../../scripts/agent3_runner_load.py)，原始脱敏指标见 [单条](evidence/agent3-load-smoke-20261106.json)、[三并发](evidence/agent3-load-mixed-20261106.json)、[四并发](evidence/agent3-load-four-20261106.json)。指标文件不含认证令牌、原始历史问题、模型回复或表格数据。

历史 agent3 数据分析 Runner 的只读聚合显示，常见问题围绕渠道、销售、订单、同比/环比、成本；46 条完成任务的 p50 约 63 秒、p90 约 129 秒。实验问题按这些类别重新编写。为避免使用其他租户的真实数据，在专用 `test` 租户通过正式上传和 Schema 接口建立 20,000 行合成订单 CSV（文档 ID `13517`，无客户或人员字段），确认 `source_status=available` 后测试。另一个 `test` 租户运行普通问答与旅行顾问的纯文本问题。仅使用这三个不要求外发/提交操作的 profile；招聘、获客、社媒、售后等 profile 可能执行外部动作，本轮未纳入。临时 Web token 在每轮结束后删除，最终库内剩余 0 个本实验 token。

### 槽数判断（用户要求 Runner 常开后复核）

agent3 宿主向系统提供 4 个逻辑 CPU（`nproc=4`，`lscpu` 显示每核 1 线程），总内存约 7.3 GiB；两槽执行后宿主可用内存约 1.8 GiB，两个 Worker 常驻约 275 MiB。业务库 `max_connections=80`，本轮峰值实际 17；当前单 Worker 业务连接池上限 15，监督进程上限 2。若直接设置 8 槽，仅 Worker 与监督进程的最坏连接上限就达到 `8×(15+2)=136`，尚未计入 API、background、monitor 和运维连接；8 个 Worker 各自 1 GiB 的内存上限相加也已超过整机内存。CPU/内存上限不是预留量，连接池上限也不表示连接会同时用满，但这些预算说明 **不能凭 CPU 线程数直接把本机设为 8 槽**。当前保留 2 槽；若提高，先在同机逐档测 3 槽，并同时评估连接池、内存余量、模型限流与每任务费用。4 核 8 线程的其他机器也需按相同资源和负载核算，超线程不等于 8 个完整物理核心。

## 环境变更与剩余验收

agent3 原有 `.env` 显式配置 `AGENT_RUNNER_WEB_ENABLED=false`，最初准入检查因此停止，没有产生 Runner。为完成端到端试验，备份 `.env` 后临时改为 `true` 并仅重建主 API。重建暴露出此前 `.env` 的 `600` 权限/所属组与容器内 `appuser` 不匹配，主 API 曾因 `PermissionError` 重启 9 次；将该文件改为组 `999`、权限 `640` 后恢复。实验结束曾把开关恢复为 `false` 并确认健康。随后用户明确要求 Runner 模式常开，已再次将 agent3 设为 `true`，主 API 运行时配置读到 `True`，6 个容器均健康。备份留在 agent3 的 `.env.bak.runner-load-20261106` 和 `.env.bak.runner-web-on-20261106`，未输出其中任何值。

本轮没有复现“某个同步工具调用连续阻塞超过 30 秒租约”的精确定向场景；数据分析总执行超过 30 秒不能替代单次阻塞工具证据。也未触发默认 30 分钟运行告警、验证平台飞书发送或已交付旧 Runtime＋CLI 组合；未审查模型回答质量或跨租户内容隔离。因此 Phase 4 仍在进行中。合成表与标记为 `LOADTEST` 的会话保留在专用测试租户，供后续对照；不将本轮 2 槽/1 GiB 配置推广为正式环境容量定值。
