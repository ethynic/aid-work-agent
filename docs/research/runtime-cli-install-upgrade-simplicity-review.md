# Runtime 与 CLI 安装升级独立简化评估

日期：2026-10-30。代码基线：master `5fafa3d0`。

范围：Runtime 桌面安装、连接恢复、插件管理、BOSS/WeCom 打包与能力发布。采用独立技术顾问视角，评价现有机制的必要性，不以既有设计作为正确性前提。本轮只读分析产品代码；未运行安装、升级、业务调用或监听，未修改当前客户端。本文是评估建议，不是已批准的实施设计或开发计划。

## 结论

存在明显可以裁剪的过度设计，集中在安装、连接修复和业务执行恢复的耦合。用户提出的“能覆盖升级就覆盖升级，不能则干净重装并保留兼容配置”应成为默认路径；插件同理。

维护风险已体现在：历史任务影响无关插件安装，安装中断不能自动收敛，列插件触发完整验包，目录结构制造长路径压力，验收签名根随打包批次增长。继续补异常分支和测试会固化这些问题，应先缩小必须保持的承诺。

必要承诺是：保留可用连接、正常升级后继续工作、真实任务按已有协议恢复、未知发送不重发。没有必要承诺重装后复原每一个旧本地执行进程和管理事务，更不应要求所有旧任务先结案才能修好安装。

当前代码也有合理部分：配置迁移已经是白名单、损坏旧指针不阻断干净安装、插件有独立不可变目录和原子写、包签名和自包含依赖。应复用这些基础，不整体重写。

## 经代码核实的问题

### 1. 普通安装也强制进入新代际与迁移

`clients/agent-desktop/scripts/runtime-clean-install.ps1:196` 的 Finalize 每次生成新 installation GUID 和 connection GUID，未按兼容升级与不兼容重装分支。`clients/agent-desktop/electron/runtimeInstallation.ts:213` 随后迁移身份、重导插件，再标记初始化完成。

代际隔离适合干净重装，但每次二进制升级都更换配置根、迁移大插件，扩大了失败面。正常升级应尽量复用稳定的数据目录，只有实际格式不兼容或明确重置才归档旧状态、白名单迁移。

不能把当前实现描述成“旧数据一坏就无法重装”：它已经允许部分迁移失败。问题是正常路径仍承担过多迁移工作。

### 2. 插件维护被全局历史任务绑定

`clients/shared/local-tool-host-core/src/management.ts:342` 在插件变更前停止整个 Runtime；`clients/agent-tool-runtime/src/runtimeHost.ts:131` 扫描全局 journal/session-tasks，要求每个旧记录都有完成证明。它没有按被修改的 provider 区分，旧 BOSS 未结案事实可以阻止 WeCom 安装。

停止自己的活动执行再换文件是合理的。要求无关历史任务全部结案才允许安装，是过度耦合。应允许下载、验包、安装到暂存区；切换版本时只处理受影响执行。初期仍停止整个 Runtime 也可以，不必立即做复杂的热更新，但不能继续以全局历史结案作为安装前提。

身份更换同样应区分“新连接可建立”和“旧任务能否在新身份下恢复”。允许前者，不等于自动转移后者的执行权限。

### 3. 安装中断标记变成无明确出口的阻塞

`clients/shared/local-tool-host-core/src/plugins/store.ts:63` 只要发现 pending.json 就直接要求核对；`transaction:210` 的标记只有 action 和 installation_id，进程硬中断后没有足够的提交状态用于自动收敛。

这不是更完整的事务恢复，而是遇到事务中断就停止。应复用现有暂存目录、不可变 release 和原子 inventory：保留最后提交的有效版本；未提交暂存目录隔离清理；损坏限制到对应插件。不能仅删除 pending 然后假定成功，须依据已提交指针和包完整性判断。

### 4. 查询插件列表承担了过重的验包与探测

`management.ts:248` 的 plugins.list 调用 refresh；`store.ts:104` 对已装插件逐个 checkRelease；`store.ts:217` 读取 archive、重新验证包、逐个比对 payload 文件，再启动 probe。`clients/agent-tool-runtime/src/pluginProbe.ts:19` 会运行 version 和 doctor 子进程。

对携带 Python、OCR 模型等大目录的 WeCom，这使普通状态查询也做昂贵的磁盘和进程操作，增加慢、瞬时进程和状态抖动。不能由静态代码断言实际每次耗时多少，但工作量本身已经不合理。

安装/升级完成时完整验包；列表返回已确认安装信息；业务就绪探测采用短期缓存或显式重试。执行文件完整性仍应按安装目录可写性和现有威胁边界保留必要检查，不能简单把验签结果永久缓存后忽略文件变化。

### 5. 已安装和业务暂未就绪仍混在一起

`store.ts:118` 仅在 ready 或 bootstrapKeys 命中时发布 provider 入口；`runtimeHost.ts:380` 只给 BOSS bootstrap 例外。其他插件即使已验证安装，也可能因为业务未登录等状态而不发布入口。

这会让 Agent 表现为“不具备工具”，而不是“工具已安装，请登录后重试”。服务端通用自动装配的修复尚不能消除 Runtime 这里的能力遗漏风险。

应让已安装、已启用、完整性与协议正确的插件可被发现；登录、窗口、网络状态通过调用结果和诊断返回。签名或协议真不兼容才禁止相应执行。不要继续逐个添加 BOSS/WeCom 特例。

### 6. 显式修复回退受版本门禁限制

`store.ts:139` 允许同一 release_id、同摘要的幂等重装，这是合理行为；但不同 release_id 必须严格升版本，且卸载留下的记录仍参与比较。明确安装旧版或同版本另一合法发行包，卸载后仍可能被拒绝。

保留“同一 release 不得悄悄变内容”；允许用户明确选择已签名、兼容且未撤销的已知可用版本。普通业务版本不应仅因数字较低就永远不可安装；若确有不可逆数据格式或真实安全撤销，再解释具体原因，而非普遍禁止回退。

### 7. 深目录与旧包保留造成持续成本

当前路径叠加 installation-v2/generations/GUID/connections/GUID/plugins/releases/GUID/payload，再承载 Python site-packages。长路径补救解决了现状下真实问题，但路径结构自身加重了问题。

Windows 长路径支持取决于调用 API、应用声明和系统设置，不能把系统开关当万能补救。参见 [Microsoft 路径限制说明](https://learn.microsoft.com/en-us/windows/win32/fileio/maximum-file-path-limitation)。

新安装建议采用较短的稳定根与 provider/release 目录，把连接标识保存在元数据里，不层层嵌入不变的程序资源路径。不建议为此新建跨插件 Python 依赖共享系统，自包含依赖仍更容易维护。

`store.ts:37` 明确保留旧 release；升级创建新目录，卸载只打标，缺少有界旧版本清理。建议默认保留当前和一个可回退版本；实际仍被未完成执行引用的内容延后清理。历史回执与执行证据另存，不能靠无限保留整个大插件包替代记录管理。

### 8. 验收打包策略使插件与 Runtime 再度耦合

`clients/agent-desktop/scripts/release-batch.ps1:154` 每次同时 bump Runtime/BOSS，`:200` 生成新测试 key_id，随后追加公钥并保存历史快照；`prepare-runtime.mjs:96` 要求保留历史快照中的验收根。

这是当前验收脚本的事实，不能外推成正式签名完全不能复用：正式插件打包已有外部 signer/profile 能力。

但如果不断把这套验收流程用于客户试用，临时签名者会随批次增长，新插件还可能因旧 Runtime 不认识新公钥而要求升级宿主。插件独立升级的目标被削弱。

客户交付应复用稳定发布者身份，正常补丁不换签名者；测试信任与正式交付信任分开，公钥轮换/撤销是明确事件。保留已交付旧包的兼容，不等于永久信任所有未交付试验包或永远无法撤销密钥。不要立即清空现有试用根，先识别真实交付范围并平滑过渡。

### 9. 离线迁移判断复核纠正

初评只沿`migrate`的verifyIdentity返回值推断离线会丢配置，未核对默认`validIdentity`的完整实现，此项判断不成立。S3源码复核确认现有实现网络异常返回可复用，非401/403也不丢弃，仅明确认证拒绝才阻止迁移。此处修正原结论，不把已有能力计为本轮新修复。

S3保留该实现，补充离线及明确认证拒绝的定向验证。联网后仍走原认证，凭据确实失效或无法解密才要求重配，不把“未验证在线”显示为在线，也不以迁移绕过服务器认证。

DPAPI 凭据通常受同一 Windows 用户及机器约束，所以“保留服务器地址”不能等同于“任意机器都能恢复原配对”。参见 [Microsoft CryptProtectData](https://learn.microsoft.com/en-us/windows/win32/api/dpapi/nf-dpapi-cryptprotectdata)。

## 建议的简单目标

Runtime 正常升级：停止自己的执行进程 → 替换程序 → 复用兼容配置 → 启动重连。数据确实不兼容或损坏：归档旧状态 → 干净安装 → 仅恢复可用的连接配置及同用户可解密凭据；不能恢复就重新配对。

插件安装升级：验签/核对协议 → 暂存解包 → 安全停止受影响执行 → 原子切换有效版本 → 启动。失败保留旧有效版本，提供重新安装或明确回退。不要求客户先登录业务应用才能安装、查看或诊断插件。

旧任务继续按现有 Device/Runner 协议恢复；重装不能证明的本地执行维持 unknown，并保留回执用于只读对账。它不应阻断新安装、无关插件或新的正常任务，也不能自动再发一次。

用户界面收敛为连接/重连、安装/重装插件、重置客户端及具体错误；无需让用户理解 generation、管理密钥恢复、重启登记等内部阶段。若自有进程或文件实际无法释放，再明确提示重启 Windows，不把重启变成历史状态不清时的常规前提。

## 必须保留的少量保护

- 验签、包完整性、平台及协议检查、解包路径安全。
- 仅操作自己拥有的 Runtime/provider 进程和目录，不清除客户的 Chrome/企业微信登录和数据。
- 连接凭据保护、正常认证、设备与实际执行权限边界。
- 未知发送不自动重试，回执/结果 outbox 不因重装悄悄丢弃。
- 服务端单独升级继续兼容已交付旧 Runtime/BOSS；不把简化安装变成强制客户升级。

## 后续收敛顺序建议

先处理客户可见的卡点：插件 pending 自动收敛、取消全局历史结案安装前提、已安装与就绪分离、列表不再全量验包探测。复用现有 store、inventory 和错误返回，不新增通用恢复框架。

随后处理成本来源：稳定签名者、短路径、显式重装/回退、有界旧包保留；最后按真实交付范围逐步缩小代际迁移和旧安装兼容分支。正常升级与干净重装采用不同路径，避免继续叠加管理恢复状态。

只验证实际承诺的场景：已交付 Runtime 0.0.29＋BOSS 0.3.27 在服务端升级后仍可工作；当前版覆盖升级与干净重装；离线保留配置；插件安装中断后原版本可用；未登录时工具可发现；unknown 发送不重发。具体实施时选择受改动影响的用例，不扩展成所有历史版本、所有损坏组合的测试矩阵。

以前通过的独立测试和 CR 证明当时限定修改的正确性，不能据此证明整体安装架构足够简单。本评估没有重新进行真机安装验收，也不声称上述建议已经落地。
