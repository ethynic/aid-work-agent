# 对 AID Work Agent 项目的真诚建议

> 日期：2026-08-12
>
> 性质：产品与工程战略审视，不是功能需求清单
>
> 适用范围：AID Work Agent 整体产品，包括 Web、渠道、服务端、Desktop、Runtime、数字员工、Skill 与行业解决方案
>
> 关联架构：[企业 Agent 平台总体架构](../system/enterprise-agent-platform/enterprise-agent-platform-integration-design.md)

## 1. 结论先行

AID Work Agent 已经不是简单的聊天机器人、模型套壳或技术 Demo。项目已经具备多租户、账号、计费、渠道、知识库、长期记忆、工具、Skill、子智能体、本地执行节点、可观测性和多种行业能力，其工程广度明显超过多数 Agent 项目。

但它目前更接近一个**能力丰富的企业 Agent 平台原型**，距离顶级产品仍有一段关键距离。差距不再是“少几个工具、模型或页面”，而是：

> 能否把已经积累的广泛能力，收敛为少数不可替代、可重复交付、可持续改善并能证明业务结果的企业工作系统。

前面已经形成的 Task、Policy、Execution Fabric、Evidence、Memory/Knowledge、Evaluation/Ops、Multi-Agent Collaboration 以及 Desktop 架构，解决的是平台可靠性和治理基础。本文不重复这些设计，重点讨论让产品从“可靠”走向“不可替代”还缺什么。

## 2. 对当前项目的真实评价

### 2.1 已经做得很好的地方

1. **不是只做对话**：系统已经能够调用服务端工具、本地工具、CLI/MCP Provider 和远端 Runtime，具备真正执行工作的基础。
2. **企业底座较完整**：租户、账号、数字员工授权、计费、渠道和管理后台不是事后补丁，而是产品的重要组成部分。
3. **垂直场景积累真实**：外贸、订单、合同、售后、旅游、招聘、社媒、视频等能力不是只有概念文档，已有大量代码、工具和真实环境验证。
4. **对失败和风险有敬畏**：项目多次主动收敛方案、保留真机证据、拒绝把“能编译”当成“可交付”。这是长期做企业软件的重要素质。
5. **测试意识强**：仓库已有大量后端测试，并建立开发、测试、Code Review 分离的工程流程。
6. **愿意推翻自己的早期判断**：视频产品定位、BOSS 执行路线、Desktop 架构等都发生过基于证据的调整。这比一开始猜对更重要。

### 2.2 当前暴露出的结构性问题

截至本次审计，仓库大致呈现以下信号：

- `src/core/agent.py` 约 4113 行，母体 Agent 承担了过多职责。
- 约 302 个 API 路由、152 个工具相关 Python 文件、11 个业务子智能体、107 个 Vue 组件。
- `docs/ideas.md` 中登记项目很多，但“部分完成”明显多于真正完成并形成稳定业务闭环的项目。
- 多个行业子智能体的 `SUBAGENT.md` 已达到数百行，部分业务规则仍依赖长 Prompt 承载。
- 工作成果、Token 和对话统计已经存在，但对业务结果的归因仍较弱。
- 后端依赖使用范围约束而非完整精确锁定，核心数据库和调度实现仍有继续产品化的空间。
- 根目录 README 仍以 V1.0 MVP 描述产品，与实际系统能力已经严重脱节。

这些现象不是说明项目做得差，而是说明项目已经进入一个危险阶段：**继续加功能会越来越容易，形成清晰产品反而越来越难。**

## 3. 第一建议：停止横向扩张，建立两个灯塔工作流

### 3.1 为什么这是第一优先级

顶级 Agent 产品不会因为“支持的工具最多”而胜出，而是因为某类工作交给它以后，用户不愿回到原来的工作方式。

当前产品横跨招聘、外贸、旅游、社媒、视频、售后、订单、合同等方向。每个方向都有价值，但如果同时作为公司级主航道，会造成：

- 每个领域都有 60～80 分能力，却缺少一个达到 95 分的闭环；
- 研发资源长期被新的连接器、页面和异常分支切碎；
- 销售无法用一句话说明最强购买理由；
- 客户成功团队难以沉淀统一实施方法；
- 每个行业都需要单独维护 Prompt、数据模型和验收标准。

### 3.2 推荐的选择方式

只选择两个灯塔工作流：

1. **一个直接创造收入的流程**：例如外贸获客 → 企业调查 → 首次触达 → 跟进 → 报价 → 订单推进。
2. **一个明显降低经营成本的流程**：例如合同/订单异常 → 核验 → 跨系统处理 → 通知 → 归档 → 管理复盘。

BOSS、视频、旅游和其他能力可以继续作为技术验证、已有客户交付或行业作业包，但不能同时抢占平台主航道。

### 3.3 灯塔工作流的完成标准

一个灯塔工作流必须同时满足：

- 每周被真实用户重复使用，而不是只演示一次；
- 从业务输入走到外部业务状态改变，而不是停在“生成建议”；
- 异常、审批、取消、恢复和人工接管都可用；
- 有明确的人工基线和 Agent 后指标；
- 至少有 3 家设计合作客户可以重复部署；
- 80% 以上交付使用同一产品包，而不是每家重写；
- 客户愿意因为这条工作流续费，而不是只认可模型效果。

### 3.4 需要主动停止的事情

- 没有真实客户或灯塔工作流消费者的新页面；
- 只为了展示能力数量而增加的新工具；
- 没有端到端负责人、指标和退出条件的新行业 Agent；
- 同一个业务问题的多套实验性实现长期并存；
- 把“代码完成”写成“产品完成”。

## 4. 第二建议：建立企业业务语义层

### 4.1 它不等于知识库

知识库回答“企业知道什么”，业务语义层回答：

- 企业正在经营哪些对象；
- 这些对象现在处于什么状态；
- 对象之间是什么关系；
- 可以执行哪些业务动作；
- 动作的前置条件和完成条件是什么；
- 哪个外部系统保存最终真实状态。

例如销售领域：

```text
客户
├─ 联系人
├─ 线索
├─ 商机
├─ 跟进记录
├─ 报价
├─ 合同
├─ 订单
├─ 交付
└─ 回款
```

招聘领域则包含职位、候选人、沟通、面试、Offer 和入职；营销领域包含品牌、内容、活动、渠道、线索和转化。

### 4.2 为什么它会成为壁垒

当前很多业务理解仍分散在子智能体 Prompt、工具参数和领域表中。没有统一语义层时，“同一客户”可能在邮件、CRM、企微、合同和订单中被当成五个不相关字符串。

统一语义层可以带来：

- 跨子智能体协作时共享同一个业务对象；
- 新接入 ERP/CRM 时只做系统字段到业务语义的映射；
- Agent 能基于业务状态推理，而不是只基于聊天上下文猜测；
- 行业能力可以复用对象和动作，而不是重复建表；
- 业务指标、权限和审计可以绑定稳定对象。

### 4.3 推荐的最小实现

不要一开始建设抽象大而全的本体平台。先从两个灯塔工作流提炼：

- 10～20 个核心 Entity Type；
- 每种对象的稳定 ID、外部引用、状态和版本；
- 20～40 个业务 Action Type；
- 对象关系与状态迁移；
- Source of Truth 与同步方向；
- 可扩展字段和租户映射规则。

只有被真实工作流消费的语义才进入公共层。

## 5. 第三建议：让 Agent 能发现企业流程

### 5.1 企业通常说不清自己的真实流程

企业客户很难一次性写出完整 SOP。真实工作方式分散在 Excel、邮件、群聊、CRM 操作、文件命名习惯、老员工经验和异常处理里。

如果产品要求客户先完成 Prompt 编写、流程配置和工具参数设计，实施成本会不断升高，最终容易退化为项目制交付。

### 5.2 推荐的产品能力

提供 Shadow / Teach-by-Demonstration 模式：

1. Agent 观察员工完成若干次真实任务；
2. 提取候选步骤、输入、判断条件和异常分支；
3. 生成可阅读的候选 SOP；
4. 由员工确认和修正；
5. 先以建议模式运行；
6. 再逐步开放自动执行；
7. 持续比较实际流程与已发布 SOP。

产品上可以表达为：

> “带着 Agent 做三次，以后这项工作逐步交给它。”

### 5.3 必须守住的边界

- 观察不等于默认采集所有屏幕和数据；
- 流程发现必须受租户策略、数据范围和员工知情控制；
- 一次行为不能自动升级为组织规则；
- 异常处理经验必须区分事实、个人偏好和组织规范；
- 自动化权限应随验证逐级开放，而不是一次性全开。

## 6. 第四建议：从“子智能体”升级为“企业作业包”

### 6.1 当前交付单元还不够完整

子智能体、Skill、工具、连接器、Prompt、业务表和 UI 目前相对分散。单独安装一个子智能体，并不代表客户已经获得了可运行的岗位能力。

### 6.2 推荐的标准交付单元

```text
企业作业包 / Solution Pack
├─ 适用岗位与业务目标
├─ 业务对象模型
├─ SOP 与异常分支
├─ Agent / Skill
├─ 工具与连接器要求
├─ 默认权限与审批规则
├─ 行业知识与模板
├─ 工作台 UI
├─ 验收用例与 Golden Tasks
├─ 业务指标
├─ 数据迁移/初始化
└─ 版本、升级与兼容规则
```

### 6.3 作业包的商业价值

- 销售可以明确售卖一个岗位结果，而不是售卖一堆能力；
- 实施可以按标准检查表交付；
- 客户可以预览依赖、权限和预期收益；
- 升级可以按版本进行，而不是人工修改 Prompt；
- 生态伙伴可以开发行业包，但不能破坏平台治理规则。

## 7. 第五建议：建立企业操作经验飞轮

### 7.1 它不等于普通记忆

长期记忆保存用户或组织事实；操作经验飞轮关注的是：用户如何修改 Agent 的工作，以及这种修改是否值得升级为企业作业规范。

典型信号包括：

- 用户修改了报价措辞；
- 销售删除了某类目标客户；
- 管理员否决了某种跟进方式；
- 员工调整了合同条款；
- 运营留下或丢弃某类内容；
- 招聘人员持续跳过某种候选人；
- 用户撤销、重做或接管了某个动作。

### 7.2 推荐的闭环

```text
Agent 原建议/动作
→ 用户修改、拒绝、撤销或接管
→ 记录结构化差异与原因
→ 识别重复模式和适用条件
→ 生成候选作业经验
→ 管理员/领域专家审核
→ 发布新版企业规范或作业包
→ 用真实业务结果验证
```

### 7.3 关键原则

- Agent 不能私下把单个用户行为升级成企业规则；
- 必须保存规则来源、适用范围、版本和审核人；
- 用户修改本身不一定是正确答案，需要结合后续业务结果；
- 经验可以提出候选，但发布必须受治理；
- 企业离开平台时，应能导出属于自己的作业规范资产。

当客户使用半年后，系统中沉淀的不只是聊天历史，而是这家企业独有的销售方式、报价习惯、品牌表达和异常处理方法。这才是长期迁移成本和产品护城河。

## 8. 第六建议：从“产出记录”升级为价值实现引擎

### 8.1 当前指标仍偏使用侧

对话数、Token、积分、生成文件数和工作成果能够证明 Agent 在工作，但不能充分证明它改变了业务结果。

企业最终关心的是：

- 商机推进了多少；
- 报价周期缩短多少；
- 合同错误减少多少；
- 售后首次响应缩短多少；
- 筛选效率提升多少；
- 内容采用率和转化率提高多少；
- 有多少异常被提前发现；
- 有多少工作从人工执行变成了人工确认。

### 8.2 推荐模型

```text
人工历史基线
+ Agent 实际参与范围
+ 人工修改/接管成本
+ 最终业务状态
+ 归因置信度
= 可审计的价值结果
```

必须区分：

- Agent 给出建议但未采用；
- 生成结果被大量修改后采用；
- Agent 独立完成动作；
- 动作完成但没有形成业务结果；
- 业务结果发生，但只能部分归因于 Agent。

### 8.3 这项能力的直接用途

- 客户续费报告；
- 行业案例和销售证明；
- 定价与套餐设计；
- 识别真正值得继续投入的 Agent；
- 识别高使用但低价值的伪需求；
- 比较不同作业包和企业规则的效果。

## 9. 第七建议：产品入口从聊天框升级为决策与异常中心

企业员工不会希望全天与 Agent 对话。他们更需要快速处理 Agent 无法自行决定的事项。

未来核心首页应优先展示：

- 需要我决定；
- 需要我补充；
- 执行出现异常；
- 等待外部人员；
- 即将超时；
- 本周重要成果；
- Agent 建议优化的流程；
- 我委托工作的当前进展。

理想状态是：

> Agent 平时主动推进工作，只在出现判断、例外、风险和重要结果时寻找人。

聊天保留为表达意图、澄清和探索的入口，但不再承担全部工作管理职责。衡量优秀交互的指标之一，应是完成同等工作所需的人类打断次数持续下降。

## 10. 第八建议：把大型母体 Agent 收敛为稳定 Kernel

### 10.1 当前问题

`src/core/agent.py` 已同时承担 Prompt、上下文、记忆、LLM 循环、工具解析、工具执行、子智能体委派、文件结果、SSE、计费、渠道差异和部分业务兼容逻辑。

这种形态在早期迭代很快，但继续增长会产生：

- 修改一个领域影响其他领域；
- 无法对核心循环做独立验证；
- 业务特例不断进入母体；
- 新的模型或执行方式接入成本越来越高；
- 故障恢复、流式输出和工具状态彼此耦合。

### 10.2 推荐 Kernel 边界

```text
ContextAssembler       上下文与输入封装
IntentCompiler         意图、约束和完成标准
TurnEngine             单回合模型协议
CapabilityResolver     Agent/Skill/Tool 能力求交
ActionDispatcher       执行目标与动作分发
ContinuationManager    等待、恢复、澄清与接续
ResultInterpreter      结构化结果与状态判断
ResponseComposer       用户可见表达与渠道适配
```

Kernel 只维护稳定协议和生命周期，不直接认识 video、travel、BOSS 等领域。

### 10.3 Prompt 与确定性逻辑的边界

多个 `SUBAGENT.md` 已达到数百行。长 Prompt 并不天然代表能力强，往往意味着业务规则尚未结构化。

以下内容应优先从 Prompt 移出：

- 数值上限和权限规则；
- 状态迁移；
- 必填字段；
- 外部 API 约束；
- 可确定的路由；
- 格式验证；
- 幂等和重试条件；
- 合规禁止项。

Prompt 主要负责语义理解、推理、内容生成和在确定性规则允许范围内选择，而不是充当不可测试的业务规则数据库。

## 11. 第九建议：把工程交付提升为可重复发布

### 11.1 当前需要继续强化的地方

- 后端依赖需要完整锁定并支持历史版本重建；
- 数据库迁移需要不可变 migration、顺序、checksum、回滚/前滚策略和多版本兼容；
- 后台任务需要明确独立运行时、租约、并发和故障恢复语义；
- 核心模块需要控制体积和依赖方向；
- 产品文档、README、销售描述和实际发布状态必须一致；
- 每个租户运行的 Agent、Skill、Prompt、工具和作业包版本必须可追踪。

### 11.2 顶级企业交付应回答的问题

- 任意历史版本能否重建？
- 数据库能否从任意受支持版本安全升级？
- 一个 Worker 崩溃是否会重复执行业务动作？
- 某租户出现问题能否定位到准确发布组合？
- 是否能在不读取客户正文的情况下诊断故障？
- 是否有备份、恢复、灾难演练和容量边界？
- 是否能明确说明某项功能是开发完成、灰度、线上验证还是正式支持？

## 12. 第十建议：把“调用子智能体”升级为企业智能体团队

当前 `delegate_to_subagent` 能调用一个数字员工，但 root 会同步等待；运行依赖单进程 `asyncio.Task` 与两小时 Redis 记录；子级不能继续委派，成员间没有持久消息、追加任务、并行汇聚和故障恢复。这与领先的多智能体产品形态存在结构性差距。

这不应靠增加一个“并行委派”工具解决。建议建立 Web/Desktop 共用的 Multi-Agent Collaboration Fabric：

- root/child 责任树管理谁对谁负责，assignment DAG 管理工作依赖；
- 每个成员拥有独立、最小上下文，通过持久 mailbox、Artifact 和 Evidence 协作；
- 提供 spawn、send、follow-up、wait、interrupt、list、publish 等可审计原语；
- 运行状态持久化并支持 lease/fencing/reconcile，不以进程内任务为权威；
- 团队有并发、深度、token、积分、时间、工具与副作用预算；
- root 必须记录对成员结论的采纳、拒绝、冲突和证据依据；
- Web 与 Desktop 展示同一团队状态并允许用户纠偏，但 `DEVICE_OWNED` 协调器始终留在原设备；
- 工具执行节点与智能体成员解耦，成员仍可调用 Server、本机或远端 Runtime 工具。

首批不要追求“智能体数量最多”，只做三类能证明价值的团队：并行深度调研、方案制作+独立复核、批量资料处理。每个团队都必须与单智能体基线比较质量、总时延和单位成功成本；没有显著收益的任务不自动组队。

详细审计、架构和实施路线见：[多智能体调研](enterprise-multi-agent-collaboration-research.md)、[协作架构](../system/enterprise-agent-platform/enterprise-multi-agent-collaboration-design.md)、[开发计划](../plans/plan-enterprise-multi-agent-collaboration.md)。

## 13. 建议的 90 天行动路线

### 第 1～30 天：收敛

1. 冻结新的横向 Agent/工具立项。
2. 选择两个灯塔工作流和 3 家设计合作客户。
3. 为灯塔流程建立人工基线、完成定义和业务指标。
4. 从真实流程提取第一版业务对象与 Action Type。
5. 画出母体 Agent 依赖图，确定 Kernel 拆分边界。
6. 更新 README 和产品定位，确保公司内部使用同一套叙事。

### 第 31～60 天：形成可复制产品单元

1. 将第一个灯塔流程封装成 Solution Pack。
2. 建立 Shadow/建议/审批执行三档自动化成熟度。
3. 上线决策与异常中心的最小版本。
4. 捕获用户修改、拒绝、撤销和接管信号。
5. 建立业务结果回写与基础归因。
6. 从母体 Agent 拆出至少 TurnEngine、ActionDispatcher 和 ContinuationManager。

### 第 61～90 天：验证护城河

1. 在 3 家客户中使用同一作业包交付。
2. 统计端到端完成率、人工介入、周期、错误和业务结果。
3. 从重复修改中生成候选企业经验，并完成首次审核发布。
4. 产出一份可审计的客户价值报告。
5. 删除或冻结无法服务主航道的实验入口。
6. 用数据决定第二季度继续强化或放弃哪些方向。

## 14. 三条最高优先级建议

如果资源只允许做三件事：

1. **停止继续横向加功能，选择两个灯塔级业务闭环。**
2. **建立企业业务语义层，并把行业能力封装成可复制的作业包。**
3. **建立“员工修改 → 候选经验 → 专家确认 → 新作业版本 → 业务结果验证”的组织学习飞轮。**

前面已经设计的平台治理体系让系统可靠；这三件事会让系统不可替代。

## 15. 今后判断新需求的过滤器

以后面对任何新功能，先回答：

1. 它服务哪个灯塔工作流？
2. 它改变哪个业务指标？
3. 哪个真实客户会在 30 天内使用？
4. 它应该进入平台、作业包还是客户定制层？
5. 是否已经存在相同能力，只是缺少组合？
6. 能否通过业务语义层复用，而不是增加领域特例？
7. 它会让 Agent 更自主，还是让用户多一个配置页面？
8. 它能否捕获反馈并改善下一次执行？
9. 失败时由谁处理，如何恢复？
10. 如果三个月后没有业务数据证明价值，是否愿意删除？

无法清楚回答前四个问题的需求，原则上不进入开发。

## 16. 最终产品定义建议

不建议长期把产品定义为：

> 一个能够调用很多工具的企业 Agent。

更有力量的定义是：

> AID Work Agent 是一个理解企业业务对象、接管完整工作流程、只把异常交给人，并持续把员工经验沉淀为组织能力的企业工作系统。

真正的顶级不表现为功能列表最长，而表现为：企业把一项关键工作交给它之后，工作方式发生了不可逆的改变。
