## 1. 核心结论

### 1.1 3chat.ai 实际用的是什么模式？

根据用户观察到的**精确场景**：

> **企业微信的一个普通员工账号**（非管理员、非客服账号）扫码后，**这个员工账号**就和 AI 机器人绑定。微信用户加了这个企业微信员工后，聊天由 AI 自动接管，也可以转人工由这个员工本人回复。

这个场景与"微信客服"模式有**本质区别**——微信客服创建的是一个独立的客服身份，用户通过客服链接进入咨询；而用户观察到的场景是**直接加员工企业微信好友**，然后在好友聊天中由 AI 自动回复。

**企业微信官方 API 的限制**：

> "员工和客户单聊时，只有欢迎语是自动发送的，其他都是人工回复" —— 企业微信官方明确说明

这意味着通过官方 API，**无法实现员工个人号与外部客户聊天时的自动回复**。

因此，3chat.ai 在此场景下使用的是**企微个人号 RPA 托管模式**——通过 RPA/协议层接管员工企业微信的消息流，实现 AI 自动回复。

### 1.2 3chat.ai 可能同时支持两种模式

3chat.ai 作为全渠道 AI 客服产品，很可能同时支持以下两种接入方式：

| 模式 | 场景 | 合规性 |
|------|------|--------|
| **企微个人号 RPA 托管** | 员工个人号扫码绑定，微信客户加好友后 AI 自动回复 | 灰色地带 |
| **微信客服第三方授权** | 创建独立客服身份，用户通过客服链接咨询 | 完全合规 |

用户看到的是第一种模式。

### 1.3 关键技术发现

| 发现 | 说明 |
|------|------|
| 3chat.ai 的实际模式 | **企微个人号 RPA 托管**，不是微信客服模式 |
| 核心限制 | 企业微信官方 API **不支持**员工与客户单聊的自动回复（只能发一条欢迎语） |
| RPA 托管原理 | 通过 RPA/协议层获取员工消息流，AI 生成回复后模拟操作发送 |
| 转人工机制 | AI 停止接管，员工在企业微信客户端手动回复 |
| 合规风险 | 微信官方称此类方式为"外挂或插件等工具非法接入"，存在封号风险 |
| 代表产品 | 3chat.ai、Weclaw/juhebot（明确宣传"AI 全自动托管运营"）、chatgpt-on-wechat 等 |

### 1.4 补充：微信客服模式的价值

虽然 3chat.ai 在用户观察到的场景中使用的是 RPA 托管模式，但**微信客服第三方授权模式**作为完全合规的官方方案，仍然是非常有价值的接入方式，只是用户体验略有不同（用户通过客服链接咨询而非加好友）。本报告同时详细分析了两种模式。

## 2. 企业微信"扫码绑定"的四种技术模式

企业微信生态中"扫码绑定"有**四种**完全不同的含义，容易混淆：

### 2.1 模式一：Web 登录（OAuth 扫码登录）

**用途**：用户在网站通过企业微信扫码完成登录。

```
构造登录链接 → 用户扫码 → 回调获取 code → 用 code 换取 userid
```

**获取信息**：corpid + userid（个人身份识别）。
**适用场景**：SaaS 用户登录、员工身份验证。

### 2.2 模式二：ISV 代开发应用扫码授权

**用途**：服务商让企业管理员扫码，在企业微信后台自动创建代开发应用。

```
服务商创建代开发模板 → 生成授权二维码 → 企业管理员扫码 → 企业微信自动创建自建应用
```

**获取信息**：企业全套 API 权限（最高权限）。
**前提条件**：需要 ISV 服务商资质。

### 2.3 模式三：微信客服第三方服务商授权

**用途**：第三方平台通过扫码获取企业微信客服的 API 调用权限。

```
第三方在 kf.weixin.qq.com 配置服务 → 构造授权链接 → 企业管理员扫码 → 第三方获得客服消息管理权限
```

**获取信息**：微信客服完整 API 权限（消息收发、会话管理、账号管理）。
**前提条件**：无需 ISV 资质，只需在 `kf.weixin.qq.com` 注册。
**合规性**：完全合规。

### 2.4 模式四：企微个人号 RPA 托管 ← 3chat.ai 实际使用的模式

**用途**：第三方平台通过 RPA/协议层接管企业微信员工个人账号的消息收发。

```
第三方平台展示二维码 → 员工用企业微信扫码 → 员工账号登录态被托管 → 第三方通过 RPA 收发消息
```

**获取信息**：员工企业微信的完整消息流（包括与微信客户的单聊）。
**前提条件**：无官方资质要求，但属于**非官方 API 的灰色方案**。
**合规性**：微信官方称此类方式为"外挂或插件等工具非法接入"，存在封号风险。

### 2.5 四种模式对比

| 维度 | Web 登录 OAuth | ISV 代开发 | 微信客服第三方授权 | **企微个人号 RPA 托管** |
|------|---------------|-----------|-------------------|----------------------|
| **扫码目的** | 身份验证/登录 | 安装应用到企业微信 | 授权客服消息管理 | **托管员工账号消息流** |
| **扫码人** | 任何企业微信成员 | 企业管理员 | 企业管理员 | **任何企业微信员工** |
| **获取的权限** | corpid + userid | 企业全套 API | 微信客服消息读写 | **员工完整消息控制权** |
| **需要服务商资质** | 否 | **是** | 否 | **否** |
| **消息收发能力** | 无 | 完整 | 仅客服消息 | **完整（含员工客户单聊）** |
| **企业微信需安装应用** | 否 | **是** | 否 | **否** |
| **审核流程** | 无 | 模板审核+应用审核 | 无 | **无** |
| **合规性** | 合规 | 合规 | 合规 | **灰色地带** |
| **用户体验** | — | 企业微信内通知 | 微信聊天列表客服窗口 | **与员工正常聊天（好友）** |
| **典型产品** | Authing | 定制 OA/CRM | 智齿科技 | **3chat.ai、Weclaw** |

## 3. 模式详解一：企微个人号 RPA 托管（3chat.ai 实际使用模式）

### 3.1 为什么必须是 RPA 托管？

**企业微信官方 API 的硬性限制**：

> "员工和客户单聊时，只有欢迎语是自动发送的，其他都是人工回复。"
> "你可能会说，不对啊，我看到有些企业员工和客户单聊时，也可以全程自动回复啊。微信官方工作人员在一个帖子回复说：这应该是使用外挂或插件等工具非法接入的。正常情况下，是可以通过接口发送一次客户欢迎语消息，第二条消息是无法通过接口发送的。"
> —— [企业微信实现自动回复的 6 种情况](https://kejiweixun.com/note/202402021826)

也就是说，通过企业微信官方 API，**员工与微信客户的好友聊天**只能：
- 发送**一条**欢迎语（通过 `send_welcome` API，客户加好友时触发）
- 之后的第二条、第三条消息**无法通过 API 发送**

这个限制是设计层面的：企业微信的"客户联系"功能中，员工与客户的单聊被视为**私人沟通**，不是客服会话，因此没有提供自动回复 API。

**只有微信客服渠道**才提供完整的消息收发 API（`sync_msg` + `send_msg`），但那是一个独立的客服身份，不是员工个人号。

### 3.2 RPA 托管的技术原理

```
┌────────────────────────────────────────────────────────────────────┐
│                       第三方平台 (如 3chat.ai)                      │
│                                                                    │
│  ┌──────────────────────────────────────────────────────────────┐  │
│  │                    RPA/协议层                                  │  │
│  │                                                              │  │
│  │  方式 A：Webhook/RPA 注入                                     │  │
│  │  - 员工扫码后，第三方平台获取该员工企业微信的登录态              │  │
│  │  - 通过 RPA（Remote Process Automation）在企业微信客户端上      │  │
│  │    监听消息、模拟操作发送消息                                   │  │
│  │                                                              │  │
│  │  方式 B：协议层代理                                           │  │
│  │  - 通过逆向企业微信通信协议，直接接管消息流                     │  │
│  │  - 实现消息的实时获取和发送                                    │  │
│  │                                                              │  │
│  │  方式 C：会话内容存档 + 外部发送                               │  │
│  │  - 利用企业微信"会话内容存档"API（官方功能）获取聊天记录        │  │
│  │  - 结合某种方式发送回复（仍需 RPA 或协议层）                   │  │
│  └──────────────────────────────────────────────────────────────┘  │
│                              │                                    │
│                              ▼                                    │
│  ┌──────────────────────────────────────────────────────────────┐  │
│  │                    AI 处理层                                   │  │
│  │                                                              │  │
│  │  1. 收到微信客户发给员工的消息                                 │  │
│  │  2. 识别消息内容，判断是否需要 AI 回复                         │  │
│  │  3. AI 生成回复内容                                           │  │
│  │  4. 通过 RPA/协议层以员工身份发送回复                          │  │
│  │  5. 如需转人工：AI 停止接管，员工在企业微信客户端手动回复       │  │
│  └──────────────────────────────────────────────────────────────┘  │
└────────────────────────────────────────────────────────────────────┘
```

### 3.3 扫码绑定的本质

员工在第三方平台看到的二维码，本质上是**企业微信 Web 登录二维码**（OAuth 扫码登录）：

```
1. 第三方平台构造企业微信 Web 登录链接
2. 员工用企业微信扫码 → 第三方平台获得员工的 corpid + userid
3. 结合 RPA/协议层，第三方平台接管该员工的消息流
4. 之后该员工与微信客户的所有聊天消息都会被第三方平台捕获
5. 第三方平台调用 AI 生成回复并通过 RPA 发送
```

扫码本身是合法的 OAuth 登录行为，但后续的 RPA 消息接管属于灰色地带。

### 3.4 转人工机制

```
正常流程（AI 接管）：
  微信客户发消息 → RPA 捕获消息 → AI 生成回复 → RPA 以员工身份发送

转人工触发条件：
  - 客户发送"人工"等关键词
  - AI 判断无法回答/需要人工介入
  - 后台手动切换

转人工流程：
  1. 第三方平台停止 AI 自动回复
  2. 消息仍然通过 RPA 展示在后台面板（供人工客服查看）
  3. 人工客服在第三方平台面板回复 → RPA 以员工身份发送
  或
  3. 员工直接在企业微信客户端看到消息并手动回复（RPA 不再拦截）
```

### 3.5 代表产品

| 产品 | 说明 |
|------|------|
| **3chat.ai** | AI 原生营销+客服智能体，支持企微个人号绑定 |
| **Weclaw/juhebot** | 明确宣传"微信/企微 AI 数字员工"、"7x24 小时自动接管"、"AI 全自动托管运营" |
| **chatgpt-on-wechat** | 开源项目，通过企微应用协议实现自动回复 |
| **LinkAI** | 支持"企微智能机器人"扫码接入，自动创建并接入 |

### 3.6 风险与合规分析

| 风险点 | 说明 |
|--------|------|
| **封号风险** | 微信官方明确表示此类方式属于"外挂或插件等工具非法接入" |
| **数据安全** | 员工消息流经过第三方平台，存在数据泄露风险 |
| **稳定性** | 依赖企业微信客户端或协议层的稳定性，版本更新可能导致失效 |
| **法律风险** | 可能违反微信/企业微信的服务条款 |
| **用户体验** | 员工需要保持企业微信在线（或 RPA 需要模拟在线状态） |

### 3.7 为什么仍有大量产品使用此模式？

尽管存在合规风险，大量产品仍选择 RPA 托管模式的原因：

1. **用户体验极佳**：微信客户直接加员工企业微信好友，聊天体验与正常微信聊天完全一致
2. **无缝转人工**：员工可以随时在企业微信客户端接管，不需要切换工具
3. **无需管理员操作**：普通员工即可自助绑定，无需企业管理员审批
4. **客户感知**：客户不知道对面是 AI 还是真人，更自然
5. **私域运营**：客户沉淀在员工的企业微信好友列表中，是企业资产

## 4. 模式详解二：微信客服第三方服务商授权

3chat.ai 等产品很可能**同时支持** RPA 托管模式和微信客服模式。微信客服模式是完全合规的官方方案，适用于需要独立客服身份的场景。

- 定价：成长版 980 元/月

## 5. 微信客服功能概述

### 4.1 微信客服是什么

微信客服（WeChat Customer Service）是腾讯微信团队为企业打造的客服解决方案。它是企业微信的**内置原生功能模块**，不是第三方应用。

核心定位：
- 企业可在**微信内外**各场景中接入
- 微信用户**无需添加企业微信好友**即可直接发起客服咨询
- 消息在用户的微信聊天列表中直接展示，体验与普通微信聊天一致

### 4.2 两种使用模式

| 模式 | 说明 |
|------|------|
| **独立使用** | 在微信客服管理后台（kf.weixin.qq.com）独立使用，不经过企业微信 |
| **企业微信接管** | 由企业微信接管微信客服账号和收发消息，支持 API 管理 |

我们关注的是**第二种模式**：通过 API 接管微信客服。

### 4.3 核心能力

| 能力 | 说明 |
|------|------|
| 多场景接入 | 视频号、公众号、小程序、微信搜一搜、网页、APP |
| 客服账号管理 | 创建、修改、删除客服账号（每企业最多 5000 个） |
| 消息收发 | 文本、图片、语音、视频、文件、图文、小程序、菜单消息 |
| 会话管理 | 获取会话状态、变更会话状态（分配、转接、结束） |
| 智能助手 | "由智能助手接待"状态 → API 实现机器人自动回复 |
| 转人工 | 从"智能助手"状态转接到"人工接待" |
| 升级服务 | 将微信客服会话升级为客户联系（添加企业微信好友） |

### 4.4 微信客服 vs 企业微信应用

| 维度 | 微信客服 | 企业微信自建应用 | ISV 第三方应用 |
|------|---------|---------------|--------------|
| 入口 | 微信聊天列表 | 企业微信工作台 | 应用市场安装 |
| 外部用户 | 无需添加好友 | 需添加好友 | 需添加好友 |
| 消息体验 | 与普通微信聊天一致 | 企业微信内通知 | 企业微信内通知 |
| 开发复杂度 | 中等 | 较低 | 较高 |
| 适用场景 | 客服咨询、售前售后 | 内部协作 | 企业级 SaaS |

## 6. 微信客服第三方服务商授权流程

这是 3chat.ai 实现扫码绑定的**核心技术流程**。

### 5.1 前提条件

1. 第三方平台需要在 **微信客服管理后台**（kf.weixin.qq.com）注册
2. 在"开发配置 → 帮助其他企业管理微信客服"处配置服务信息
3. 配置回调 URL、Token、EncodingAESKey

### 5.2 授权流程

```
┌─────────────────────────────────────────────────────────────────┐
│                     第三方平台 (如 3chat.ai)                      │
│                                                                 │
│  1. 获取预授权码 (pre_auth_code)                                 │
│     POST https://qyapi.weixin.qq.com/cgi-bin/service/get_pre_auth_code
│     ?suite_access_token=SUIT_ACCESS_TOKEN                       │
│                                                                 │
│  2. 构造授权链接（生成二维码供企业管理员扫描）                      │
│     https://open.work.weixin.qq.com/3rdparty/install?           │
│       suite_id=SUITE_ID                                         │
│       &pre_auth_code=PRE_AUTH_CODE                              │
│       &redirect_uri=REDIRECT_URI                                │
│       &state=STATE                                              │
│                                                                 │
│  ★ 企业管理员在第三方平台页面看到二维码 → 扫码授权 ★              │
└───────────────────────────────┬─────────────────────────────────┘
                                │ 扫码授权成功
                                ▼
┌─────────────────────────────────────────────────────────────────┐
│                      企业微信服务器                               │
│                                                                 │
│  3. 授权成功，回调临时授权码到 redirect_uri                       │
│     redirect_uri?auth_code=AUTH_CODE&state=STATE                │
│     （临时授权码 10 分钟内有效）                                  │
└───────────────────────────────┬─────────────────────────────────┘
                                │
                                ▼
┌─────────────────────────────────────────────────────────────────┐
│                     第三方平台后端                                │
│                                                                 │
│  4. 用临时授权码换取永久授权码                                    │
│     获取企业 access_token                                       │
│     → 可调用该企业微信客服的所有 API                              │
│                                                                 │
│  5. 授权完成后：                                                 │
│     - 该企业微信客服的所有消息和事件都回调给第三方平台             │
│     - 第三方平台可创建/管理客服账号                               │
│     - 第三方平台可收发客服消息                                    │
│     - 第三方平台可管理会话状态（转人工等）                        │
└─────────────────────────────────────────────────────────────────┘
```

### 5.3 关键点

1. **授权是互斥的**：同时只能授权给一个第三方平台，授权后可取消
2. **授权范围**：仅微信客服相关的 API 权限，不涉及通讯录、审批等企业管理功能
3. **授权时效**：永久授权码长期有效，除非企业主动取消授权
4. **企业侧操作**：企业管理员只需扫码，无需在企业微信后台做任何其他配置

### 5.4 另一种更简单的接入方式：手动配置凭证

如果不想走第三方授权流程，还有一种更简单的方式：

1. 企业管理员在微信客服管理后台开启 API
2. 获取 `corpid` 和微信客服 `Secret`
3. 手动将凭证和回调 URL 配置到第三方平台
4. 第三方平台用 corpid + secret 获取 access_token

这种方式不需要第三方在 kf.weixin.qq.com 注册，但需要企业管理员手动操作更多步骤。

## 8. 转人工机制详解

### 7.1 会话状态流转

```
                          ┌──────────┐
              ┌──────────│ 0-未处理  │◄── 客户发消息咨询
              │          └──────────┘
              │                │
              │         ┌──────┴──────┐
              │         ▼             ▼
              │   ┌──────────┐  ┌────────────┐
              │   │1-智能助手 │  │2-待接入池  │    ← AI 机器人工作于此状态
              │   │  接待     │  │  排队中    │
              │   └──────────┘  └────────────┘
              │         │             │
              │         ▼             ▼
              │         ┌──────────────┐
              │         │ 3-由人工接待  │◄── 转人工目标状态
              │         └──────────────┘
              │                │
              │                ▼
              │         ┌──────────────┐
              └────────►│ 4-已结束     │
                        └──────────────┘
```

| service_state | 状态名 | 可变更到的状态 |
|---------------|--------|---------------|
| 0 | 未处理 | 1（智能助手）、2（待接入池）、3（指定人工） |
| 1 | 由智能助手接待 | 2（待接入池）、3（指定人工） |
| 2 | 待接入池排队中 | 3（指定人工） |
| 3 | 由人工接待 | 3（转接其他人工）、4（结束会话） |
| 4 | 已结束/未开始 | 不可通过 API 变更 |

### 7.2 AI 接管 + 转人工完整流程

```
1. 用户发消息 → 会话状态变为 0（未处理）

2. 系统自动将会话设为 1（由智能助手接待）
   POST /cgi-bin/kf/service_state/trans
   {"service_state": 1, "open_kfid": "wkxxx", "external_userid": "wmxxx"}

3. AI 自动回复用户消息
   POST /cgi-bin/kf/send_msg
   {"msgtype": "text", "text": {"content": "AI回复..."}, ...}

4. 用户请求转人工 / AI 判断需要转人工

5. 变更会话状态为 3（由人工接待）
   POST /cgi-bin/kf/service_state/trans
   {
       "service_state": 3,
       "open_kfid": "wkxxx",
       "external_userid": "wmxxx",
       "servicer_userid": "zhangsan"   // 指定接待人员
   }
   或放入待接入池：
   {"service_state": 2, "open_kfid": "wkxxx", "external_userid": "wmxxx"}

6. 接待人员在企业微信客户端看到该会话 → 手动回复

7. ⚠️ 转人工后，通过 send_msg 发送的消息会失败（fail_type=5）
   此时只能由接待人员手动回复
```

## 9. 消息收发架构

### 8.1 消息接收：回调通知 + 主动拉取

微信客服采用**回调通知 + 主动拉取**的混合模式：

```
消息接收流程：

1. 微信用户发送消息
2. 企业微信后台向回调 URL 发送事件通知（XML 格式）
   ┌─────────────────────────────────────────┐
   │ <xml>                                    │
   │   <ToUserName>ww12345678910</ToUserName> │
   │   <MsgType>event</MsgType>               │
   │   <Event>kf_msg_or_event</Event>         │
   │   <Token>ENCApHxnGDNAV...</Token>        │ ← 10 分钟内有效
   │   <OpenKfId>wkxxxxxxx</OpenKfId>         │ ← 有新消息的客服账号
   │ </xml>                                   │
   └─────────────────────────────────────────┘
   注意：通知中不包含具体消息内容！

3. 第三方平台收到通知后，调用 sync_msg 接口拉取具体消息

4. 处理消息，生成 AI 回复

5. 调用 send_msg 接口发送回复
```

### 8.2 sync_msg 读取消息

```
POST https://qyapi.weixin.qq.com/cgi-bin/kf/sync_msg?access_token=TOKEN

{
    "cursor": "4gw7MepFLfgF2VC5npN",   // 上次返回的 next_cursor
    "token": "ENCApHxnGDNAV...",        // 回调通知中的 Token
    "limit": 1000,                       // 最大 1000
    "voice_format": 0,
    "open_kfid": "wkxxxxxx"
}

// 返回
{
    "errcode": 0,
    "next_cursor": "4gw7MepFLfgF2VC5npN",
    "has_more": 1,
    "msg_list": [
        {
            "msgid": "from_msgid_4622416642169452483",
            "open_kfid": "wkAJ2GCAAASSm4_FhToWMFea0xAFfd3Q",
            "external_userid": "wmAJ2GCAAAme1XQRC-NI-q0_ZM9ukoAw",
            "send_time": 1615478585,
            "origin": 3,      // 3=微信客户 4=系统事件 5=接待人员
            "msgtype": "text",
            "text": {
                "content": "你好，我想咨询一下"
            }
        }
    ]
}
```

**注意事项**：
- 只能拉取**最近 3 天内**的消息
- 必须用 cursor 增量拉取，强烈建议持久化 next_cursor
- `has_more=1` 时 msg_list 可能为空，不能以此判断停止

### 8.3 send_msg 发送消息

```
POST https://qyapi.weixin.qq.com/cgi-bin/kf/send_msg?access_token=TOKEN

// 文本消息
{
    "touser": "wmAJ2GCAAAme1XQRC-NI-q0_ZM9ukoAw",
    "open_kfid": "wkAJ2GCAAASSm4_FhToWMFea0xAFfd3Q",
    "msgid": "unique_msg_id_001",
    "msgtype": "text",
    "text": {
        "content": "您好，我是AI客服小助手，请问有什么可以帮您？"
    }
}

// 菜单消息（交互引导）
{
    "touser": "EXTERNAL_USERID",
    "open_kfid": "OPEN_KFID",
    "msgtype": "msgmenu",
    "msgmenu": {
        "head_content": "请选择您需要的服务：",
        "list": [
            {"type": "click", "click": {"id": "101", "content": "咨询产品"}},
            {"type": "click", "click": {"id": "102", "content": "转人工客服"}},
            {"type": "view", "view": {"url": "https://example.com/faq", "content": "查看常见问题"}}
        ],
        "tail_content": "您也可以直接输入问题"
    }
}
```

### 8.4 发送事件响应消息（欢迎语等）

```
POST https://qyapi.weixin.qq.com/cgi-bin/kf/send_msg_on_event?access_token=TOKEN

| 场景 | code 来源 | 可发送的消息 |
|------|----------|------------|
| 用户进入会话 | enter_session 事件的 welcome_code | 欢迎语（1条，20秒内） |
| 进入待接入池 | 变更状态到 2 时返回的 msg_code | 排队提示语 |
| 从待接入池接入 | change_type=1 的 msg_code | 接入提示语 |
| 结束会话 | change_type=3 的 msg_code | 结束语 |
```

### 8.5 消息发送限制

| 限制项 | 说明 |
|--------|------|
| 发送时限 | 用户发消息后 **48 小时**内 |
| 发送条数 | 每次用户消息后最多 **5 条**，用户继续发消息后额度刷新 |
| 消息保留 | sync_msg 只能拉取最近 **3 天**的消息 |
| 文本长度 | 最多 **2048 字节** |
| 回调超时 | 回调 URL 需在 **5 秒**内响应 |

```python
class WeChatKFTenantConfig:

```
统一回调 URL：https://your-domain.com/api/wechat-kf/callback

根据回调 XML 中的 ToUserName（即 CorpID）路由到对应租户：
1. 解析 XML，提取 ToUserName
2. 查找 ToUserName 对应的租户配置
3. 使用该租户的 access_token 处理消息

### 9.3 企业接入流程（用户自助）

## 12. 类似产品对比

| 产品 | 接入方式 | 特点 |
|------|---------|------|
| **3chat.ai** | 企微个人号 RPA 托管 + 微信客服 | AI 原生，MCP 协议，跨境电商，26+ 语言 |

1. 继承 `ChannelAdapter`，实现 `parse_message` / `send_message` / `verify_signature`
2. 回调 URL 注册到 FastAPI 路由（`src/main.py`）
3. 消息格式转换：微信客服消息 → 统一消息格式 → 智能体处理
4. 会话映射：`external_userid` + `open_kfid` → 系统的 `session_id`
5. 转人工信号：智能体决定转人工时 → `service_state/trans` API

### 13.3 实施路线（双路线并行）

推荐采用**双路线并行**策略：

#### 路线 A：微信客服模式（合规优先，先上线）

**阶段 1：基础接入（1-2 周）**

1. 在 kf.weixin.qq.com 注册并配置第三方服务
2. 实现 access_token 管理（获取、缓存、刷新）
3. 实现回调 URL 接收通知
4. 实现 sync_msg 消息拉取
5. 实现 send_msg 消息发送
6. 单租户验证

**阶段 2：智能体集成（1 周）**

1. 消息路由：微信客服消息 → 智能体消息处理流程
2. 会话管理：新会话自动设为"智能助手接待"状态
3. AI 回复：调用智能体获取回复 → send_msg 发送
4. 转人工逻辑：转人工判断 + 状态变更

**阶段 3：多租户 SaaS（1-2 周）**

1. 多企业管理：每个企业独立存储凭证
2. 动态回调路由：根据 CorpID 路由到对应企业
3. 扫码授权页面：企业管理员自助绑定
4. 客服账号管理：为每个企业创建/管理客服账号
5. 配置管理界面：企业管理员自助配置页面

#### 路线 B：企微个人号 AI 托管模式（自研，体验优先）

> ⚠️ 此路线存在合规风险，需充分评估后再决定是否实施

##### B1. 豆包方案的分析与纠正

豆包给出的"方案 B：自己开发（API + 大模型）"存在一个**致命错误**：

> 豆包声称"基于企业微信客户联系 API + 大模型"可以实现员工与客户单聊的自动回复。

**这是做不到的。** 企业微信官方明确说明：

> "员工和客户单聊时，只有欢迎语是自动发送的，其他都是人工回复。"
> —— [企业微信实现自动回复的 6 种情况](https://kejiweixun.com/note/202402021826)

具体来说，企业微信"客户联系"API 对员工与外部客户的单聊，只提供了以下能力：

| 能力 | API | 能否自动回复 |
|------|-----|------------|
| 添加好友时发欢迎语 | `send_welcome` | 只能发**一条**，且仅限加好友时触发 |
| 获取客户列表/详情 | `get_customer` / `batchget` | 只读，不涉及回复 |
| 创建企业群发 | `create_msg_template` | 群发营销消息，非实时聊天回复 |
| 获取客户行为数据 | `get_user_behavior_data` | 统计数据，不涉及回复 |
| **实时回复客户单聊消息** | **不存在** | **官方没有这个 API** |

豆包方案中描述的"接收企微推送的客户消息 → 调用大模型生成回复 → 调用企微 API 发回给客户"这个流程，**在员工与客户 1v1 单聊场景下，第三步"发回给客户"没有对应的 API 可以调用**。

##### B2. 自研的真实技术路径

既然官方 API 不支持，自研"员工个人号 AI 托管"只有以下几条路径：

**路径 B2-1：会话内容存档 API（读）+ 发送缺口（写）**

```
读取侧（可行）：
  企业微信"会话内容存档"API → 可准实时获取员工与客户的聊天记录
  - 需要：企业开通"会话内容存档"功能（管理工具中开通）
  - 需要：安装企业微信提供的 SDK（加解密）
  - 调用：GetChatData(seq) 增量拉取会话记录
  - 频率：最高 600 次/分钟，准实时

写入侧（不可行）：
  ❌ 企业微信没有提供"以员工身份向客户发送消息"的 API
  ❌ send_welcome 只能在加好友时用一次
  ❌ 没有类似微信客服 send_msg 的接口
```

结论：**能读到消息，但没法通过官方 API 回复**。所以这一条路单独走不通。

**路径 B2-2：会话内容存档 API（读）+ RPA 发送（写）**

```
读取侧：会话内容存档 API（官方合规）
  ↓
AI 处理
  ↓
写入侧：RPA 模拟员工操作发送消息（非官方，灰色地带）
```

这是目前 Weclaw、juhebot 等产品的实现方式。读取用合规的官方 API，发送用 RPA/协议层。

**路径 B2-3：纯 RPA/协议层方案（读 + 写都非官方）**

```
读取侧：RPA/协议层监听企业微信消息
  ↓
AI 处理
  ↓
写入侧：RPA/协议层模拟操作发送消息
```

这是 chatgpt-on-wechat 等开源项目的实现方式。完全不走官方 API。

**路径 B2-4：微信客服"升级服务"机制（合规替代方案）**

```
客户加员工企业微信好友
  ↓
员工发欢迎语（包含客服链接）
  ↓
客户点击链接 → 进入微信客服会话
  ↓
微信客服会话由 AI 通过 API 自动回复（完全合规）
  ↓
需要人工时 → 转人工
```

这是一个**折中的合规方案**：客户先是加员工好友，但实际的 AI 对话在微信客服窗口中进行。缺点是多了一步跳转。

##### B3. 自研路线评估

| 路径 | 可行性 | 合规性 | 开发量 | 推荐度 |
|------|--------|--------|--------|--------|
| B2-1 会话存档（只读） | 读取可行，回复不行 | 合规 | 低 | ❌ 不完整 |
| B2-2 会话存档 + RPA | 可行 | 读取合规，发送灰色 | 中 | ⚠️ 可考虑 |
| B2-3 纯 RPA | 可行 | 灰色 | 中 | ⚠️ 可考虑 |
| B2-4 微信客服升级服务 | 可行 | 完全合规 | 中 | ✅ 推荐 |

##### B4. 如决定实施路径 B2-2/B2-3 的步骤

**阶段 0：调研评估（1 周）**

1. 调研 chatgpt-on-wechat、Weclaw 等的开源实现
2. 评估企业微信客户端 RPA 的稳定性和维护成本
3. 评估合规风险和法律影响
4. 决策：是否实施

**阶段 1：消息读取（1-2 周）**

1. 开通企业微信"会话内容存档"功能
2. 实现会话存档 SDK 集成（加解密、增量拉取）
3. 实时获取员工与外部客户的聊天消息
4. 消息过滤和路由

**阶段 2：AI 回复 + 发送（1-2 周）**

1. 集成 AI 智能体（消息 → 智能体处理 → 生成回复）
2. 实现 RPA/协议层消息发送
3. 转人工机制：标记会话状态，AI 停止介入
4. 多账号管理

**阶段 3：管理后台（1 周）**

1. 员工扫码绑定/解绑
2. 会话监控面板（实时查看 AI 对话）
3. 转人工操作界面
4. AI/人工模式切换

**两种路线的定位**：

| 路线 | 定位 | 适用客户 |
|------|------|---------|
| 路线 A（微信客服） | **正式产品**，推荐所有客户使用 | 所有企业客户 |
| 路线 B（RPA 托管） | **可选增强**，按需提供给有特殊需求的客户 | 需要员工个人号 AI 托管的客户 |

## 14. 限制与注意事项

### 14.1 RPA 托管模式的风险（重要）

| 风险 | 等级 | 说明 |
|------|------|------|
| **封号风险** | **高** | 微信官方明确称此类方式为"外挂或插件等工具非法接入" |
| **数据安全** | **高** | 员工消息流经过第三方平台，存在数据泄露风险 |
| **稳定性** | **中** | 依赖企业微信客户端或协议层的稳定性，版本更新可能导致失效 |
| **法律风险** | **中** | 可能违反微信/企业微信的服务条款 |
| **运维成本** | **中** | 需要持续维护 RPA/协议层以适配企业微信更新 |

**建议**：如果选择实施 RPA 托管模式，需要：
1. 在用户协议中明确告知风险
2. 优先推荐微信客服合规方案
3. 做好随时切换到合规方案的准备

### 14.2 微信客服模式的限制

#### 消息限制

| 限制项 | 说明 |
|--------|------|
| 发送时限 | 用户发消息后 48 小时内 |
| 发送条数 | 每次用户消息后最多 5 条 |
| 消息保留 | sync_msg 只能拉取最近 3 天 |
| 客服账号数 | 每企业最多 5000 个 |
| access_token | 2 小时有效，需提前刷新 |

### 14.3 功能限制

| 限制项 | 说明 |
|--------|------|
| 开启 API 后原生规则失效 | 必须通过 API 处理所有消息 |
| 接待人员需在应用可见范围 | 否则返回错误码 60030 |
| 转人工后 send_msg 失效 | fail_type=5，只能由接待人员手动回复 |
| 授权互斥 | 同时只能授权给一个第三方 |
| 不再支持系统应用 Secret | 2023.12.1 起，必须用自建应用或第三方应用 Secret |

### 14.4 开发注意事项

1. **cursor 持久化**：强烈建议将 sync_msg 返回的 next_cursor 持久化存储
2. **消息加解密**：回调消息使用 AES 加密，需使用企业微信提供的加解密库
3. **access_token 缓存**：不要频繁调用 gettoken，建议缓存并在过期前刷新
4. **回调 5 秒超时**：回调 URL 需在 5 秒内响应，处理逻辑应异步化

### 14.5 开通微信客服的条件

| 条件 | 说明 |
|------|------|
| 企业微信账号 | 必须注册企业微信 |
| 企业认证 | 需完成企业验证 |
| 费用 | **免费开通**，基础功能免费 |
| 未验证且未绑定视频号 | 仅可接待 100 位客户 |
| 已验证或已绑定视频号 | 不限接待人数 |
