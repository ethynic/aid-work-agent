## 1. 假设

微信 4.x 主窗口当前打开的聊天会话，其输入框可通过 Kimi k3 视觉模型定位中心坐标；通过点击输入框聚焦、剪贴板粘贴文本、**Enter 键发送**，可完成单条文本消息发送，且发送成功可机器验证（最后一条消息特征匹配）。

## 4. 关键发现（两个，直接影响正式 tool 设计）

### 4.1 发送动作必须走 Enter 键，不能靠视觉定位"发送按钮"

Kimi k3 定位输入框准确，但**定位"发送按钮"失败**：返回的坐标 png=(913,932) 经 vision 二次核对，落在微信 4.x 底部右侧的**语音通话按钮（麦克风图标）**上，不是发送按钮。

原因：
- 微信 4.x 底部右侧常驻的是语音/通话类按钮，"发送"按钮的视觉特征与这些按钮易混；
- 且微信 4.x 的"发送"按钮往往是**输入文本后才出现的动态按钮**，空输入框态截图里可能根本不可见或不可点；
- 模型对 "send button" 的语义判断不可靠（与 p1 §5.3.2 一致：返回了坐标但语义判错）。

**结论：发送动作走 Enter 键**（微信默认 Enter=发送、Shift+Enter=换行）。这是比视觉定位更稳定、零识别成本的路径。正式 `weixin_message_send` 不应依赖"发送按钮"视觉坐标。

### 4.2 输入框坐标可缓存复用（本次实验核心可复用结论）

> 用户明确指示："对于输入框的坐标，在我们的场景里面只要定位一次就可以记住了，因为微信窗口不会有变化，输入框的坐标不变，失败了再重新定位。"

微信主窗口在**不被用户拖动/缩放**的前提下，输入框中心坐标（相对窗口左上角的 PNG 偏移）**恒定不变**——切换会话、收发消息只改变内容区，不改变窗口布局。因此：

| 元素 | 定位策略 |
|---|---|
| 输入框中心坐标（PNG 相对偏移） | **首次定位后缓存**，后续发送直接复用；仅在坐标失效（点击未聚焦 / 窗口移动 / 窗口尺寸变化）时重新定位 |
| 发送动作 | 不定位，走 Enter 键 |

**缓存键**：以 `window_rect.left/top + 窗口尺寸`（或窗口 HWND + 版本）为键。窗口位置/尺寸变了才失效。**不要以"会话"为键**——输入框坐标与当前是哪个会话无关，只与窗口几何有关。

**失效检测**：发送后若输入框未被清空（vision 核对 / 或 Enter 后输入框仍有残留），判定坐标失效，下次发送前重新定位。p1 的"overlay HWND 消失"终态判据在这里不适用（发送不会打开/关闭覆盖层），需改用"最后一条消息特征匹配 + 输入框清空"。

### 4.3 与 p1 的关系

p1 验证了「导航类」动作（Ctrl+F 搜索 → 点击进入会话）的视觉定位链；p2 验证了「写类」动作（定位输入框 → 输入 → 发送）。两者共用同一 Kimi k3 视觉底座（[p1 §5.3.1](./p1-chat-search-group.md)），差异在：

| 维度 | p1（导航） | p2（写） |
|---|---|---|
| 视觉定位目标 | 搜索结果项（每次都不同） | 输入框（**可缓存**，§4.2） |
| 提交动作 | 点击结果项 | **Enter 键**（不点按钮，§4.1） |
| 终态判据 | overlay HWND 消失 | 最后一条消息特征 + 输入框清空 |
| 风险等级 | P1（导航） | P2（真实发送） |

## 5. 结论

| 假设子项 | 结论 |
|---|---|
| 当前会话输入框可用 Kimi k3 定位 | ✅ 成立（坐标精准，vision 二次核对通过） |
| "发送按钮"可用视觉定位 | ❌ **不成立** — 误识为语音通话按钮，改用 Enter 键 |
| 点击输入框聚焦 → 剪贴板粘贴 | ✅ 成立（沿用 p1 已验证的剪贴板输入法） |
| Enter 键发送 | ✅ 成立（vision 核对消息已发出） |
| 发送成功可机器验证 | ✅ 成立（最后一条消息=目标文本 + 右侧气泡 + 输入框清空） |
| 输入框坐标可缓存复用 | ✅ 成立（窗口几何不变则坐标不变，失败才重定位） |

**整体：P2 写目标达成，单条文本消息 `你好` 已成功发送并由 vision 二次确认。** 发送链路为「视觉定位输入框（可缓存）→ 剪贴板粘贴 → Enter 发送 → vision 核对终态」。

## 6. 后续决策（晋级 P3 / 正式 tool 前必须解决）

1. **坐标缓存落地**：正式 `weixin_message_send` 需实现输入框坐标缓存（键=窗口几何），失效检测=发送后输入框未清空。缓存命中时跳过 Kimi 调用，降低延迟/成本/API 依赖。
2. **Enter 发送的边界**：当前验证的是单行短文本。多行文本（含换行）、超长文本、含 emoji/特殊字符的发送行为未测，需 P3 覆盖。微信"发送方式"设置（Enter=发送 vs Ctrl+Enter=发送）也需探测——若用户改过设置，Enter 可能换行而非发送，需读取设置或回退到点击"发送"按钮。
3. **失败不重试原则**：probe.json 已禁止 `retry_on_unknown`。正式 tool 发送失败（vision 核对未通过）时返回 `unknown`，由调用方/人工介入，**不自动重发**，避免重复发送。
4. **稳定性矩阵（P3）**：当前 1 次成功、1 个 DPI、1 个版本、浅色主题。需扩展 DPI/主题/版本/多行文本/发送方式设置矩阵。
