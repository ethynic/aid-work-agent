# 企业微信自建应用配置与验证手册

> 本文档面向运维人员，聚焦「从零配置到验证通过」的最短路径。
> 详细技术说明见 [wecom-integration.md](./wecom-integration.md)。

---

## 一、管理后台配置（共 5 步）

### Step 1: 创建自建应用

1. 用企业管理员登录 [企业微信管理后台](https://work.weixin.qq.com/wework_admin/frame)
2. 进入「应用管理」→「自建」→「创建应用」
3. 填写:
   - **应用名称**: 如「智能助手」「数字员工」
   - **应用logo**: 上传一个头像（支持 300x300 PNG）
   - **可见范围**: **选择「全体成员」**（确保所有员工都能搜索到并私聊）
4. 点击「创建应用」

> 应用不会出现在通讯录组织架构树中，但员工可在消息列表搜索应用名称直接私聊，或在群聊中 @应用名称。

---

### Step 2: 获取并记录凭证

创建完成后，在应用详情页和「我的企业」页面记录以下信息:

| 凭证 | 获取位置 | 格式示例 |
|------|----------|----------|
| **CorpID** | 「我的企业」→「企业信息」顶部 | `ww2ed7298c926e081c` |
| **AgentId** | 应用详情页 → 「AgentId」 | `1000003` |
| **Secret** | 应用详情页 → 点击「查看」| snAMwJwIWJ4n7kBFDhIXvWLCoxWW2aJTrHPKbjVjdiw |

**安全**: Secret 只能查看一次，建议立即复制到密码管理器或环境变量中。

---

### Step 3: 配置 API 接收消息（最关键）

1. 在应用详情页，找到「接收消息」→「设置 API 接收」
2. 填写:
   - **URL**: `https://your-domain.com/t/{tenant_id}/wecom/callback/{config_id}`，例如 https://agent2.aidingyi.cn/t/tenant_1dc997a1806b/wecom/callback/chan_a1b2c3d4e5f6（config_id 在渠道配置页面创建后显示）
   - **Token**: 点击「随机获取」（或自行输入 16+ 字符） JgYuzLoE42tD3MUCtnZPysh5lmd
   - **EncodingAESKey**: 点击「随机获取」（43 字符 Base64） hUHJd3LTJDb3q9RlDIQ7GdjGlUQmDe73OgIaS9CHt3y
3. **顺序很重要**: 先在服务器配好环境变量并启动服务，再点「保存」。企业微信会立即发 GET 请求验证。

---

### Step 4: 配置可信 IP

1. 应用详情页 →「企业可信IP」→「配置」
2. 添加服务器出口公网 IP
3. 如果有负载均衡/NAT，添加 NAT 网关的公网 IP

> 未配置可信 IP 会导致后续主动发消息返回 `errcode=60020`。

---

### Step 5: 申请通讯录权限

1. 应用详情页 →「权限」
2. 申请「获取成员详情」权限（`contact:user.read`）
3. 让超级管理员在「管理工具」→「权限管理」中审批通过

---

## 二、服务端配置（共 3 步）

### Step 6: 在管理后台配置渠道

> 企业微信渠道凭证 **不再通过 `.env` 配置**,改为在管理后台「渠道配置」页面录入并加密存储到 `tenant_channel_configs` 表中。

登录管理后台,进入「渠道配置」→「新增渠道」,选择渠道类型 `wecom`,填写从 Step 2 获取的凭证:

| 字段 | 来源 | 必填 |
|------|------|------|
| `channel_type` | 固定 `wecom` | ✅ |
| `corp_id` | 「我的企业」→ 企业信息 | ✅ |
| `agent_id` | 应用详情页 AgentId | ✅ |
| `secret` | 应用详情页 Secret | ✅ |
| `token` | API 接收消息 → Token | ✅ |
| `encoding_aes_key` | API 接收消息 → EncodingAESKey | ✅ |
| `welcome_message` | 首次会话欢迎消息 | ❌ |

保存后系统会为当前租户创建一条 `ChannelConfig` 记录,无需重启服务即可生效。

---

### Step 7: 验证服务端健康

```bash
curl https://your-domain.com/health
# 预期返回: {"status": "ok"}
```

确认日志无异常:
```bash
tail -f logs/app.log | grep -i "wecom\|WeCom"
# 预期看到: "WeCom adapter initialized"
```

---

### Step 8: 完成回调 URL 验证

回到企业微信管理后台 Step 3 的页面，点击「保存」。

- **成功**: 页面提示「保存成功」
- **失败**: 页面提示「URL 验证失败」→ 见下方「故障排查」

---

## 三、功能验证测试（共 7 项）

### Test 1: 私聊文本消息

1. 打开企业微信手机端/桌面端
2. 在消息列表顶部搜索框输入应用名称（如「智能助手」）
3. 点击进入，发送一条文本消息: `你好`
4. **预期**: 10-60 秒内收到 Agent 回复
5. **检查日志**:
   ```
   Received wecom message: xxxx, content: 你好...
   WeCom 后台消息处理成功
   ```

### Test 2: 群聊 @应用

1. 在企业微信群聊中 @应用名称 发送消息
2. **预期**: Agent 收到消息并回复到群聊
3. **已知问题（待修复）**: 群聊中 `@智能助手 帮我查订单` 会将 `@智能助手 ` 前缀一并传给 Agent，可能导致理解偏差。当前 workaround: 用户发送消息时不带前缀，或在 Agent 提示词中说明忽略 @前缀。

### Test 3: 关注事件（首次进入）

1. 找一个未使用过该应用的员工账号
2. 搜索应用名称，点击进入
3. **预期**: 当前版本 **不会** 自动发送欢迎消息（已知问题，待修复）
4. 员工会看到一个空聊天界面，需要主动发第一条消息

### Test 4: 长消息拆分

1. 发送一条请求让 Agent 生成超过 100 字的回复
2. **预期**: 如果回复超过 2048 字节，自动拆分为多条消息发送
3. **验证**: 检查是否收到连续的多条消息

### Test 5: 图片/文件消息

1. 发送一张图片给应用
2. **预期**: Agent 能感知到用户发送了图片（消息内容显示为 `[图片消息]` 或图片链接）
3. 注意: 图片内容解析（OCR/视觉理解）需要额外的工具配置，默认仅识别到「用户发了图片」这一事件

### Test 6: 应用工作台入口

1. 打开企业微信 →「工作台」
2. 找到应用图标
3. 点击进入
4. **预期**: 直接进入单聊界面，可以发消息

### Test 7: 重启后会话连续性

1. 进行几轮对话
2. 重启后端服务
3. 在同一会话中继续发消息
4. **预期**: Agent 能感知到之前的对话内容（依赖 Phase 2.1 短期记忆修复是否已完成）

## 四、故障排查速查表

| 现象 | 最可能原因 | 排查命令/步骤 |
|------|-----------|--------------|
| URL 验证失败 | Token/EncodingAESKey 不匹配 | 对比管理后台和 `.env` 中的值是否完全一致 |
| URL 验证失败 | 服务未启动或不可访问 | `curl https://your-domain.com/health` |
| URL 验证失败 | SSL 证书问题 | 检查证书是否过期、是否为自签证书 |
| 发了消息没回复 | 可信 IP 未配置 | 管理后台检查「企业可信IP」 |
| 发了消息没回复 | Secret 错误导致 token 获取失败 | 日志搜索 `获取 access_token 失败` |
| 发了消息没回复 | 用户不在应用可见范围内 | 日志搜索 `errcode=81013` |
| 发了消息没回复 | Agent 处理异常 | 日志搜索 `WeCom 后台消息处理失败` |
| 收到重复回复 | 去重器失效（多 worker 部署）| 检查是否用 Gunicorn 多 worker 模式 |
| 消息发送失败 errcode=60011 | 应用没有发送消息权限 | 检查应用权限配置 |
| 消息发送失败 errcode=40014 | access_token 过期 | 正常，系统会自动刷新，如频繁出现检查并发 |

## 五、已知问题清单（代码层面，待修复）

| # | 问题 | 影响 | 临时 workaround |
|---|------|------|----------------|
| 1 | 群聊 `@应用名称 ` 前缀未清洗 | Agent 可能将 @前缀理解为消息内容 | 在 Agent 系统提示词中说明「忽略消息开头的 @应用名称」 |
| 2 | 用户首次进入应用无欢迎消息 | 新用户看到空界面，不知道能做什么 | 无 |
| 3 | 多 worker（Gunicorn）部署时消息去重失效 | 可能收到重复回复 | 单 worker 部署（`--workers 1`） |
| 4 | 速率限制配置未生效 | 理论上无限制，存在被滥用的风险 | 在 Nginx 层做限流 |
| 5 | 会话 metadata 序列化不规范 | `str(dict)` 存入数据库，读取时可能异常 | 避免在 metadata 中存储复杂结构 |
| 6 | ~~未校验消息的 `ToUserName` / `AgentID`~~ | ~~存在被其他应用消息误触发的风险~~ | 已通过回调 URL 包含 config_id 解决，每个应用独立回调地址 |
