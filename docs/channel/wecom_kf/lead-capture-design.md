# 微信客服（wecom_kf）售前咨询客户留资设计

> 版本: v1.0 | 创建: 2026-08-21 | 状态: 已确认（产品方案，4 项决策点已拍板，见第十二节）
> 关联文档: [wecom_kf_design.md](wecom_kf_design.md) / [transfer_to_human_optimization.md](transfer_to_human_optimization.md) / [kf-account-referral-plan.md](kf-account-referral-plan.md)

---

## 一、背景与适用范围

### 1.1 场景定位

wecom_kf（企业微信客服）渠道已支持微信侧用户与智能体对话，目前用于**售后客服支持**场景已完全满足需求，无需改造。

本文档针对 **wecom_kf 作为售前咨询智能体** 的**客户留资**需求：智能体先与微信用户进行一段对话，评估认为是有意向的客户、且收集了基本需求后，进入留资阶段，引导客户：

1. **留下手机号**：客服专员在几小时内联系客户；
2. **添加员工微信/企微**：给出客服账号归属员工的微信/企业微信二维码，引导客户扫码添加，沉淀为长期私域客户。

### 1.2 适用范围说明

> **本文档仅覆盖 wecom_kf 渠道作为售前咨询智能体时的留资改造。若 wecom_kf 仅作为售后客服支持使用，则无需任何改造，现有功能即满足需求，本设计不影响售后场景的既有行为。**

### 1.3 售前留资 vs 售后客服的核心差异

售后场景会话结束即问题解决，无需再触达客户；售前场景会话结束只是开始——**潜在客户若没有留下任何联系方式，将随会话一起永久流失**。这是售前留资必须做、而售后不必做的根本原因。

---

## 二、核心洞察

wecom_kf 会话本质是**一次性触点**：会话结束，微信侧客户就"失联"（企微侧仍有客户标识，但被动触达渠道已断）。

因此整个售前留资方案要解决的本质问题是：**把"一次性客服会话"转化为"可长期触达的客户资产"**。留手机号和加微信，只是这条转化链上的两条分支，应该**统一设计**，而不是两个独立功能。

---

## 三、三种人工触达手段的统一设计

把"人工介入"设计成三种互补的手段，共用同一个"客户需要人工介入"的判定入口，只是动作不同：

| 手段 | 触达方式 | 前置条件 | 转化结果 |
|------|---------|---------|---------|
| 转人工 | 会话内即时对话 | 客服在线 + 有空（工作时间） | 会话内完成，仍是一次性触点 |
| 留手机号 | 客服事后回拨 | 无（不受工作时间限制） | 销售线索 |
| 加微信/企微 | 长期私域好友 | 无（二维码可离线展示） | 私域客户 |

**关键决策：转人工不是留资的替代品，而是三选一中的一个选项。**

与转人工相比，留资的两点关键差异（用户确认）：

1. **触达持续性**：转人工结束后会话即终结，若会话中客户未留联系方式，之后无法再触达该客户；留资则把客户沉淀为可回拨线索 / 可私聊好友。
2. **时间限制**：转人工必须在工作时间、员工能处理企微消息时才可用；收集手机号、引导加微信则**不受工作时间限制**，非工作时间的咨询也能转化为线索——这是留资相对转人工的核心增量价值。

---

## 四、留资会话状态机

**不能只靠修改提示词实现留资。** 提示词是概率性的，租户配置不同、模型不同，行为就不稳定。留资需要能"按状态推进"，因此在会话层引入显式状态机：

```
探索期 → 判定期 → 留资期 → 完成期（或 放弃 / 超时）
```

| 阶段 | 行为 |
|------|------|
| 探索期 | 闲聊 + 收集需求，不打断客户 |
| 判定期 | 触发条件满足，评估是否有效客户（见第五节） |
| 留资期 | 按规则引导留资：留手机号 or 加二维码（见第六节） |
| 完成期 | 留资成功 / 客户明确拒绝 / N 轮无响应后放弃 |

**会话状态需持久化**：客户中途离开再回来，应恢复到离开时的阶段，不能从头再来。

---

## 五、有效客户判定规则【决策点 1、2 已确认】

### 5.1 判定标准由租户管理员控制

**已确认（决策点 1）**：判定标准**由租户管理员通过修改智能体提示词决定**。系统默认给出宽松的判定口径，管理员可按自身业务收紧或放宽。

**默认宽松口径**："客户主动表达购买意向"或"需求字段达到覆盖度"任一满足即可，命中即进入留资期。

### 5.2 两层判定（产品建议的默认提示词口径）

- **硬信号（行为触发）**：客户主动表达购买意图（"怎么买""多少钱""下单""报价"等）；或客户主动索要联系方式（"怎么联系""加个微信""留个电话"等）。**命中即进入判定**。
- **软条件（字段覆盖度）**：从对话中抽取结构化需求字段（预算、数量、地区、交付时间等），覆盖度达到阈值（如 ≥2 个核心字段）视为有效客户。
- **兜底**：对话轮数超过 N 轮且客户未表达"只是随便问问"，可询问是否需要专人联系。

### 5.3 客户主动发起留资

**已确认（决策点 2）**：客户主动发起留资（如直接询问联系方式）**允许**，且视为**最高优先级信号**——不受"有效客户判定"前置门槛限制，直接进入留资期。

> 设计原则：判定结果只是"进入留资期"的开关，**不是生硬的表单弹窗**。留资引导应使用自然的对话话术，由智能体在对话中顺滑引出。

---

## 六、留资方式的选择逻辑

**不强制二选一**：智能体按场景推荐，同时给客户留出口，避免被唯一选项卡住：

| 场景 | 优先推荐 | 理由 |
|------|---------|------|
| 客服在线（工作时间） | 引导**添加员工企微/微信** | 即时沟通，转化链路最短 |
| 客服不在线（非工作时间） | 引导**留下手机号** | 客服几小时内回拨，不受时间限制 |

**话术上两条都给出**，例如："您可以留下手机号，我们几小时内联系您；也可以直接添加这位同事的微信 XX，随时咨询。" 由客户自选。

**企微原生"转接接待专员"能力（即现有转人工）已跑通**，可作为留资期的高阶选项——客服在线时可直接转接会话，比引导加微信更快。该能力已在上游文档设计，本文档不重复展开。

---

## 七、二维码配置设计

留手机号现有代码即可支持（改提示词），**引导添加员工微信/企微则需要二维码配置**：

- **配置位置**：渠道配置界面的"客服账号"下，增加"归属员工二维码"上传，并区分**员工个人微信二维码** / **企业微信个人二维码**两种类型。
- **归属关系**：二维码必须绑定到客服账号（即归属员工）——因为"留资后通知谁跟进"依赖这个归属关系。一个客服账号对应一个归属员工二维码。
- **提示词引用**：留资话术模板中引用该二维码（图片下发 + 说明文字），微信侧客户可直接查看 / 长按识别添加。
- **复用既有图片管线**：二维码以图片形式下发，走项目既有 ImageRef 图片管线（代码阶段确认复用细节）。

> 关联说明：`kf-account-referral-plan.md`（引流归因）已实现客服账号管理 + 生成客服推广二维码（C 端客户扫码进入会话）。本设计的二维码是**员工个人/企微二维码**（客户扫了添加好友），与引流归因的**客服账号二维码**（客户扫了进入会话）是两类不同二维码，互不冲突。

---

## 八、留资数据闭环

留了资不能白留，必须形成完整闭环，否则客服不知道有线索：

- **留资记录**：客户标识（微信侧 customer_id）+ 联系方式（手机号 / 二维码类型）+ 来源会话 + 对话中抽取的需求字段 + 留资时间，落一条"销售线索"记录。
- **通知**：**已确认（决策点 4）——即时通知 + 定时汇总都提供**：
  - **即时通知**：留资成功即通知归属客服（企微应用消息 / 管理后台待办）；非工作时间产生的留资自动转为次日待办。
  - **定时汇总**：按周期（如每日）汇总未处理线索，避免客服遗漏、便于批量跟进。
- **跟进状态**：线索状态机（新线索 → 跟进中 → 已成交 / 已放弃），供客服在管理后台处理。
- **敏感信息**：手机号等联系方式**加密存储**，查看权限仅限归属客服 + 租户管理员（符合项目安全原则）。

---

## 九、老客户识别与重复留资

- 微信侧客户有稳定标识（customer_id），可识别**已留资客户**再次会话。
- 已留资客户再次进入 → **不再重复索要联系方式**，告知"您上次的需求我们已记录，客服专员会尽快联系"，并补充提供二维码作为私域触达通道。
- 避免同一客户被反复索要手机号（体验差且有骚扰嫌疑）。

---

## 十、边界情况

| 场景 | 处理原则 |
|------|---------|
| 客户在留资期明确拒绝（"不用了""不方便"） | 尊重客户，结束留资引导，回到正常对话，不纠缠 |
| 客户留资中途离开（说了手机号但未确认） | 以"确认收到完整手机号"为成功标准；不完整则不记录，客户回来可继续 |
| 非工作时间产生留资 | 正常记录，即时通知转为次日待办，不受时间限制 |
| 同一客户重复留资 | 以最新一次为准或合并到既有线索，不产生重复线索 |
| 手机号格式异常 | 智能体引导重新提供，校验通过才算留资成功 |
| 客服账号未配置归属员工二维码 | 留资话术只提供"留手机号"分支，不出现无法提供的二维码 |

## 十一、MVP 分期建议

| 阶段 | 内容 | 说明 |
|------|------|------|
| **Phase 1** | 留手机号：改留资话术 + 留资记录落库 + 通知归属客服 | 复用现有能力，改提示词即可上线；同步把"留资状态"纳入会话层，为后续打基础 |
| **Phase 2** | 二维码留资：渠道配置上传员工二维码 + 留资话术引用 + 客服端查看 | 需要二维码配置 + 图片下发 + 归属关联 |
| **Phase 3** | 完整判定状态机 + 线索管理闭环（老客户识别、跟进状态、汇总看板） | 完整的售前留资运营能力 |

建议先以 Phase 1 落地验证留资转化率，再决定 Phase 2、3 的优先级。

## 十二、已确认决策点

| # | 决策点 | 结论 |
|---|--------|------|
| 1 | 有效客户判定标准 | 由**租户管理员通过修改智能体提示词**决定；默认适当宽松（"客户主动表达购买意向"或"需求字段达到覆盖度"均可） |
| 2 | 客户主动发起留资 | 允许，视为**最高优先级信号**，不受判定门槛限制 |
| 3 | 企微原生"转接接待专员"能力 | 即现有**转人工**功能，已跑通，本文档不重复设计 |
| 4 | 线索通知方式 | **即时通知 + 定时汇总**都提供 |

- 员工二维码的图片管线复用（ImageRef）
- 定时汇总的频率、格式与查看入口
