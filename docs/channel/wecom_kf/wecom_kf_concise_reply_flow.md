## 一、背景与反馈

销售在微信客服渠道演示旅行社智能体（语音对话）时反馈：回复啰嗦，一段文字里带表格，又生成一个 md 文件让客户看全文（全文并不长），再加上行程 Word、报价 Excel，东西重复繁琐。

反馈的现象全部由机制导致：渠道发送层与旅行社提示词各自按自己的场景设计，叠加后同一份内容出现三种形态。

## 二、现状（2026-11-23 调研，均为代码与生产数据事实）

### 2.1 渠道发送层（所有智能体共用）

微信客服平台约束：客户每发 1 条消息企业最多回 5 条（`WeComKfReplyBudget(total=5)`）；单条文本不超过 2048 字节；文本消息不显示 Markdown 表格。

`src/channels/wecom_kf/reply_delivery.py` 的 `prepare_reply`：

```
智能体回复
  ├─ 不超长、无表格、无图片 → 直接发 1 条文字
  └─ 超长 / 含表格 / 含图片
        ├─ 生成《详细答复.md》（完整回复原文）
        ├─ 正文含图片 → 整段长图 + md（2 条）
        └─ 其余      → 前缀文字 + md（2 条）
                       前缀文字：≤500 字，表格压成「字段：值；字段：值」列表
```

- 触发条件在 `reply_delivery.py:201`：含表格即触发，与长短无关。
- 只有正文含图片才渲染长图（`reply_delivery.py:224`）。

### 2.2 旅行社提示词（跨渠道共用，为 Web 端设计）

`subagents/travel-consultant/SUBAGENT.md`：

- 详细行程（阶段二第四步）：**先在对话中展示 5 列表格 → 客户确认 → 再调用 `word_process` 生成 Word**，并注明“严格规则，不可跳过”。
- 报价（阶段三）：对话中**输出报价明细表** + 合计 + “Excel 已生成”。

生产环境的 travel-consultant 提示词来源是仓库文件：`subagent_definitions` 表中没有该智能体的行，只有一个 7 月的测试行 `travel-pro`。

租户 `tenant_ea24cd1a1097` 的演示会话，客户说 4 句话，收到 10 条消息、4 个文件：

### 2.5 渠道提示语如何到达模型（生产实证）

微信客服路由每轮都会注入一句渠道提示语（`channel_routes.py` 的 `_KF_CHANNEL_EXTRA_SYSTEM_PROMPT`）。它的实际传递方式：

- `channel_routes.py` 把它作为 `agent_extra_system_prompt` 传入会话处理；`ChannelRunnerAgent` 把它装进 Runner 请求的 `prompt_augmentations`；执行服务把它作为**一条 role=user 的消息，追加在本轮客户消息之后**（`context_assembler.py:102`）。
- 它**不在 system prompt 里**。`prompt_sources._build_system_prompt` 虽有 `extra_system_prompt` 参数，但 Runner 执行链路上没有任何调用方给它传值。
- 生产实证（租户 `tenant_ea24cd1a1097` 的微信客服会话，2026-11-18 的两个任务）：这句话从本轮第一次模型调用起就存在，调用工具的过程中一直保留在消息列表里；两个任务的 system prompt 都不含这句话。
- 追踪记录对大输入只存摘要（`summary_only: true`），不能据此统计“模型是否收到”。

## 三、设计决策（2026-11-23 逐条确认）

| # | 决策点 | 结论 |
|---|--------|------|
| 1 | 微信客服下详细行程怎么给 | 客户确认粗略行程后**直接发行程 Word**，不再先在对话里展示表格等第二次确认 |
| 2 | 微信客服下报价怎么给 | **一句话（总价、人均）+ 报价 Excel**，对话里不再输出明细表 |
| 3 | 其他智能体输出表格或回复确实超长时的兜底 | **只发 md 文件，不发前缀文字**；md 准备或发送失败时才降级发前缀文字 |
| 4 | 旅行社提示词靠什么判断当前在微信客服渠道 | 渠道提示语开头加**固定标识** `【渠道：微信客服】`，提示词按标识判断（2026-11-23 评审时补充确认） |

补充约定：

- 决策 3 保留 md 而不用图片，原因是图片无法复制文字。
- 真正超长与含图片的回复维持现有 md 交付方式；含图片仍是长图 + md。
- 范围外的已知问题（见 §七）不在本次处理。

## 五、详细设计

### 5.1 旅行社提示词：微信客服渠道分支（决策 1、2）

改动文件：`subagents/travel-consultant/SUBAGENT.md`、`src/saas/api/channel_routes.py`（`_KF_CHANNEL_EXTRA_SYSTEM_PROMPT` 常量）。

**渠道识别**（2026-11-23 评审修正）：

- `src/saas/api/channel_routes.py` 的 `_KF_CHANNEL_EXTRA_SYSTEM_PROMPT` 开头加固定标识，改为：`【渠道：微信客服】当前会话来自企业微信客服渠道：用户在手机微信内阅读，回复务必精简、面向手机端，避免长篇分节说明。` 标识之后的原文不变。
- `SUBAGENT.md` 以“对话中出现渠道标识「【渠道：微信客服】」”为分支条件，不依赖标识之后的文字，也不依赖这句话出现在哪种角色的消息里。
- 分支针对的是微信客服渠道本身（该渠道文本不显示表格、每轮最多回复 5 条），不是泛指手机端；其他渠道即使在手机上使用也不适用。
- 标识不出现时一律走现有流程，Web 端及其他渠道行为不变。其他走微信客服的子智能体只是多看到这个标识，没有对应的分支规则。
- 渠道提示语到达模型的方式不变（见 §2.5）。

初稿此处写的是“以『系统提示说明当前会话来自手机聊天渠道』为分支条件”，与实际不符，已改正。

**详细行程（阶段二第四步）在微信客服渠道下改为**：

1. 客户对粗略行程表示满意后，直接进入细化，不再追问是否需要细化。
2. 内部完成详细行程 Markdown（5 列表格，景点与游玩项目的白名单自检保留），不在回复文字中输出。
3. 直接调用 `word_process` 生成 Word。
4. 回复一两句话说明行程文档已生成，并引导客户反馈或进入报价；不重复行程内容，不出现表格。

Word 作为可下载文件由渠道层随回复自动发送，模型只需说明文档已生成。

**同步调整的同一流程环节**：

- 客户对详细行程提出修改：修改后直接重新生成 Word 并发送，不再先展示表格。
- 报价（含换酒店后的新报价）：回复只写一句话，含总价、人均，并说明明细在 Excel 里；不输出报价明细表。
- 报价的 `itinerary_text`：使用生成行程 Word 时的同一份完整行程 Markdown。原规则要求“粘贴之前发给客户的行程原文”，新流程下表格不再出现在回复文字里，需明确取值来源。

**不改的部分**：阶段一了解需求、阶段二粗略行程与调整、四项必填信息、转人工、客户数据推送、Web 端的全部流程。

### 5.2 渠道层：md 单独发送（决策 3）

改动文件：`src/channels/wecom_kf/adapter.py`（`_send_prepared_reply`），必要时涉及 `reply_delivery.py`。

| 交付模式 | 现状 | 新行为 |
|---|---|---|
| 含图片（image） | 长图 + md | 不变 |
| 其余进入 md 路径（prefix / notice / llm） | 前缀文字 + md | **只发 md** |
| md 准备失败（failed） | 固定失败话术 | 降级发前缀文字 |
| md 上传失败 | 前缀文字 + 下载链接 | 下载链接；无可用链接时降级发前缀文字 |

- 前缀文字仍按现有算法计算并保存在 `channelDelivery.text`，用于降级和排查，正常情况下不发送。
- 降级发送的前缀文字去掉“完整回复请查看发送的文件《详细答复.md》。”这句提示，并受单条 2048 字节上限约束。
- 会话历史仍保存完整回复全文，不变。

### 5.3 回复预算

改动文件：`src/saas/api/channel_routes.py`。

- 进度提示为最终交付预留的条数维持 2，不变。这样进度提示仍最多 3 条。
- 最终交付从 2 条降为 1 条，省下的额度留给业务文件（行程 Word、报价 Excel）。image 模式仍占 2 条。

### 5.4 不改的部分

- 非微信客服渠道的发送逻辑。
- 未携带回复预算的旧发送路径（生产环境的微信客服路由始终创建预算）。
- 提问确认单（`send_ask_file`）。
- 其他子智能体的提示词。
- 渠道提示语的传递方式（作为 user 消息到达模型，见 §2.5）。

## 六、风险与验证

| 风险 | 说明与应对 |
|---|---|
| 提示词分支依赖模型遵守 | 不遵守时退回现有流程：对话里输出表格，渠道层只发 md，客户确认后生成 Word。比现状少一条前缀文字，不会更差。真机验证核对 |
| 渠道约束提示词曾干扰工具失败后的恢复（2026-08 废除过一次） | 本次措辞限定为“不发给客户的回复文字里输出表格”，表格仍写入 `word_process` 参数。真机验证需覆盖 `word_process` 失败后的恢复路径 |
| 只发 md 时客户在聊天里只看到文件卡片 | §14.10 曾有“点开文件前看不到内容”的反馈。陆伟知情选择；决策 1、2 落地后旅行社不再触发该路径 |
| 老旧 iOS 微信不渲染 md 表格 | §14.9 已知限制，维持现状 |
| 客户想改详细行程时 Word 已生成 | 需重新生成一次，多一次工具调用 |
| 报价 `itinerary_text` 取值来源变化 | 真机验证核对报价结果与原流程一致 |

验证方式：

- 后端单测：各交付模式的实际发送序列（只发 file、不发 text；image 仍 2 条）、各失败分支的降级、预算消耗。
- 前端：无改动。
- 真机（agent2，微信客服渠道）：完整走一遍演示对话，核对消息序列为 6 条、文件为 2 个；检查模型在微信客服渠道分支下的遵循情况；验证 `word_process` 失败后的恢复；验证报价结果。
- 回归：Web 端旅行社流程不变；其他子智能体在微信客服下的表格回复只发 md。

## 七、范围外的已知问题

11 月 10 日至 13 日，生产日志记录了 21 个客户文件被回复预算静默丢弃（`suppressed_reply_budget`，`remaining=0/5`），均为一次生成多个文件的课件类任务：进度提示与自动 md 先占满额度，业务文件排在其后。客户没有收到这些文件。建议另立项调整优先级，让业务文件排在进度提示之前。
