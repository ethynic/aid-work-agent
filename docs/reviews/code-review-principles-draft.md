# 代码评审准则

> 用途：为非平凡代码开发和逐阶段交付提供通用评审依据；具体功能以其已确认的需求、设计和计划为准。

## 评审目标

评审以已确认的需求、设计、实施计划和现有代码契约为依据，判断实现是否正确、兼容且易于维护。优先找会影响真实使用的缺陷；不以增加代码、测试或限制的数量衡量评审质量。

## 判断原则

1. **核对目标行为**：沿实际调用链检查正常流程、关键边界和失败后的行为。确认实现覆盖设计要求，也确认没有擅自扩展范围或改变未授权的业务语义。
2. **核对架构与兼容性**：复用现有入口、数据结构和项目约定；检查现有调用方、旧数据及恢复路径。指出重复状态、重复计算、单次用途抽象、无效分支和与功能无关的改动。
3. **问题必须有证据**：从真实入口追到用户可见的后果，用可复现结果或完整的源码调用链说明。优先检查正常使用、已支持的升级和重试，以及能说明来源的故障。证据不足时，只记录会影响验收的待验证事项。
4. **防御与门禁按实际风险设置**：只保留权限、数据正确性、恢复等真实边界需要的检查。质疑重复校验、静默兜底、任意阈值、费用或性能门禁，以及为极端但不可达场景增加的限制。不能为了减少代码而移除必要的租户隔离或授权保护。
5. **测试验证意图**：要求测试能在关键业务规则被破坏时失败，覆盖有实际回归风险的路径。删除镜像实现的测试、重复证明同一行为的用例和无关的大范围回归；已有同一代码状态的有效验证结果可以复用。
6. **控制评审范围**：按影响分级报告问题。功能缺陷和安全问题应修复；命名、格式及可选优化不作为阻断项。评审者默认只读报告，由开发者统一修复，修复后只复核受影响部分。逐阶段评审只判断当前阶段的目标与依赖是否成立，不用后续阶段尚未开发的内容阻断当前阶段。

## 提交评审意见前

1. **说明场景如何发生**。谁在什么正常操作、已支持的维护流程或实际故障下进入这段代码？异常数据由哪个入口写入，原子写、重试或既有校验是否已覆盖该触发方式？故障注入可以验证后果，但要说明注入模拟的是哪种真实故障。无法交代来源时，不把手工构造的状态列为缺陷。低频但有明确触发链、会造成重复执行或数据丢失的问题仍应报告。
2. **核对建议会不会把正常路径卡住**。在建议新增校验、等待或阻断前，说明现有机制解决不了什么，哪些任务需要受限，用户怎样恢复。优先沿现有证据和恢复流程处理；只有受影响的操作需要等待时，其他任务继续。明确遵守用户禁止的验证方式。
3. **按受影响的真实入口验收**。涉及排队和并行时，分别验证两个方向的影响，覆盖正常重叠执行和一种有明确来源的失败。涉及开发、测试或打包入口时，按现有手册从适用的环境执行，并明确记录失败、跳过和补齐的前置条件。
4. **把结论写成可验证的意见**。每条缺陷写代码位置、触发步骤或调用链、具体后果、验证结果与最小修正方向。已有问题用基线核对，注明是否由本次变更引入或扩大。无符合证据要求的问题时，直接给出结论与验证范围。

## Runtime 评审例子

- **历史台账与恢复**。若意见依赖台账损坏，先找正常写入、升级或恢复路径能否产生该状态，并检查原子写能覆盖什么。历史记录本身不足以证明旧会话仍有进程。按现有契约核对可用的进程证据与继续接单的条件，遵守用户关于 Windows 重启核验的限制。
- **串行与并行执行**。BOSS 串行任务 A 执行期间，企微只读任务可以开始。A 结束后，BOSS 串行任务 B 可以在企微任务结束前启动。并行领取返回 503 时，核对 B 是否仍按串行队列节奏启动。这些观察能验证调度隔离是否满足要求。
