# 代码评审准则

> 用途：为非平凡代码开发和逐阶段交付提供通用评审依据；具体功能以其已确认的需求、设计和计划为准。

## 评审目标

评审以已确认的需求、设计、实施计划和现有代码契约为依据，判断实现是否正确、兼容且易于维护。优先找会影响真实使用的缺陷；不以增加代码、测试或限制的数量衡量评审质量。

## 判断原则

1. **核对目标行为**：沿实际调用链检查正常流程、关键边界和失败后的行为。确认实现覆盖设计要求，也确认没有擅自扩展范围或改变未授权的业务语义。
2. **核对架构与兼容性**：复用现有入口、数据结构和项目约定；检查现有调用方、旧数据及恢复路径。指出重复状态、重复计算、单次用途抽象、无效分支和与功能无关的改动。
3. **问题必须有证据**：每条阻断性意见写明代码位置、可发生的触发条件、影响及最小修正方向。区分已证实缺陷、合理风险与个人偏好；不把无法在实际调用链中发生的假设场景当作缺陷。
4. **防御与门禁按实际风险设置**：只保留权限、数据正确性、恢复等真实边界需要的检查。质疑重复校验、静默兜底、任意阈值、费用或性能门禁，以及为极端但不可达场景增加的限制。不能为了减少代码而移除必要的租户隔离或授权保护。
5. **测试验证意图**：要求测试能在关键业务规则被破坏时失败，覆盖有实际回归风险的路径。删除镜像实现的测试、重复证明同一行为的用例和无关的大范围回归；已有同一代码状态的有效验证结果可以复用。
6. **控制评审范围**：按影响分级报告问题。功能缺陷和安全问题应修复；命名、格式及可选优化不作为阻断项。评审者默认只读报告，由开发者统一修复，修复后只复核受影响部分。逐阶段评审只判断当前阶段的目标与依赖是否成立，不用后续阶段尚未开发的内容阻断当前阶段。
