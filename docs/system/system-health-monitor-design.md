# 系统健康监控页面设计（管理后台）

日期：2026-11-10。状态：评审完成（同日评审意见已吸收，原 P1/P2 合并为首期），待开发。
关联事故：[excel_process 同步读取阻塞全部 Runner 调度（2026-11-05）](../incidents/excel-process-shared-runner-blocking-20261105.md)。

## 1. 背景与目标

2026-11-05 事故暴露的核心盲区：Runner worker 进程活着（healthcheck 仅 pgrep）、主 API 正常接单，但共享事件循环被同步重活卡死，12 个请求排队最长 37 分钟无人察觉。事后已落地三项工作：excel_process 工具修复、Runner 执行槽隔离（runner slot）、运行超 30 分钟任务飞书预警。

本设计在管理后台新增健康监控页面，把上述散落的健康信号集中到一个实时视图，让平台管理员与产品经理随时（含手机端）看到：

- 任务是否在正常推进（而不是「进程活着但卡死」）
- 槽位/队列负载水位
- 系统资源与业务活跃度

**不做的事**（与事故文档 §5.5 一致）：不新造监控平台、不做跨服务器汇总、不引入 Prometheus/Grafana 等外部依赖、不盲目自动重启或重放任务。

## 2. 定位与范围

| 决策点 | 结论 |
|---|---|
| 部署形态 | **单机页面**：每台服务器各自部署，页面只看本机（各机独立 DB/Redis，跨机汇总需另建上报通道，成本不成比例） |
| 访问者 | platform_admin，路径 `/portal/system-health`（`/portal/monitoring` 已被 TraceBrowser 占用） |
| 手机端 | **必须支持**（产品经理随时查看） |
| 呈现形态 | **纯数字卡片 + 任务明细表，无曲线图**（2026-11-10 用户裁决：以简化为先；异常用红/黄高亮传达，不做历史趋势） |
| 刷新方式 | 前端定时轮询（15s），可暂停；请求失败静默重试，不弹错误 |

## 3. 指标体系

### 3.1 基础四组（首轮已确认）

| 分组 | 指标 | 数据来源 |
|---|---|---|
| Runner 执行面 | 槽位占用（running/finalizing ÷ concurrency）、排队深度（queued 数）、最老任务运行时长、排队等待时长（accepted→首次 running）、当前 active 告警 | `agent_runners` 表 + supervisor 槽位状态；复用 `RunnerAlertRepository.candidates()` |
| 系统资源 | CPU% / load / 内存 / 磁盘 IO 速率 / storage 与日志分区使用率 | psutil（主 API 容器内，/proc 反映宿主机级） |
| 业务面 | 在线用户（最近 5 分钟活跃会话数）、今日请求量、今日错误率 | `chat_records` / `chat_sessions` 聚合 |
| 响应时长 | 任务执行耗时 P50/P95、模型调用错误率 | `chat_records` 或追踪库 obs_spans |

### 3.2 补充指标评估（2026-11-10 追加）

按三个取舍原则筛选：① 与事故同源的活性信号优先；② 低成本 DB/Redis 查询优先；③ 重聚合、低频消费的放后期。

**纳入（按优先级）：**

| 指标 | 分组 | 理由 | 成本 |
|---|---|---|---|
| **worker 调度推进活性** | Runner | **以 DB 行状态推进为唯一判据**：owned_attempts 集合变化、slot 状态迁移、排队深度与 running 数的相对推进——直接回答「进程活着但事件循环卡死」，事故 §7.1 的直接教训。**两个反例信号必须排除**：①「DB lease 是否被续期」不可用——slot 隔离后租约由 supervisor 进程代续（supervisor.py 明文设计「child 阻塞在同步工具时无法自行心跳」时仍续租防误杀），worker 卡死时 lease 照常续期，该信号恒显健康，恰好掩盖要检测的故障；②「心跳文件 mtime」不可用——slot 容器无心跳文件，background 容器的 `.bg_runner_alive` 只反映 background 自身，且有共享 storage 卷心跳互相掩盖的历史教训。**判断逻辑放在采集器侧（纯 DB 读），不在被检测的 worker 循环里**；与既有 agent-runner-monitor 容器的分工见 §4.4 | 极低（DB 轮询对比） |
| **排队等待时长分位 P50/P95** | Runner | 事故中排队 2 分～37 分钟是核心证据；只看「排队数」看不出队列是否在推进 | 低（按 accepted/first_running 时间差聚合） |
| **attempt 重试分布** | Runner | attempt>1 占比升高说明任务不稳定（取消/超时/重试），是执行面劣化的先行信号 | 低（GROUP BY attempt） |
| **DB 连接数水位与查询延迟** | 中间件 | PG 连接耗尽会全站瘫痪；`SELECT 1` 延迟是最便宜的 DB 健康探针 | 极低 |
| **Redis 连通与降级状态** | 中间件 | redis_client 有内存降级逻辑，**降级本身是重要健康信号**（多 worker 状态共享失效） | 极低 |
| **KeyPool 并发水位** | 模型 | 信号量耗尽时模型请求排队，表现为「Agent 不回复」但无错误 | 极低（读信号量计数） |
| **模型调用错误率与延迟** | 模型 | 区分「模型侧慢/错」与「Runner 侧堵」，避免误判（事故排查曾需排除模型接口慢） | 低（chat_records/追踪库聚合） |
| **渠道投递失败计数** | 渠道 | 事故 §10：Runner completed ≠ 客户收到（95003 配额、send_ok=false）；投递失败是独立故障面 | 低（channel_messages metadata 或回执表聚合） |
| **今日错误日志增量** | 业务 | log_error 表按小时计数，与现有日志巡检习惯衔接，异常激增及时暴露 | 低 |
| **积分消耗速率与余额不足租户数** | 业务 | 异常激增检测（外部推送 token 失控类事故的前兆信号） | 低 |
| **tmp/存储目录堆积** | 资源 | tmp 清理任务失效时无感知，目录大小是最直接信号 | 低（目录 du，低频执行） |

**暂不纳入（记录理由）：**

| 指标 | 理由 |
|---|---|
| 慢查询明细 | 需要 pg_stat_statements 等扩展配合，且已有追踪库覆盖请求级耗时；先观察 |
| Gunicorn worker 重启/OOM 追踪 | 容器 RestartCount 需对接 docker socket，权限敏感；先用磁盘心跳文件兜底 |
| 各渠道回调延迟分位 | 回调处理链路目前无统一耗时打点，需先补埋点，单独立项 |
| 防滥用告警数 | 已有独立防滥用中心页面与通知链路，不重复展示 |

### 3.3 分期

| 期 | 内容 | 理由 |
|---|---|---|
| **首期**（原 P1+P2，2026-11-10 评审裁决合并） | Runner 执行面全部指标（调度推进活性、等待分位、attempt 分布）+ psutil 系统资源卡 + 业务面（在线用户/今日请求量/今日错误率/错误日志增量）+ 中间件低成本项（DB 水位与 SELECT 1 延迟、Redis 连通与降级、KeyPool 并发水位）+ 模型错误率与延迟 + 响应时长 P50/P95 + 采集心跳 + **AI 健康研判（见 §9）** + 页面（研判横幅 + 四张状态卡 + 运行中/排队任务两张表，含手机端） | 合并原因：研判的核心价值是组合异常判别（如「CPU 高/低 + 队列不推进」区分同步阻塞与事件循环卡死），拆两期会让首期 LLM 输入不足、研判沦为单指标复述；全部指标均为单轮采集内可完成的 DB/Redis/psutil 轻查询，合并不增加架构复杂度 |
| **后期**（原 P3） | 渠道投递失败、积分消耗速率、tmp 堆积、与通知规则引擎联动外发 | 重聚合与外发联动放后期，观察首期上线后的实际判读需求再定，避免指标堆砌 |

**取消历史曲线**（2026-11-10 用户裁决）：不做任何指标的历史存储与趋势图。采集器只维护 Redis 当前快照，不写环形历史；`/history` 接口取消。若后续确需回溯（如事故取证），追踪库与日志已覆盖请求级耗时，不依赖监控页自建历史。

## 4. 采集架构

### 4.1 采集器

- APScheduler 周期任务挂**独立 background_runner 运行时**（`SERVER_MODE=background` 容器；主 API HTTP worker 已明文零后台任务，不得在其内新增），**15s 一轮**采集全部指标
- 部署前提：目标服务器已部署 background 容器。sim 私有云 compose 明文不部署 background 容器（物理消除定时类外呼），该环境采集器无宿主，页面按 §4.5 口径显示「采集中断（未部署采集器）」，不做静默降级
- 每轮写 Redis 快照（整体 JSON，TTL 90s），**不写环形历史**（无曲线，见 §3.3）
- 每次采集刷新心跳键 `monitor:collector_heartbeat`；页面超 60s 未更新显示「采集中断」黄条

### 4.2 多 worker 与活性原则

- 所有状态走 Redis，不落进程内存（`monitor:*` 前缀注册进 `CacheKeys`，记录进 cache_usage.md），符合 Gunicorn 多 worker 隔离规范
- **Runner worker 的活性判断放在采集器侧**（DB 状态推进观察，判据与两个反例信号见 §3.2），不在被检测的 worker 循环里——Runner 指标全部来自 DB，worker 卡死不会掩盖数据源；若采集器自身循环卡死，心跳键停更，页面直接显示「采集中断」

### 4.3 复用而非新造

- Runner 指标全部查 `agent_runners`（事故文档 §5.5：复用心跳/租约/排队时间观察调度停滞）
- 告警复用 `runner_alerts.py` 飞书推送链路，页面只展示 active 告警，不重复发通知

### 4.4 与既有 agent-runner-monitor 容器的分工

runner 栈已有 `agent-runner-monitor` 容器（`src/services/agent_runner/monitor.py`），每 60s 执行 `RunnerAlertRepository.scan_once()` 并维护 health timestamp，负责告警判定、落库与飞书推送。本设计的采集器**只做页面展示用的指标聚合，不重复告警判定**：

- 告警产生与推送仍归 monitor 容器独占，采集器只读 active 告警展示
- monitor 的 health timestamp 可作采集器健康的旁证（两者任一在推进即说明 DB 可达）
- 两个循环频率不同（15s vs 60s）、职责不同，互不替代

### 4.5 Redis 故障时的页面口径

快照与心跳键均存 Redis，Redis 不可用时页面无法凭既有信号区分「采集器中断」与「存储不可用」，必须显式区分：

- `/overview` 在快照缺失时**现场探测一次 Redis**：探测失败或 redis_client 处于内存降级态 → 返回 `storage_unavailable`，横幅显示「监控存储不可用（Redis）」
- 探测成功但快照/心跳缺失 → 「采集中断」（未部署 background 容器的环境同此口径，附注原因）
- 内存降级期间多 worker 快照互不一致，**不读降级内存里的快照充当数据**，统一按存储不可用展示（不伪装健康）

## 6. 前端页面

### 6.1 页面结构（PC）

- **顶部**：AI 研判横幅（绿/黄/红 + 一句话结论 + 建议动作，标注「AI 研判」；LLM 不可用时回落为规则层判定文案），见 §9
- **上部**：状态卡区——Runner 负载 / 系统资源 / 业务活跃 / 告警四张卡，卡内为数字指标（如「槽位 2/4」「排队 3」「最老任务 12 分」），异常值红/黄高亮，右上显示采集时间戳与刷新暂停开关
- **下部**：两张表——「运行中任务」（runner_id/租户/数字员工/已运行时长，超 30 分钟标红）与「排队任务」（已等待时长倒序）
- 遵循 page_patterns 统计页规范 + Base* 组件；路由注册 `frontend/web/router/portalRoutes.ts`，组件 `frontend/web/components/saas/SystemHealthMonitor.vue`

### 6.2 手机端适配（强制要求）

- 产品经理随时查看，手机端为一等公民；断点 768px（`useMobile`）
- 状态卡由 4 列网格变单列纵排；异常高亮与采集时间戳保留
- 两张任务表转为卡片列表（runner_id、租户、时长、状态纵向排列），横向滚动表格在手机上不可用
- 监控页数据量小（运行中任务最多 concurrency×N 行、排队任务有限），直接全量渲染，**不需要**分页/累积加载
- 注意：本页属平台管理后台，不在 page_metadata.yaml 业务页面选择器登记范围

## 7. 风险与边界

| 风险 | 对策 |
|---|---|
| 采集查询本身拖慢 DB | 聚合查询限频（15s 一轮）、走只读轻查询；后期重聚合指标单独降频（分钟级） |
| 监控数据失真（采集器与被监控者同容器） | Runner 数据源在 DB；心跳键停更即「采集中断」，不伪装健康（事故 §7.2：不能把卡死主循环伪装成健康） |
| 误用 lease 续期/心跳文件当活性信号 | 已在设计层排除（§3.2）：slot 隔离后 supervisor 代续租约，worker 卡死时 lease 恒新鲜；slot 容器无心跳文件。活性只认 DB 状态推进，开发与 CR 阶段按此核对 |
| LLM 研判误判或不可用 | 研判仅展示不驱动任何自动动作；硬阈值告警与飞书推送保持独立；LLM 失败回落规则层文案；结论标注「AI 研判」 |
| 敏感信息泄露 | 任务明细只含 runner_id/租户名/员工名/时长，不含用户消息内容与凭证；研判 prompt 输入仅含指标数值；错误响应统一脱敏 |
| 手机端管理后台无既有先例 | 本页单独做响应式，不要求其他管理页面跟进；样式遵循语义 token |

## 8. 验收要点

- [ ] 模拟 worker 卡死（如临时插入长同步任务）：页面「调度推进」变异常、排队任务表可见积压增长
- [ ] 停掉采集器（或杀 background 容器）：60s 后页面显示「采集中断」
- [ ] 停 Redis（或触发 redis_client 内存降级）：页面显示「存储不可用」而非误报「采集中断」，恢复后自动回到正常
- [ ] 30 分钟长任务出现时与现有飞书预警一致，页面标红
- [ ] AI 研判：模拟排队积压，横幅红/黄高亮即时出现（规则层驱动），**2 分钟内**给出人话结论（60s 评估间隔 + LLM 推理 + 15s 页面轮询的最坏叠加）；停掉模型网关，横幅回落规则层判定、数据展示不受影响
- [ ] 手机端（375px 宽）四卡单列、任务卡片列表可读、无横向滚动
- [ ] 多 Gunicorn worker 下任一 worker 的请求都能读到相同快照（Redis 共享）

## 9. AI 健康研判（2026-11-10 追加，用户提议）

### 9.1 动机

产品经理看到一堆数字难判断「到底正常还是异常」。把每轮采集快照交给 LLM 综合研判，输出「一句话结论 + 分组判读 + 建议动作」，让非技术角色一眼读懂。

### 9.2 架构

- **位置**：研判任务在采集器侧后台执行，**不在 HTTP 请求路径**（页面轮询 15s 只读 Redis 缓存好的结论，不触发 LLM）
- **触发**：默认每 60s 评估一次；**哈希去重的口径是「阈值带离散化」**——所有指标先按阈值表离散为 normal/watch/critical 三态再拼哈希（剔除采集时间戳等纯时变字段），阈值带组合不变则复用上次结论（平静时段零 LLM 调用）。**不能直接对原始数值做内容哈希**：最老任务时长、今日请求量等字段每轮必然变化，原始哈希永远不相等、去重失效；异常出现后最坏 ~2 分钟出结论（60s 评估间隔 + LLM 推理 + 15s 页面轮询），横幅红/黄高亮由规则层即时驱动、不等 LLM
- **输入**：紧凑指标 JSON（仅数值，无敏感内容）+ 判定标准（阈值表来自配置，与规则层同源，避免两套口径）
- **输出**：结构化 JSON——`{overall: normal|watch|critical, summary: 一句话结论, items: [{group, status, note}], suggestion: 建议动作}`；解析失败降级为规则层判定并记日志
- **展示**：页面顶部大状态横幅（绿/黄/红 + summary + suggestion，标注「AI 研判」）；原始数据仍完整展示，LLM 结论只解释数据、不隐藏数据
- **降级**：LLM 失败/超时不影响任何数据展示，横幅回落为规则层判定文案（硬阈值兜底）

### 9.3 与规则层的关系（双层判定分工）

| 层 | 职责 | 特点 |
|---|---|---|
| 规则层（runner_alerts、硬阈值） | 确定性告警、飞书推送、页面红黄高亮 | 即时、可信赖、零成本 |
| LLM 研判层 | 综合研判 + 人话解释，捕捉**组合异常**（CPU 高+队列不推进=同步阻塞；CPU 低+队列不推进=疑似事件循环卡死） | 有延迟与不确定性，仅供人看 |

组合异常正是单个指标都看不出、PM 也无法人工判断的盲区，是 LLM 层的独特价值。**LLM 结论不触发任何自动动作**（不重启、不重试、不发通知），通知链路仍由规则层独占。

### 9.4 计费与合规

**免计费（2026-11-10 用户裁决）**：本页属平台管理后台运维功能，研判 LLM 调用不向租户计费。落地要求：

- 调用点**显式注释豁免理由**（平台级运维监控，参照 `send_sms_code` 豁免先例与 [billing_audit.md](../../.claude/rules/billing_audit.md) §3.8/§5.2 口径），实现时在 billing_audit.md §5.2 豁免索引登记该调用点
- 研判在采集器后台执行、无 HTTP request 上下文，**不适用** §4.3 `record_admin_llm_usage` 模式；如需调用次数/用量观测留痕，走追踪库 span 或独立 `ChatRecordDB.create(source_type=admin_llm_ops, credit_cost=0)` 仅记录不扣费，实现时再定
- 选用 flash 级低配模型，prompt 小、输出 ≤300 字；哈希去重保证平静时段零调用，成本可控

### 9.5 分期

**随首期交付**（2026-11-10 裁决：原 P1/P2 合并，见 §3.3——研判核心价值是组合异常判别，输入缺 CPU/内存时无法区分「同步阻塞」与「事件循环卡死」，拆期交付会让首期研判沦为单指标复述）。研判输入 = 首期全部指标（Runner 执行面 + 系统资源 + 中间件 + 模型面）；后期新增指标（渠道投递/积分速率等）接入后研判输入随之扩展。

## 10. 修订记录

- 2026-11-10：修正采集器重试占比口径 bug——实现误写 `attempt > 0`（acquire_claim 每次 claim 自增，attempt=1 即首次执行，占比恒为 100%），对齐设计改为 `attempt > 1`；同时排队等待分位（accepted -> execution_started_at）限定 attempt<=1 行，重试行的 execution_started_at 是最后一次 claim 时间、含重试间隔，会拉爆 P95（agent2 实例：单条 attempt=3 任务把 P95 顶到 163s）。修正后 agent2 当日实测 P95 38.8s、重试占比 16.7%，均回归正常。
