## N01 职责边界（已确认）

插件是其业务功能的完整实现者，Runtime 是插件的通用调度与管理载体，Agent 根据用户目标使用插件开放的能力。

- Agent 负责理解用户需求，从插件向其开放的能力中选择并调用工具，根据返回结果继续处理。同一会话逐次调用，后续调用使用前次结果。插件内部具体执行步骤由插件维护。
- Runtime 负责插件安装、启停、升级、通用资源和进程管理、任务转交，以及进度、日志和回执的传输。Runtime 代码不根据 BOSS、企微或微信等具体业务名称决定执行步骤、失败跳过或业务恢复策略。
- 插件负责完整业务流程，包括批量遍历、单项失败处理、业务进度保存、业务恢复位置与最终汇总。插件按业务步骤调用获准使用的云端服务。云端业务接口核验授权、处理数据和计费。Runtime 按通用授权提供必要的运行条件、调度作业及传输消息。解耦评审第 3 项已确认。

以筛选一百位候选人为例，Agent 向 BOSS 插件提交目标，BOSS 插件自行处理本批候选人及单项异常并报告结果。Runtime 按通用协议承载这一作业。

能力声明、作业控制、回执、资源、云端服务和迁移规则分别见 N02～N13。

## N02 插件自主声明开放能力（已确认）

插件是自身开放能力清单和业务参数定义的唯一生产者。Runtime 通过统一协议读取、校验并上报声明，服务端通过通用能力映射提供给 Agent，调用权限沿相应授权契约核定。

- 声明包含插件标识与版本，以及各开放功能的稳定标识、用途说明、输入参数和结果格式。支持的字段形状及版本规则在技术定稿时落实为统一 schema。
- 插件明确列出对 Agent 开放的功能，插件内部辅助方法及仅面向配置界面的能力不自动加入 Agent 工具集合。业务用途和参数含义由插件维护。
- Runtime 维护实际安装、启用、连接等通用状态，附带插件报告的功能可用状态与原因。Runtime 和通用服务端装配层不针对 BOSS、企微等名字推导或手工补齐业务功能。
- 新插件或新功能符合统一声明与授权契约后，沿同一发现和映射链路接入。增加业务能力无需修改 Runtime 的插件专属功能清单；插件自己维护相应业务实现及必要的业务服务。

解耦评审第 1 项已确认。Runtime 从已验签插件获取身份、入口、开放工具与调度属性，禁止在安装或执行路径内写死具体插件名称、标识和工具清单。首轮用另一个已有测试发行授权的插件，通过正常导入、能力发现、Agent 调用和回执验证通用接入。

例如 BOSS 插件声明筛选能力、目标数量与筛选条件的输入，以及进度和汇总的结果格式，Agent 据此发起一次筛选作业。Runtime 只理解声明格式和通用运行状态。

任务生命周期、授权、调度、进度和结果传输分别见 N03～N13。

## N03 按完整作业派发及关联（已确认）

一次插件能力调用对应一个完整作业。Agent 按插件声明提交业务目标、参数和已授权范围，经现有受权派发入口交给 Runtime。Runtime 调度到对应插件。插件在作业内自行决定具体步骤、循环、分页和内部批次。

- 复用 `invocation_id` 作为 Runtime 与插件的作业编号。进度、状态、控制和回执均沿此编号关联原作业。Agent 调用由服务端在原 Runner 执行范围内关联已有 `tool_call_id`，后台直调沿统一受理入口分配 `invocation_id`。请求参数的通信格式随技术设计定稿。
- 作业大小由插件开放能力及用户授权共同确定。一个用户目标需要调用多项开放能力时，Agent 根据前次结果选择下一次调用；每次调用分别对应一个作业。某项插件作业的内部操作由插件自行完成。
- 插件可以用多个小 CLI 命令实现内部操作，再组合成一个完整的业务 CLI 命令向 Agent 开放。业务命令负责协调内部操作，报告可展示的过程结果和最终结果。内部命令的拆分及具体开放清单由插件设计确定。

例如 BOSS 开放筛选一批候选人的能力后，Agent 提交一次筛选作业，附带目标数量和条件。插件内部可以每次读取几份、分多页处理，整个过程沿同一作业报告进度并返回汇总。

过程和最终结果、接单去重、取消及续接见 N04～N10。

## N04 作业的过程结果与最终结果（已确认）

插件产生业务执行事实。长作业在执行中按同一作业编号报告已取得的过程结果，结束时报告最终结果。Runtime 根据消息类别转发，Agent 根据插件返回的事实展示进度和结果。

- 过程结果表示截至该次报告的实际进展。插件按业务能力报告适用的内容，例如已处理数量、成功数、失败数或已生成成果。报告过程结果后作业可以继续执行。
- 最终结果表示插件已经结束本次作业，并给出最终状态、成果及未完成情况。支持部分完成的业务命令可以在汇总中保留成功项与失败项。
- 通用契约统一作业编号与消息类别。具体进度字段和结果内容由插件的开放能力声明描述。Runtime 的连接及进程状态独立报告，Agent 展示的业务进展来自插件。

例如筛选作业报告“已处理 3 位，2 位成功、1 位失败”，Agent 可以当场展示。作业结束时，插件再提供本次筛选的最终汇总。

## N05 Runtime 向服务端补传已有最终回执（已确认）

本条约定 Runtime 与服务端之间的结果通信。Runtime 收到插件的最终结果后，为这份结果保存唯一标识并持久保存原回执，直至服务端确认接收。网络失败或确认回包丢失时，Runtime 使用原作业编号和同一个结果标识重试发送原结果。服务端按结果标识只记录一次，重复送达返回已接收确认。

回执待补传属于传输状态。已有最终结果的作业按实际结束状态记录，Runtime 继续调度资源允许且独立的后续作业。补传沿原作业发送已有结果。

例如 BOSS 已经完成筛选，Runtime 已收到最终统计，发送过程中断网。Runtime 保存统计，连接恢复后补送同一份回执。符合执行条件的下一项独立作业可以继续调度。

本条适用于 Runtime 已取得最终结果的情形。插件中断且尚无最终结果时按 N06、N08 处理。

## N06 插件执行中断与故障诊断（已确认）

Runtime 确认插件执行异常中断且尚未取得最终结果时，为该次中断保存唯一的问题编号，关联原作业及已收到的过程结果。同一次中断的日志和补报沿用同一个问题编号。Agent 根据已收到的事实向用户展示已经完成的进展、可说明的错误原因，以及可复制的问题编号。

Runtime 记录这次中断的诊断信息，包括原作业编号、发生时间、Runtime 和插件版本、最后收到的进度、可取得的退出码及错误堆栈，以及相关的 Runtime 和插件日志。运营与开发人员按权限用问题编号在服务端查到对应的诊断记录及日志。日志按现有脱敏要求处理。网络不可用时先在本机保存，恢复连接后按原编号补报。采集不到的证据如实标明缺失。

Runtime 与服务端之间的连接中断作为通信状态单独报告。作业执行状态以插件报告或可验证的本机执行事实为准。相关资源释放后，符合条件的独立作业可以继续调度。

插件负责判断并处理业务步骤卡住或超时。Runtime 按插件异常退出等可确认的执行事实报告中断及问题编号。总耗时和过程消息间隔用于诊断，设备心跳、作业续租与插件进度独立处理。作业仍在运行且异常无法确认时继续等待，当前串行作业实际结束或确认停止后再调度下一项。此决议替代此前按静默时限自动结束作业的规则。

例如 BOSS 上报处理了 3 位候选人，随后插件进程异常退出。Agent 可以显示“已处理 3 位，其中 2 位成功、1 位失败。执行中断，未取得最终结果。问题编号 R-8F2K”。运营与开发人员用同一编号查看当时的进程退出信息及上下文日志。原作业的续接按 N08。

## N07 插件错误上报及 Runtime 兜底（已确认）

插件使用统一结构报告错误，包含可识别的错误码、可向用户展示的说明，以及已确认的部分结果。出现需要定位的异常时，错误报告关联可查询的问题编号。业务错误码与含义由插件维护，Runtime 校验统一结构并转发。

插件崩溃、返回格式无效或未能提供有效错误报告时，Runtime 按同一结构报告可确认的通用错误，例如插件进程异常退出、插件响应无法解析，并关联已有进度和问题编号。业务失败及其处理策略由插件报告，Runtime 根据实际观察到的执行和通信事实生成兜底报告。

Agent 接收错误码、可展示说明、已有结果及适用的问题编号。可取得的异常堆栈、进程输出和上下文日志按 N06 的权限及脱敏规则记录，供运营和开发按编号查询。插件异常文本及诊断日志与 Agent 的公开结果分别传输。

## N08 插件中断后续接原作业（已确认）

插件通过统一能力声明表明是否支持续接，并持久保存可以续接的原作业进度。业务中断后由用户决定是否继续。用户明确要求继续、原授权仍有效且执行资源重新可用时，Runtime 才转交关联原作业及进度的续接请求。能否接续由插件根据自身保存的进度决定，插件负责恢复具体业务位置。BOSS 对外开放的继续筛选命令与参数在 BOSS CLI 独立设计中确定。

同一作业恢复后，插件保留已完成的成果与已尝试但结果未知的记录，从尚未处理的部分继续。已尝试且结果未知的业务动作在原尝试结束，用户明确要求重做时另发新尝试。过程与最终结果继续归入原作业，中断问题编号保留在作业记录中。

插件不支持续接或无法读取可靠进度时，原作业保留中断结案及已确认成果。Runtime 继续调度符合资源条件的其他作业。

例如 BOSS 已完成前 22 位，第 23 位的招呼已尝试但结果未知。插件确认可以续接时，从尚未处理的第 24 位继续。原作业编号及第 23 位的记录保留。作业取消与授权撤销按 N10、N12。

## N09 同一个作业重复送达时的处理（已确认）

服务端受理作业时固定 `invocation_id`。同一受理请求或派发因网络问题重送时，沿用原编号和原请求参数。插件以该编号确认是否已经接单，并在开始执行前持久保存接单记录。Runtime 按 N05 保存及补传原回执，服务端按结果编号去重归档。解耦评审第 5 项已确认。

同一作业重复送达时，插件按已有记录返回接单确认、当前状态或已有结果。同一编号对应同一份请求，参数不符时报告请求冲突。原作业的接续按 N08 由插件决定。

例如服务端派发筛选作业，插件已接单，但接单确认回包丢失。重送使用原作业编号。插件根据已有接单记录回复状态，整批筛选只启动一次。

## N10 取消作业与停稳确认（已确认）

取消请求关联原作业编号，范围为该项作业。尚未开始的作业标记为取消，其余作业继续排队。运行中的取消由 Runtime 转交对应插件，并按实际状态报告正在取消或已取消。插件收到取消后停止启动新的业务步骤，安全收尾当前执行，并返回已完成、结果未知和未执行的情况。

插件确认作业已停止，或 Runtime 取得对应执行已停稳的直接证据后，才确认取消完成并释放该作业占用的资源。取消期间沿原资源规则调度其他独立作业。取消请求到达时作业已结束，则返回已有的最终状态与结果。已取消作业保留原进度及结果记录。

例如用户取消筛选一百位候选人的作业，插件当前已完成三十位。插件安全结束后报告已完成的成果和剩余情况，Agent 按实际结果展示取消完成。

## N11 按 CLI 并行声明调度（已确认）

首轮对外业务 CLI 只声明是否允许并行。由插件提供方人工确认可以全程在后台完成且与串行作业无冲突的命令，并标记为可并行。例如只读本地数据库的命令。其余对外命令默认进入同一个串行队列。插件内部命令由插件按 N03 自行组织。

Runtime 按该 CLI 的声明调度。Agent 或后台发起的串行作业在同一个 Runtime 内共用一个队列，当前作业实际结束或确认停止后开始下一项。BOSS 对外 CLI 全部声明为串行。可并行作业直接执行，可以相互并行，也可以与一项串行作业同时运行。

并发主要来自多个用户或会话。例如用户 A 执行 BOSS 串行作业时，用户 B 提交声明可并行的聊天记录数据库查询，可以同时执行；用户 C 的另一项串行作业进入同一队列等待。同一 Agent 会话按结果依赖逐次调用开放能力，后续调用使用前次结果。会话顺序由 Agent 的调用流程形成，`session_id` 和 `runner_id` 沿 N12 用于可选关联。

## N12 作业授权与会话关联（已确认）

安装插件授权在该设备上使用该插件。服务端受理作业时，从可信认证和既有设备授权确认用户、目标设备、开放能力及该次作业的允许范围。涉及受权文件或云端服务时，使用原有授权接口绑定所需范围。

Runtime 按已受理作业的设备、插件和授权范围调度。插件在本次授权范围内实施业务，续接沿原作业有效授权执行。Agent 的职责是依据用户需求和授权提交参数。授权失效时，相关作业停止启动新的业务动作并按通用停止规则收尾。

例如用户授权筛选一百位候选人，本次作业的范围包含读取、评分与约定的入库。向候选人发招呼属于另外授权的业务动作。

服务端派发作业时，可附带 `session_id` 和 `runner_id` 用于会话归档及前端展示。Runtime 在原作业记录中保存已提供的字段，回传进度、状态、错误和最终结果时按原值附带。服务端依据原作业归属核对关联，并将结果归入对应会话或 Runner 执行记录。

两个字段均可单独缺省。已受理且授权有效的作业按作业编号执行、关联和留存。Session 和 Runner 信息由 Runtime 保管，CLI 的业务入参沿插件能力声明传递。身份和执行授权以原作业的受信授权为准。

## N13 新版契约生效与升级切换（已确认）

Runtime、BOSS CLI 与 WeCom CLI 的首轮发布目标均为 `1.0.0`。产品版本和通信契约版本分别登记。服务端、Runtime 和插件均支持对应契约能力时，新的作业使用该能力。

用户在解耦评审第 2 项确认企微与 BOSS 一起重构。两个插件直接按新版作业契约声明和上报自身工具，进入同一个调度器。1.0.0 上线后统一升级 Runtime 和所使用的插件，旧作业协议及原拟议的企微兼容入口退役。微信排除首轮交付和验收。

已受理作业按接单时绑定的插件版本、契约与授权处理。切换版本前完成旧作业，或按 N10 取消并确认停稳，交付已保存回执。升级沿用有效设备配对身份。切换后的新作业统一使用新版协议。

Runtime 重启后按原身份自动恢复上线和通信，补传已保存的原回执。服务端尚未被领取、仍有效且授权成立的排队作业继续按原记录调度。已启动作业依据原调用状态及保存的结果报告实际情况，已经中断的业务沿 N08 由用户决定是否继续。Runner 根据原作业状态处理等待、结果或中断通知，聊天前端通过原 Runner 查询和事件通路取得状态。

## 首轮实施范围（已确认）

首轮重构以 Runtime、BOSS CLI 与 WeCom CLI 为实施对象，产品发布目标均为 `1.0.0`。两个插件的对外业务命令及内部 CLI 拆分分别在各自设计中确定。共同契约版本登记为 3.0，通信字段及协议版本随实施阶段样例定稿。
