# Runtime 与业务插件 1.0.0 重构设计

**设计已确认，待开发。** 本文是共同契约 3.0 在 1.0.0 的实施正文。Runtime、BOSS CLI 和 WeCom CLI 同轮重构及发布，微信排除首轮。各组件产品版本为 `1.0.0`，通信协议版本及精确字段随接口设计登记。开发和验收见[独立实施计划](../plans/plan-runtime-plugin-1.0.0.md)。

## 1. 职责

| 组件 | 负责事项 |
| --- | --- |
| Agent 与 AgentRunner | 理解目标，按用户授权选择开放能力，管理上层任务、推理和用量，使用插件的过程及最终结果。同一会话按前次结果逐次调用工具。 |
| 服务端 | 核定身份、设备、版本和授权，受理并派发作业，按结果编号去重、归档并提供给 Agent。Desktop 使用公开 Runner 网关，Runtime 使用设备 API。 |
| Runtime | 管理插件的安装、启停和升级，读取能力声明、管理受管进程、调度作业、转发进度和结果、补传回执并报告运行异常。独立 Runtime、Desktop 与 CLI 入口共用 Runtime core。 |
| 业务插件 | 声明对外能力，执行完整业务，组织内部 CLI、分页、批量与单项失败处理，保存进度，提供最终汇总并判断业务是否可续。 |
| 云端业务接口 | 核验业务授权、处理数据和计费。插件按自身业务步骤发起获准的云端调用，Runtime 按通用授权提供所需运行条件。 |

## 2. 安装与能力声明

插件是自身能力声明的唯一来源。受信声明包含插件身份、入口、版本、能力稳定标识、用途、参数、进度和结果格式、可用状态及调度属性。插件明确面向 Agent 的命令与配置专用或内部能力。Runtime 按签名、发布信任及统一格式校验并上报，服务端按授权映射到 Agent。具体插件名、标识、工具名单和业务规则禁止写死在 Runtime 和通用装配路径中。

安装授权在该设备上使用插件。安装、启用和业务就绪分别管理。插件负责判断窗口、浏览器、登录、数据库等业务条件，按统一格式报告。作业、文件和云端服务的访问范围沿既有可信授权核定。设备 Skill 的安装、分析及 workspace 授权沿既有边界适用。

## 3. 作业、编号与调度

一次对外能力调用对应一个完整插件作业。服务端受理时固定 `invocation_id`、执行设备、插件版本、契约和授权范围。Agent 发起时在原 Runner 执行范围内关联 `tool_call_id`，后台直调由同一受理入口分配 `invocation_id`。Runtime 和插件用 `invocation_id` 关联派发、进度、控制和回执。同一受理或派发请求重送沿原编号和参数，插件在开始前持久记录接单。重复送达返回已有接单状态或结果，同编号参数冲突时报错。

`session_id` 与 `runner_id` 各自可选。Runtime 保存已提供的值，随进度、状态、错误和结果原样回传，服务端按原作业核对关联。缺省时按 `invocation_id` 照常执行和留存，插件业务参数由能力声明定义。

同一 Runtime 中，Agent 或后台发起的串行作业跨插件共用一条队列。当前作业实际结束或确认停止后开始下一项。命令默认串行，插件提供方人工确认可独立运行后才标记可并行。标记的作业直接执行，可以与串行作业同时运行。BOSS 对外命令全部串行。Runtime 按声明调度。首轮基础调度用受控测试命令验收，BOSS 和企微各自验证实际业务。

## 4. 进度、回执与诊断

插件按原作业编号报告已取得的过程结果、最终状态和汇总，部分完成时保留成果与失败项。Runtime 转发，Agent 展示。Runtime 收到最终结果后保存原回执及唯一结果编号。网络或确认回包丢失时补传同一份回执，服务端按结果编号只记录一次并确认，符合条件的独立作业继续调度。

插件用统一结构报告错误码、可展示说明、已确认的部分结果及适用的问题编号。Runtime 遇到插件退出、返回无效或缺失时，按实际执行事实报告通用错误。确认异常中断而无最终结果时，保存唯一问题编号并关联原作业与已知进度。用户看到已完成内容、可展示错误及编号。运营与开发按权限查询编号关联的脱敏日志、版本、时间、进度及可取得的退出码和堆栈。断网时先本地保存，恢复后按原编号补报，缺失证据如实标明。

## 5. 长作业、取消和继续

业务卡住和业务超时由插件判断及处理。Runtime 记录运行时长、过程消息间隔和实际退出等事实。设备心跳、作业续租和业务进度独立处理。作业仍在运行且异常无法确认时继续执行，后续串行作业等待实际结束。长批次按同一规则处理。

取消只处理指定 `invocation_id`。未开始的作业标记取消，运行中的作业由插件停止开始新步骤并安全收尾。插件确认停止或 Runtime 取得直接停稳证据后确认取消并释放串行执行资格。已结束时返回已有结果，取消保留已完成、结果未知及未执行的事实。其他独立作业继续执行。授权失效时停止启动新业务动作并按本规则收尾。

插件声明是否支持续接。业务中断后，由用户决定是否继续。用户明确要求、原授权仍有效且执行条件恢复时，Runtime 转交关联原作业的续接请求。插件根据保存进度判断能否从尚未处理的部分继续。已完成的成果和已尝试但结果未知的记录保留，用户明确要求重做时另发新尝试。插件无法续接时按中断结案，其他符合条件的作业继续调度。

## 6. 设备连接、配对与启动恢复

设备身份以服务端发放的设备 ID、凭据和已提交配对回执为依据，上线以原身份的服务端心跳回执为依据。Runtime 使用原身份自动重连和补传已有回执。服务端尚未领取且有效、授权成立的排队作业继续调度。Runner 根据原调用事实报告等待、结果或中断，前端通过原 Runner 查询和事件通路获取状态。

配对由用户显式发起，沿配对协议 4 先准备、在本机保存候选身份、再确认切换。换绑沿原凭据或服务端授权的替换票据验证。明确失败时结束本次尝试、说明原因并保留有效原设备身份。再次配对由用户发起。确认响应不明时以同一事务查询状态。普通启动、重连及启动重试沿已配对身份进行，旧待配对记录退出活动入口。

登录或唤醒后需要自动恢复 Host 时，使用原身份尝试最多 5 次，含第一次。尝试间短暂等待，每次重试前查询 Host 和已有启动操作。已在运行则结束启动恢复，明确未启动时才发起启动。逐次记录失败，5 次仍无法恢复时向用户报告错误。已运行的 Host 继续原心跳与领取重连循环。

## 7. 运行状态与安全切换

| 事项 | 判定依据 |
| --- | --- |
| 本机实例与安装交接 | 自身安装目录、独占租约、安装记录及已登记进程。升级交接已知旧实例。 |
| 受管执行停稳 | 受管进程实际退出或可信的退出回执。执行停止与业务结果分别报告。旧执行确有冲突时限制对应执行资格，设备连接独立恢复。 |
| 业务就绪 | 插件自己报告桌面、浏览器、应用、登录或数据库等条件。 |
| 设备归属与调度 | 服务端授权的设备身份、作业及实际执行状态。本机由 Runtime 队列与插件并行声明调度。 |
| 故障诊断 | Runtime 自身记录、服务端回执和插件消息。Windows 登录或唤醒可触发状态检查，系统日志供人工取证。 |

Windows 提供进程、文件权限、凭据保护和本机通信。1.0.0 的状态判断退役开机标识、Windows 会话编号、重启见证、机器指纹、全机进程枚举、通用锁屏门禁以及按浏览器、插件或工具名的调度特例。旧判断在对应替代路径验证后退役。受支持的多入口确实共用物理输入时，验证互斥由同一队列或明确的输入互斥承接。缺少旧本地 Job 或进程记录时保留未确认事实。

统一升级前按接单时绑定的版本收尾，或取消并确认停稳，交付已保存的回执。升级沿用有效配对身份和作业记录。切换后服务端、Runtime 和对应插件共同使用新版作业契约，旧作业协议和企微兼容入口退役，旧组合显示升级提示。回退按经过验证的服务端和客户端组合进行。
