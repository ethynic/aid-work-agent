## 1. 触发：竞品对比下的定位焦虑

### 1.1 现状

- v0.4 MVP 已完成 Phase 0-5（选场景->上传素材填文案->抽 1-3 张卡->留用精修->下载），跑通阿里云万相 + Minimax-H3 两套模型。
- 实测 Minimax-H3 效果更好、性价比更高，768P 成本价 **0.5 元/秒**。
- 现有「视频创作」页面作为 MVP 原型保留，功能完整闭环，可满足短期演示任务；新功能（本文档讨论的企业级能力）独立开发，避免破坏原页面。等新功能成熟后删除原页面。

### 1.2 竞品对比

| 维度 | 可灵 / 小云雀 / 即梦 | 本项目视频创作智能体 |
|------|-------------------|--------------------|
| 功能完成度 | 高（剪辑/特效/转场/字幕一应俱全） | MVP 仅抽卡+精修，无帧级剪辑 |
| 品牌口碑 | 已有行业知名度 | 无品牌积累 |
| 价格 | 小云雀 C 端 **0.33 元/秒**（720P，订阅会员） | 成本即 0.5 元/秒，售价最低 1.5 元/秒 |
| 目标用户 | C 端创作者 | （现行 PRD）电商运营人员 |

**结论**：在「工具效率 + 单秒价格」维度，我们没有任何优势。继续在 C 端赛道卷工具功能，必败。

### 1.3 价格倒挂的本质

C 端产品能压到 0.33 元/秒的原因：①自建模型摊薄成本；②订阅制锁定使用量；③流量广告补贴；④以创作者个人为付费单位，规模效应摊销。

我们走 API 转售路径，成本结构决定了**单秒价格永远打不过 C 端自建模型产品**。继续在「单秒价格」上竞争是死路。

## 2. 核心判断：回到企业级定位

### 2.1 项目总体定位

本项目是企业员工智能代理系统（B2B SaaS），所有数字员工的总体定位是「让企业员工更高效地完成工作、让企业管理者感知 AI 价值、推动续费」。

视频创作智能体作为数字员工之一，**不应脱离总体定位去做 C 端工具**。现行 PRD v0.4 把目标用户限定为「电商运营人员」、产品形态为「抽卡式工具」，是 MVP 阶段的合理收敛，但不是终态定位。

### 2.2 差异化方向

**不在「单秒生成价格」上竞争，而在「组织能力沉淀」上竞争。**

C 端工具解决「个人创作者怎么快速出一条视频」，企业级智能体要解决：

- 员工离职后，他攒的素材、提示词、成片怎么办？
- 团队多人协作时，素材和品牌规范怎么统一？
- 管理者怎么知道这个月的视频积分花在了什么地方、产出了什么？
- 企业合规（AI 标识、肖像授权、违禁词）怎么强制？
- 一条成功视频的"出片配方"怎么变成团队都能复用的资产？

这些问题 C 端产品**不解决、也不想解决**。这就是我们的差异化空间。

## 3. C 端工具 vs 企业级智能体的本质差异

| 维度 | C 端工具（可灵/小云雀/即梦） | 企业级智能体（本项目目标） |
|------|------------------------|-------------------------|
| 用户角色 | 创作者个人 | 员工 + 团队 + 管理者 + 管理员 |
| 资产归属 | 个人账户，员工离职即流失 | 企业组织资产，员工离职不带走 |
| 素材来源 | 用户自己拍/找 | 企业产品库、品牌素材库、历史成片 |
| 协作模式 | 单人完成全流程 | 创作->审核->发布->数据回流多角色协作 |
| 质量要求 | 创意性、个人表达 | 一致性、合规性、可复用性 |
| 成本承担 | 个人订阅 | 企业预算（需 ROI 度量） |
| 知识积累 | 个人 prompt 收藏 | 企业提示词库 + 模板库 + 失败经验黑名单 |
| 使用频次 | 高频个人 | 中频团队（单次价值更高） |
| 决策权 | 用户即买家 | 使用者≠决策者≠付费者（三权分立） |
| 合规要求 | 平台基础合规 | 企业品牌规范 + 行业合规 + 肖像授权 |
| 价值证明 | 不需要 | 必须（让管理者感知 ROI 推动续费） |

**核心洞察**：C 端工具的护城河是「模型能力 + 创作者生态」，企业级智能体的护城河是「组织资产 + 业务流程嵌入」。两者不在同一赛道。

## 4. 新的产品定位

### 4.1 一句话定位

> **企业级视频创作智能体：把企业素材、提示词经验、品牌规范沉淀为组织资产，让团队任何人都能产出符合品牌标准的高质量视频，并让管理者看见每一笔积分的产出价值。**

### 4.2 目标用户（角色扩展）

| 角色 | 使用场景 | 诉求 |
|------|---------|------|
| 创作者（市场/运营/销售） | 日常生成视频 | 用企业素材快速出片，不必从零开始 |
| 审核者（部门主管/品牌经理） | 审核视频合规与品牌一致性 | 一键驳回违禁词/不规范视频 |
| 发布者（社媒运营） | 多渠道分发 | 一次创作多端适配 |
| 团队管理者 | 看板洞察 | 团队产出/留用率/ROI |
| 租户管理员 | 配置与计费 | 品牌规范、权限、配额 |

### 4.3 核心价值主张（与 C 端的差异）

| C 端卖点 | 我们的企业级卖点 |
|---------|----------------|
| 模型多、生成快 | **资产沉淀**：素材/提示词/成片归企业所有 |
| 价格便宜 | **协作闭环**：创作-审核-发布-回流一站式 |
| 创意自由 | **品牌一致**：规范强制、合规自动、肖像可溯 |
| 个人即买家 | **价值可见**：管理者看见 ROI、推动续费 |

## 5. 五大差异化核心能力

### 5.1 企业素材资产中心（用户原想法①的深化）

**不只是「上传素材」，而是「品牌资产中心」**。

| 子库 | 内容 | 关键能力 |
|------|------|---------|
| 产品图库 | 多角度产品图、SKU 关联、详情页图 | 多角度关联、版本管理、复用统计 |
| 模特素材库 | 真人/AI 模特图 | **肖像授权状态管理**（授权范围、到期日，未授权禁用） |
| 品牌视觉规范 | logo、字体、配色、AI 标识样式 | 强制注入（生成时自动套用） |
| 历史成片库 | 已审核通过的视频 | 可作参考素材、可溯源提示词 |
| BGM/配乐库 | 带版权标识的背景音乐 | 版权过滤（按渠道选可用 BGM） |
| 实拍片段库 | 用户上传的实拍素材 | 与 AI 生成素材混合使用 |

**与 v0.4 MVP 的关系**：MVP 不建产品库（PRD §7.2 推迟到 Phase 1）。本能力是 Phase 1 的核心，但范围扩展为「企业素材资产中心」，不止「产品库」。

### 5.2 提示词知识沉淀（核心壁垒，用户原想法③的深化）

**这是与 C 端产品最大的差异化**：C 端产品的提示词是个人资产（用户自己存草稿），我们的提示词是组织资产（团队共享、可溯源、可复用）。

#### 5.2.1 两层提示词模型

| 层级 | 内容 | 例子 |
|------|------|------|
| **生成层提示词**（喂给视频模型） | 可灵 8 层框架：元素参考/镜头标签/景别主体/动作/运镜/场景光影/音频/风格锚点 | `product_1, medium shot, slow push in, ...` |
| **策略层提示词**（喂给文本模型） | 把用户模糊需求转成生成层提示词的策略 | 「为美妆产品生成开箱视频，强调水貂毛材质，暖色调」 |

#### 5.2.2 沉淀什么

| 资产类型 | 来源 | 用途 |
|---------|------|------|
| 高留用率提示词模板 | 用户留用视频的提示词自动入库 | 团队复用，新员工直接套用 |
| 失败提示词黑名单 | 驳回视频的提示词模式 | 防止重蹈覆辙 |
| 提示词片段库 | 光影描述、运镜描述、材质描述 | 像搭积木一样组合 |
| 企业风格偏好 | 团队使用习惯统计 | 「我们公司偏爱暖色调、慢运镜」自动注入 |
| **成片->提示词溯源链** | 每个成片都能反查到完整提示词链路 | 复盘、教学、合规审计 |

#### 5.2.3 与组织知识沉淀调研的对接

[组织知识沉淀调研](../../research/org-knowledge-sedimentation-research.md)提出的「双层 Graph（个人+组织）」「Topic Cluster 自动抽取」「专家识别」机制在视频场景的具体落地：

- **专家识别**：某员工在「美妆开箱视频」上的留用率高 -> 自动识别为该场景专家 -> 其提示词模板优先推荐给团队。
- **置信度阈值**：留用率达阈值才入库，避免低质模板污染。
- **管理员审核**：高价值提示词模板经管理员审核后正式发布。

### 5.3 双模型协同的提示词引擎（用户原想法④的深化）

**用户痛点**：实测发现借助豆包/千问生成视频提示词再粘贴回来，效果比直接写好。说明现有提示词引擎（PRD §5.6）不够强。

**问题本质**：用户用第三方 AI 的本质是「需要创意发散 + 结构化整理」，而现行提示词引擎只做「填模板」。

#### 5.3.1 改进方案：双模型协同

```
用户输入（业务层，中文）
    "为假睫毛产品做开箱视频，强调 12mm 水貂毛"
        ↓
[文本模型：DeepSeek / Qwen]
   - 创意发散：3-5 个分镜构思
   - 结构化整理：可灵 8 层框架
   - 输出提示词草稿
        ↓
[用户确认环节]（关键，用户原想法④的核心）
   - 展示草稿，支持修改
   - 高级用户可手改
   - 修改差异反馈给引擎做 few-shot 学习
        ↓
[视频模型：Minimax-H3 / 万相]
   - 基于确认后的提示词生成视频
        ↓
[留用/驳回反馈]
   - 留用 -> 提示词入库（5.2）
   - 驳回 -> 失败模式记录
```

#### 5.3.2 提示词三层架构

| 层 | 用户可见 | 内容 |
|----|---------|------|
| 业务层 | ✅ 中文，员工能看懂 | 「美妆开箱视频，强调水貂毛」 |
| 工艺层 | ⚠️ 高级用户可见 | 可灵 8 层框架结构化 prompt |
| 模型层 | ❌ 不可见 | 视频模型实际输入（含 seed/negative_prompt） |

**关键设计**：业务层是员工与 AI 协作的接口，工艺层是引擎内部，模型层是 provider 适配层。员工改业务层 -> 引擎自动重排工艺层 -> provider 翻译成模型层。

#### 5.3.3 学习机制

用户修改后的提示词与原稿对比，差异作为 few-shot 样本喂给文本模型，使引擎逐步学习企业风格偏好。这是与 C 端产品（提示词引擎是静态的）的根本差异：**我们的引擎会随企业使用越来越懂这个企业**。

### 5.3.4 MVP+ 阶段的会话化创作模式

> 本节是把 §5.2 提示词沉淀、§5.3 双模型协同的核心理念，前置到 MVP+ 阶段可落地的产品形态。核心改造：从「独立页面 + 表单」转为「会话聊天 + 工具栏」，与主聊天流统一；用「精修/敏捷」双模替代抽卡式生成。
>
> 用户决策：现有「视频创作」页面作为 MVP 原型保留，新功能独立开发，避免破坏原页面。

#### 5.3.4.1 问题：抽卡式工具与沉淀理念冲突

现行 MVP 抽 2-3 张卡快速看效果，是迎合小白用户的「赌博式生成」设计：

- **优势**：用户不会写提示词也能多次尝试碰运气，留用率相对高
- **缺陷**：
  - 多张用了不同 seed/参数，留用某张后无法反推是哪个变量起作用
  - 提示词对用户不可见，留用即入库时模板质量低（黑盒）
  - 失败的卡是沉默成本，没有学习价值
  - 与 §5.2 提示词沉淀理念根本冲突（沉淀需要「单次留用可溯源」）

#### 5.3.4.2 会话化 UI 形态

参考小云雀的视频创作体验，从独立页面改为会话聊天形式：

- 用户在聊天框中描述想法 + 点加号上传图片（1张或多张，不区分产品图/模特图）
- 智能体识别意图、补充提示词
- 视频以文件卡片形式回显在聊天界面
- 历史会话复用左侧菜单下方区域，与其他智能体统一

**数据归属**：基于会话的视频创作走 `chat_sessions` 表，与主聊天完全融入；`gen_sessions` 表保留给原「视频创作」页面使用，历史会话无需迁移。

#### 5.3.4.3 会话界面工具栏设计

输入框左下角「加号」（添加附件）图标右侧新增「工具栏」，第一阶段包含「视频生成」工具。

点击「视频生成」向上展开参数弹框，第一阶段参数：

| 参数 | 选项 | 说明 |
|------|------|------|
| 创作模式 | 精修模式 / 敏捷模式 | 默认精修模式；模版模式第一阶段不做 |
| 视频时长 | 5s / 10s / 15s / 30s | 根据模型支持情况 |
| 视频比例 | 16:9 / 9:16 / 1:1 / 4:3 / 3:4 / auto | 根据模型支持情况 |
| 分辨率 | 720p / 768p / 1080p / 2K | 根据模型支持情况 |
| 生成条数 | 精修模式固定 1 条；敏捷模式可选 1/2/3 条 | |

**未来扩展**（后续迭代）：是否要字幕、是否要口播、配音、加企业 logo 水印等。

#### 5.3.4.4 创作模式总览

| 模式 | 定义 | 提示词生成 | 用户确认 | 生成条数 |
|------|------|----------|---------|---------|
| 精修模式 | 用户关心提示词内容，愿意多轮调优 | 1 段提示词 | 需要 | 固定 1 条 |
| 敏捷模式 | 小白用户，只看效果，不关心过程 | N 段略有不同的提示词 | 不需要 | 1/2/3 条可选 |
| 模版模式（第一阶段不做） | 套用历史留用提示词 | 直接复用 | 不需要 | 1 条 |

**与原探索模式的本质差异**：原探索模式是 1 段提示词生成 N 条视频（不同 seed），留用时不知道哪段提示词起作用；敏捷模式是 N 段提示词生成 N 条视频，留用时可溯源到具体提示词。

#### 5.3.4.5 精修模式（简化版）

**交互流程**：

```
1. 用户上传图片（1张或多张，不区分产品图/模特图）
2. 用户在输入框描述需求（业务层中文）
3. 智能体调用文本模型生成视频提示词
4. 智能体返回 md 文件卡片（提示词预览）
   - 用户点击卡片可预览完整提示词
   - 第一阶段不提供提示词编辑面板（暂缓）
5. 用户确认：发送"确认"或"开始生成"
   - 智能体调用视频模型
   - 等待期间发送"生成视频，预计需要3分钟"
   - 视频返回后作为文件卡片回显
6. 用户调整：在输入框描述调整方向
   - 智能体重新生成提示词，回到步骤 4
```

**简化点**：第一阶段不做提示词编辑面板，用户要调整就在输入框描述，AI 重新生成。

#### 5.3.4.6 敏捷模式

**交互流程**：

```
1. 用户上传几张图片（不区分类型）
2. 用户在输入框说一句简单的话，例如"帮我生成电商产品介绍视频"
3. 视频生成参数中指定：敏捷模式 + 生成条数3条
4. 用户点击发送
5. 智能体静默生成3段略有不同的视频提示词
   （包含元素参考/镜头标签/景别主体/动作/运镜/场景光影/音频/风格锚点等内容）
   - 无需用户确认
   - 直接提交给视频模型
6. 视频返回后，分3条消息发给用户
   - 每条消息包含一个文件卡片
   - 用户可分别预览/下载/留用/不喜欢/查看提示词
7. 用户满意其中一个视频，点击"留用"
   - 系统将对应提示词收录进"提示词库"
8. 用户点击"不喜欢"，可选填原因
   - 系统将对应提示词收录进黑名单
9. 用户要继续调整，在输入框中说"基于第1个视频结果，帮我微调..."
   - 智能体静默修改视频提示词
   - 无需用户确认，直接提交视频模型
   - 默认生成条数为1条（除非用户改为2条或3条）
```

#### 5.3.4.7 精修与敏捷的混合使用

敏捷模式和精修模式并无严格区分，可无缝切换：

```
场景示例：
1. 用户选择敏捷模式 + 生成3条
2. 拿到3条视频，都不满意
3. 用户点击其中一个视频，查看提示词
4. 发现提示词需要精修调整
5. 切换为精修模式
6. 用户说"基于第一条视频的提示词，我要修改为..."
7. 智能体按精修模式要求修改提示词，给用户确认
8. 用户确认后提交视频模型生成视频
```

#### 5.3.4.8 提示词显式化（沉淀的前提）

视频生成结果必须可追溯到完整提示词（对应 §5.3.2 三层架构）：

| 层 | 默认可见 | 内容 |
|----|---------|------|
| 业务层 | ✅ 显示 | 中文，员工可读：「美妆开箱视频，强调水貂毛材质，暖色调」 |
| 工艺层 | ⚠️ 折叠展开 | 可灵 8 层框架结构化 prompt，高级用户可查看 |
| 模型层 | ❌ 不可见 | seed/negative_prompt 等参数 |

**第一阶段简化**：工艺层提示词以 md 文件卡片形式回显，用户点击预览；不提供编辑面板，调整通过输入框描述。

#### 5.3.4.9 留用即入库

留用按钮旁默认勾选「收入提示词库」：

- 入库字段：业务场景标签、提示词全文（业务层+工艺层）、参数、留用者、行业品类、留用时间
- 与 §5.2.2「高留用率模板自动入库」机制对接
- 用户可主动取消勾选（如个人实验性留用不想入库）

#### 5.3.4.10 失败原因选填

不满意重试时，提供失败原因快选 chip（光线偏暗/动作不自然/构图有问题/其他）：

- **选填**，不强制用户填写，避免体验摩擦
- 选填内容进 §5.2.2 的「失败提示词黑名单」，带标签的失败样本价值高于无标签
- 未选填时仅记录提示词本身，仍可作为隐式失败样本入库

#### 5.3.4.11 抽卡展示

无「卡片组」气泡，无需并排展示：

- 智能体拿到一条视频结果就发一条消息，包含一个文件卡片
- 等待期间智能体发送一句话："生成视频，预计需要3分钟"
- 敏捷模式 3 条视频：分 3 条消息发送，每条一个卡片

#### 5.3.4.12 UI 改造重点

- 输入框工具栏：加号旁新增「视频生成」按钮，点击展开参数弹框
- 文件卡片：视频结果以文件卡片形式回显，含预览/下载/留用/不喜欢/查看提示词
- 提示词预览：md 文件卡片，点击可预览完整提示词（业务层+工艺层）
- 留用勾选：默认勾选「收入提示词库」，可取消
- 失败原因快选：4-5 个常用原因 chip，一键选择，可选填
- 已消耗积分实时显示：避免重试时成本不透明

#### 5.3.4.13 与 Phase 1-2 的关系

这套设计是 §5.2/§5.3 的**前置落地**，不依赖完整能力，但为后续能力沉淀打基础：

| MVP+ 阶段（本节） | Phase 1+ 完整能力 |

#### 5.6.2 视频库与工作成果的关系

**问题**：智能体生产的所有文件都应进入"经验中心"-"工作成果"，视频创作的视频也进入工作成果，与视频库有重叠。

**推荐方案**：视频库作为工作成果的视频类型视图（单一数据源）

- 工作成果是统一资产表（跨智能体），含 type 字段（video/document/image/report 等）
- 视频库是工作成果按 type=video 的过滤视图，附加视频专属元数据（提示词、生成参数、留用者、肖像授权等）
- 单一数据源，无冗余
- 菜单"视频库"作为入口，看到的就是工作成果中视频类型的记录
- 用户感知的"重叠"在底层是同一份数据，两个查询入口


#### 5.6.3 提示词库的三类内容

| 类别 | 来源 | 用途 |
|------|------|------|
| 留用提示词 | 用户留用视频时自动入库 | 团队复用、新员工参考、专家识别 |
| 黑名单提示词 | 用户点击"不喜欢"时入库（可选填原因） | 防止重蹈覆辙，失败模式分析 |
| 模版提示词 | 租户管理员将留用提示词升级 | 模版模式（第一阶段不做）的提示词来源 |

**关键能力**：租户管理员在提示词库界面，可将「留用提示词」升级为「模版提示词」，作为后续模版模式的提示词来源。

## 7. 价格策略与商业模式

### 7.1 不与 C 端比单秒价格

继续按秒计费、与 C 端比价是死路。应转向：

| 计费模式 | 适用场景 | 优势 |
|---------|---------|------|
| **企业席位订阅** | 中型企业，按月/年 | 用户无负担使用，强调团队价值 |
| **视频条数打包** | 业务波动型企业 | 含协作/审核/合规/资产沉淀全套 |
| **积分制（已有 #42）** | 多数字员工综合使用 | 视频作为积分消耗场景之一 |

### 7.2 强调总拥有成本（TCO）

C 端看似便宜，但企业用 C 端工具的隐藏成本：

| 隐藏成本 | 说明 |
|---------|------|
| 素材管理 | 无企业素材库，员工各自管理，重复采购 |
| 合规风险 | 无品牌规范强制、肖像授权管理，违禁风险 |
| 协作成本 | 无审核流，需另行搭建协作工具 |
| 知识流失 | 员工离职带走个人 prompt，新人重新摸索 |
| 价值不可见 | 管理者不知积分花在哪、产出多少 |

**TCO 视角**：我们 1 元/秒 × 团队使用 = 远低于 C 端 0.33 元/秒 × 个人使用 × 隐藏成本总和。

### 7.3 与已有数字员工打包

视频创作智能体不单独售卖，作为「企业 AI 智能体套件」的一部分（与社媒营销、工作日报、外贸等打包），强化整体方案价值。

### 7.4 接入 chat_records 计费与 VIDEO_GEN_USAGE_FACTOR 独立配置

> 本节是 Phase 1 启动前必须就绪的计费基础设施，单独成节强调其重要性。

#### 7.4.1 接入现有 chat_records 计费机制

视频创作智能体每次大模型调用（含文本模型与视频模型）都必须写 `chat_records` 并扣减积分，与主业务计费链路完全对齐。两类调用的计费方式不同：

| 调用类型 | 触发阶段 | 计费方式 | chat_records 字段映射 |
|---------|---------|---------|---------------------|
| 文本模型（提示词引擎） | Phase 2 双模型协同 | 按 token × video_gen_usage_factor | `prompt_tokens` / `completion_tokens` / `model` 填文本模型名 |
| 视频模型（万相/Minimax） | MVP 已有，Phase 1 接计费 | 按秒 × 单价 × video_gen_usage_factor | `model` 填视频模型名（如 `MiniMax-H3`），`execution_details` 存 `{seconds, cost_per_second_yuan, provider_task_id, resolution, cards:[...]}`，`prompt_tokens/completion_tokens` 留 0 |

**关键约束**：
- `source_type = "video_gen"`（与主业务 `chat` / `wecom_kf` 等区分，便于 ROI 看板按场景统计）
- 单次 session 一条 chat_records（含 N 个 card 的 execution_details），避免每个 card 一条导致记录爆炸
- 余额不足时拒绝创建新 session（复用 `_check_tenant_credit_blocked`）
- FAILED 任务退还预扣 credit_cost；SUCCEEDED 后按实际秒数结算差额
- 与工作日报打通：视频产出的 credit_cost / 留用率 / 驳回率作为员工日报指标（详见 §5.5.1）

#### 7.4.2 新增 env 变量：VIDEO_GEN_USAGE_FACTOR

**问题**：现行 `BILLING_USAGE_FACTOR=100`（10 倍加价）适用于主业务对话场景（每次对话几分钱，10 倍后仍便宜）。但视频创作的核心成本是视频生成 API（Minimax 0.5 元/秒），10 倍加价后 5 元/秒，远高于小云雀 0.33 元/秒，完全无竞争力。

**设计**：在 `BillingConfig` 新增 `video_gen_usage_factor: int = 30`（3 倍加价），通过 env `VIDEO_GEN_USAGE_FACTOR` 覆盖。

**3 倍加价后的价格测算**：

| 场景 | 成本 | 主业务加价（10×） | 视频创作加价（3×） | 小云雀 C 端（订阅） |
|------|------|----------------|------------------|------------------|
| 30s 768P 视频 | 15 元 | 150 元（不可接受） | 45 元 | 9.9 元 |
| 60s 768P 视频 | 30 元 | 300 元 | 90 元 | 19.8 元 |

**结论**：3 倍加价仍贵于小云雀 4-5 倍，但含企业级能力（素材沉淀/协作/合规/价值可见/提示词溯源）。**不在单秒价格上竞争，而在 TCO 上竞争**（详见 §7.2）。

**为何不直接调低主业务 usage_factor**：
- 主业务按 token 计费，10 倍加价是 SaaS 行业标准（覆盖运营/支持/续费风险）
- 视频创作按秒计费，成本结构完全不同（单次成本高 2-3 个数量级），应独立配置而非拖累主业务定价
- 若强制主业务降为 3 倍，会损失主业务收入；若视频创作保持 10 倍，售价完全无竞争力。**两套独立加价是唯一解**

**默认值 30 的依据**：
- 1 倍（成本价）：无毛利，不可持续
- 2 倍：覆盖运营成本但无利润空间
- 3 倍：覆盖运营 + 企业级能力开发投入 + 合理利润，仍有调价空间应对竞争
- 5 倍：偏贵，但仍有企业愿为合规/审计/协作付溢价
- 10 倍：完全脱离市场

#### 7.4.3 实现要点（Phase 1 必做）

1. **配置层**（三处同步）：
   - `src/config/settings.py` 的 `BillingConfig` 增加 `video_gen_usage_factor: int = 30`
   - `configs/config.yaml` 的 `billing:` 块增加 `video_gen_usage_factor: 30`
   - `.env.example` 增加 `VIDEO_GEN_USAGE_FACTOR=30`

2. **billing.py 扩展**：
   - `calculate_credit_cost()` 增加 `usage_factor_override: Optional[int] = None` 参数，传入时覆盖默认 `usage_factor`，视频创作模块调用时传 `settings.billing.video_gen_usage_factor`
   - 新增 `calculate_video_credit_cost(seconds, cost_per_second_yuan, provider, model)` 函数：`credit_cost = ceil(seconds × cost_per_second_yuan × video_gen_usage_factor × 100) / 100`

3. **video_gen/service.py 接入计费**：
   - `create_session`：提交 N 个 card 任务时，按预估总秒数 × 单价 × video_gen_usage_factor 预扣 credit_cost，写 chat_records（`status=pending`，`source_type=video_gen`）
   - `poll_pending_cards`：SUCCEEDED 后按实际秒数结算差额，更新 chat_records（`status=completed`）；FAILED 退还预扣（`status=refunded`）
   - 在 `execution_details.cards[]` 内记录每个 card 的 `{card_id, seed, duration_sec, cost_per_second_yuan, provider_task_id, status}`

4. **租户余额拦截**：复用 `_check_tenant_credit_blocked`，余额不足时拒绝创建新 session（前端提示"积分不足，无法发起视频生成"）

5. **单价表维护**：
   - 方案 A（推荐）：在 `token_cost_prices` 表增加视频模型记录（`model=MiniMax-H3` / `wan2.7-r2v`），复用 `input_price_per_m` 字段记秒单价（语义略别扭但零新增表）
   - 方案 B：`video_gen` 模块内置单价常量（按 provider+model 维护字典），简单但脱离统一计费体系
   - 倾向方案 A，保持计费数据归一

#### 7.4.4 与现行 MVP 的关系

- **MVP 已有**：`gen_sessions` / `gen_cards` 表，无 chat_records 接入，调用视频 API 不计费
- **本节新增**：计费链路接入（不改 MVP 表结构，仅扩展 `video_gen/service.py` 写 chat_records）
- **优先级**：Phase 1 必做（与会话化创作、企业素材库同期），因为素材库的肖像授权管理、ROI 看板都依赖计费链路

| **Phase 3：协作与价值度量** | 审核工作台 + 工作日报/工作成果打通 + 团队洞察看板 | 3-4 周 |
| **Phase 4：合规与品牌** | 品牌规范强制 + 言辞/行业合规 + 肖像授权管理 + 操作审计 | 3-4 周 |
| **Phase 5：业务流程嵌入** | 与社媒营销智能体打通（发布回流）+ 数据反哺提示词库 + 模版模式 | 4-6 周 |

**优先级排序理由**：
1. **会话化创作 + 素材库 + 计费接入**（Phase 1）是核心差异化基础，会话化是沉淀的前提，计费是 ROI 看板的基础。
2. **双模型提示词引擎**（Phase 2）是 §5.3 的完整落地，依赖 Phase 1 的会话化 UI 框架。
3. **协作与价值度量**（Phase 3）是「让管理者感知价值」的关键，对接工作日报调研的落地点。第一阶段已删除角色权限和 ROI 度量，本阶段聚焦审核工作台和团队看板。
4. **合规品牌**（Phase 4）是企业级必须但 C 端也做基础合规，差异不算最大，可稍后。
5. **业务流程嵌入**（Phase 5）依赖社媒营销智能体的发布链路就绪，排在最后；模版模式也在此阶段落地。

## 9. 风险与边界

### 9.1 范围风险

**风险**：企业级能力扩张无节制，导致系统复杂度爆炸、开发周期失控。

**边界**：
- 不做帧级剪辑（PRD §0.4 已明确，仍保持）
- 不做 AI 模特生成（PRD §2.4 已明确）
- 不做自建模型（Phase 1+ 评估，MVP 阶段用 API）
- 素材库不做 DAM（数字资产管理）系统的全功能，聚焦视频创作所需
- 第一阶段不做模版模式、提示词编辑面板、角色权限、ROI 度量

### 9.2 与横向能力的关系

| 横向能力 | 关系 |
|---------|------|
| 工作日报调研 | 视频产出作为员工日报内容（Phase 3 对接） |
| 组织知识沉淀调研 | 提示词库/素材库作为组织资产（Phase 1 落地） |
| 社媒营销智能体 | 视频->审核->发布->回流闭环（Phase 5 对接） |
| 积分计费 #42 | 视频生成作为积分消耗场景（Phase 1 接入） |

视频创作智能体是这些横向能力的**首个落地场景**，验证横向能力价值后推广到其他数字员工。

### 9.3 提示词沉淀的冷启动

**风险**：新企业入驻时提示词库为空，差异化价值不显。

**对策**：
- 系统预置通用提示词模板库（按行业/品类/场景分类）
- 行业专家冷启动：首批客户由实施团队协助沉淀企业专属模板
- 提示词库随使用量增长自动丰富（留用视频自动入库）

## 附录 A：决策记录

| 决策 | 选择 | 理由 |
|------|------|------|
| 产品定位 | 企业级视频创作智能体（回归项目总体定位） | C 端工具赛道无优势，企业级是唯一差异化路径 |
| 差异化核心 | 提示词沉淀 + 素材资产中心 + 协作价值度量 | C 端产品不解决这些，是企业级真痛点 |
| 计费模式 | 企业席位订阅 / 视频条数打包 / 积分制 | 不与 C 端比单秒价格，强调 TCO |
| 与 MVP 关系 | 演进而非推翻；现有「视频创作」页面作为原型保留 | MVP 已投入 10-17 人日，新功能独立开发避免破坏原页面 |
| 提示词引擎 | 双模型协同（文本+视频）+ 用户确认 + few-shot 学习 | 解决用户实测中"借第三方 AI 生成提示词"的痛点 |
| 优先级 | 会话化创作 + 素材库 + 计费 > 双模型引擎 > 协作价值度量 > 合规品牌 > 业务流程嵌入 | 会话化是沉淀前提，计费是 ROI 基础 |
| **计费接入** | 视频创作每次大模型调用都写 chat_records（source_type=video_gen） | 与主业务计费链路对齐，支撑 ROI 看板与工作日报指标 |
| **usage_factor 独立配置** | 新增 `VIDEO_GEN_USAGE_FACTOR` env，默认 30（3 倍加价），区别主业务 100（10 倍） | 视频按秒成本高，10 倍加价脱离市场；3 倍覆盖成本+利润仍有竞争力 |
| **按秒计费** | 视频模型按秒 × 单价 × video_gen_usage_factor，文本模型仍按 token | 视频生成成本结构是秒级，与 token 计费完全不同维度 |
| **会话化 UI 形态** | 从独立页面改为会话聊天形式，复用 chat_sessions 表，与主聊天流统一 | 参考小云雀体验；与其他智能体 UI 统一；为精修/敏捷双模提供自然载体 |
| **创作模式** | 精修模式（默认）+ 敏捷模式（小白路径），模版模式第一阶段不做 | 双模覆盖不同用户；敏捷模式 N 段提示词生成 N 条视频可溯源 |
| **数据归属** | 会话化创作走 chat_sessions 表；gen_sessions 表保留给原「视频创作」页面 | 历史会话无需迁移，原页面保留作为 MVP 原型 |
| **抽卡展示** | 一条视频一条消息，无「卡片组」气泡；等待时发送"预计需要3分钟" | 简化 UI，避免复合组件复杂度 |
| **提示词编辑面板** | 第一阶段暂缓，文本模型生成提示词后给 md 文件卡片，调整通过输入框描述 | 减少代码改动量，待 Phase 2 双模型引擎时再做 |
| **精修模式前置（MVP+）** | 默认单卡 + 提示词显式化（md 卡片）+ 留用即入库 + 失败原因选填 | 抽多卡模式与沉淀理念冲突；前置到 MVP+ 为 Phase 1 提示词库沉淀打基础 |
| **失败原因选填** | 不强制，避免体验摩擦；选填内容进黑名单 | 用户可能不想填，但隐式失败样本仍有价值 |
| **角色权限 / ROI 度量** | 第一阶段删除，聚焦核心创作流程；协作与价值度量后续迭代 | 减少第一阶段复杂度，待核心能力稳定后再做 |
| **菜单归属** | 素材库/视频库/提示词库从属于「视频创作智能体」一级菜单（排在「视频创作」后）；「知识中心」一级菜单保持原样仅含知识库 | 这三个菜单项仅对已订阅视频创作智能体的租户有意义，未订阅租户看到会莫名其妙；知识中心是通用能力，不与具体智能体绑定 |
| **素材库范围** | 视频创作附件自动入库；其他智能体附件手动收藏 | 避免全量入库导致素材库被低质文件污染 |
| **视频库与工作成果** | 推荐方案 A：视频库作为工作成果的视频类型视图（单一数据源） | 避免数据冗余，菜单"视频库"是工作成果的过滤视图 |
