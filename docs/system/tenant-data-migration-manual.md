# 租户数据迁移手册（人工执行）

> **用途**：原平台内置「租户数据迁移」功能（编辑租户弹框-数据迁移 tab）已于 2026-11-10 删除。后续如出现个别租户的数据迁移需求（如把测试环境的某个租户数据迁到生产、或租户在环境间搬迁），**由 AI 助手按本手册执行**，不恢复常驻功能。
>
> **为什么删除而不是扩展**：该功能的前提是测试/生产同机（254 服务器）跨库直连 + 共享存储路径（`/app/source_storage`），生产迁至 243 后前提失效；跨服务器化需要远程 DB 凭据、文件同步、向量库搬迁等大量新代码，而功能已数月无人使用。个别租户迁移走一次性脚本 + 运维手段更直接。
>
> **旧实现参考**（仅作思路参考，禁止直接复用——表结构与文件目录可能已变）：git 历史 `scripts/tenant_migrate_kb.py`、`src/saas/api/tenant_migration.py`（均删除于 2026-11-10，`git log --follow` 可找回）。

## 核心原则（防 bug 的关键）

1. **先盘点、后动手**：不假设任何表结构、字段、文件目录布局。两环境的 schema 版本（`db_update.yaml` 水位）和目录规范可能不同，迁移前必须双侧实地盘点。
2. **目标租户数据先备份**：replace 模式会清空目标租户既有数据，动手前必须先备份（DB 行 + 文件目录），并和用户确认模式。
3. **一次性脚本、用后即删**：迁移脚本放 `scripts/` 下执行，完成后删除，不入库——避免遗留半年后表结构已变、脚本成了误导性死代码。
4. **验证闭环**：迁完必须做行数比对 + 抽样验证（文档检索命中、文件可打开），不能只看脚本退出码。

## 环境拓扑

- 测试环境在 254 服务器（agent2/agent3），生产环境在 243 服务器；SSH 用 `ubuntu@`（禁 root），服务器现状见 `deploy/服务器部署现状.md`。
- 跨服务器文件传输：`tar` 打包 + `scp` 传输，两侧都落到 `storage/tenants/{tid}/` 对应场景子目录。

## 租户数据构成（盘点起点，不是完整清单）

DB 侧（按 `tenant_id` 过滤的行）：

| 数据 | 表 | 备注 |
|------|-----|------|
| 知识库文档 | `documents` / `chunks` / `chunks_vec`（向量） | 向量维度与 embedding 模型绑定 |
| 知识库分类 | `knowledge_categories` | |
| 业务数据 | 所有 `bs_*` 表 | 清单会随子智能体增长，不能照抄本表 |
| 会话历史 | `chat_sessions` / `chat_messages` / `channel_*` | 默认不迁，需用户明确要求 |
| 计费审计 | `chat_records` | **默认不动**（计费审计数据，迁了会污染目标环境账目） |

文件侧：`storage/tenants/{tid}/` 各场景子目录（`conversation/`、`knowledge/`、`export/`、`report/` 等），以及历史遗留的 `storage/uploads/tenant_{tid}/` 平铺结构。

**盘点方法**：不要依赖上表——用 `information_schema.columns` 扫出目标库所有含 `tenant_id` 列的表，逐个确认是否在迁移范围内。

## 执行步骤（AI 按此操作）

1. **需求确认**：与用户确定迁移方向（源环境/源租户 -> 目标环境/目标租户）、数据范围（知识库/业务表/会话）、模式（replace 清后插入 / merge 按 UUID 去重跳过已存在）。
2. **双侧盘点**：
   - 对比两环境 `deploy/db_update.yaml` 水位，schema 不一致先说明差异（缺列的表迁过去会丢数据）；
   - 扫含 `tenant_id` 的表，列出各表源租户行数；
   - 核对文件目录现状：`storage/tenants/{tid}/` 结构 + 是否有历史平铺残留。
3. **备份目标租户**：DB 用 `pg_dump` 按表导出或建备份表；文件目录整体 `tar`。备份文件命名带日期，放目标机临时目录，迁移验证通过后再清理。
4. **执行迁移**：
   - DB：写一次性迁移脚本（参数化源/目标 DSN 与租户），UUID/业务唯一键**原样保留**，自增 `id` 重新分配，关联关系靠 UUID 等稳定键在应用层重建；
   - 文件：`tar` -> `scp` -> 解到目标 `storage/tenants/{tid}/` 对应场景子目录；`documents.file_path` 按目标目录规范**逐条重映射**（旧平铺路径 `knowledge/{filename}` 迁入时改为 `knowledge/{source_type}/{filename}` 新规范）；
   - 向量：`chunks_vec` 随 chunks 一并迁；**先确认两环境 embedding 模型一致**，不一致则向量不可直接复用，需在目标环境重嵌入（费用与耗时先告知用户）。
5. **验证**：逐表行数比对（源行数 vs 目标新增行数）；抽样 2-3 个文档走知识库检索确认命中；抽样文件经页面/下载链接确认可打开；有业务表的抽查页面列表展示。
6. **收尾**：删除一次性脚本与临时备份（与用户确认），在会话总结中记录迁移结果（行数、文件数、验证结论）。

## 已知陷阱

- **schema 水位差**：两环境 `db_update.yaml` 水位不同时，源库有的列目标库可能没有；先对齐 schema（部署到同版本）再迁数据。
- **`documents.file_path` 的 `source_type` 段**：路径形如 `knowledge/{source_type}/{filename}`，与知识库检索授权（`knowledge_retrieval.md` 的共享/栏目授权）相关，重映射时不得丢失语义。
- **pgvector 维度绑定**：embedding 模型一换，旧向量全部失效，不能盲迁 `chunks_vec`。
- **知识库共享/授权是配置不是数据**：`tenant_knowledge_shares` / `subagent_knowledge_sources` 等配置表默认不随数据迁移，需用户明确要求才处理。
- **`chat_records` 计费口径**：迁移业务数据时绝不复制计费审计行，避免目标环境积分账目被污染。
- **数据库禁忌**：迁移脚本同样遵守 `database_dev.md`——不建触发器/外键/存储过程，关联完整性在脚本逻辑中保证。
