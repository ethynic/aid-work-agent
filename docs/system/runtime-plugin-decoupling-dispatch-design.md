# Runtime 插件解耦与并行接单设计

2026-11-11 · 待评审

## 插件自己声明工具

插件在已有的签名包工具清单里声明自己的入口、工具名、参数格式和运行属性。Runtime 安装时读清单，启动时按入口连接插件，沿用 MCP stdio 调用工具。当前写在 Runtime 里的插件身份、工具名单和按工具名分支的业务规则，分别交回插件声明和对应的业务代码。Runtime 只读通用字段。装入另一个已授权的插件时，Runtime 源码无需增加它的名字或工具名单。

新版 CLI 在签名清单中提供带版本的工具声明。所有命令都串行的插件也要带这份声明。能与同机其他作业一起运行的命令，可以在声明中标记 `parallel: true`。声明里某条命令没有并行标记时，该命令按串行执行。企微读本地库可以作为验证例子，操作企微窗口发消息和 BOSS 桌面操作按串行执行。Runtime 读取并上报已验签的声明，服务端沿用现有设备和工具授权。

## 服务端排队，Runtime 领取能开工的任务

待执行任务留在服务端现有作业表。服务端按目标设备和该设备上报的工具声明确定作业能否并行。领取继续用长轮询，服务端从同一队列里取第一条符合领取条件的任务，并在同一个数据库事务里标为已领取，避免重复派发。

| Runtime 当前状态 | 可以领取什么 |
| --- | --- |
| 没有串行任务在执行 | 可以领串行或并行任务，串行任务保持原有先后顺序。 |
| 串行任务已领走，仍在执行或停止中 | 继续长轮询，只领带并行标记的任务。队列里的串行任务原地等待。 |

Runtime 领到就启动。并行命令可以和其他命令同时运行，包括同一插件内的其他命令。串行占用和桌面锁只限制需要排队的命令。串行任务实际结束或确认停止后，下一轮领取恢复为两种任务都可领。结果沿原回执保存和上报，补传回执期间仍能领取独立的并行任务。

例如 A 正在用 BOSS 筛简历，服务端先收到一条要操作桌面的 B，再收到一条读企微本地消息的 C。Runtime 此时只领并行任务，服务端把 C 交给它。C 立即开始，B 继续留在服务端。A 结束后再领 B。A 就算运行很久，这条规则也一样。

## Runtime 退出

Runtime 退出时，尚未领取的任务仍留在服务端，恢复上线后照常领取。已领取的任务沿原任务编号处理结果、取消和恢复。结果未知时保留该次调用的原状态。

## 旧版本兼容

**只升级 CLI 可以。** 同一份新版 BOSS 或企微签名插件包能在已交付的旧 Runtime 上安装和升级。旧 Runtime 按原来的 MCP stdio 入口调用已有工具，使用原有参数和结果格式，任务仍按原规则串行执行。

**升级 Runtime 时，所用的 CLI 也要升级到带新版声明的版本。** 缺少整份声明的旧 CLI 无法接入新版 Runtime。Runtime 将该插件显示为「需要升级插件」，继续为其他符合条件的插件接单。该插件尚未领取的任务留在服务端，插件升级后可继续领取仍有效的任务。

新版 CLI 保留旧 Runtime 可读的签名包和 v1 清单格式、插件身份、入口及运行环境。新版声明作为同一份签名清单的扩展，旧 Runtime 可忽略，新 Runtime 接入插件时必须读取。原 `tools` 结构和 `schema_digest` 的算法沿用旧规则。旧 Runtime 安装时会把 `version --json` 的工具清单和摘要与签名清单比对，因此继续用现有的同源打包方式，保留 `version --json` 和 `doctor --json` 的旧用法。

建议给现有领取请求加可选的 `parallel_only`，服务端通过现有心跳告知新版 Runtime 是否支持该参数。服务端和 Runtime 都支持时才启用并行领取。仅升级服务端时，旧 Runtime 与旧 CLI 继续使用已有工具、结果上报、恢复和计费。
