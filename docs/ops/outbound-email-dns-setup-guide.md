# 外发邮箱配置指南（域名 DNS 侧）

> **适用对象**：需要使用智能体外发邮件能力（如 AI 获客开发信）的租户，以及协助租户配置的实施/运维人员。
>
> **背景**：2026-10-28 tulin.cn 外发域名体检实战沉淀。体检未通过就直接发信，大概率**静默进垃圾箱**，且会损伤主域信誉——此时即使收件方把你加了白名单也无济于事。本指南覆盖发送域名必须配置的四条 DNS 记录（SPF / DKIM / DMARC / MX）、以「网易免费企业邮 + 阿里云解析」为例的操作步骤、验证方法与踩坑速查。
>
> **前置条件**：企业已在系统「企业设置 → 租户邮箱」中配置 SMTP/IMAP 账号（发信账号与域名归属需一致）；拥有域名的 DNS 解析后台权限。

---

## 1. 四条记录总览

| 记录 | 作用 | 缺失后果 | 必须性 |
|------|------|---------|--------|
| SPF（TXT `@`） | 声明哪些服务器有权以本域名发信 | 邮件被判为伪造，进垃圾箱 | 必须 |
| DKIM（TXT `<selector>._domainkey`） | 对每封邮件做数字签名，防中途篡改 | 严格接收方（Gmail 等）降权 | 强烈建议（视邮箱服务商能力） |
| DMARC（TXT `_dmarc`） | 告知接收方验证失败怎么办 + 汇总报告 | 防伪策略无法生效、无法观察来源 | 必须 |
| MX（`@`） | 声明收信服务器 | 收不到回信、DMARC 报告也进不来 | 必须 |

**一个常见误区**：MX 不是「发送」记录——发信只走 SMTP（不需要 MX），MX 决定的是**收信**。但获客场景里客户回信、DMARC 汇总报告都依赖 MX，所以发信域名同样必须有正确的 MX。

## 2. 操作步骤（以 163 企业邮 + 阿里云解析为例）

### 2.1 从邮箱服务商后台拿配置值

登录邮箱服务商管理后台（163 企业邮为 qiye.163.com → 域名管理），获取：

- **SPF 官方推荐值**（163 为 `v=spf1 include:spf.163.com -all`，以后台显示为准）
- **DKIM**：后台开启 DKIM 后获取 selector 名称与公钥 TXT 值（一长串，`v=DKIM1; k=rsa; p=...` 开头）
- 注意区分**免费版与付费版**：网易免费企业邮**不提供 DKIM 配置入口**（找不到不是操作问题，是产品功能限制），只有付费版开放；此时 DKIM 一项只能缺失，SPF + DMARC 仍要配齐

### 2.2 在 DNS 解析后台添加记录

以阿里云「云解析 DNS → 域名 → 解析设置」为例：

| 类型 | 主机记录 | 记录值 | 优先级 | TTL |
|------|---------|--------|--------|-----|
| TXT | `@` | `v=spf1 include:spf.163.com -all`（用服务商后台给的值） | — | 10 分钟 |
| TXT | `<selector>._domainkey` | 服务商后台复制的 DKIM 公钥 | — | 10 分钟 |
| TXT | `_dmarc` | `v=DMARC1; p=none; rua=mailto:管理员邮箱@本域名` | — | 10 分钟 |
| MX | `@` | `mx.ym.163.com`（用服务商后台给的收信服务器） | `10`（服务商指定值） | 10 分钟 |

TTL 先设 10 分钟便于纠错，稳定后再调长。

## 3. 各记录配置要点与易错点

### 3.1 SPF

- **全域只能有 1 条 SPF 记录**（多条 SPF 直接判 permerror 全部失效）；已存在旧记录时是**修改**而不是新增
- 体检发现的典型病例：一条空的 `v=spf1`（无任何机制、无结尾策略）——等于没配
- 结尾策略用 `-all`（硬失败），跟随服务商推荐值即可；`~all`（软失败）效果弱一档
- 若同一域名还用其他系统发信（如 CRM、EDM），把这些服务的 include 串并进**同一条**记录

### 3.2 DKIM

- 主机记录是 `<selector>._domainkey`（如 selector 为 `s1` 则填 `s1._domainkey`），**不是**裸的 `_domainkey`
- 公钥值很长且含分号，整段粘贴；部分解析后台会自动处理引号与分段，不要手工拆改内容
- 配好后把 selector 告知体检方（或自行验证，见第 4 节）

### 3.3 DMARC

- 主机记录固定 `_dmarc`
- 起步策略必须 `p=none`（只观察不拦截），确认报告无异常后再逐级升级：`p=none` → `p=quarantine`（可疑进垃圾箱）→ `p=reject`（直接拒收）
- `rua=mailto:` 填本域名下的邮箱（聚合报告会发到这里），该邮箱依赖 MX 正常才能收到报告
- DMARC 的验证通过依赖 SPF 或 DKIM 之一通过**且域名对齐**（发信域 = 信封域），服务商标准配置下自然满足

### 3.4 MX（本项目实战最大坑）

- **主机记录必须填 `@`**。填成 `mx` 会创建 `mx.tulin.cn` 这种子域的 MX——对收信毫无作用，且主域 MX 变空、收信静默中断，表象就是「昨天还好好的，今天 MX 查出来是空」
- 记录值与优先级用服务商后台指定值（163 免费企业邮：`mx.ym.163.com`，优先级 `10`）
- 只有**一条** MX 记录时，优先级数值不影响功能（不存在备选排序），但建议仍按官方文档填写

## 4. 配置后验证

命令行验证（任选其一）：

```bash
nslookup -type=TXT tulin.cn          # SPF
nslookup -type=TXT _dmarc.tulin.cn   # DMARC
nslookup -type=TXT s1._domainkey.tulin.cn   # DKIM（selector 换成实际值）
nslookup -type=MX tulin.cn           # MX
```

本地无 dig/nslookup 时可用 DoH 接口（浏览器直接打开）：

```
https://dns.alidns.com/resolve?name=tulin.cn&type=TXT
https://dns.alidns.com/resolve?name=_dmarc.tulin.cn&type=TXT
https://dns.alidns.com/resolve?name=tulin.cn&type=MX
```

**重要：区分「权威 DNS」与「公共缓存」**：

- 解析后台保存后，**权威 DNS 立即生效**；但公共递归 DNS（8.8.8.8、阿里公共 DNS 等）上旧值要等 TTL 过期（最多数小时）才刷新
- 若公共查询结果与解析后台不一致，不代表没保存成功——**以权威 DNS 为准**。可查询域名 NS（`type=NS`）拿到权威服务器（阿里云托管为 `dns*.hichina.com`），直接向权威服务器查询确认
- 验证判定口径：权威 DNS 上查到的值与解析后台一致 → 配置成功；公共缓存旧值最迟等 TTL 过期自然消失，无需干预

## 5. DMARC 聚合报告解读（rua 的用途）

`rua=mailto:xxx` 的含义：全球邮件接收方（Gmail、QQ 邮箱等）每天把「收到哪些自称本域名的邮件、是否通过 SPF/DKIM 验证」整理成 XML 报告投到该邮箱。报告价值：

1. **发现冒充**：陌生 IP 以本域名发信（伪造/钓鱼）会在报告中现形
2. **验证配置**：自己服务商 IP 发出的正常邮件显示 SPF 通过，等于第三方确认配置在工作
3. **支撑 p 策略升级**：观察 1--2 周，确认合法来源只有服务商 IP 后，再升级 `p=quarantine`/`p=reject` 真正发挥防伪作用

报告量不大（每家大邮箱服务商每天约 1 封、XML 附件几百 KB），可设过滤规则归档；XML 不可读，可用 dmardian 等工具解析。

## 6. 踩坑速查表（tulin.cn 实战，2026-10-28）

| 症状 | 根因 | 处理 |
|------|------|------|
| 体检报「SPF 是空的 v=spf1」 | 域名上残留一条无机制、无结尾策略的空记录 | 替换为服务商完整 SPF 串（`-all` 结尾），全域只留一条 |
| 163 免费企业邮后台找不到 DKIM 入口 | 免费版无此功能（仅付费版开放） | 如实告知体检方「DKIM 平台能力缺失」；SPF + DMARC 配齐后可先上线观察到达率，必要时升级付费版或换发信通道 |
| 体检报「MX 记录没了，昨天还在」 | MX 记录的主机记录被误填为 `mx`（子域），主域 `@` 上无 MX | 修改该记录：主机记录改回 `@`，记录值/优先级按服务商指定值 |
| 公共 DNS 查到的值与解析后台不一致 | 递归缓存未过期（TTL 内旧值） | 以权威 DNS 查询结果为准（见第 4 节）；等缓存自然过期 |
| 配置了 DMARC 但收不到报告 | MX 损坏导致报告投递失败 | 先修复 MX，报告会在下个周期自动恢复 |

## 7. 检查清单（租户外发域名配置验收）

- [ ] SPF：`@` 上有且仅有 1 条 TXT，值为服务商完整推荐串，带结尾策略
- [ ] DKIM：服务商支持时，`<selector>._domainkey` 公钥已配置，selector 已回告体检方；服务商不支持时已如实登记
- [ ] DMARC：`_dmarc` 上 `v=DMARC1; p=none; rua=mailto:本域名邮箱` 已配置
- [ ] MX：`@` 上有 MX 记录（主机记录不是子域名），值与优先级为服务商指定值
- [ ] 权威 DNS 验证：以上记录在权威 NS 上查询与后台一致
- [ ] 企业设置 → 租户邮箱：SMTP/IMAP 账号已配置并可登录
- [ ] 首批实测信件的到达率已观察；erp/管理员邮箱能收到 DMARC 报告

## 8. 缺 DKIM 时的决策参考

| 方案 | 效果 |
|------|------|
| SPF + DMARC 上线观察 | DMARC 靠 SPF 对齐通过，比裸奔强很多；部分严格接收方（尤其海外）仍可能降权 |
| 升级服务商付费版补 DKIM | 体验最完整，适合长期把邮件获客当主通道的租户 |
| 更换支持 DKIM 的发信服务商 | 适合对到达率有硬指标的场景 |

建议路径：先按「SPF + DMARC + MX」上线，实测到达率并观察 DMARC 报告 1--2 周，再决定是否为 DKIM 升级或换通道。
