### 2.1 external_push 推送循环失败 + ERP 参数错误（#1）

**现象**（`log_error` 6484~6543，11-23 19:42~21:04 密集出现，约每 2 分钟 1 条）：

- `[recap] task=external_push 失败（不影响对话）: 推送循环未收到完成报告，最后模型输出: `（空）—— sales-assistant，40+ 次，其中 2 次触发「连续 3 次工具调用失败，熔断终止」。

- `module_data_update ... Data too long for column 'neirong'`（MySQL 1406）——3 次（11-23 17:45/18:53、11-24 09:46）。

**根因方向**：external_push 每轮推送由 LLM 编排 ERP 接口调用；LLM 给 `module_listing_view` 传了接口文档未声明的参数（fields/total_sum/order_by/select）-> 工具层失败 -> 循环收不到完成报告 -> 每轮重试刷屏；`neirong` 列是 ERP 侧 MySQL 列宽不足，写入即 1406。

**处理建议**：
1. 核对 `storage/tenants/{tid}/templates/sales-assistant-api.md`（或对应租户 api 文档）是否明确声明 `module_listing_view` 的参数集合，把「不支持任意扩展参数」写清楚，必要时收紧 http_api 工具的参数透传提示。
2. ERP 侧 `neirong` 列扩容（TEXT）或推送侧截断/分片；先与 ERP 数据责任人确认列用途。
3. 推送风暴期间计费正常（每轮 background_llm 计费 0.02 积分，见 chat_records rec_e38af389bf15），无漏计，但重试风暴本身烧 token，修好后应消失。

### 2.3 CHANNEL_EXECUTION_INTERRUPTED（#3）

**现象**：`[SessionQueue] processor 异常 ...: CHANNEL_EXECUTION_INTERRUPTED`（RunnerError 409）12 次（11-19×4、11-20×1、11-23×2、11-24×5）。每次发生后渠道向客户发送 22 字兜底文案「抱歉，处理您的消息时遇到了问题，请稍后重试。」（session.py:1304 失败提示路径），即客户可感知的中断回复。

**链路**：channel_routes.py:3331 -> session.py:1206 _processor -> runner_agent.py:296——轮询 runner 行时发现 status ∈ {paused, interrupted} -> cancel -> 抛 409。

**数据面**：`agent_runners` 表当前仅剩 1 行 interrupted（11-19 18:52，accepted 18:39 -> 中断，运行约 12.5 分钟）；其余中断行已被 auto_local_recovery 等机制推进到终态。追踪库无 failed trace（中断不落 failed）。

**根因（2026-11-24 追踪库/事件表深查已定性）**：

1. **最初怀疑（lease 过期/心跳延迟）被证伪**：`agent_runner_events` 逐 runner 分析显示，interrupted 事件距最后一次 running 事件**恒为 605±10 秒**（14 例中 13 例），不是 lease=30s 过期的随机间隔；看门狗 tlog（`log/temp/runner看门狗.log`）不存在、`agent_runner_controls` 无 cancel 记录、PG 无连接耗尽——三类候选全部排除。
2. **实锤链路：doc-layout-clone 技能 skill_execute 命令 600s 超时 -> runner 中断**。追踪库有 16 个 `tool:skill_execute` span 恰为 605 秒（=600s `SKILL_COMMAND_TIMEOUT_SECONDS` + 收尾开销）后 failed，时间与 interrupted 事件在 41ms 内对齐（如 12:34:19.188 span -> 12:44:24.668 span 结束 -> 12:44:24.709 interrupted）。全部 16 次都是 doc-layout-clone 技能。
3. **命令不是"慢"而是"挂死"**：超时命令含 `python3 -c "import docx; print(...)"`、`sed -n references/analysis_schema.md`、`ls -la` 等瞬时命令——命令内容与挂死无关，是**子进程执行环境整体挂住**（spawn 后无任何输出直到 600s 被 SIGKILL）。
4. **超时后模型未收到失败结果**：trace 中 605s 失败 span 之后无任何 llm_call（trace 终态 cancelled）——中断发生在工具完成处理路径上（worker execute() 异常分支 -> interrupt_attempt）。最可能机制：UsageScope.check() 的 failure_file 闸门（usage_context.py:21-38，子进程记账失败写 `AID_RUNNER_FAILURE_FILE` -> worker `scope.check()` 抛 `CheckpointFailure('RUNNER_CHILD_USAGE_STORAGE_FAILED')` -> interrupt），属待验证候选。seq15（interrupted）与 seq16（control_revision 0->1）双写中后者是渠道侧看到中断后发 cancel 的回执，为果非因。
5. **挂死根因核实（11-24 二次核查）——不是文档大、不是 doc-layout-clone bug，是执行环境间歇性整体卡死**：
   - prep.py **零 LLM 调用**（纯本地：扫描 -> pdf2docx 本地转换 -> python-docx 解析 -> JSON 摘要），LLM 决策在主对话层（trace 可见命令间 1-4s 独立 llm_call），「大文档来回调 LLM」不成立；
   - 16 个挂死命令中仅 5 个涉及文档，其余为 `import docx`、`sed` 读 references、`ls -la`、`json.load` 等瞬时命令；
   - **同一命令不同时刻耗时差 60 倍（决定性证据）**：`import docx` 11-23 18:05 完成 67s / 18:16 挂死 605s；`sed -n analysis_schema.md` 11-24 09:30 完成 10s / 11-20 09:49 挂死 605s；`ls -la` 单文件 106s；honorplan 同一 prep 12:31 完成 53s -> 12:34 挂死 605s；
   - baseline 本身异常：成功的 `sed` 10s、`import docx` 67s、prep.py 全流程 53s~379s（正常应秒级~数十秒）——skill 子进程存在巨大固定启动开销（bootstrap 含同步 `init_postgres_pool`，无超时）+ 间歇性整机卡顿（聊易已知 cgroup 上限合计 ~16.7G > 物理 7.3G+swap 4G，重负载并发时的 swap/IO 争用是土壤）；
   - **不建议放宽 600s -> 1800s**：挂死是环境问题而非任务耗时，放宽只会把客户等待从 10 分钟中断拉长到 30 分钟阻塞；修复应针对环境与行为（见下方修复方向）。
6. 12:56 部署后 2 小时零复现，但 12:10~12:44 连续 3 次说明是间歇性环境问题；事故期 worker 容器日志已随重建销毁，无法直取异常栈。

**修复方向**：
1. **行为修复（已实现，2026-11-24）**：skill_execute 命令超时不再放大为整个 runner 中断——新增 `observe_child_timeout()`（call_observer.py）与 `UsageScope.child_timeout()`（usage_context.py），超时 kill 走独立语义：在途 skill-call 收据按既有 uncertain 口径标记 unknown 交由结算/对账（新增 `UsageRepository.abandon_inflight_skill_calls`），不再触发 sticky fatal；真实异常退出（崩溃/OOM/exit 87）保持原 fatal 语义不变。超时结果作为工具失败返回模型继续执行。
2. **环境修复（已实现，2026-11-24）**：skill bootstrap 惰性化 DB 依赖——`install_subprocess_observer`/`subprocess_usage_scope` 启动期不再做 `init_postgres_pool`/租约校验，改由 `_ensure_subprocess_runtime` 在首个真实 provider 调用时惰性初始化（双检锁幂等，LeaseLost 校验保留）。非 LLM 技能命令（import 校验/文件操作/prep 解析等）完全不触碰 DB，DB 抖动不再放大为全部技能命令失败。注：连接层已有 `connect_timeout=5`（database.py），挂死主因是非 Python 命令的宿主 IO 层 D-state 停滞（内存超卖土壤，属运维治理）。
3. **复现取证**：下次复现时先 `docker logs app-runner-worker-* --since` 抓栈再重建容器；在 skill bootstrap 关键步骤加 tlog 计时。

单测：`tests/unit/services/agent_runner/test_usage_child_timeout.py`（7 用例：child_timeout 收据收口不中断 / 仓库失败保持 fail 语义 / child_exit(None) 回归保护 / executor 超时分支走 observe_child_timeout / bootstrap 启动期零 DB / 惰性初始化幂等 / LeaseLost fail 语义），容器内全绿；相关回归 644 通过，7 个失败均为未改动模块的既有问题（overlay_flow/executor fixture，与本次无关）。
