## Phase 1 清单与申请记录

- 在连接中心的微信 Agent 中加入清单上传、自动排除提示、默认全选与逐行取消、批次默认验证语、提交进度和分批次记录。在同一个页面挂载群聊总结与批量加好友，复用设备状态区。核对切换时两个视图各自的状态，复核原有总结链接。
- 批次和逐人结果按租户及发起用户授权，支持刷新后恢复显示。仅微信确认送出时记为「已提交」，已申请、已是好友、直接添加和未知结果均有独立说明。
- 覆盖 XLSX/CSV 导入、自动排除及原因计数、默认全选、逐行取消后提交范围、全部被排除、同批和历史重复、设备未就绪、刷新恢复，以及租户和用户之间无法读取或操作他人的批次。

## Phase 2 Runtime 与验收

- 依据 [Runtime 共同契约](../system/runner-desktop-runtime-integration-contract.md) 先登记工具版本、适用设备、写入回执、重复执行与旧 Runtime 兼容方案，再复用现有单人微信 CLI 接入。每次在一台设备串行处理，请求送出但结果未知时停止自动重试该目标。
- 用模拟回执覆盖微信确认送出、已申请、已是好友、直接添加、查无目标和超时无法确认。用明确授权的微信目标验证真实提交及持久化回执，并复核现有群聊能力。

## Phase 3 设备配对视觉与本机只查验收

- 按[微信视觉配对契约](../system/runner-desktop-runtime-integration-contract.md#微信视觉使用设备配对)复用 Runtime 设备配对，微信好友定位沿用现有多模态服务和计费。兼容旧设备与已激活的旧终端调用。
- 通过微信 CLI 同一个 add 入口加 --search-only 在真机定位指定手机号，确认退出前未点击添加，搜索结果可见。记录模型调用、身份和桌面路径的实际验证范围。

## 验证记录

- 2026-11-26 Phase 3：使用已安装 Windows Runtime CLI 与隔离服务真实配对，通过设备凭证和实际 GLM-5.3-Flash 调用运行新版微信 CLI 0.1.5 的 add --search-only。首次前台失焦，使用微信 CLI 恢复主窗口后重试完成。指定手机号返回 TARGET_NOT_FOUND，effect=none。微信仍前台显示「添加朋友」，未进入申请窗口；四个定位步骤在本地测试租户记录了实际多模态用量。正式 agent2 配对、签名安装与真实申请回执留待对应发布验收。
- Phase 3 独立验证覆盖新旧设备鉴权、租户隔离、余额、现有模型和计费、Windows 只查停手。后端 91 项、Windows CLI 206 项、Runtime 7 项及完整构建通过。

- 独立验证涵盖 XLSX/CSV 导入、排除与默认勾选、取消后提交范围、历史回看、租户和用户隔离、可信签名、清单变更、并发幂等、未知回执，以及旧群聊总结和定时链路。Web 构建、API 和 Runner 导入检查通过。
- 从上一版数据库的迁移水位执行新迁移两遍，验证批次表、索引与水位，迁移单测 31 项通过。旧 Runner 列快照断言在原基线和当前版本均失败。
- 代码评审发现更换清单失败会保留旧草稿。已修复并经独立前端复测，失败后的旧名单不可提交。
- 发布验收使用已签名的 0.1.4 插件与明确授权的微信目标，验证 Runtime 安装、微信确认提交和申请记录。
