提审版包含 Phase 1 和 Phase 2。首版交付一套通用小程序、租户品牌扫码物料、微信身份下的文字历史、人工领取与回复以及原会话手动交回 AI。手机号、头像昵称、语音图片、自动接管、订阅消息与外部微信客服跳转列为后续范围。

## Phase 0 · 核实账号与样板

- [ ] 运营侧以目标 AppID 核对主体、名称、账号认证、备案、合法请求域名和实际可选服务类目。用两个企业品牌样例核对共用 AppID 承载租户服务的提审说明。确定实际模型版本、备案或登记适用路径，以及模型供应商可出具的材料。 [微信类目](https://developers.weixin.qq.com/miniprogram/product/material/) · [微信网络配置](https://developers.weixin.qq.com/miniprogram/dev/framework/ability/network.html)
- [ ] 选定两套试点租户数据。至少一套有经确认可对外的产品问答资料和可以登录 AID 后台的接待员工。记录运营方、租户、数据处理责任、保留策略及受理渠道。
- [ ] 确认设计稿中的接待权限、停用策略、来源与历史写入边界。按项目规则登记实际要改的数据表和契约。确定开发和体验环境的 AppID、API 与数据隔离，明确不将正式客户数据用于提审样板。

完成条件是目标账号的实际约束有回证，且可提供真实样例说明用户从扫码到人工交回的完整路径。若共用 AppID 的适用类目、主体或材料有疑义，继续做可验证的内部工作，并在 Phase 3 提审前关闭具体疑义。

## Phase 1 · 发码与 AI 会话

- [ ] 后端实现发布授权、品牌配置、原码与海报、停用，建立每个租户实例的固定入口。完成微信 code 交换、外部访客映射、入口凭据、会话归属、请求去重以及用量限制。
- [ ] 增加 Runner 渠道接入，验证可信实例绑定、固定消息历史水位、公开知识范围、回合登记及恢复、唯一历史写入和用量结算。访客 API 只读取渠道公开投影。同步核心表文档及增量、初始化 SQL。
- [ ] 实现小程序扫码及分享打开、无入口提示、当前服务聊天、同一服务历史、新会话、刷新与前后台切换。实现租户后台发布和下载素材。短请求与增量读取支持重试，出现失败时保留仍可发送的草稿。

完成条件是在隔离环境用两个租户、每租户两个实例和两名微信访客完成实际发码、打开、微信登录、多轮回复与历史恢复。检查租户和访客隔离、去重、禁用、权限撤回及记录归账。

## Phase 2 · 人工接待和交回 AI

- [ ] 增加接待成员授权及工作台，支持待领取、领取、文字回复、交回和管理员收回。小程序展示等待、已领取和切换过程。同一会话内可看到 AI、客户和人工公开消息。
- [ ] 实现接待版本与待答消息位置。用用户操作触发 Runner 衔接，校验旧结果的公开权。不同情况下覆盖交回有新客户留言、无待答消息、坐席只答到指定消息位置、被撤权及交接时 Runner 仍在途。
- [ ] 测试多个副本下抢单与并发转接、断网重发、进程重启、旧 AI 结果迟到、发布停用再启用、知识授权中途撤回。按持久消息和 Runner 实际用量分别对账。

完成条件是访客在同一会话经历 AI → 等待人工 → 人工回复 → 交回 AI，交回后有待答消息只续答一次，无待答消息时等客户提问。接待人以实际授权为准，原消息和回合状态经恢复可以继续查阅。

## 提审前验收清单

Phase 3 用最终准备提交的代码和配置重新核对下表。记录微信体验包或审核包版本、主 API 与 Runner Worker 构建版本、测试账号角色、对应场景、结果、复现说明和证据位置。服务端结论使用与候选版本匹配的环境。证据去除密钥、令牌、OpenID 和真实客户信息。

| 检查项 | 提交前必须确认的结果 | 证据 |
| --- | --- | --- |
| R1 主体、类目和材料 | 目标 AppID 的主体、适用类目和小程序备案状态已核对。确认公开 AI 问答、真实调用模型与申报材料一致。共用 AppID 下两家租户如何展示及提供服务能在审核说明里说清楚。 | 目标后台状态、适用材料清单、服务说明和对外样例。遇到平台限制时附处理结果。 |
| R2 真实扫码和品牌 | 至少一台 iOS、一台 Android 真机扫描体验环境的原码和品牌海报。分别验证双租户、同租户双实例、热启动 A 切 B、转发卡回访、印刷或压缩样张、停用旧码及最近使用入口。 | 四个入口样例、设备记录、操作录像或截图。正式原码在正式路径可用后做同样冒烟。 |
| R3 登录和越权 | 两位微信用户无法通过修改会话、入口等 ID 读取对方消息；同一微信用户访问两个租户时历史隔离。后台员工无法串租户、绕过名单或复用已撤权的领取状态。 | 隔离库和真实入口结果，补一组真机账号切换。 |
| R4 人工交接 | 真实小程序和后台完成发消息、转人工、两人同时领取、人工回复、交回、AI 续答。AI 正在生成时转人工，迟到结果不会进入公开历史。测试无人领取、回到 AI、交回无待答消息和坐席撤权。 | 双端录像、脱敏会话位置和接待审计记录。 |
| R5 恢复、额度和停用 | 请求丢响应后重试不重复创建、发送、接单或扣费。前后台切换、短断网和服务重启能补读。入口停用后不再接单，余额用尽时授权人工接待仍可用，另外一个服务能继续运行。 | 真实 PostgreSQL 场景、重启记录、候选账单与 Runner 对账。 |
| R6 隐私、公示与内容安全 | 页面正确展示运营方和服务企业、AI 标识与隐私反馈入口。审核说明与首版实际使用的身份数据一致。测试违规输入、违规 AI 输出、内容检查不可用、越界知识请求和用户提出删除请求时的后台处置。 | 小程序页面及后台检查记录、脱敏的内容安全结果和受理记录。 |
| R7 审核人员可复现 | 准备两套虚拟品牌与咨询资料，提供进入路径、扫码或分享方式、提问与转人工步骤及可联系到的测试接待人。当前审核包可执行所说明的流程，AI 问答与人工回复标识清楚。 | 微信提交资料草稿、样例码及体验版演示记录。 |

R1–R7 均完成才将当前版本标为可提审。微信审核结果与正式发布后的原码扫码属于后续确认，分别记录。修复若改动鉴权、公开内容或发布绑定，重验受影响项。

## Phase 4 · 试点与下一期取舍

- [ ] 审核通过且按授权启用后，抽样正式码、正式域名和模型配置，按租户检查账单归属。先限定已确认的租户和服务实例，再看扫码转首问、解决率、人工接起时长、转回 AI 成功率及每次有效咨询成本。
- [ ] 复盘试点。客户反复需要回拨时再做手机号按需授权与线索入库。客户反复因为无人领取而等待时，验证自动交回的触发和投诉豁免。会员、设备报修、附件及客户自有 AppID 分别按业务价值与审核要求决定。

## 开发、发布与回退

Phase 1–2 涉及公开鉴权、租户隔离、并发和计费，按仓库高风险流程执行开发自测、独立测试与独立 CodeReview。先按[开发环境手册](../guides/development/local-dev-environments.md)准备容器。后端走 `bash scripts/dev_test.sh <相关测试> -p no:cacheprovider -q`，多租户、竞态和 SQL 走隔离库。后台前端在容器内运行 `npm run build` 并验窄屏功能。小程序通过微信开发者工具构建体验版及真机测试，后台构建结果不能代替真机记录。

发布先准备加性表结构，再部署支持新来源的接单、Worker 和回合投影，确认同一领取池可消费，再开放小程序入口。回归已有普通 Web、微信客服和受影响的已交付 Runtime＋CLI 服务端升级组合。回退时先关新受理，由兼容版本处理已接单执行和费用结算，再回退 Worker。服务器环境变更和部署遵守仓库真机部署授权。
