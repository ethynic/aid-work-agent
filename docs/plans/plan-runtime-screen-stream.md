## 实施

### Phase 0 技术验证

单机实测只能证明隐藏窗口能采集、720p 能编码、浏览器能播放，不能当作跨网络的验收。按三组进行：

| 组 | 做什么 | 通过标准 | 状态 |
| --- | --- | --- | --- |
| 一、同网段两台电脑 | 一台运行验证程序的 `serve` 模式充当 Runtime，另一台用浏览器打开观看页 | 观看端收到首帧；选中的 ICE 路径是内网地址，没有中转；Runtime 判定「确认非同机」之后才开始采集；服务器经手的字节数不随视频码率增长 | 待做。只补规则 2 的证据（Runtime 能解析另一台电脑的 mDNS 名字）；跨网段已实测通过。两台电脑连同一个手机热点即可 |
| 二、真实跨网络（建议 Phase 2 开工前做） | 办公网、家庭宽带、手机热点两两组合，各端配上 STUN；Runtime 侧经信令中转模式主动连出 | 逐组记录直连成功还是失败。成功时：首帧到达，路径是公网映射地址、没有中转，服务器字节不随码率增长。失败时：Runtime 关闭采集，网页提示无法直连 | 待做，需要另一网络上的电脑、两端都能访问的信令入口和 STUN。按实测的办公网出口类型（对称型 NAT），预期从外部打洞不成功；要在不友好和友好的网络各测一次 |
| 三、直连失败 | 不交换地址，或两端之间没有可用路径 | 网页提示「当前网络无法直连」；Runtime 全程未采集，或采集后立即关闭；服务器不留残留会话 | 单机通过；跨机复核待做 |
| 附、同一局域网内不同 VLAN（2026-11-27 实测通过） | 电脑 A 运行验证程序充当 Runtime（加放行入站 UDP 的临时规则），电脑 B 用浏览器打开观看页，经信令中转；另用 `net-check.cjs` 检测网络条件 | 连接建立；判定为非同机之后才采集；B 出画面 | 通过：0.54 秒两端连接，B 打开页面 3.7 秒收到首帧，1280×720、14.3 帧、约 1.1 Mbps，连续 1756 秒没有断连，内网直连、无中转、往返 4 毫秒。名字解析不出，靠规则 6（对端端口不属于本机）判为非同机；本机对照 5 次全部判为同机、没有采集。验证程序为此修了两处：信令按顺序发；网络检测的套接字绑定网卡地址。网络条件：内网直达通，出口不支持 NAT 回环，出口是对称型 NAT。数据见调研报告 6.1 |
| 附二、降低画质（2026-11-28 单机实测通过） | 验证程序在开始采集 20 秒后降低画质、40 秒后恢复，分「只有发送端」和「发送接收同一进程树」两种配置；另用 `cpu-load.ps1` 给验证程序设 CPU 上限，模拟电脑很忙 | 降低的动作生效、连接不断、能恢复；Runtime 一侧的 CPU 明显下降；CPU 不够时降低后能达到 5 帧 | 通过：输出 852×480、5 帧，Runtime 一侧的 CPU 少约一半（软件、硬件编码一致）；CPU 上限 0.5 个核心时，原画质 11 帧，降低后 4.9 帧。编码器的「因 CPU 受限」信号在 CPU 不够时不出现，设计 4.5 已修订。阈值未在真实的弱机器上验证。数据见调研报告 6.1 |

另外两项单机做不了，随上表一起做：

- 公网 HTTPS 页面连接内网地址时浏览器是否弹「本地网络访问」权限，以及不允许时的表现。需要一个公网 HTTPS 测试页。
- 锁屏、UAC 弹窗、远程桌面断开时的画面；多显示器；其他缩放比例。需要用户在场时触发一次。

**同机判定要记录的证据。** 地址候选只提供三样明文可见的证据：网页内网候选解析出的地址、网页的公网映射地址、Runtime 自己的公网映射地址。名字解析不出时，再用连接建立后对端连入用的端口（2026-11-27 加入，规则 5、6）。验证程序的摘要里 `sameMachine` 一栏有 `verdict`（结论）、`rule`（放行或拒绝所用的规则编号）和 `evidence`（手里有哪些证据，只有计数和是否不同，不含地址）。两台设备时逐项记录：

| 情形 | 应当用的规则 | 必须记录 |
| --- | --- | --- |
| 同一台电脑（浏览器没有单独走另一条出口） | 1（名字解析出本机地址），或解析不出时 5 | 结论只有这两种，`capture.started` 为 `false`。浏览器单独走另一条出口且名字解析不出时，会被规则 3 判成另一台电脑并采集：这是设计 4.2 接受的例外，遇到时如实记录，不算不通过 |
| 同网段的另一台电脑 | 2 | `evidence.viewerResolved` 是不是 1，即另一台电脑的名字能不能被本机解析；不是 1 时靠规则 6（对端端口不属于本机）判为另一台电脑，2026-11-27 跨网段实测即如此；对端端口也查不到时结论必须是 4 |
| 另一个网络的电脑 | 3 | `evidence.mappedDiffers` 是不是 `true`；两端的 STUN 是不是都拿到了映射地址 |

解析不出另一台电脑的名字不影响连接（2026-11-27 实测：浏览器主动连 Runtime 公布的内网地址，不需要解析浏览器的名字），只影响同机判定，判定由规则 5、6 补上。同网段那一组还差的只是规则 2 的证据，即 Runtime 能否解析另一台电脑的名字。规则 1～4 已用构造的地址单测（`node verdict.test.cjs`，21 条）。

验证程序在 `spikes/runtime-screen-stream-poc/`，用法见其 [README](../../spikes/runtime-screen-stream-poc/README.md)。画面只在隐藏窗口或本机浏览器之间传输，不显示、不保存、不外传。

2026-11-24 单机结果：结论与数据见[调研报告第 6 节](../research/runtime-screen-stream-feasibility-research.md)。没有发现需要改换技术路线的问题；评审的四条已落实到设计和验证程序：只做点对点、先建连后采集、同机判定三种结果、画面租约。为了能做跨机验证，验证程序另加了两样，单机已复测通过：独立的信令中转（Runtime 侧只主动连出，与产品做法一致）和 30 秒建连超时（没有可用路径时会话按时结束）。

2026-11-25 单机模拟并行实测：验证程序的 `pair` 模式可以在本机模拟采集负载，与本机运行的其他程序并行。用它和已安装的微信插件做了一次并行实测，做法与数据见调研报告 6.1 节。这只说明采集负载没有拖慢那一种工具的本机读取，不能代替 Phase 4 经 Runtime 的真实并行验收。

以下是要点全文：

**第 A 轮遗留（B、C 轮接入时注意，2026-11-28 审查结论）：**

- `netstat` 端口表解析只认 Windows 格式：Host 只在 win32 上把 `isLocalPort` 接到 `readLocalPorts`，其他平台返回 `null`（查不到）。适配层每次判定只读一次 UDP/TCP 表，不要逐端口各查一遍。
- 现有 `checkDesktopInteractive()`（`src/legacy/desktopCheck.ts`）把检测失败表示为 `{interactive: false}`：接入锁屏检测时，失败必须按「没有变化」处理，不能映射成锁屏。
- 判定为同机时依赖采集页自己结束并报 `closed`；页面不报则 15 秒验证超时按 `machine_check_unknown` 收尾（方向安全，原因不准），采集页要实现这一点。
- 迟到的 `pending` 心跳会短暂重开刚结束的会话，靠第一条信令或读取得到 `ended` 自愈；服务端保证同一设备只有一个未结束的会话，可接受。
- **Host 与共享 core**：会话状态机、同机判定、画面租约、信令客户端、锁屏检测放在共享 core，便于用 Node 测试直接覆盖；Host 负责接入心跳、能力上报和 IPC。只有壳在启动参数里声明支持时才上报能力。
- **信令按顺序发**：连接请求先于地址候选。两者是分开的请求，到达服务器的先后没有保证；候选先到时，浏览器因为没有远端描述会拒绝加入（2026-11-27 验证程序踩过，新打开的页面因此连不上）。
- **同机判定**：取本机全部网卡地址；网页的地址候选是明文 IP 就直接用，是 mDNS 名字就交给系统解析器；连同采集窗口报告的本机公网映射地址，按设计的规则 1～3 得出结论。名字解析不出时（跨网段就是这样），连接建立后由采集窗口取每个成功候选对里对端候选的端口，Host 查本机端口表（`netstat -ano -p udp` 和 `-p tcp`，实测约 30 毫秒）：全是本机套接字是同机，有不属于本机的是另一台电脑，查不到是无法确认。不用对端地址，统计里也拿不到。两端公网出口不同时不向服务器下发内网候选。
- **与现有流程隔离**：画面会话逻辑是 Host 里一段独立的异步流程，在心跳成败判定之外被调用；异常全部在模块内消化，不向主循环抛出；定时器不阻止进程退出。`screen.stop`、采集窗口崩溃、租约到期、因资源不足停止都只关画面会话，不触碰插件进程、任务租约和结果补传。
- **任务优先**（设计 4.5，2026-11-28 修订判断方式）：Host 每 5 秒读一次电脑 CPU 占用（`os.cpus()`），采集窗口每 5 秒报告编码器是否因 CPU 受限；有任务在执行、且连续两次判断为资源不足（电脑 CPU 占用不低于 90%，暂定；或编码器报受限）时，Host 让采集页降低画质（改采集轨道的约束：帧率上限 5 帧、宽高上限 854×480），并向网页发 `status: degraded`；降低后仍然连续两次资源不足才结束观看，原因 `resource_busy`。没有任务在跑时不受这两步影响；任务结束后恢复并向网页发 `status: restored`。降低画质用采集轨道的约束，不用发送端的编码参数：单机实测只改编码参数，Runtime 一侧的 CPU 只少约 30%，改采集约束少约 50%（调研报告 6.1）。
- **壳**：隐藏采集窗口、独立会话分区的屏幕采集授权、`setDisplayMediaRequestHandler` 指定主显示器、专用 preload、新增的私有 IPC 消息类型、托盘文字。主窗口权限处理器保持不变，并加测试固定这一点。采集窗口会话放行的权限名是 `media`，并限定请求页面地址为采集页，摄像头和麦克风的请求必须被拒绝。安装器在可提权时添加放行 Runtime 程序入站 UDP 的规则（内网直连的关键条件，2026-11-27 实测），同时放行 UDP 5353（供系统解析器解析 mDNS 名字）；不可提权时管理界面提示在 Windows 的防火墙提示里点「允许访问」。壳与 Host 之间的消息增加「降低画质」和「恢复」两种。
- **采集页**：新的构建入口。先建立不含画面的连接，收到「确认非同机」后才 `getDisplayMedia`，用 `replaceTrack` 接上画面；编码参数按设计 6.1。信令全经 IPC，页面不访问网络。能按 Host 的要求降低画质和恢复。
- **Runtime 管理界面**：解码 Host 状态里的 `screen`，显示横幅、「拒绝」「停止查看」、是否已降低画质，以及收不到服务器确认时的秒数；接入管理方法 `screen.stop`。
- **契约产物**：更新 `contracts/runtime-host/v1` 的 `host-state`（`screen` 含可选的「是否已降低画质」）、管理请求与响应 schema、fixture，保证 `check.py` 和消费测试通过。现有 schema 顶层不允许未知字段、管理方法是固定枚举，所以升 wire 候选版本；并验证旧界面连接新 Host 且恰逢画面会话时的表现，把结论登记回共同契约 2.25。
- **打包**：采集页资源随 Runtime 安装包分发，更新内容安全策略与构建校验脚本，Runtime 版本号按现有规则递增。
- 测试覆盖：状态机的每条转移与超时；判定规则 1～4（把验证程序的单测搬到共享 core），mDNS 解析失败、本机没有公网映射地址时都落到无法确认；采集只在确认非同机之后开始；连续 30 秒没有续期时关闭采集窗口，其他任务不受影响；没有可用地址时 30 秒建连超时由会话自己结束；停止时先关窗口；旧服务端（心跳响应无新字段）下行为不变；命令行方式启动不上报能力；摄像头和麦克风请求被拒绝；公网出口不同时不发内网候选；画面模块抛出异常、心跳响应缺少画面字段或字段类型不对时，主循环照常运行，设备不标记离线，回执补传照常；`screen.stop`、采集窗口崩溃、租约到期、因资源不足停止之后，插件进程、任务租约和结果补传不变；没有任务在跑时电脑 CPU 占用达到阈值或编码器受限，既不降低画质也不结束观看；任务运行中连续两次判断为资源不足时降低画质并发出 `degraded`，观看不中断；降低后仍然连续两次资源不足才结束观看，原因 `resource_busy`；任务结束后恢复并发出 `restored`；电脑 CPU 占用的读数可注入，阈值和「连续两次」用注入的读数验证；降低画质只改采集页的采集约束，任务租约和结果补传不变；传画面期间的状态信令被服务端以 409 拒绝时不重试，画面和任务都不受影响；信令接口返回 503 `SCREEN_STREAM_BUSY` 时稍后重试，不结束会话；下一次轮询从收到上一次响应时起算，间隔带少量随机抖动：服务端的占用闸不排队，固定节拍的同步轮询会让排在后面的请求一直拿不到名额（见 Phase 1 小节）；信令按顺序发，连接请求先于地址候选；名字解析不出时按对端端口判定：对端端口全是本机套接字是同机，有不属于本机的是另一台电脑，查不到是无法确认、不采集。

### Phase 3 网页

- 「本地工具」页新增「实时画面」入口，容器放宽到 `max-w-6xl`。
- 新增观看弹框组件和连接组合函数：三步进度（唤醒、建立直连、确认观看设备）、`RTCPeerConnection`、信令轮询、线路判定。用 `ontrack` 给的轨道，不预先加通道。网页必须等到收到 `prepared` 才发 `start`，提前发会使会话按超时结束（设计 5.4）。地址候选可能先于连接请求到达（分开传输，先后没有保证），网页把早到的候选缓存到连接请求处理完，再按顺序加入；读取、信令和结束接口返回 503 `SCREEN_STREAM_BUSY` 时稍后重试，不据此结束会话；下一次轮询从收到上一次响应时起算，间隔带少量随机抖动：服务端的占用闸不排队，固定节拍的同步轮询会让排在后面的请求一直拿不到名额（见 Phase 1 小节）。不新增路由、页面元数据登记或菜单开关。
- 结束态覆盖：确认同机、无法确认、无法直连、自动停止，以及原有的离线、停止、掉线。
- 降低画质的提示：收到 Runtime 的 `status` 为 `degraded` 时，在画面左上角显示「对方电脑正在执行任务，已降低画质」；收到 `restored` 或观看结束时移除。不中断画面，不需要用户操作。
- 测试覆盖：状态机各分支、接口调用参数、结束路径（关闭、Esc、结束按钮、对方停止、掉线）、禁用入口的原因提示、降低画质提示的出现与消失。
- 在容器内构建前端，检查交互状态、键盘操作和窄屏布局。

### Phase 4 联调与验收

按「验收」节的清单在真实环境验证。需要部署到测试环境的步骤和 STUN 的部署，等用户明确指示后执行。部署前核对 PostgreSQL 连接数预算：原有预算加上「API 进程数 × `SCREEN_DB_POOL_MAX`」。并行相关的用例需要真实的插件任务（例如 BOSS），在 Windows 真机上执行，同时记录任务耗时和画面帧率，与不开观看时对比。另找一台性能较弱、没有硬件编码的电脑，验证资源不足时降低画质后能继续观看、任务不受影响，并校准电脑 CPU 占用的阈值。

### Phase 5 可选增强

各自独立，按用户决定逐项启动：

- **唤醒加速**：让任务领取的长轮询在有查看请求时提前返回，把等待从最长 5 秒降到约 0.5 秒。会改动领取接口，属加性字段，需单独登记契约并做旧端兼容验证。
- **多显示器选择**、**更高帧率**：视用户需求。

## 验收

- 同网段两台电脑：网页点「实时画面」后出画面，线路显示「局域网直连」，选中的 ICE 路径没有中转；Runtime 判定「确认非同机」用的是规则 2，判定之后才开始采集；浏览器权限分别选允许和阻止各验一次。
- 同一局域网内不同网段（企业里常见的多个 VLAN）：同样出画面，线路显示「局域网直连」，没有中转；Runtime 判定「确认非同机」用的是规则 6（对端端口不属于本机），判定之后才开始采集；Runtime 所在电脑的入站 UDP 已由安装器放行，不弹防火墙提示。
- 跨网络：能直连时显示「点对点直连」，判定用的是规则 3；不能直连时显示「当前网络无法直连」，Runtime 端不留残留窗口和采集。
- 直连失败或 30 秒建连超时：提示无法直连，Runtime 全程不采集。
- 同一台电脑的浏览器打开页面：提示「同一台电脑无法使用此功能」，全程不采集；名字解析不出来时按对端端口判定，对端端口是本机的同样这样提示，查不到才提示无法确认，两种都全程不采集。浏览器单独走另一条出口（代理或 VPN）且名字解析不出来时，会被当成另一台电脑并开始采集；这是设计 4.2 接受的例外，不在这一条的范围里，遇到时如实记录。
- 无法确认观看设备：提示无法确认是否为同一台电脑，全程不采集。
- 整机断网或服务端停止：观看中让 Runtime 连不上服务器超过 30 秒，画面自行停止，横幅显示秒数。这时这台电脑上的 Agent 任务按原有的断网规则处理（本地继续执行，进度回传暂丢，心跳失败后标记离线并退避重试，恢复后补传回执）；本条只验画面能自行停止，不要求任务不受影响。
- 只断画面信令、设备接口仍可用：任务照常领取、执行、续租和上报，见下面「观看时仍能接单」里对应的一条。
- Runtime 离线、Runtime 版本过旧：入口禁用或给出对应提示；列表显示在线而实际离线时，超时后提示并可重试。
- 观看中：Runtime 端窗口和托盘显示「正在被远程查看」；点「停止查看」后网页立即提示对方已停止；Runtime 掉线后网页提示连接已断开。
- 目标电脑锁屏：网页提示已锁屏、画面停止更新；解锁后自动恢复。
- Runtime 端点「拒绝」：网页提示对方拒绝，全程不采集。
- 同一设备第二个窗口：提示已有窗口在查看。
- 服务器带宽：传画面期间服务器只经手信令，字节数不随视频码率增长。
- **观看时仍能接单**（发布验收项，用真实的插件任务，按原有串行、并行规则各验一次）：
  - 先开始观看，再下发新任务：照常领取、执行、续租和上报。
  - 任务运行中开启观看：原任务不暂停、不取消、不重跑。
  - 观看中手动停止观看：原任务不受影响。
  - 只有画面信令失联（服务端的画面接口不可用，或 Runtime 侧取不到画面会话），设备心跳正常：原任务照常，画面 30 秒后自动停止。
  - 任务运行中资源不足：编码器先自动降帧；电脑 CPU 占用达到阈值（暂定 90%）或编码器报受限持续 10 秒时降低画质（5 帧、480p），画面继续，网页提示「对方电脑正在执行任务，已降低画质」；降低后仍然资源不足 10 秒才停止观看，网页提示对方电脑资源不足、已优先保证任务；任务结束后恢复。任务本身不被拖到失败或超时。
- **画面这一路出问题不拖累设备心跳**（发布验收项）：
  - 服务端画面会话查询超时或报错：心跳返回成功，Runtime 保持在线，任务领取和回执补传照常；画面按租约停止。
  - 采集窗口崩溃、`screen.stop`、租约到期：只关画面，插件进程、任务租约、结果补传不变。
  - Runtime 端画面模块抛出异常：主循环不退出，设备不标记离线。
- 查看不产生工具调用和计费记录。
- 只升级服务端：已交付的旧 Runtime 加旧插件保持原有工具、任务恢复、回执和计费不变，设备列表仅多出一个字段。
- 新 Runtime 连接旧服务端：原有功能不变，不进入任何会话。
- 画面全程不在服务器落盘，会话表只含设计 5.5 所列字段；日志中不出现信令内容、来源地址和凭据。

## 回滚

- 服务端把 `screen_stream.enabled` 设为 `false`：接口返回 503，网页入口隐藏。会话表保留，不影响其他功能。
- Runtime 不升级即不上报能力，功能对其不可用。
- 三端都可以单独回退，不需要同步操作。
