只修改服务端 `scheduler/manager.py` 与 `wecom_conversation/proxy_monitor.py`、`proxy_dispatcher.py`：全局 job 每 10 秒只查询活跃设备组，为每组分别登记监控和派发 job；每组的任务、目标和批次 SQL 只取本设备，组内原有串行和锁语义不变。组来源包括有 active 目标或待收敛停止请求的运行任务、已停止任务的执行中批次，直到它结算；仅有 halted 目标且无停止请求/执行中批次时移除空转 job；等待/停止后的未决批不自行恢复。新组立即执行第一轮，服务端重启从持久表恢复登记，不改 Runtime/CLI。以 A 设备持续慢超过 10 秒、B 设备监控与派发均完成第二轮为验收点；另测停止任务的执行中批次仍有派发 job、halted 后不空转且停止请求能收敛、组查询隔离、现有监控/派发回归。部署 agent2 须用户当场明确指示。

## 1. 成功标准

1. 创建任务时固定 Runtime、企微账号和租户授权智能体；真实运行 WeCom CLI `doctor --localdb` 和双点标定，检查 `mode=db`、桌面就绪、坐标缓存成功。仅新代理功能依赖新配置检查能力，旧客户端原业务保持可用。
2. 页面只用“启动 / 停止”；运行中不可编辑，停止等待当前执行结束或进入等待，等待中的批次留待下次启动。停止后可改标题、会话范围和代理指令；保留会话继续原位置，停止后新增会话从编辑加入时的最新位置起算，初建会话在首次启动建基线。软删除后历史可在 UI 查阅。
3. 每个固定 Runtime＋企微账号仅一个监控循环和代理队列；每目标独立 `wb1` 游标，单循环串行读取，监控读取与代理 Runner 不并行。无新入站消息时不创建回答 Runner、不调用模型；空闲 2 小时实测 0 模型请求和 0 模型积分。
4. 一个会话一批入站消息使用一个有限 Runner；每个任务内的会话固定 `session_id`，新任务即使监控同一会话也生成新 ID，每批新 `runner_id`。回答可逐人、合并或无需回复，明确 @ 当前账号须按智能体指令回复；上下文复用现有 Runner 历史/摘要，并含本批、近期原文和按需追溯的旧记录。
5. Runner 正常结束输出结构化 JSON，记录需要回复与否、已回复的原消息/回复文本/CLI 本地库证据、未回复消息/CLI 错误和日志编号。明确无需回复或至少一条经 CLI 确认发送即推进本批冻结位置；零发送且确定无副作用只重试一次，发送 unknown 只读对账而不自动重发。
6. CLI 忙碌等待重试；Runtime 离线、账号变化、源库游标失效、智能体失权均保留原位置和可查日志，按设计恢复或人工处理。同账号同会话不允许两个运行代理同时接管。普通手动发送和每日总结保留原路径，不加入代理队列。

## 2. 开发前共同检查点

- 更新[Runner / Desktop / Runtime 共同契约](../system/runner-desktop-runtime-integration-contract.md)：登记服务端代理监控在用户保存授权下创建受信 `wecom_read_sessions` 只读 invocation 的唯一写入者、固定任务/设备/账号、调用身份和失败语义；保持通常 Runner 创建业务动作的规则。监控读与代理回答共用服务端持久队列，不改现有 Runtime 业务 wire。
- 登记创建页专用的远程 `doctor --localdb` 与双点标定调用能力、版本/能力协商和结果 schema。当前命令仅是本机 CLI 子命令，尚未暴露给网页；需通过原设备授权与 Runtime 结果通路增加受信配置入口，不暴露给模型。`doctor` 的退出码 0 不代表 `localdb_ready=true`，也须检查基础桌面条件和登录账号；标定须返回标题与输入点坐标。缺新能力只禁新代理创建/启动，不改变已交付旧客户端原工具、恢复、结果上报与计费。
- 冻结代理配置、会话目标、批次结束 JSON、执行日志及位置 schema；按数据库规范同步迁移、初始化 SQL 和变更记录。一个配置可多选会话，一个工作项只对应一个会话；每目标独立 `wb1` cursor，连续已处理位置和本机最新消息位置分开。`session_id` 按任务＋会话固定，新任务不能复用旧智能体的会话历史，每批新 `runner_id`。
- 代理批次要走会加载 `session_id` 历史和活动摘要的受信 Runner 提交路径。现有 `source='scheduled'` 是零历史，不能把定时任务路径直接用于代理回答；复用现有摘要与 CLI 原文回读，不另建跨轮记忆系统。
- 冻结任务级工具装配：只列租户有权智能体，在每次代理 Runner 中注入企微读发和任务指令，企微调用限定当前目标会话，不改共享 profile。智能体失权时停止任务；会话归属在并发启动时唯一。
- 2026-11-07 agent2 旧 continuous 任务基线：上海时间 12:51–14:36，`runner_4bd2f499277e4265bddab0bdd129b792` 有 196 attempts、406 次按 runner_id 归属的模型用量回执、355.37 积分；同时间窗 195 次成功的 `wecom_read_session` 回执 `new_messages=0`。工具次数是同用户/时间窗关联，并非严格 runner_id 外键归属；新方案的节省须用自身实测证明。

## 3. 阶段实施

### P1：跨模块契约（仅文档）

完成 §2 的共同契约与版本化输入/输出 schema：确定 CLI doctor/标定的本地工具契约、Runtime 能力字符串及受信调用、后台固定设备/账号与批次 JSON 的生产消费关系。明确旧客户端缺能力只影响新代理，不改原 Device wire 或全局最低版本。本阶段只修改契约、设计和计划文档；按 CLI → Runtime → 后台的生产消费顺序形成可核对样例。契约见 [wecom-proxy-task-contract.md](../design/wecom/wecom-proxy-task-contract.md)（§9 为 2026-11-08 设计者评审决议记录 Q1–Q6），共同契约登记见 [2.17 修订段](../system/runner-desktop-runtime-integration-contract.md)；已按两轮评审意见修订并于 2026-11-08 冻结为编码基线，后续变更须升 schema_version 并登记兼容影响。

### P2：WeCom CLI

**唯一代码模块：`clients/wecom-cli/`。**复用已有 `doctor --localdb` 与 `calibrate` 实现，按 P1 契约增加供受信配置流程调用的结构化本地入口，返回完整诊断和双点坐标结果；不加入 Agent 模型工具集。不改原发送、读取和 OCR 边界。本模块验证真实结果中 `doctor` 退出 0 但 `localdb_ready=false`、登录/桌面未就绪、标定失败与成功坐标；产物为可由 Runtime 调用的插件能力。此阶段不修改 Runtime、后台或页面。

### P3：Runtime（含共用 Host Core）

**唯一代码模块：`clients/agent-tool-runtime/` 与其共用 `clients/shared/local-tool-host-core/`。**按 P1 契约将 P2 的配置工具纳入受信插件工具名单、真实能力发现和原 Device invocation/result 通路；普通业务工具与旧插件能力保持原行为。本模块用新/旧 CLI 插件夹具核对能力上报、配置调用、旧客户端原工具与恢复；不修改 WeCom CLI、后台或页面。

### P4：后台配置与 API

**唯一代码模块：服务端 `src/wecom_conversation/`、本功能所需的本地工具受信接点和数据库迁移。**新增代理配置、会话目标、位置与批次事实；固定 Runtime/账号/智能体，复用现有会话目录，创建时经 P2/P3 结果检查 doctor、标定与账号。API 实现创建、启动、停止、已停止编辑、软删除和只读历史；创建时初选目标在任务首次启动建基线，已运行任务停止后新增目标在编辑加入时只读一次记水位，后续启动不得覆盖它；停止期间不做周期监控。停止等当前执行结束或进入等待，等待中的批次保留且停止期间不得恢复；软删除或移除会话使对应未决批次结束，历史仍可查。并发启动只允许同账号同会话一个运行归属。此阶段用后台测试核对租户权限、状态转换、旧客户端缺新能力只影响代理功能、数据库迁移；不修改 CLI、Runtime 或前端。若增加配置字段，同步核对 `src/config/settings.py` 与 `configs/config.yaml`。

### P5：后台监控循环与队列

**唯一代码模块：服务端代理监控与队列。**固定设备/账号只运行一个监控循环，目标间隔 10 秒，整轮未完成不重叠；每目标用独立 `wb1` 游标调用 `wecom_read_sessions({sessions:[该稳定会话]})` 并排空分页，增删目标不换保留目标游标。监控读与代理 Runner 共用持久队列占用，Runner 执行期间不读；先持久化新 peer 候选再推进读取游标，自己/系统消息不激活。按发现顺序排会话，同会话只有一个未决批次；等待 Runner 释放位置，恢复前核对任务未软删且目标仍被选中，终态失败不恢复原 Runner。服务端重启从持久事实继续。手动发送和日报不入队，外部 `BUSY` 等待重试；Runtime 离线或切号按原账号恢复，源库代际/游标失效中断受影响会话并显示原因。本模块用后台假 Runtime 回执与真实数据库验证位置、竞争、重启和停止，不修改 CLI、Runtime 或前端。

### P6：后台回答 Runner 与结束记录

**唯一代码模块：服务端代理 Runner 受信提交、工具装配、结果及日志。**按会话冻结本批上界、原文与当时的任务指令；旧等待 Runner 恢复仍用旧指令，新指令只用于新批次。每个任务＋会话固定 `session_id`、每批新 `runner_id`；使用会加载历史和活动摘要的提交路径，不能使用 `source='scheduled'` 的零历史路径。不另建记忆库，附本批与近期 CLI 原文，远期事实用现有日期页按需核对。选择固定智能体，仅本次装配当前会话的企微读发和任务指令；恢复及每次企微工具派发核对任务未软删、目标仍被选中。Agent 决定逐人、合并或无需回复；@我为智能体必答指令，但批次仍按已确认的简化推进规则处理。正常结束 JSON 列出原消息、回复文本、CLI `receipt_id` 与 `verification_detail.message_id/source_generation` 等本地库证据，以及未成功回复的错误和调用/日志编号；服务端保存并展示，不对已核验发送重复查库。明确无需回复或至少一条确认发送就推进到冻结上界；零发送且确定无副作用仅重试一次，unknown 只读对账且不重发。消息 100 批后下批从 101 到下次实际读取位置，不被本人回复 110 覆盖。本模块测试 JSON、原会话历史加载、跨会话隔离、发送事实、异常及积分归属；不修改 CLI、Runtime 或前端。

### P7：前端页面

**唯一代码模块：`frontend/`。**增加与每日总结同级的代理任务页面，使用 P4–P6 API 展示创建检查、会话多选、智能体选择、启动/停止、停止后编辑和软删除历史；详情显示每批 JSON、回复文本、CLI 证据、错误日志和对应 Runner，证据文案仅称“本机客户端已记录发送”。任务列表显示最近检查/新消息、空闲读取次数、错误及实际回答积分。本模块运行 `npm run build`，验证创建与状态交互、只读历史和窄屏布局；不修改后台、Runtime 或 CLI。

### P8：跨模块联测与交付

在各模块分别自测通过后，按项目高风险流程完成独立测试与独立 CodeReview，并按 CLI → Runtime → 后台 → 前端逐段联测。真实 PostgreSQL 和真实 Runtime/CLI 验证创建检查与标定、同设备多任务单循环、逐目标游标、队列串行且监控读不与 Runner 冲突；空闲 2 小时 0 回答 Runner/模型/积分。验证群聊逐人/合并/闲聊/@我、历史上下文、同会话固定 `session_id`、新任务新 `session_id`、不同批次 `runner_id`、结束 JSON 与 CLI 回执/错误。覆盖停止/启动补读、等待中停止并修改指令后旧批次沿旧指令、软删除或移除目标后等待批次不再发消息、软删除历史可查、101 起点、零发送重试/unknown 无重发、外部 `BUSY`、离线/切号/源库失效、同会话双任务冲突和智能体失权。记录实际输入/缓存 token 与积分，不用相同 ID 推断模型缓存。按“仅升级服务端、旧 Runtime＋CLI 保持原版本”的组合回归原工具、任务恢复、结果上报和计费。阶段完成先更新本计划再同步 `docs/ideas.md`；真机部署须用户当场明确指定环境。

## 4. 当前限制

P1–P7 与 P10 已完成开发，P8 真机联测进行中。真实业务 Agent 回答、空闲零积分和旧客户端兼容组合仍待验证。10 秒是每设备组的目标轮询间隔，逐目标读取仍消耗设备和数据库资源，组内目标多时实际轮次会更长，须以真机延迟验收。
