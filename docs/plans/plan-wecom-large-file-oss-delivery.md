# 微信侧大文件交付 OSS 化（讨论稿）

> **状态**：讨论稿，方案未定稿，暂不实现（2026-10-18）
> **背景提交**：`d8c18929`（≤20MB 走 file 消息直发，已解部分问题）
> **结论倾向**：交付文件与知识库原始文件迁腾讯云 COS，用归档分层控制长期存储成本，成本按次转积分由租户承担。

---

## 1. 问题

微信侧用户索要知识库文件、智能体交付文件时，**iOS 微信内置下载器在长时间低速传输下卡死**。

**根因**：文件走本站链路下载，受服务器公网出口 5Mbps + nginx 下载 location 限速（`limit_rate 128k` / `limit_rate_after 1m`，见 `deploy/agent*.aidingyi.cn.conf`）双重约束。

**已解（2026-10-09，`d8c18929`）**：≤20MB 文件先 `upload_media` 上传企微临时素材，以 **file 消息直发**（经微信服务器中转，不经本站链路），失败降级 link 卡片。落点 `src/channels/wecom_kf/adapter.py` 的 `_send_file_as_file_message()`，阈值 `20 * 1024 * 1024`。

**未解**：**>=20MB 文件**无法走 file 消息（企微临时素材 file 上限即 20MB 硬限制），仍降级为本站 link 卡片 → iOS 仍会卡死。

## 2. 方案选型：CDN vs OSS

| 方案 | 能否解决 | 说明 |
|------|---------|------|
| CDN | 部分 | 只加速分发；**冷文件首次回源仍走源站 5Mbps + nginx 限速**，20MB 首次下载仍慢。只有被下载过第二次的文件才快 |
| OSS 对象存储 | 是 | 文件生成即上传 OSS，用户从 OSS 下载，源站零参与，冷热都快 |

**结论：选 OSS。** CDN 仅在"同一文件被多人/多次下载、命中边缘缓存"时才有价值；本项目是微信侧单用户索要文件的场景，走 CDN 反而要付 CDN 下行 + CDN 回源两笔费用，比直连 OSS 贵。**CDN 不作为本期方案，仅在后续有高重复下载场景时叠加。**

> **交付方式提醒**：无论 CDN 还是 OSS，**都不能用本站反代**（nginx `proxy_pass`）-- 反代会让文件流经本站 5Mbps 出口，带宽瓶颈照旧。必须让用户**直连**存储节点，鉴权用 302 重定向实现（见 §6）。

## 4. 存储时长与分层策略

**不设"1 年后删除"**：删了就是 404，用户翻几个月前聊天记录点下载是常态，投诉/流失成本远高于存储费。

**分层：标准存储（首 1 年）→ 归档存储（1 年后）**

| 阶段 | 存储类型 | 单价 | 取回 |
|------|---------|------|------|
| 0~1 年 | 标准 | 0.099 元/GB/月 | 实时 |
| 1 年以上 | 归档 | **0.03 元/GB/月** | 异步，分钟级 |

1 年后转归档成本降 **70%**，文件仍保留可访问。OSS 生命周期规则原生支持自动转换，配置即可。

**决策：不采用低频存储。** 低频存储 0.08 元/GB/月，仅比标准低约 20%，且仍要收实时取回费，性价比低，**无吸引力，跳过低频层**。分层简化为"标准 → 归档"两段。

**已确认可接受的代价**：归档为**异步取回**，用户点链接不能立即下载，需先触发恢复（分钟级）。需在下载入口做"文件已归档，正在取回，稍后重试"的提示 + 后台异步恢复任务。

## 5. 成本模型与积分转嫁

**单文件全生命周期成本（以 30MB 为例）**：

| 项 | 计算 | 成本 |
|----|------|------|
| 存储（首年标准） | 0.03GB × 1.19 元/GB/年 | 0.036 元 |
| 存储（次年起归档） | 0.03GB × 0.36 元/GB/年 | 0.011 元/年 |
| 流量（下载 1 次） | 0.03GB × 0.5 元/GB | 0.015 元 |
| **合计（首年）** | | **约 0.05 元** |

**转积分模型**：**1 积分 = 0.1 元**（即 1 元 = 10 积分）。充值记录如「10000 积分 = 660 元」属业务促销/折扣，产品定价时忽略，按 1 积分 = 0.1 元计。交付动作**按次 + 按大小阶梯**扣分，覆盖流量 + 存储全生命周期成本：

| 文件大小 | 生命周期成本 | 交付扣分 | 折元 | 覆盖倍数 |
|---------|-------------|---------|------|---------|
| ≤50MB | ~0.05 元 | 1 积分 | 0.1 元 | ~2x |
| 50~200MB | ~0.17 元 | 3 积分 | 0.3 元 | ~1.8x |
| >200MB | ~0.5 元 | 8 积分 | 0.8 元 | ~1.6x |

（上表为示例定价，最终按业务定；成本随文件大小线性增长，扣分阶梯与之对齐。）

按次扣分的好处：客户可感知（"交付一份文件扣 0.5 积分"），比"按月扣存储费"透明。

**"由客户承担"的正确形态 —— 保留时长做成租户可配置计价项**：

| 租户选择 | 效果 | 计费 |
|---------|------|------|
| 30 天 | 到期删除，链接失效 | 最省（只收流量） |
| 1 年（默认） | 到期转归档 | 标准（交付按次扣） |
| 永久 | 一直保留 | 略高，或按年续扣存储积分 |

默认"1 年"，想省的租户主动选"30 天"，把成本承担变成"客户为保留付费，也可选择不保留省钱"。

## 6. 架构演进：cp 工具从"复制"到"引用"

**现状**（`src/tools/file/cp_tool.py`）：`copy2` 一份源文件到 `storage/tenants/{tid}/conversation/`，生成独立 `file_id`，注册下载元数据，返回 `/api/files/{file_id}/download`。

**问题**：知识库文件若已在 OSS，交付时复制副本意味着**同一内容在 OSS 存两份**（知识库对象 + 交付对象），存储浪费。

**演进方向**：cp 从"复制文件"变成"**为源文件生成一条交付引用**" —— 省掉 `copy2` 与一次对象搬运，指向同一 OSS 对象。

**但 cp 的四项职责不能省**：

| 职责 | 为什么不能省 |
|------|-------------|
| 生成独立 `file_id` + `/api/files/{id}/download` | 客户链接必须走 file_id 维度（doc_id 下载接口是租户管理员 + 票据语义） |
| 跨租户共享授权校验（`cp_tool.py:230`） | 安全边界，知识库按 `(owner, source_type)` 授权，交付前必须验 |
| work_outcome 登记（`cp_tool.py:623`） | 日报/复盘依赖"交付了什么文件" |
| 显示名 + visible 控制 | 微信侧 file 消息与下载都以显示名为准 |

**待决策：交付是"引用"还是"快照"？**

| | 引用（省存储） | 快照（现状语义） |
|---|---|---|
| 存储 | 不复制，最省 | 每份交付存一个对象 |
| 知识库文档更新 | 客户拿到新版 | 客户仍拿旧版 |
| 知识库文档删除 | 需引用计数保护，否则历史链接失效 | 天然安全 |
| 授权撤销 | 已发出的引用仍可下（file_id 已授权） | 同样存在，但副本是独立资产 |

倾向：微信客户索要的是"知识库里那份资料"，**引用语义更贴合**；若有"交付即定版"的合规要求则走快照。

**安全与带宽约束 —— 用 302 重定向，禁用反代**：

- **反代不可用**：`myhongtao.aidingyi.cn` 的反代模式（nginx `proxy_pass` 到 OSS）会让文件流**经本站 nginx 再吐给用户**，**依然占满 5Mbps 小带宽**，等于没解决核心问题。**反代不能作为大文件交付的标准模式**（图片等小文件反代可接受，大文件不可）。
- **正确做法：302 重定向**。`/api/files/{file_id}/download?ticket=xxx` 在本站完成票据鉴权（可撤销、可审计、可限流），随后 **302 跳转到 OSS 签名 URL**。302 响应仅几 KB，文件流量全部走 OSS 网络，**本站零带宽占用**。
- **域名屏蔽**：302 的目标不要用 OSS 默认域名（`*.myqcloud.com` / `*.aliyuncs.com` 等第三方直链域名易被微信拦截），改用**自有域名 CNAME 到 OSS**（流量仍走 OSS 节点，不经本站）。

## 7. 知识库原始文件是否迁 OSS（单列决策）

知识库原始文件**不属于"交付存储"** —— 它是租户资产（上传后长期供 RAG 检索），删了知识库就残了，应**长期保留，成本走知识库服务的既有计费/订阅**，不按交付文件的生命周期处理。

**迁 OSS 的收益**：统一存储层（消除 `file_usage.md` 已抱怨的新旧双轨路径）+ 存储成本降低。

**迁 OSS 的改造点**：

1. **解析/嵌入要本地文件**：流程变为"本地临时落盘 → 解析分块嵌入 → 上传 OSS → 删本地"，多一步搬运（一次性成本）。
2. **OSS key 必须保留租户/栏目语义**：现在跨租户共享授权靠 `extract_knowledge_refs` 解析磁盘路径 `tenants/{owner}/knowledge/{source_type}/...`；OSS key 必须保持同构，否则路径守卫、cp 共享放行（`cp_tool.py:259`）全部要重写。
3. **删除级联**：删知识库文档要同步删 OSS 对象。

**建议分期**：第一期只做"交付文件走 OSS"（收益最直接），知识库原始文件迁 OSS 单列后续评估。

## 9. 未决风险

- **归档取回延迟**：用户点旧链接需等待分钟级恢复，需明确提示文案与超时兜底。
- **引用模式的级联保护**：知识库文档删除/替换时，已交付引用需引用计数或版本保护，否则历史链接失效。
- **授权撤销时效**：302 方案在跳转前过本站鉴权，可撤销；跳转后的 OSS 签名 URL 在有效期内不可撤销，需短时效控制（权衡微信用户可能延迟点击）。
- **反代禁用**：任何"反代 OSS"方案都会让文件流经本站 5Mbps 出口，无法解决带宽瓶颈，必须用 302 重定向或直连。
- **微信域名屏蔽**：OSS 默认直链域名（`*.myqcloud.com` / `*.aliyuncs.com`）可能被微信拦截，需自有域名 **CNAME 到 OSS**（不是反代），并隐藏 `Content-Disposition`。
- **成本核算口径**：交付文件与知识库文件的存储成本归属需分清，避免重复计费或漏计。
