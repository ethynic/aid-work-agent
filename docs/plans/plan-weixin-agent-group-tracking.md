## Phase 1

实施约束见 [Runtime 共同检查点](../system/runner-desktop-runtime-integration-contract.md#微信正文仅限本机共同检查点)。群配置使用稳定 ID，执行时快照群名及时间。批次结果通过该次拥有者与批次 ID 访问，逐群摘要复用本机工具调用结果。定时任务用既有后台进程触发，计划点与批次创建具备并发去重。通知沿用现有规则和投递账本，按批次终态发送一条受登录和归属控制的链接。

- 明确租户及当前用户的群配置与摘要读写边界。确认改名、移除、旧记录访问和摘要保存策略。
- 通过 Runtime 共同检查点登记兼容方案。核对自动定位已保存群的唯一性、星期和跨日时间标签、七天读取边界、逐群结果回执与存在缺口时的反馈。
- 以用户点击生成或重试时的设备、群和时段为准，沿用一次性凭证和模型调用积分检查。摘要和运行元数据入库，原文只在该次模型请求中使用。
- 核对定时任务执行归属、设备缺席、暂停恢复、重复调度和结果链接定位。复用默认通知和群机器人规则，两种配置统一以本次执行的结果链接通知。通知投递状态和总结状态分别记录。
- 历史列表按执行时间倒序，以批次 ID 查询该次逐群结果。按群筛选批次，打开详情仍展示该次全部群。旧单群结果可作为单群批次回看。

## Phase 2 实现

- 群聊、批次和计划保存于独立业务表。批次固定设备、群名及时间；原时段仍在最近 168 小时内时，显式重试生成一条关联原批次的单群记录。今日总结旧记录在全部群历史中打开原结果页。
- 专用签名工具通过原有一次性授权上传时段正文。查找只接受原生身份可核对的群聊，分钟边界、缺失时间、裁切和无法覆盖的历史保留为部分读取或失败。
- 定时任务按北京时间配置，由既有调度进程在同一事务推进日期并创建批次。停机错过多次执行时合并到最近一次计划时间。终态通知复用原投递账本，按用户权限解析到本次批次。部分完成按完成事件匹配规则，通知显示「部分完成」。规则未订阅该终态时，不创建通知并记录为「按规则跳过」。

## Phase 2 验证记录

- 独立复测通过 28 项 Windows CLI 回归、731 项 Python 回归、6 项隔离 PostgreSQL 集成和 49 项前端回归。前端生产构建、独立安装与升级的数据库结构比对、路由及调度注册检查、隔离签名打包验证通过。
- 评审复核自动任务同名群拒绝读取、通知规则按终态匹配、批次历史直接打开详情并保留筛选。使用模拟数据在 Chromium 验证 1280 与 390 像素布局。
- 另有 10 项导航独立测试在基线复现失败，测试桩缺少 `hiddenMenus`。真机读取与实际通知投递待发版验证。

## Phase 3 真机验收

- 2026-11-24，agent2 部署 `888c7d47`，本机 Runtime 1.3.1 安装验收签名插件 0.1.2。手动近三天两群批次中一群成功，按群筛选后仍展示整批详情。定时双群按计划触发，实际站内失败通知直达同一批次。
- 微信会把唯一精确会话列在「最常使用」区。CLI 0.1.3 将可能包含群聊的搜索分组一起核对，仅唯一精确候选可打开，读取前再次核对目标群身份。同名、截断、未完整加载时仍拒绝读取。Windows 全套独立复测 202 项通过。

- 一次保存多个群，刷新或重登可直接选择，改名和移除后旧总结仍可回看。确认注册配置时不读取群消息。
- 验证一次多群总结只出现一条历史记录，进入可看到该次全部群结果。同一时间点的两次执行分别显示，按群筛选后仍可查看完整批次。
- 使用北京时间预设和自定义起止，点生成即可开始。逐群串行，单群失败不阻断其余群。点重试仅以原时间范围重跑该群。
- 验证每天和每周按计划执行并保存摘要，关闭通知时不投递。验证默认通知与群机器人通知均发送任务名、执行状态和结果链接，访问链接须登录并核对任务归属，通知失败后仍可回看历史。
- 实际设备用有正文、无正文、覆盖不完整和目标歧义的案例联调。核对付费入口、隔离、原文不落库及既有今日总结行为。
