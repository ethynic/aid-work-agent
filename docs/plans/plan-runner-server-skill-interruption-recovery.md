## 2. Phase 1 · 按原检查点继续模型与工具

1. 从 AgentEngine 已提交的模型回复、`pending` 与工具结果确定位置。沿既有保存顺序复用完整回复和已完成调用，回复未保存完整时用原上下文再请求模型。继续后的工具参数来自该次已保存的模型回复。验证多个工具调用、部分完成和完整回复尚未应用的情况。
2. 在 `RecoveryCoordinator`、`ApplicationToolRecovery` 与 `ToolDispatcher.recover()` 接入同一套具体调用判定。优先读取原结果。可重复的未完成步骤取得新 attempt 后经正常工具执行入口重做。现有安全重做能力能复用就复用，通用技能按原工具调用、完整参数、实际脚本和输入输出范围核对。保留旧检查点原调用及其参数，覆盖旧报价任务和至少一种非报价工具。
3. 收敛现有继续入口。用户点击后立即收起按钮和播放入口，处理未知结果时沿原请求键观察。确认再次中断或恢复失败且可重试才显示。用通用文案处理云端恢复失败，原设备核对提示保留给设备操作。

Phase 1 独立验证覆盖历史报价的真实控制、Worker 与解析链路，以及同名租户技能覆盖、认领后能力变化和前端重复点击。扩展本机测试的 16 项失败在干净基线逐一复现，实体旧 Runtime＋CLI 组合待验。

## 3. Phase 2 · 补齐继续所需的文件和用户核对

1. 优先解析原会话已登记的文件引用。原 Excel 确实无法读取时，用原会话提问要求用户补传并指定文件。复用现有附件授权与等待控制，在本次恢复的有效输入中绑定明确替换的文件引用，历史原参数保持可查。解析继续使用相同 Runner、原工具步骤和原上下文。
2. 对可能产生外部效果的调用先查原结果。无法确认且无法安全重做时，在原会话提出具体问题，绑定原执行节点、待处理调用和等待 ID。用户确认已完成则带用户确认继续，缺业务结果所需信息时再问；明确未完成并要求重试则重做原动作；用户选择跳过则继续独立步骤。沿原回复、归属、版本和幂等检查，迟到可信结果在重做前重新核验。用户答复只记录为用户陈述，实际工具回执及计费沿原写入者。
3. 在等待答案和提交新结果的事务中保留原 claim、检查点及历史，防止重复发送、跨会话应用答复或并发使用两个文件。原工具不可用且没有可行替代时给出具体原因，保留停止或重新发起出口。

Phase 2 独立验证覆盖实际 API、Worker、PostgreSQL、回环 SMTP/HTTP 和页面。隔离恢复用例 16 项及最终 HTTP 专项 3 项通过，相关单测与工具回归通过，前端 113 项、构建和宽窄屏交互通过。旧预算用例在 Phase 1 干净基线复现，验证中按既有失败排除。

## 4. Phase 3 · 独立验收与发布

风险等级为高，涉及恢复、并发、计费与共同契约。正式开发按项目完整三智能体流程执行，开发自测后独立测试与只读 CodeReview。阶段完成后先更新本文进度区，再同步索引状态。

| 用例 | 必须验证的结果 |
|---|---|
| agent2 现场形状的旧 `skill_execute` 检查点，数据库恢复，原清单可用 | 从已保存的完整命令和参数定位报价解析。同一 Runner 点击一次，复用已保存结果，只重做解析，再完成报价流程 |
| 不同的只读或可重算工具，或同轮多个工具调用 | 按同一恢复路径从第一个缺结果的调用继续。完成的兄弟调用只消费原结果，既有正常执行顺序和下游功能通过 |
| 有完整模型回复、无完整回复、部分文本已展示 | 已保存回复不重复请求，未保存完整时用原上下文请求。结果替换旧的未完成展示，后续工具参数来自最终使用的完整回复 |
| 解析完成后结果提交失败，或在提交成功后中断 | 结果未提交时安全重算，结果已提交时复用。跨 Worker 只接受当前 attempt 的提交，同一原用量不重复结算 |
| 原文件路径过期、可恢复的已登记文件、需补传 | 优先找回原文件。确实缺失时仅在原等待使用用户选定且有权访问的附件，原 Runner 继续。拒绝无权访问、错会话、错等待或不明确的文件替换 |
| 外部写入结果不明、用户确认已完成、请求重试或跳过 | 先查原结果，未查明时实际发出核对问题并等待答复。三种用户选择均有可验证后续，用户陈述不作为可信成功回执或计费凭据 |
| 同一技能名带额外写入或外发动作，可信迟到回执与用户答复并发 | 不按技能名放行未知组合。迟到的成功事实参与恢复判断，重复、过期答复及已完成的外部动作不触发重做 |
| 点击继续、`202`、响应超时、页面刷新和再次中断 | 点击后立即收起继续入口，处理中与恢复运行时保持收起。同一请求只开始一次，响应未知时观察原请求，服务端确认再次中断或可重试失败后入口恢复。通用错误不给出本机 Runtime 指引 |
| 普通任务与持续任务、旧端及服务回退 | 普通任务等用户点击，持续任务沿原自动恢复机制并遵守同一判定。受影响的旧 Runtime＋CLI 工具、恢复、结果上报及计费通过，在途新等待可完成或安全结束 |

后端用本机隔离 PostgreSQL，经 `./scripts/dev_test.sh --isolated-db <相关集成测试> -p no:cacheprovider -q` 验证。使用受控的连接耗尽或故障注入复现写入失败。前端运行相关 Vitest、`npm run build` 并检查现有任务卡和提问组件的实际交互。发布前验证相关服务启动、Producer/Consumer 组合与回退。agent2 现场验收在明确授权部署后执行。

同实例连接预算与拒绝数由 [现有容量计划](plan-runner-capacity-load-separation.md#73-agent2-重配与验收1-轻-4--3-通用) 跟踪。现有现场证据未确定各进程在故障峰值时的连接占用。
