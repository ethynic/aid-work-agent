# 合同生成技能 Contract Generator

## 运行环境注意（必读）

- **每次 skill_execute 调用都在独立的临时工作目录中执行**，调用间不共享 cwd，调用结束后临时目录被清理。所有中间产物（template_dump.txt、analysis.json、answers.json、output.docx、fill_report.json）**必须用绝对路径**读写，统一放在 `$SKILL_TMP_DIR` 下的任务目录中（环境变量已注入，持久不清理）：
  ```bash
  OUT=$SKILL_TMP_DIR/contract_work/<客户简称>
  mkdir -p $OUT
  python3 scripts/prep.py --work $OUT --templates $OUT/templates
  ```
  下一步引用上一步产物时，显式写出 `$OUT/analysis.json` 等绝对路径，不要依赖「上一步的当前目录」。
- 命令中的 `scripts/xxx` 会被自动替换为脚本绝对路径，无需自行拼接技能目录。
- 同一客户的多次任务可复用同一个 `$OUT` 目录（缓存与答案都在其中）；换客户必须换目录。

## 铁律：工作流固定，技能不随模板改变

本技能的工作流**永远是下面 4 步**，与模板数量、模板内容完全无关：

1. **判断客户需求与哪套模板最合适**
2. **分析对应合同，确定要完整生成还需要哪些信息，并缓存记录下来**
3. **通过单轮问答一次性获取这些信息，并缓存记录下来**
4. **把信息填写到合同中**

以下做法一律禁止：

- 在 `SKILL.md`、references 或脚本里，为某套模板写死字段清单、问答话术、关键词映射或金额公式。
- 在合同模板里插入占位符，或以任何方式修改模板原件。模板就是客户提供的真实 Word 合同。
- 把「需要填什么」预先登记成配置。它只能在第 2 步**运行时读模板分析**得出。

**新增模板 = 提供一份新的 .docx 原件**（来源见下节），技能一个字都不用改：第 1 步自动发现，第 2 步重新分析。

## 合同模板从哪里来（四条渠道，按优先级）

| 优先级 | 渠道 | 获取方式 |
|--------|------|---------|
| 1 | **数字员工「模板文件」** | 系统提示词「### 可用模板文件」中列出的 file_id（形如 `file_xxx`）。用 `scripts/fetch_file.py --file-id <file_id> --dest $OUT/templates/` 解析落盘 |
| 2 | **知识库文档** | 用 `knowledge_file_search` 按文件名/标题定位合同模板文档，返回的 `file_path` 用 `scripts/fetch_file.py --src <file_path> --dest $OUT/templates/` 归位 |
| 3 | **用户会话上传** | 用户直接上传的 .docx 模板（会话附件路径），复制到 `$OUT/templates/` |
| 4 | **平台内置模板** | 技能包 `assets/templates/` 目录（git 部署、平台统一维护），`prep.py --templates` 直接指向该目录扫描 |

渠道 1/2/3 的文件都先归位到 `$OUT/templates/`（保持原始文件名），再用 `prep.py --templates $OUT/templates` 扫描；多套模板并存时按语义选一套（单模板自动选定，多模板先给精简目录确认）。**不要在模板里插入占位符，不要修改模板原件**——技能只做「定位回填」，版式原样保留。

## 工作目录（缓存都放这里，技能目录只读）

每次任务在 `$SKILL_TMP_DIR/contract_work/<客户简称>/` 建独立目录，存放：

| 文件 | 产生步骤 | 内容 |
|------|----------|------|
| `template_dump.txt` | 1+2（prep.py） | 模板结构化内容（落盘，**不必读回全文**） |
| `analysis.json` | 2 或缓存命中 | **分析缓存**：需要哪些信息 + 每项填在哪里 + 清单表结构 + 派生公式 |
| `answers.json` | 3/4（stdin 自动落盘） | **答案缓存**：字段值 + 服务清单 |
| `output.docx` / `fill_report.json` | 4 | 成品合同 / **含验收结论**的回填报告 |
| `../_analysis_cache/<hash>.analysis.json` | 4 自动 | 按模板 hash 的跨任务复用缓存（`$SKILL_TMP_DIR/contract_work/_analysis_cache/`，非技能包内） |

## 何时使用

用户说「帮我和客户起草一份合同」「生成公有云合同」「做私有化定制开发协议」「把这份报价落成合同」等。

## 性能准则：最少往返（务必遵守）

本技能的脚本都是毫秒级，**耗时几乎全部来自每一次工具调用对应的大模型推理**。因此目标是**用尽量少的工具往返完成合同**，而不是优化脚本速度。

| 准则 | 做法 |
|------|------|
| **合并机械步骤** | 第 1+2 步用 `prep.py` **一次调用**搞定，不要分别跑 scan / dump / 读价格 / 读脚本源码 |
| **只读摘要，不读全文** | `prep.py` 的 `compact_dump` + `anchors` + `tables_schema` 已足够写 `analysis.json`；**不要**把整份 dump、脚本源码、schema 全文读进上下文 |
| **复用分析结果** | `analysis_cache.hit=true` 时 `analysis.json` 已就位，**直接跳过第 2 步**，不读 dump、不重写 analysis |
| **一次问全** | 第 3 步把所有必填项 + 默认值列成一张清单**一轮问完**，不要 1–3 项分多轮 |
| **一次回填 + 报告验收** | 第 4 步用 stdin 传 answers，一次调用完成「写答案 + 生成 + 验收」；看 `summary`/`verification` 即可复核，**不要再打开 docx 读回核对** |
| **默认填满** | 能推断的（日期、编号、大写、合计）一律 `default`/`formula`，不向用户提问 |
| **并行无依赖调用** | 互不依赖的工具调用放在同一条消息里并行发起 |

标准往返预算：**同模板复用约 3–4 次**（prep → 问答 → 回填 → 展示）；**首次约 5–6 次**（取模板 → prep → 写 analysis → 问答 → 回填 → 展示）。若明显超出，检查是否违反了上表。

## 第 1+2 步：一次编排（选模板 + 分析 + 缓存检查）

```
python3 scripts/prep.py --work <工作目录> --templates <模板目录> \
    [--template <选定的模板文件名>] [--no-compact]
```

`prep.py` 一次调用完成：扫描模板目录 → 选定模板（单模板自动选定；多模板先给精简目录，选定后再调一次并传 `--template`）→ dump 落盘 → 计算模板内容 SHA256 → 检查 `analysis.json` 缓存。stdout **只输出精简 JSON 摘要**：

- `catalog`：模板清单（标题 / 段落数 / 表头 / 摘要）
- `compact_dump`：紧凑坐标全文（`P003|原文` / `T0 R01 C02|原文`）
- `anchors`：候选待填位置的**精确 repr**（含空格与制表符），`locators` 的 `text` 直接从这里逐字抄，**无需再单独跑脚本核对锚点**
- `tables_schema`：每张表的行列数与前几行内容，供 `service_tables` 声明
- `analysis_cache.hit`：**命中时已把缓存的 `analysis.json` 复制到工作目录，直接跳到第 3 步**
- `next_action`：明确下一步做什么

**本技能不内置任何合同模板或价格数据**（平台内置模板目录 `assets/templates/` 由运维按租户需求投放，对技能逻辑透明）。模板获取见「合同模板从哪里来」一节；不要用硬编码关键词表或凭文件名猜测模板。

### 缓存复用规则

- 缓存放在**任务工作区**（`$SKILL_TMP_DIR/contract_work/_analysis_cache/`，按模板内容 hash 命名），**不写进技能包**。
- 第 4 步生成成功（`ok=true`）时 `fill_contract.py` **自动把 `analysis.json` 入缓存**，无需额外操作。
- 模板内容一变 hash 就变，缓存自动失效；自检失败（`ok=false`）**不会**入缓存，避免把有缺陷的分析缓存下去。
- 命中缓存仍要按本次客户核对 `answers.json`，但**字段清单与定位逻辑无需重做**。

### 分析合同（仅 `analysis_cache.hit=false` 时执行）

依据 `prep.py` 输出的摘要判断：

- 哪些是本次需要变化的信息（**相对方**主体信息、编号、金额及大写、期限、比例、日期、清单项……）。
- 哪些是固定条款——保留原值，**不要拿去问用户**。特别明确两类：
  - **卖方（乙方）的静态信息**：模板里已写明的卖方公司全称、地址、联系人、电话、统一社会信用代码、开户行、收款账号、平台/品牌名等，属于模板自带的固定条款。**不要向客户确认"是否正确/是否需要修改"，也不要把它们列进待采集字段**，直接保留。
  - **法律条款、通用说明**等。
- **价格一律以租户知识库报价清单为准（模板中的示例价格忽略）**：模板里出现的任何价格（清单样例行、示例金额、示例点数等）都只是排版示例，**绝不作为定价依据、也不作为参考**。真实价格只来自**租户知识库（knowledge base）官方报价清单 / 标准价格表**（见第 3 步取价），分析时不要因为模板写了某个价就当成正确答案。
- 每项信息**填在文档哪个位置**，用哪种定位方式。
- 有无产品/服务清单表：指出表序号、表头行、样例行、合计行、列与字段的映射关系。
- 金额之间的派生关系（合计＝各行总价之和、大写、首期款＝总价×比例、月度费＝……）。

把结论写成 `<工作目录>/analysis.json`，格式见 `references/analysis_schema.md`。

硬性要求：

- `locators` 中的原文必须**逐字来自 dump**，不得臆造；一个值出现在多处时用 `scope: all` 或写多个 locator。
- 优先用 `cell` / `paragraph` 坐标；用 `literal` 时确认原文可唯一定位，或用 `where` / `contains` / `table,row,col` 限定范围。
- 标好 `required`；能由其它字段算出的写 `formula`，不向用户提问。
- 清单表用 `service_tables` 声明，`sample_rows` 指出模板里哪些是样例行（生成时会被替换成实际行数，行数可多可少）。
- 缓存写好后，先用一两句话向用户复述「本次需要收集哪几类信息」，再进入第 3 步。

## 第 3 步：一次问全（单轮）

**把所有必填项连同建议默认值列成一张清单，一轮问完**，不要 1–3 项分多轮、也不要为确认默认值再往返一次。用户一次回复后即可进入第 4 步；仅当用户答案本身有歧义/缺失时才补问。

- 已有答案、`default` 或 `formula` 字段不重复问。
- **卖方（乙方）信息不询问**：模板中已写明的卖方静态信息按第 2 步判定为固定条款，直接保留，**不要向客户提出"请确认卖方信息 / 是否需要修改"之类的确认式问题**。只有当客户主动声明"我方不是模板中的卖方、请用我方信息替换"时，才整体替换为客户提供的内容（这属于客户明确指令，不是确认式提问，但仍应保留模板版式）。
- **价格（一律以租户知识库报价清单为准）**：模板里出现的任何价格（清单样例行、示例金额、示例点数等）均仅作排版示例，**绝不作为定价依据、也不作为参考**。真实价格必须严格取自**租户知识库（knowledge base）官方报价清单 / 标准价格表**（用 `knowledge_base_search` 检索，或用户直接告知的标准售价）。取价流程：
  1. 先用 `knowledge_base_search` 在租户知识库检索权威报价清单并核对标准售价。
  2. 若用户提供了本地价格库 CSV（会话上传文件），可用 `--prices` 传入驱动 `lookup_price.py` 批量补价。
  3. 单条对照（仅用于用户提供的价格库）：
  ```
  python3 scripts/lookup_price.py <价格库.csv> "产品名称" --mode 公有云|私有云 --json
  ```
  命中多条或未命中时，告知用户并请其确认或补充。**知识库与用户均无价格条目时向用户询价，绝不得回退到模板中的任何示例价格。**
- **产品/服务清单**：让用户逐条添加，条数不限（可以多于或少于模板样例行）。每条至少给出「名称 + 数量」；单价留空由知识库补；需要归类时补 `category` 等字段，供附件拆分表与小计使用。写入 `answers.json` 的 `service_items`（或 `rows_source` 指定的其它数组）。
- 必填项齐备后直接进入第 4 步，不必再单独确认一次（用户已在回复里给出全部信息）。
- **用户拒答降级（我方增强，上游原版无此机制，合并上游更新时勿被覆盖）**：区分两种情形——用户**漏答**（回复里没有某必填项）→ 按上文补问一次；用户**明确拒答/暂不提供**（如「地址后面再补，先出稿」）→ 走降级，**不再追问、不得卡死**：把 `analysis.json` 中对应字段的 `required` 改为 `false`（`locators` 保留），不提供该答案直接进入第 4 步。回填脚本对「空值且非必填」的字段自动跳过，模板该位置保持原样留空，不会写入空值。交付说明中必须列出待补项，提醒用户打印或签署前补齐。**不得为空缺字段编造内容，也不得在模板里插入占位符。**

## 第 4 步：一次回填 + 报告验收

把 `answers.json` 的内容**通过 stdin 一次传入**（`-`），脚本会自动落盘、生成、验收并把 `analysis.json` 入缓存：

```
python3 scripts/fill_contract.py <模板.docx> <工作目录>/analysis.json - <工作目录>/output.docx \
    --report <工作目录>/fill_report.json \
    [--prices <价格库.csv>] [--cache-dir $SKILL_TMP_DIR/contract_work/_analysis_cache] <<'JSON'
{ ...answers.json 内容... }
JSON
```

> 也可用已有的 `<工作目录>/answers.json` 文件路径；stdin 只是省掉一次单独写文件的往返。

**只看回填报告即可复核，不要再打开 docx 读回来核。** 报告新增：

- `summary`：一行结论（`ok / 字段 / 清单项 / 未命中定位 / 警告 / 大写重复`）
- `verification.fields`：每个字段的最终回填值
- `verification.tables`：各清单表实际行数与条数
- `verification.amount_lines`：成品中含金额/大写的原文行（可直接核对大写金额）
- `verification.checks`：占位符残留、**大写「元整…元整」重复**、未命中定位、缺失必填、警告数
- `analysis_cached`：本次是否入缓存

内置自检会在一次生成内拦住历史缺陷（如只替换「叁仟」留下模板「元整」造成的「陆仟元整  元整」）：命中即 `ok=false` 且**不入缓存**。

若 `ok=false`，按 `missing_required` / `unmatched_locators` / `warnings` 回到第 2 或第 3 步修正**缓存**（不要改模板），重跑第 4 步。

最后用 `cp` 工具把 `$OUT/output.docx` 交付给用户（返回下载链接），并据 `summary` 列出已填关键字段、清单行数与价格来源，请用户复核。

## 价格来源与价格库

**权威来源（必须）**：**租户知识库（knowledge base）官方报价清单 / 标准价格表**（即租户己方的标准售价）。所有合同定价**严格以知识库记录的标准售价为准**，不得偏离。

**严禁作为定价依据**：合同模板中出现的任何价格（清单样例行、示例金额、示例点数）——它们只是排版示例，绝不作定价参考。本技能**不内置任何价格数据**，也没有可供套用的示例价目。

**如何取价**：先用 `knowledge_base_search` 在租户知识库检索权威报价清单并核对标准售价；检索不到时向用户询价或请其提供价格表文件。如需用本地 CSV 驱动 `lookup_price.py`，请用**用户提供的**价格库文件通过 `--prices` 传入，并在 `answers.json` 中标注价格来源。单价也可直接在 `answers.json` 写明，无需查价。

查价字段（名称/模式/单价/单位/币种/备注）与过滤规则由第 2 步的 `analysis.json` 声明，不在技能里写死。后续可直接把 `lookup_price.py` 的取数实现替换为知识库检索 API，不影响上层工作流。

## 新增模板

把新的 .docx 原件放入任一模板渠道（数字员工模板文件 / 知识库文档 / 平台内置 `assets/templates/`）。**不要修改本技能的任何文件**，也不要给模板加占位符。下一次任务会自动扫描到它并重新分析。
