# 检索层实测笔记（web-search v1.3）

本文件是 `scripts/web_search.py` 内部已处理的关键坑位与判断逻辑的说明，改动脚本前先读。

## 0. 设计目标

本技能是**通用**检索工具（不局限于找邮箱/电话）。核心是 `search`，`extract` 只是
可选的"从页面抽结构化字段"特征。三条原则：

1. **全球主流搜索引擎注册表** —— 按区域登记各大搜索引擎（见 `ENGINES` / `REGION_ENGINES`）。
2. **智能路由** —— 据输入内容（语种/文字 + `site:` 国别域名）自动选引擎，区域主引擎
   之后始终追加 Google / Bing / DDG 全球备份；任一失败自动降级。
3. **噪音域名分场景处理** —— 搜官网时硬过滤，搜信息时作备选。

## 1. 全球引擎注册表与智能路由（`select_engines` / `_detect_region`）

`ENGINES` 登记了所有引擎的 URL 模板 + 解析器。`REGION_ENGINES` 把区域映射到主引擎，
`GLOBAL_ENGINES = [google, bing, ddg]` 是全球备份。

区域 → 主引擎：
| 区域 | 主引擎 |
|---|---|
| 中国 cn | baidu, sogou, so |
| 韩国 kr | naver, daum |
| 日本 jp | yahoojp, goo |
| 俄罗斯 ru | yandex |
| 捷克 cz | seznam |
| 法国 fr | qwant |
| 伊朗 ir | parsijoo |
| 越南 vn | coccoc |
| 瑞士 ch | swisscows |
| 荷兰 nl | startpage |
| 其他（global） | google |

`select_engines(query, engine)`：
- 显式 `--engine xxx` → 返回 `[xxx]`（仅该引擎内部重试，不跨引擎降级）。
- `auto` → `_detect_region` 先判 `site:<域名>` 国别提示（查 `TLD_TO_REGION`），
  再判文字/语种；取区域主引擎 + 去重追加 Google/Bing/DDG。

文字/语种判定（`_detect_region` 第 2 步）：
- **先判假名** `kana>=1` → jp（日文汉字与中文同处 CJK 区，故假名优先）；
- 否则 `cjk/total>=0.3` → cn；
- `hangul/total>=0.3` → kr；
- `cyr/total>=0.3` → ru；
- 其余 → global（Google）。

**已知局限**：纯汉字的日文查询（无假名、无 `site:.jp`）会被判为中国引擎。这类场景
建议用户显式加 `site:.jp` 或用含假名的写法（自然日语几乎都含假名）。

## 2. URL 模板与占位符

`market` 字典含 `cc/setlang/hl/gl`，仅 Google/Bing 模板引用；其他引擎模板只用 `{q}`/
`{n}`，多余 kwargs 在 `.format` 时被忽略，无副作用。各引擎无需 API key。

## 3. 跳转链接解码

- **Bing**：`bing.com/ck/a?...&u=a1<base64url>` → 剥 `a1` 前缀、补 `=` 对齐后
  base64url 解码（`_unwrap_bing`）。
- **百度 / 搜狗 / 360**：`baidu.com/link`、`sogou.com/link`、`so.com/link` 等 →
  `_resolve_redirect`（HEAD 跟随 302）还原真实 URL。
- **Google**：`google.com/url?q=<real>` → 解码 `q` 参数（`_clean_google`）。
- **DDG**：`duckduckgo.com/l/?uddg=...` → 解码 `uddg` 参数（`_clean_ddg`）。

## 4. 相关性校验（`relevance_ok`）

为什么必须有这一步：实测在部分网络环境下（代理 / 缓存污染），搜索通道会返回与
query 完全无关的结果。做法：取 query 中长度 ≥ 3 的英文词或 ≥ 2 的中文词，按长度加权
（≥5 的词权重 2），检查前 5 条结果里 title+snippet+url 是否命中足以达到 `min_hit=0.4`
的加权比例。不达标一律判定失败并提示换通道，**绝不返回给调用方**。

## 5. 噪音域名分场景（`_split_noise` + `search`）

`NOISE_DOMAINS`（词典 / 百科 / 翻译站）在"搜官网"场景下是噪音；在"搜信息"场景下
往往是答案来源。

处理逻辑（`search`）：

- **搜信息（默认，`companies_only=False`）**：
  1. 拆成 `clean`（非噪音）与 `noise`（噪音）；
  2. 先对 `clean` 做相关性校验，通过则返回 `clean + noise`（噪音作**备选**排在后）；
  3. 若 `clean` 为空、但 `noise` 通过相关性校验，则直接采用 `noise`；
  4. 两组都无相关结果才判该引擎失败、降级下一引擎。
- **搜官网（`--companies-only`）**：在 `clean` 基础上再滤掉 `NON_COMPANY_DOMAINS`
  （社媒/黄页/电商/招投标）；过滤后为空则回退到未过滤结果。

**回退原则**：过滤/拆分后若结果为空，回退到未处理的结果，避免"全滤掉比留着噪音更糟"。

## 6. 解析器与降级

- 强解析器（百度 / 搜狗 / 360 / Bing / Google / Yandex / Naver / DDG）走专用 `_clean_*`。
- JS 较重、无稳定结果容器的区域引擎（Yahoo!Japan / Goo / Seznam / Qwant / Daum /
  Parsijoo / Cốc Cốc / Swisscows / Startpage / Brave）走通用 `_clean_generic`：抽取
  站外 http 链接作为结果；若页面纯 JS 渲染返回空，则 `search` 自动降级到下一引擎，
  不会 crash。

## 7. 结构化抽取（`extract_contacts`）的取舍

`extract` 是可选特征，与通用搜索无关：
- **邮箱**：优先 `mailto:` 链接，其次页面正则；去噪。
- **电话**：只用 `tel:` 链接与带"电话/Tel"标签的同行文本，刻意不用全文正则扫数字。
- **负责人**：中文称谓 + 英文职位模式匹配，弱信号，须人工核对。
- **备案 / 主体**：中国站点取 ICP 备案与地址（可信），主体名称取最长候选。

## 8. 超时 / 重试 / 总预算（v1.3 护栏）

- **超时拆分**：连接 `CONNECT_TIMEOUT=8s`（不可达主机快速失败），读取 `READ_TIMEOUT=15s`（容忍大页面/慢引擎）。
- **重试**：单引擎最多 `retries=1`（即 2 次尝试）。
- **连接类错误不重试**：`ConnectTimeout / ReadTimeout / ConnectError / ProxyError / RemoteProtocolError` 立即放弃重试，避免死引擎把时间耗在重试上。
- **整次预算**：`SEARCH_DEADLINE=75s`，跨引擎尝试时在每个引擎开始前检查；已耗尽则停止并提示，避免病态挂起。
- **备份排序**：`GLOBAL_ENGINES = ["bing","google","ddg"]`，Bing 排最前——本机实测 Bing 比 Google/DDG 更可达。

## 9. 本机真实网络实测结论（2026-10-23）

沙箱放行后用真实网络逐引擎验证：

- **稳定可用**：百度、搜狗、360、Naver（v1.3 修复外链解析）、Seznam、Swisscows。
- **本机不可用（环境限制）**：Google / DDG（502/超时）、Yahoo!Japan / Goo / Daum / Qwant / Startpage / Brave（连接超时/502）、Yandex（验证码墙）、Cốc Cốc / Parsijoo（JS/Cookie 墙 + 代理 502）。
- **Bing 特殊**：本机代理把 Bing SERP 篡改成无关页面（"best vector database" 返回 Best Buy + 词典），真实结果不在 HTML 里；`_unwrap_bing` 解码本身正常，但 `relevance_ok` 会正确拦截这些无关结果。**切勿为让 bing 出结果而放宽 `relevance_ok`**。
- **Naver 修复**：旧选择器 `div.total_wrap` 失效；改为抽取页面外链（非 naver 自有域）+ 去重 + 清理「새 창 열림」后缀，真实结果（如 hkcosm.com）稳定。
- **JS 重定向跟随**：`_follow_js_redirect` 提取 `window.location` / meta-refresh 跳转目标并跟随（最多 2 跳），服务 Cốc Cốc / Parsijoo；若目标仍要求 JS 则只能浏览器兜底。

**结论**：脚本逻辑正确，在受限网络下通过降级链 + `relevance_ok` 保证"不返回垃圾、不长时间挂起"；受限引擎在干净网络环境应可正常出结果。

# v2 增强层（web-search-pro）

v1 解决了「多引擎检索 + 抓取 + 字段抽取」。v2 补上宿主内置 WebSearch/WebFetch 的两个
关键差距：**JS 渲染** 与 **内容级摘要**。

## 10. 渲染兜底层（`scripts/render.py`）

### 为什么要做

v1 的 `fetch` 是纯 HTTP 抓取，遇到「首屏由 JS 渲染」的站点只能拿到骨架 HTML。实测踩到的：

| 站点 | 纯 HTTP 结果 | 渲染后 |
|---|---|---|
| `aiqicha.baidu.com`（爱企查企业详情页） | 只返回标题「爱企查」，正文空 | 完整工商信息（法人/电话/股东/人员） |
| `qcc.com` / `tianyancha.com` | 同上，另有反爬指纹 | 可取（需真实 UA） |
| `zhipin.com` / `m.zhaopin.com` | 职位内容懒加载不全 | 可取 |
| 官网 `positions.html` 等前端框架页 | 空 | 可取 |

宿主内置 WebFetch 能拿到这些内容，正是因为它在**服务端做了渲染**。v2 用 Playwright
在本地补上这一层，技能才真正具备等价能力。

### 设计要点

- **独立可选**：`playwright` 不装 → 退出码 4 + 安装指引，**不影响**其它工作流。
- **资源拦截默认开**：拦掉 image/media/font，渲染速度提升明显；需要完整资源用
  `--no-block-resources`。
- **懒加载处理**：默认滚到底再回顶（`--no-scroll` 关闭），触发图片/列表懒加载。
- **等待策略**：`--wait-for SELECTOR` 等具体元素优于固定 sleep；`--delay` 作为兜底。
- **`JS_HEAVY_DOMAINS` 白名单式判断**：`is_js_heavy()` 只对已知 SPA 站点优先渲染，
  且把 google/bing/baidu 等「直接抓就行」的域名单独排除（渲染这些反而慢且易被风控）。
- **优雅降级**：`pipeline.py` 里渲染失败不会中断流程，只是该页退回 HTTP 结果并记录 error。

### 退出码约定

| 码 | 含义 |
|---|---|
| 0 | 成功 |
| 2 | 渲染失败（页面打不开、超时） |
| 3 | 参数错误 |
| 4 | Playwright 不可用（未装包 / 未下内核） |

## 11. 组合管线层（`scripts/pipeline.py`）

### 链路

```
search()  ──►  top-N URL  ──►  HTTP 抓取  ──►  正文过薄/失败？  ──►  render.py 渲染
                                    │                                      │
                                    └──────────────┬───────────────────────┘
                                                   ▼
                              extract_contacts()  +  可选 LLM 内容级摘要
```

### 自动渲染判定

`THIN_TEXT = 200`：HTTP 抓取抛异常，或正文短于 200 字（疑似 SPA 空壳），即转渲染重试一次。
正文非空但不薄 → 不渲染（省时间）。`--no-render` 可完全禁用。

### 两种输出模式

- **`mode: "collect"`（采集模式，零 LLM 依赖）**：输出 `pages[].text` 结构化正文，
  由调用方智能体自行总结。**这是默认且始终可用的路径**——任何智能体宿主本身就有
  LLM 能力，不该让 skill 强依赖一个外部 API Key。
- **`mode: "llm"`（内容级摘要）**：配置了 `WSP_LLM_BASE_URL` / `WSP_LLM_API_KEY` /
  `WSP_LLM_MODEL`（或对应命令行参数）后启用，把收集到的正文喂给 OpenAI 兼容的
  `chat/completions`，按 `--prompt` 生成聚合答案。这才是宿主 WebSearch 那种
  「内容级摘要」的等价物。

摘要系统提示词的约束（写在 `_llm_summarize` 里）：优先给具体可用的信息（人名+职务、
电话、邮箱、地址、备案号）；区分「页面明确写出」与「推断」；冲突时列出各来源；
号码邮箱原样输出不改写；确实没有就明说「未找到」。

正文预算：单页 `MAX_PAGE_CHARS=6000`，总量 `MAX_TOTAL_CHARS=40000`，超出即截断。

### 输出结构

```json
{
  "query": "...", "engine": "baidu", "route": ["baidu", "sogou", "..."],
  "mode": "collect",
  "serp": [{"title": "...", "url": "...", "snippet": "..."}],
  "pages": [{
    "url": "...", "title": "...", "method": "http|render",
    "text_len": 1234, "text": "...",
    "emails": [], "phones": [], "persons": [], "meta": []
  }],
  "errors": [], "hint": "..."
}
```

## 12. 实战案例：爱企查跨 tab 掩码还原完整手机号

**背景**：v1 方案在爱企查上只能拿到被遮蔽的号码 `1391680****`（主页面）与
`139****7580`（核心人员页）。

**方法**：同一号码在不同 tab 的掩码窗口不同——主页面掩后 4 位，核心人员页掩中 4 位。
两个掩码的**并集**即完整号码：

| 来源 | 掩码 | 已知位 |
|---|---|---|
| 企业详情页 | `1391680****` | 第 1–7 位 = `1391680` |
| 核心人员页 | `139****7580` | 第 8–11 位 = `7580` |
| 合并 | `13916807580` | 11 位全解 |

**校验**：号段 `1391680` 归属上海移动，与公司注册地（上海市嘉定区）一致。

**结论**：跨页面交叉比对掩码，是还原「工商登记手机号」这类敏感字段的通用手法。
前提是**同一号码在多个页面出现**——爱企查还提供「更多电话 / 同电话企业」聚合，
命中概率更高。

## 13. 中文品牌名检索的拆词陷阱

**现象**：查「爱定义（上海）科技有限公司」时，百度/搜狗把「爱定义」拆成
「爱的发」「爱曾」「爱彼此家居」等，返回一堆无关企业；短词查询「爱定义」则直接
被 `relevance_ok` 判为无关而丢弃。

**原因**：中文搜索引擎对 3 字品牌名做二元切分，品牌名不在其词库中。

**对策**（按优先级）：
1. **加上下文词拉长查询串**——「爱定义（上海）科技有限公司」「爱定义 品牌」比裸品牌名有效；
2. **换引擎**——搜狗/360 的切分策略与百度不同，可能命中；
3. **直连目标站点**——已知官网域名时用 `fetch` / `render` 直接抓，绕开检索；
4. **本地检索替代**——宿主内置 WebSearch 走商业索引，对中文品牌的覆盖明显更好。

**结论**：这是**公开搜索引擎的固有短板**，不是脚本缺陷。`relevance_ok` 在此处的行为
是正确的——宁可报「未取到结果」并提示换词，也不把噪音喂给调用方。

## 14. v2 实测结论（2026-10-23，Windows + 代理网络 + Chromium 已装）

### 通过的用例

| 用例 | 结果 |
|---|---|
| `render.py https://example.com --json` | ✅ 标题/正文/耗时全部正常（17s，含浏览器冷启动） |
| `render.py` 浏览器内核缺失 | ✅ 优雅降级：JSON 错误提示 + 退出码 4，不崩溃 |
| `pipeline.py urls <url> --extract` | ✅ method=http，正文 1483 字，CSS 已清理 |
| `pipeline.py urls <url> --prompt`（未配 LLM） | ✅ 降级为 `mode: collect` 并给出明确 hint |
| `pipeline.py search`（中文引擎返回噪音） | ✅ SERP 清洗识别出「全是噪音」，报错并给出换词建议 |
| `web_search.py fetch / extract / batch` | ✅ 基础能力无回归，抽取精度反而提升 |

### 失败的用例（如实记录）

| 用例 | 结果 | 原因 |
|---|---|---|
| `render.py` 抓爱企查企业详情页 | ❌ 拿到「百度安全验证」滑块页 | 站点反爬拦截自动化浏览器 |
| `render.py` + `--warmup` 拿 cookie 后再抓 | ❌ 仍被拦 | 同上，滑块需人工过 |
| `pipeline.py search` 多个中文查询 | ⚠️ 引擎大面积返回无关内容 | 本机代理劫持搜索引擎（v1 已知环境限制） |

### 从失败里得出的三条结论

1. **渲染层解决的是「JS 渲染」，不是「反爬」**。两者常被混为一谈。带滑块/点选验证的
   站点（百度系企业信息平台是重灾区）必须换通道：宿主 WebFetch（服务端可能已有白名单）
   或人工浏览。本技能对此**不假装能绕过**，只在 notes 里如实标注。
2. **cookie 预热 + 会话持久化**（`--warmup` / `--storage` / `--save-storage`）对
   「需要正常会话但无滑块」的站点有效，对滑块无效。属于「值得一试」而非「保证成功」。
3. **搜索成功率受环境影响，管线的价值在于「失败时给出可操作的下一步」**——
   清洗后为空时明确报「换更长的查询词 / 换引擎 / 改用 urls 模式直抓」，
   比返回一堆噪音有用得多。

## 15. v2 抽取精度改进（实测数据）

同一页面 `https://www.aidingyi.cn/about.html`（页面排版为「号码 + 称谓」）：

| 版本 | phones | persons |
|---|---|---|
| v1（标签前置规则） | `[]` | `['上海总', '在上海总']`（误命中） |
| v2（补号码前置模式） | `['13701602974', '13817140566']` | `['芮女士', '高先生']` |

v2 的三处改动：

1. **新增三类高精度号码正则**：大陆手机号 `(?<![\d\-])1[3-9]\d{9}(?![\d\-])`、
   400/800 服务号、带区号固话。两侧断言确保不会截取长数字的一部分。
2. **号码后置称谓解析**：号码后紧跟的「芮女士」「高先生」被提取为人名线索。
3. **去掉 `PERSON_CN_RE` 里的裸「总」**：`上海总部` 会被误判成人名「上海总」，
   `总经理` 已单独列出，裸「总」纯属噪音。

正文抽取同时新增 `_strip_css_noise`：部分站点（百度首页、部分 SPA）把 CSS 以文本形式
留在 body 里，直接送 LLM 会浪费大量 token。

## 16. 掩码号码还原（v2.1 新增能力，已并入 `pipeline.py`）

### 原理

企业信息平台对登记电话打码，但**打码窗口随页面而变**。实测「爱定义（上海）科技有限公司」：

| 页面 | 显示样式 | 掩的位 | 可知位 |
|---|---|---|---|
| 爱企查·企业详情 | `1391680****` | 后 4 位 | 1–7 |
| 爱企查·核心人员 / 税务资质 | `139****7580` | 中 4 位 | 1–3, 8–11 |
| 水滴信用·移动版 | `139******80` | 中 6 位 | 1–3, 10–11 |
| 爱企查·2023/24/25 年报 | `139********` | 后 8 位 | 1–3 |
| 爱企查·2021/22 年报 | `180********` | 后 8 位 | 1–3（**另一个号码**） |

前三者并集覆盖 11 位全号 → **13916807580**。第四、五者属不同号码（掩码长度/首三位不同），
合并器会因已知位冲突而拒绝合并。

### 实现

- `web_search.extract_masked_phones(text)`：抽 `139****7580` / `021-*****66` 形态，
  输出 `{raw, pattern}`（pattern 中 `*` 为未知位）。
- `pipeline.merge_masked_phones(pages)`：按位合并。
  - 两掩码长度一致且已知位不冲突 → 视为同一号码的不同视图，合并（未知位减少）。
  - 冲突 → 不同号码，各自独立成组。
  - 合并到无 `*` → 还原完整号码，`confidence=high`（多源）或 `medium`（单源）。
  - 仍有 `*` → **不输出**（信息不足不臆断）。

单元验证（`scripts/test_mask_merge.py`）覆盖三种情形：三掩码互补 → 正确还原；
两号码不误合并；单掩码不下结论。

### 附带发现：年报是号码历史的天然时间序列

「联系电话」字段的掩码宽度与号码本身可能不同。对爱定义（上海）的实测：

| 2023 / 2024 / 2025 | `139********` | 嘉定区墨玉南路888号2201室 | 凌锶科技 70%、函于木 20%、朱炜 10% |

### 官网全站爬取是找邮箱的最优路径

工商登记邮箱普遍为空（爱定义 5 份年报「电子邮箱」全为 `-`），但**官网**有：

- `www.aidingyi.cn/join.html`（加入我们）→ 原文
  `<h4>投递邮箱</h4> <p id="join-hr-email">hr@aidingyi.cn</p>`
- `www.aidingyi.cn/about.html`（关于我们）→ `<h4>电话</h4> <p>13701602974 芮女士</p>`、
  `<p>13817140566 高先生</p>`（苏州研发中心）
- `order.html` 是登录页（`用户登录 - AI员工服务平台`），无商务邮箱。

**结论**：找企业联系方式的优先级应为「官网 about/contact/join 页 → 工商年报/登记 →
注册表平台掩码还原」，而不是只查工商库。
