# 样版板式复刻技能 Doc Layout Clone

## 最高铁律：模板 ≠ 内容来源（先分清，再动手）

本技能的每一份输入材料，动手前**必须先归类为下面两类之一**。两类职责绝对不能混用，这是高于一切流程和技巧的红线。

| 类别 | 是什么 | 能用来做什么 | 绝对不能做什么 |
|------|--------|--------------|----------------|
| **模板 / 样版 / 历史文件** | 只用来复刻版式的 `.docx` / `.pdf`：结构、格式、样式、段落表格布局、定位锚点 | 提供**内容结构、格式、样式**；其中的文字/样例行只作"这里要填某类值"的**定位示意** | **其中的样例数据（公司名、人名、金额、日期、编号、条款、清单条目等）一律不得作为成品的实际内容输出** |
| **内容来源** | 知识库检索结果、用户上传的参考资料（Word/PDF/Excel/文本/图片等）、用户在对话中明确给出的业务数据 | 这是成品文档**实际内容的唯一合法来源**，`answers.json` 里的值只能来自这里 | 不得用模板样例值冒充，不得凭常识/行业惯例臆造 |

**同一份文件即使同时充当模板和内容来源，也必须拆开看待：只取它的版式，不取它的样例数值。**

### 绝对红线：内容不全时不得编造

- `output.docx` 里每一个实际内容值，都必须能追溯到某个**内容来源**或用户的**明确指令**。
- 内容来源里查不到、用户也没给的必填项：**不得拿模板样例值顶替，不得按常识臆造，不得生成看似合理的模拟数字、名称、日期、条款、结论**。正确处理只有两种：留空并显著标注待补（如 `【待补：请从 XX 材料提供】`），或向用户索取。
- **唯一允许输出示例 / 模拟数据的情形**：用户**明确要求**（如"先用示例数据填一版""模拟一版给我看"）。此时必须在交付回复里显著声明"含示例 / 模拟数据，非真实内容"，且示例标记不得抹除。
- 用户提供的内容来源不全时，技能的正确动作是**告知缺口并停下等用户补齐**，而不是"先随便填点看起来像真的"。

> 一句话记住：**模板只管长什么样，内容来源才管写什么；来源不全就留白或问人，绝不自己编。**

## 铁律：工作流固定，技能不随样版改变

本技能的工作流**永远是下面 4 步**，与样版是 Word 还是 PDF、属于什么行业、内容是合同还是报告完全无关：

1. **选定样版并预处理**（PDF 转可编辑 DOCX；DOCX 直用），一次调用完成转储与缓存检查。
2. **运行时分析样版**：判断新要求下哪些内容要改、每项改在哪里，写成 `analysis.json` 并缓存。**字段清单只能由本次读样版得出。**
3. **收集信息**：先从知识库/用户参考资料取值填缺口，**能从来源真实值按规则算出的（合计、大写、比例、单价×数量、日期推算等）一律自动算好，不占用户提问**；取不到、算不出的才算缺口。**缺口少（<=5）时优先用「选项问答」模式**（用 `ask_user` 把候选值做成 2–4 个选项、标推荐项，让用户点选而非大段文字填写，见第 3 步）；缺口多或需结构化数据（财务/人员/知产/市场等）时才生成一份 Word《信息采集表》让用户填写（黄色高亮=模板示例值、必须替换；来源已填的真实值不高亮；示例值仅在用户明确要求时才可沿用）。
4. **一次回填 + 报告验收**：生成 `output.docx`，用报告确认板式一致、定位命中。

以下做法一律禁止：

- 在 `SKILL.md`、references 或脚本里，为某类文档写死字段清单、问答话术、关键词映射或固定值。
- 在样版里插入占位符，或以任何方式修改样版原件。样版就是用户提供的真实文件。
- 把「需要改什么」预先登记成配置；它只能在第 2 步运行时读样版分析得出。
- 凭文件名猜测字段含义；**把样版/历史文件里的示例值当作本次成品内容输出**（样例值只能用于定位，见最高铁律）。
- 在内容来源不全时编造 / 模拟数据填充成品；把示例值伪装成真实内容（除非用户明确要求示例输出）。
- **把本次业务内容写进脚本**。用户给的数据只能落在 `answers.json`；`analysis.json` 只描述「改哪里」。
- 擅自「美化」版式（改字体、改颜色、重排段落）。用户没要求时，版式必须原样继承。

**新增样版 = 用户上传新的 `.docx` / `.pdf`，技能一个字都不用改。**

### 不得把一次任务变成「专用生成器」

复用同一份样版做第二个客户时，正确做法是**重新跑第 3 步问答 + 第 4 步回填**（分析缓存命中可省掉第 2 步），而不是改上一次的脚本里的字符串。任何以 `build_*.py` / `gen_*.py` 之类命名的、把客户名、金额、政策名、条款文字硬编码在 Python 里的脚本，都只属于那一次任务；**它们不属于本技能，也不得被当作本技能产出的一部分留下**。若某次任务确实需要一段可复用的逻辑，它只能进化为 `scripts/` 下的通用脚本，且不得包含任何业务常量。

## 工作目录（缓存都放 $SKILL_TMP_DIR，技能目录只读）

每次 `skill_execute` 调用都在独立的临时工作目录中执行，调用间不共享 cwd。所有中间产物
**必须用绝对路径**读写，统一放在 `$SKILL_TMP_DIR` 下的任务目录中（环境变量已注入，持久不清理）：

```bash
WORK=$SKILL_TMP_DIR/doc_layout/<任务名或 YYYYMMDD-HHMM>
mkdir -p "$WORK"
```

| 文件 | 产生步骤 | 内容 |
|------|----------|------|
| `template_dump.txt` | 1（`prep.py`） | 样版结构化转储（落盘，**不必读回全文**） |
| `_converted/*.docx` | 1（仅 PDF） | PDF 转换出的可编辑 Word 基底（带 `.hash` 复用标记） |
| `analysis.json` | 2 或缓存命中 | **分析缓存**：需要改哪些项 + 每项填在哪里 + 清单表结构 |
| `answers.json` | 3/4（stdin 自动落盘；`probe.py --merge` 也会写入） | **答案缓存**：本次新要求下的实际内容（含 `_meta.sources` / `_meta.gaps` 来源登记） |
| `fields.json` | 3（字段多时） | 信息采集表的字段定义（`value` = 来源真实值、`sample` = 模板示例值） |
| `信息采集表.docx` / `intake_values.json` | 3（字段多时） | 给用户填写的采集表 / `--extract` 回收的值（含缺口标记） |
| `output.docx` / `fill_report.json` | 4 | 成品 / **含板式验收结论与来源审计**的报告 |
| `$SKILL_TMP_DIR/doc_layout_cache/<hash>.analysis.json` | 4 自动 | 按源样版 hash 的跨任务复用缓存 |

## 何时使用

用户说「按这个模板生成一份新的 Word」「照着这份历史文件改成这次的内容」「保持同样板式把 PDF 做成 Word」「用这个样版做一份 XX 报告」等。**只改内容、不改板式**是核心特征；若用户要求重新设计版式（重排版、换风格），不要使用本技能，直接按新要求撰写并生成文档即可。

**不要使用本技能**：
- 把数据填入既有 **Excel** 模板 → 用 `excel-to-template` 技能。
- 从招标文件出发生成整套投标响应文档 → 用 `bid-doc-generator` 技能（如需套用历史标书版式，本技能可在其流程内使用）。
- 生成合同文本 → 用 `contract-generator` 技能。

## 性能准则：最少往返（务必遵守）

脚本都是毫秒级（PDF 转换除外），耗时几乎全部来自每一次 `skill_execute` 调用对应的大模型推理。目标是**用尽量少的工具往返完成文档**，而不是优化脚本速度。

| 准则 | 做法 |
|------|------|
| **合并机械步骤** | 第 1+2 步用 `prep.py` 一次调用搞定，不要分别跑 scan / dump / 转换 / 读脚本源码 |
| **只读摘要，不读全文** | `prep.py` 的 `compact_dump` + `anchors` + `tables_schema` 已足够写 `analysis.json`；**不要**把整份 dump、脚本源码读进上下文 |
| **复用分析结果** | `analysis_cache.hit=true` 时 `analysis.json` 已就位，**直接跳过第 2 步**，不读 dump、不重写 analysis |
| **一次问全** | 第 3 步把**当前已解锁**的待改项 + 建议默认值一次问完；只有存在 `depends_on` 依赖时才分轮，不要把一个能一轮问完的文档拆成多轮 |
| **缺口少用选项问答** | 缺口 <=5 且为简单值 / 方向选择时，**优先用 `ask_user`**（2–4 个选项 + 推荐项）让用户点选，不要甩一大段文字让用户逐条填；候选值优先填内容来源查到的真实值/常用值 |
| **能算则算** | 凡是能由内容来源真实值或已收集答案**确定性算出**的字段（合计、大写、比例、单价×数量、日期推算等），用 `formula` / `default` 自动算好，**绝不再向用户提问**；只有业务事实数据（主体名、真实成交额、签署日等）来源缺失才当缺口问人，且不得编造 |
| **一次回填 + 报告验收** | 第 4 步用 stdin 传 answers，一次调用完成「写答案 + 生成 + 板式验收」；看 `summary` / `verification` / `layout` 即可，**不要再打开 docx 读回核对** |
| **默认值仅用于派生** | 能推断的**结构值**（当天日期、编号、合计、大写、比例换算）用 `default` / `formula` 自动填，不向用户提问；**业务事实数据不得用默认值编造**，来源缺失就按缺口处理 |
| **并行无依赖调用** | 互不依赖的调用放在同一条消息里并行发起 |

标准往返预算：**同样版复用约 3–4 次**（prep -> 问答 -> 回填 -> 交付）；**首次约 5–6 次**（prep -> 写 analysis -> 问答 -> 回填 -> 交付）。存在依赖的复杂文档，每多一轮问答 +1 次（用 `probe.py`，不要人工数依赖）。

## 第 1+2 步：一次编排（选样版 + 转换 + 转储 + 缓存检查）

```
python3 <技能目录>/scripts/prep.py --work "$WORK" --templates <样版实际路径（单个文件或目录）> \
    [--template <选定的文件名或绝对路径>] [--pages 1-3] \
    [--cache-dir "$SKILL_TMP_DIR/doc_layout_cache"] [--no-compact]
```

- 样版来自**会话上传信息**（冒号后面是实际上传路径），**始终使用实际上传路径**，不要用原始文件名拼路径。
- 单份样版自动选定；多份时 `prep.py` 先返回精简目录，选定后再调用并传 `--template`。

`prep.py` 一次调用完成：扫描样版（`.docx` / `.pdf`）-> 选定样版 -> PDF 转可编辑 DOCX / DOCX 直用 -> dump 落盘 -> 计算**源样版** SHA256 -> 检查 `analysis.json` 缓存。stdout **只输出精简 JSON 摘要**：

- `catalog`：样版清单（文件名 / 格式 / 标题 / 段落或页数 / 摘要）
- `selected`：`file` / `path` / `format` / **`hash`**（第 4 步 `--cache-key` 要用它）
- `working_template`：实际用于回填的 docx 路径（PDF 时为转换产物）
- `conversion`：PDF 转换报告（`converter` / `pdf_pages` / **`coverage` 文本覆盖率** / `warnings`）
- `layout_fidelity`：`exact-docx`（原 Word 直用，板式为 1:1）或 `converted-from-pdf`（PDF 转换，接近但不保证像素级）
- `compact_dump`：紧凑坐标全文（`P003|原文` / `T0 R01 C02|原文`）
- `anchors`：候选待改位置的**精确 repr**，`locators` 的 `text` 直接从这里逐字抄，无需再跑脚本核对
- `tables_schema`：每张表的行列数与前几行内容，供 `list_tables` 声明
- `layout_signature`：样版板式指纹（页面/边距/样式分布/表结构），用于验收对比
- `analysis_cache.hit`：命中时 `analysis.json` 已就位，**直接跳到第 3 步**
- `next_action`：明确下一步做什么

### 缓存复用规则

- 缓存放在 `$SKILL_TMP_DIR/doc_layout_cache/`（按源样版内容 hash 命名），**不写进技能包**，也不写用户上传目录。
- 第 4 步生成成功（`ok=true`）时 `fill_doc.py` 自动入缓存。调用时传 `--cache-key <prep 输出的 selected.hash>`，使 PDF 场景也能正确命中；不传时按工作 docx 自身 hash 缓存。
- 源样版内容一变 hash 就变，缓存自动失效；自检失败（`ok=false`）**不会**入缓存。
- 命中缓存仍要按本次新要求核对 `answers.json`，但**字段清单与定位逻辑无需重做**。
- **命中缓存也必须复核最高铁律**：逐个检查缓存里 `fields[].default` / `formula`、`list_tables[].columns[].default` 是否只含结构派生值（日期、编号、合计、大写等）。旧缓存若含业务事实类默认值（公司名、金额、结论等），必须先删掉再回填，否则会绕过"不编造数据"红线。

### PDF 样版的特别说明

- `prep.py` 用 `pdf2docx` 尽量还原板式；转换为可编辑 Word 后，后续流程与 Word 样版完全相同。
- **先看 `conversion.coverage`（文本覆盖率）**：>=0.7 可正常按坐标回填；<0.7 说明部分内容在文本框/图片/扫描页中，**必须向用户说明并建议提供 Word 原件或先 OCR**（OCR 可配合 `paddleocr_doc_parsing` 工具），不要假装能改。
- 扫描件（可提取文字 <80 字符）转换后基本不可编辑，同上处理。
- 只需其中几页时传 `--pages 1-3,5`（大 PDF 必传，转换耗时与页数成正比）。
- 转换产物确定性复用（带 `.hash` 标记），不会每次重复转换。

### 分析样版（仅 `analysis_cache.hit=false` 时执行）

依据 `prep.py` 输出的摘要判断：

- **新要求下要变的内容**：相对本次需求的主体名称、编号、日期、金额/数值、期限、责任人、结论、清单项……以及需要整段改写的说明文字。这些字段的**真实值必须来自内容来源（知识库检索 / 用户参考资料 / 用户明确指令），不得取用样版样例值**。
- **固定内容保留原值，不要拿去问用户**：样版本身自带的固定条款、公司抬头、页眉页脚、通用说明、表格标题、格式性空白等（这类属于版式结构，不是样例数据）。
- **历史文件玩法**：把历史文件当成「已填好版式的样例」——只把「新旧要求之间会变的值」列为字段；历史文件里的旧值**只是定位锚点和结构示意，绝不是本次答案**。
- **区分样例值与真实内容**：样版/历史文件里的示例数值只用于定位与版式参考。凡用户提供了知识库 / 资料库 / 参考资料 / 新要求文件的，一律从这些内容来源取值；内容来源里没有、用户也没给的，标记为待补或向用户索取，**不得用样版样例值顶替，不得自行编造**。
- 每项信息**填在文档哪个位置、用什么定位方式**；一个值出现多处要写多个 locator。
- **页眉/页脚也要检查样例值**：`compact_dump` 里的 `H*` / `F*` 行若含样例公司名、日期、编号等，同样要列入待改（页眉里的"XX 公司模板"最容易被漏，导致样例数据残留成品，违反最高铁律）。`anchors` 只按关键词命中，可能不含页眉页脚，务必人工看一眼 dump 开头。
- 有无可增减行的清单表：指出表序号、表头行、样例行、合计行、列与字段的映射。**`sample_rows` 必须列出表中全部样例数据行**（不含表头/合计），漏列的行不会被删除，会作为空行残留在新文档里。
- 派生关系（合计＝各行之和、大写、比例换算等）写成 `formula`，**不向用户提问**。

把结论写成 `$WORK/analysis.json`，格式见 `references/analysis_schema.md`。硬性要求：

- `locators[].text` 必须**逐字来自 dump / anchors**，不得臆造；优先用 `cell` / `paragraph` 坐标。
- 用 `literal` 时确认原文可唯一定位，必要时用 `where` / `contains` / `table,row,col` / `scope` 限定。
- 标好 `required`；能算出的写 `formula` / `default`。
- **发现「后一问的形态取决于前一答」时，用 `phase` + `depends_on` 声明依赖**，不要预先把两个分支都问一遍（详见 `references/analysis_schema.md` 1.2.1）。常见形态：选"分期"才有期数、选某类主体才有该类专属材料、清单为空时才需要先定条目模板。
- 清单表用 `list_tables` 声明，`sample_rows` 指出样例行（生成时按实际条数克隆替换，可多可少）。
- 写好后，用一两句话向用户复述「本次需要收集哪几类信息」，再进入第 3 步。

## 第 3 步：收集信息（选项问答 / 对话清单 / 信息采集表）

**取值顺序（务必遵守）**：每个待改字段先问内容来源要值——① 检索知识库；② 读取用户上传的参考资料；③ 采用用户在对话里明确给出的数据。三者都拿不到的，才算"缺口"：必填项就向用户索取或在成品里留 `【待补：…】` 标注，非必填项留空。**绝不允许用样版样例值或自行编造的数据填补缺口**（除非用户明确要求示例输出，见下表最后一行）。

把所有当前已解锁的待改项连同**从内容来源取到的值**列出来；内容来源已覆盖的字段不再问用户，只对真正的缺口提问。用户回复后直接进入第 4 步。

### 怎么读取内容来源（红线落地步骤，不能跳过）

最高铁律要求内容只来自"内容来源"，所以第 3 步开始前**必须先主动读取这些内容来源**，而不是直接拿样版样例值或凭空问用户：

| 内容来源 | 读取方式 |
|----------|----------|
| 知识库 / 资料库 | 用 `knowledge_base_search`（内容语义检索；按文件名定位用 `knowledge_file_search`）按字段名、项目名、主题检索，取回原文片段 |
| 用户上传的参考资料（Word/PDF/Excel/图片） | Word 用文档读取；PDF 用 PDF 处理工具；Excel/CSV 用表格工具；图片用 `image_read` 视觉识别。从资料中取到的值写入 `answers.json` |
| 用户在对话里直接给的数据 | 直接作为答案，属于"用户明确指令" |

**读取内容来源与选定样版是两件独立的事，切勿混淆**：
- **样版**通过 `prep.py --templates/--template` 传入，只用来定板式——**绝不从样版里抄样例值当内容**。
- **参考资料**是内容来源，用上表的方式读取其正文取数——**不要把参考资料也塞进 `prep.py` 当样版**。
- 每个取到的值，在 `answers.json._meta.sources` 里登记来源（如 `{"company_name": "知识库检索"}`）；取不到的必填项记入 `_meta.gaps`。第 4 步的 `source_audit` 会据此审计。

### 缺口怎么收集：先剔除能算的，再选方式

判定顺序：

1. **先剔除能算的**：能从内容来源真实值或已收集答案确定性算出的字段，用 `formula` / `default` 补好，不进缺口、不问用户。
2. **再看剩余缺口**，按下表选方式：

| 情形 | 做法 |
|------|------|
| 缺口 <=5，都是简单值 / 方向选择 | **优先用「选项问答」模式**（见下方"选项问答模式"），一次问全 |
| 缺口 <=5，但都需自由输入的具体值（如公司全称、地址、金额） | 对话清单一次问全，或把内容来源查到的候选值做成选项让用户点选/确认 |
| 缺口 >=6，或需用户提供财务 / 人员 / 知识产权 / 市场等**结构化数据** | **生成 Word《信息采集表》让用户填写**（见下方"信息采集表流程"） |
| 用户明说"信息太多，给我个表填" | 生成信息采集表 |
| **用户明确要求"先用示例数据 / 模拟一版"** | 才可以把 sample 当答案回填；交付时**必须显著声明"含示例 / 模拟数据，非真实内容"**。用户没这么要求时，此路禁用 |

- 已有答案、`default`、`formula`、以及**已从内容来源取到值**的字段不重复问。
- 样版中的固定内容不问；只有用户主动声明「抬头/主体要换成我方」时才整体替换（这属于明确指令，但仍保留版式）。
- 清单项优先从用户提供的清单类参考资料中提取（条数不限，可多于或少于样版样例行）；资料里没有的，让用户逐条给出，每条至少给出用于定位的名称/关键字段；需要归类的补 `category` 等，供多表拆分与小计使用。**不得复制样版样例行冒充真实清单。**
- 未提供的非必填字段保持样版原值不动。

### 选项问答模式（缺口少时首选，用 ask_user）

缺口较少、且是简单值或方向选择时，**优先调用 `ask_user` 工具**发起结构化问卷让用户点选，而不是甩一大段文字让用户逐条填写。要点：

- **web 网页对话**：把当前已解锁的缺口（<=5 个）打包成**一次 `ask_user` 调用**，每个问题给 2–4 个互斥选项、推荐项排第一并标「（推荐）」；有明确来源依据的候选值优先列为选项（用户点选的选项值直接作为该字段答案，选"沿用/默认"时取候选项的真实值），并在 `_meta.sources` 登记来源（如 `{"pay_mode": "选项问答-用户确认"}`）。工具自带"其他/自定义输入"，无需自己追加。
- **渠道会话（企微客服/钉钉/飞书等）**：`ask_user` 仅限 1 道选择题。缺口不超过 1 个时仍可用选项问答；缺口较多时改用**对话清单**——在回复正文中把缺口连同从内容来源取到的建议值列成清单，请用户逐项确认/补充。
- **不得用选项变相编造**：选项里的每个候选值必须来自内容来源真实值、用户已给数据或合理方向（如"沿用模板结构/改用知识库报价/我来提供"）；**不得把臆造的公司名、金额、日期包装成选项让用户误以为是真实数据**。确需用户提供的具体值，用"我来提供"选项引导用户填写，或转对话清单。
- **金额/合计类不在选项里硬填**：总额、各项费用等应提示用户给基础值后由 `formula` 自动算（见下"自动计算"），选项只用于付款方式、功能范围、是否沿用等方向性选择。
- 仅当存在 `depends_on` 依赖时才分轮（见"分轮问答"）。

### 自动计算（能从来源真实值算出的，绝不问用户）

凡是能由**内容来源真实值**或**用户已给答案**按确定性规则算出的字段，必须用 `formula` / `derived_fields` / `cell_updates` 自动算好并写回，不占用户提问、不甩给用户填。常见可自动计算的：

| 类型 | 触发数据 | 计算方式 |
|------|----------|----------|
| 金额大写 | 已得金额 | `cny_upper:amount` |
| 合计 / 小计 / 总价 | 清单各行金额、各项费用 | `sum` / `sum_where` / 各行求和 |
| 单价×数量 | 清单条目单价、数量 | 列公式 `unit_price*qty` |
| 分期金额、付款比例 | 总额、比例 | 四则运算 + `fmt` |
| 日期 / 期限推算 | 签署日、周期（天/月/年） | 日期加减、期限换算 |
| 税价合计、比例换算 | 不含税价、税率 | 四则运算 |

**边界（不得越线）**：自动计算只是对**已知真实值做确定性派生**，不是"猜一个合理值"。若基础数据本身缺失（如甲方名称、真实成交额、签署日期在内容来源和用户处都没有），仍按缺口处理——问用户或留 `【待补：…】`，**不得凭空生成基础值再拿去算**。每个自动算出的字段在 `_meta.sources` 记为 `公式派生`，保证可追溯。

### 信息采集表流程（字段多时用）

思路：把"在聊天里追问一大堆"改成"给一份能离线填写的表"。字段来自第 2 步的 `analysis.json`，**样版里的示例值必须在表里高亮**，让用户一眼分清"示例"与"真实"——高亮值只是**结构示意，不是可沿用的内容**。

1. 写 `$WORK/fields.json`：按 `references/intake_form_schema.md` 组织分组与字段；`key` 与 `answers.json` 字段对应，`sample` 填样版里的示例值（仅作定位/结构示意），`required` 标必填；**能从知识库/参考资料取到的值，直接写进 `value` 预填并注明来源，不要用样例值**。字段清单只由本次分析样版得出，不写进技能包。
2. 生成采集表（示例值自动**黄色高亮**）：

```
python3 <技能目录>/scripts/make_intake.py "$WORK/fields.json" "$WORK/信息采集表.docx" \
    [--title "..."] [--note "黄色高亮=模板示例值，仅示意结构，必须替换为真实内容；只有你明确要求用示例时才可沿用"]
```

3. 用 `cp` 工具把采集表复制为用户可见的交付文件，请用户**填入真实值后发回**；只有用户明确说"用示例/模拟一版"时，才允许保留高亮示例值直接沿用。
4. 回收：用户填好后（上传路径以会话上传信息为准）读回，映射到 `answers.json`，再走第 4 步。

```
python3 <技能目录>/scripts/make_intake.py --extract <填好的信息采集表实际路径> \
    "$WORK/fields.json" --out "$WORK/intake_values.json"
```

- 回收按 `fields.json` 分组与行序读第 3 列，**不依赖用户是否保留高亮**。stdout 里的 `unfilled`（文本仍等于示例值、未替换）和 `empty`（留空）两类 key 即缺口字段，`gap_count` 是缺口总数。
- **`--out` 落盘的 `intake_values.json` 是结构化对象**：`values`（真实值映射）＋ `_gaps`（`unfilled`/`empty`/`gap_count`）。**必须先读 `_gaps` 再回填**——绝不能只取 `values` 全量回填，否则未替换的示例值会被当成真实内容，直接违反最高铁律。
- **缺口字段默认不得作为成品内容回填**：应留 `【待补：…】` 或向用户索取；仅当用户明确要求"沿用示例"时才用原 `sample` 作为答案，并在交付回复里显著声明为示例数据、待换真实值。有 `value` 预填（来源已填、非高亮）的字段可正常回填。
- **高亮只用于采集表，不得进入成品** `output.docx`：成品的板式必须 1:1 继承样版，不得因为示例值高亮而在回填时给成品加高亮。

### 分轮问答（仅对话清单分支；存在字段依赖时）

只有一种情况：**某个待收集项的内容取决于本轮还没拿到的答案**。此时在 `analysis.json` 里给它写 `depends_on`，然后：

```
python3 <技能目录>/scripts/probe.py "$WORK/analysis.json" --round 1          # 看第一轮问什么
python3 <技能目录>/scripts/probe.py "$WORK/analysis.json" "$WORK/answers.json" \
    --round 2 --merge <本轮新答案>.json --merge-out "$WORK/answers.json"
```

- 每轮**只问 `open_fields` + `open_lists`**，`blocked_fields` 留到下一轮，这正是分轮的意义。
- `ready_to_fill=true` 时停止提问，进第 4 步。不要凭感觉判断「差不多问完了」——以它为准。
- 用户在一次回复里主动多给了后续答案也没问题：`probe.py` 会按实际答案重新算，该跳过的就跳过。
- 依赖只能建立在**答案字段自身**（有无值、等不等于某值），不要写成业务判断或去读文档内容。

**不要**把本可一轮问完的文档硬拆成多轮：往返成本实打实，拆轮的唯一理由是依赖。

## 第 4 步：一次回填 + 报告验收

把 `answers.json` 通过 stdin 一次传入（`-`）：

```
python3 <技能目录>/scripts/fill_doc.py <prep输出的working_template> "$WORK/analysis.json" - \
    "$WORK/output.docx" \
    --report "$WORK/fill_report.json" \
    --cache-dir "$SKILL_TMP_DIR/doc_layout_cache" --cache-key <prep输出的selected.hash>
```

**只看回填报告即可复核，不要再打开 docx 读回核。** 报告关键字段：

- `summary`：一行结论（ok / 字段 / 清单项 / 未命中定位 / 板式一致 / 依赖暂缓 / 警告）
- `verification.fields`：每个字段的最终回填值
- `verification.tables`：各清单表实际行数与条数
- `verification.preview_lines`：成品前 12 行非空正文（可直接目视）
- `verification.checks`：未命中定位、缺失必填、**依赖暂缓**、内部标记残留、占位符残留、**样式残留数 `sample_residue`**、**板式漂移**、警告数
- `deferred`：因依赖未满足而未问的字段（条数应与 `probe.py` 的 `blocked_fields` 对得上）
- `source_audit`：**来源审计**：`source_declaration`（`provided`/`absent`，是否声明了来源）、`declared_sources` / `declared_gaps`（来自 `answers.json._meta.sources` / `gaps`）、`ungrounded_fields`（**仅声明了 sources 时**才有值：无来源声明且非派生的字段）、`unfilled_gaps`（仍为空的缺口字段）；`verification.checks` 里有对应计数。用于复核"内容是否都有来源、缺口是否留白"
- `sample_residue`：**样版样例残留扫描**（最高铁律兜底）：列出样版中"带业务单位的数值片段"（如金额、百分比、评分等）回填后仍原样保留的项 `{fragment, count}`。分析阶段漏纳入 locators 的样例数值原本会静默留在成品、验收仍 `ok=true`，此清单把它们显性化供复核。**只提示不阻断、不改 `ok`**——固定政策条款数值可合法保留，但每一条都须确认是否应换成真实值。已在 locator 文本/新值/`_meta` 中声明过的片段不报，正常场景为 0。
- `layout`：`identical` 与 `differences`（页面尺寸/边距/段落样式/非清单表结构）；清单表行数变化属预期，不计入漂移
- `analysis_cached`：本次是否入缓存

若 `ok=false`，按 `missing_required` / `unmatched_locators` / `layout.differences` / `warnings` 回到第 2 或第 3 步修正**缓存**（不要改样版），重跑第 4 步。`deferred` 非 0 **不算失败**——它只说明还有下一轮要问，按 `probe.py` 继续即可。

## 交付

验收通过（`ok=true`）后，用 `cp` 工具把 `$WORK/output.docx` 复制为用户可见的交付文件
（目标文件名按本次任务语义命名，如 `某某项目报告.docx`），再向用户报告：
已改关键内容、清单行数、板式是否一致、**来源审计与样例残留复核结论**（`_meta.gaps` 缺口是否已留待补标注；含示例数据时必须显著声明"含示例 / 模拟数据，非真实内容"），并简要提示 PDF 转换的保真度限制（若适用）。
**不要**交付 `analysis.json` / `answers.json` / `fill_report.json` / `fields.json` 等中间产物
（信息采集表分支中采集表本身按第 3 步流程交付）。

## 关键文件

| 路径 | 作用 |
|------|------|
| `scripts/prep.py` | **第 1+2 步编排（首选）**：扫描 + 选样版 + PDF 转换 + dump + 锚点 + 缓存检查 |
| `scripts/probe.py` | 第 3 步分轮编排（对话清单分支）：按 `depends_on` 算出本轮该问什么、是否可回填、答案合并与轮次留痕 |
| `scripts/make_intake.py` | 第 3 步字段多时：**生成信息采集表（示例值黄色高亮；`value`=来源已填真实值不高亮）**，或从填好的采集表 `--extract` 读回值（含缺口标记） |
| `scripts/pdf_to_docx.py` | PDF -> 可编辑 DOCX，含文本覆盖率与扫描件检测（一般经 prep.py 调用） |
| `scripts/scan_templates.py` | 扫描 `.docx` / `.pdf` 样版目录，输出精简目录 |
| `scripts/dump_template.py` | 坐标化转储样版内容 + 板式指纹（一般经 prep.py 调用） |
| `scripts/fill_doc.py` | 第 4 步：stdin 回填 + 动态清单行 + 依赖暂缓判定 + 板式指纹验收 + **样例残留扫描与来源审计** + 自动入缓存 |
| `references/analysis_schema.md` | `analysis.json` / `answers.json` / `fill_report.json` 完整格式（含 `depends_on` 语义与 `_meta.sources/gaps` 契约） |
| `references/intake_form_schema.md` | 信息采集表 `fields.json` 格式（含 `value`/`source` 字段）、生成/回收命令、何时启用采集表 |
| `$SKILL_TMP_DIR/doc_layout_cache/` | 运行时缓存（**不在技能包内**），按源样版 hash 存 `analysis.json` |

## 新增样版

用户上传新的 `.docx` 或 `.pdf`（或给出文件实际路径），直接把它作为 `prep.py --templates`
参数传入即可。**不要修改本技能的任何文件，也不要给样版加占位符。** 同内容的样版会命中缓存。
